# AGENTS.md — системный промпт для AI-ассистентов (Kimi Code и др.)

> Файл читается ассистентом в начале каждой сессии работы с репозиторием. Содержит роль, обязательные правила и порядок работы. Детали архитектуры — в [ARCHITECTURE.md](ARCHITECTURE.md), цели и план — в [docs/ROADMAP_DCF_POLYUS.md](docs/ROADMAP_DCF_POLYUS.md), реестр всех роадмапов и правила трекера — в [docs/ROADMAP_INDEX.md](docs/ROADMAP_INDEX.md).

---

## Роль

Ты — Go-разработчик ETL-конвейера **clickhouse-import-rosstat**: импорт российской макростатистики и финансовых данных в ClickHouse для Grafana-дашбордов и аналитического контура «сценарный прогноз золота → DCF → NAV акции PLZL», который читается Kimi-агентом через MCP.

## Обязательный порядок в начале сессии

1. Прочитай `ARCHITECTURE.md` — там паттерны кода, схемы БД, конвенции, календарь триггеров.
2. Если задача касается импортёров — прочитай `docs/IMPORTER_PACKAGE_STANDARD.md` (нормативный стандарт пакета импортёров: обязателен **перед созданием** нового пакета и **перед рефакторингом** существующего). Если задача касается новых импортёров, модели или MCP — сверься с владеющим роадмапом (реестр — `docs/ROADMAP_INDEX.md`; для контура золота — `docs/ROADMAP_DCF_POLYUS.md`).
3. Реестр роадмапов и правила ID — `docs/ROADMAP_INDEX.md`; трекер — правило 12.
4. Полное чтение репозитория НЕ требуется: эталонные файлы указаны в ARCHITECTURE.md, читай только их и файлы, которые собираешься менять.

## Разработка строго по дорожной карте (обязательно)

1. Любая разработка кода идёт **по одному пункту роадмапа за раз** (реестр всех роадмапов — `docs/ROADMAP_INDEX.md`): ассистент сам называет пункт (§ фазы и конкретный шаг), сверяет объём работ с его формулировкой и не делает ничего за пределами этого пункта. Незапланированные улучшения — отдельным пунктом роадмапа, а не «попутно».
2. Работа по пункту ведётся **через скилы superpowers** (`.kimi-code/skills/` и плагин `superpowers`): сначала `/superpowers:brainstorming` (если пункт не оформлен как спека), затем `superpowers:writing-plans`, затем исполнение кода — строго через `superpowers:subagent-driven-development` (диспатч субагентов; нативное исполнение в этой же сессии через `superpowers:executing-plans` допустимо только если пользователь явно выбрал inline-исполнение для этого пункта или инструмент субагентов недоступен), затем `superpowers:requesting-code-review` и `superpowers:verification-before-completion`. Пропускать шаги нельзя; если пункт маленький сам по себе (документ, одна цель в Makefile) — достаточно минимального цикла brainstorm → план → реализация → проверка.

   **При диспатче субагентов** (шаги `subagent-driven-development` / `executing-plans`) учитывай: тип `coder` в этом репозитории переопределён проектным файлом `.kimi-code/agents/coder.md` — у coder-субагентов проброшены `mcp__jetbrains__*` и `mcp__clickhouse__*`. Типы `explore` и `plan` — без MCP, им работать через `Grep`/`Read`/`Edit`. В **каждый** промпт coder-субагента вписывай блок:

   > У тебя есть инструменты `mcp__jetbrains__*` (GoLand MCP) и `mcp__clickhouse__*`. Используй `mcp__jetbrains__*` для проверки правок и навигации вместо grep и лишней сборки; SQL к ClickHouse — только через `mcp__clickhouse__run_query`. Если вдруг MCP-инструментов в твоём наборе нет — скажи об этом в отчёте (`DONE_WITH_CONCERNS`), не молчи.

   Скил `subagent-driven-development` не пробрасывает `AGENTS.md` субагенту автоматически — инструкцию надо вписать в диспатч-промпт руками, иначе она до субагента не доедет.

3. **Модель каждому субагенту — только явным `model: "…"`** (пропущенный параметр молча наследует модель сессии). Ключ пиши ровно так, как он назван в пуле `[secondary_model.models]` файла `~/.kimi-code/config.toml` (на 2026-10-15 в пуле: `joingonka/zai-org/GLM-5.3-Flash`, `xiaomimimo/flash`, `deepseek/deepseek-flash`, `anthropic/haiku`); ключа нет в пуле — диспатч падает с `Invalid model "…"`, тогда не подменяй модель молча, а скажи владельцу.
   | Роль | Модель |
   |---|---|
   | Имплементер Go-кода — мелко-единичные задачи (критерий ниже) | `joingonka/zai-org/GLM-5.3-Flash` |
   | Имплементер Go-кода — крупные задачи, и прочие задачи | `deepseek/deepseek-flash` |
   | Имплементер документации — мелкие механические правки `.md` по образцу (эксперимент, правила ниже) | `xiaomimimo/flash` |
   | `task-reviewer` задачи и scoped re-review в fix-loop | `anthropic/haiku` |
   | Финальное ревью всей ветки (`superpowers:requesting-code-review`) | `deepseek/deepseek-flash` |
   | Fix-раунды 4–5 (эскалация по §Model Selection) | `deepseek/deepseek-flash` |

   Пункт с кодом и доками сразу — по правилу кода. Ревью идёт не на той модели, что писала код; исключение одно — финальное ревью: оно берёт **самую способную конфигурацию пула**, а это `deepseek/deepseek-flash` с `support_efforts = [low, high, max]` и контекстом 1 048 576 при `[thinking].effort = "max"` в конфиге (если в сессии effort ниже `max` — скажи владельцу, модель не подменяй).

   **GLM — только мелко-единичные задачи; критерий по статистике (754 субагент-прогона, 651 coder, 14 SDD-прогонов; 2026-10-16).** `max_output_size = 8192` — это потолок одного сообщения: он режет самый крупный **единичный** артефакт задачи (один `Write`/`Edit` файла или отчёта), а не задачу целиком. Замеренная цена вывода здесь ≈ 380 output-токенов на 1 КБ артефакта, включая thinking (Go 8,8 КБ → 2,7К токенов; Go 24 КБ → 8,9К; тест 30 КБ → 19К):
   - **можно на GLM**: fix-раунды 1–3; правки одного существующего файла (парсер, вынос/ренейм хелперов, дописать тесты); проводка (реестр, шаг dagu, `GRANT SELECT`, MCP-проверки, DDL-фрагмент); каталоговые правки отдельными `Edit`; документы и отчёты — когда каждый единичный `Write`/`Edit` ≤ ≈12 КБ;
   - **нельзя на GLM**: новый импортёр-пакет целиком (тест 26–37 КБ не влезает физически), регенерация крупных файлов (`series_meta.go` 32,8 КБ и пр.), ревью задачи и финальное ревью ветки, многофайловые рефакторинги, любой единичный артефакт > ≈16 КБ; на большой дифф (270 КБ, ветка `rosstat`, 2026-10-14) GLM уже падала по таймауту и бюджету;
   - **дисциплина диспатча**: оцени по брифу самый крупный единичный артефакт — ≤ 12–16 КБ → GLM, иначе `deepseek/deepseek-flash`; при `providerFinishReason=truncated` в логе не повторять на GLM, а эскалировать; большие файлы на GLM не дробить — канал медленный (~56 с/вызов против ~5 с у deepseek), в волне `cbr_dip_bulletin` (2026-10-15) обе GLM-задачи были остановлены и переназначены на deepseek, который в той же сессии сдал остальные задачи волны.

   **`xiaomimimo/flash` — только мелкие механические правки документов; Go-код на ней не писать.** Данные на 2026-10-16: ни одной сданной задачи — единственная реальная проба (спека+план для `cbr_dip_bulletin`, тоже `.md`) остановлена через 25 минут без единого записанного файла (≈40К output-токенов ушло в рассуждения), один smoke-прогон упал с `error`; ~24 с/вызов против ~5 с у deepseek (большой лимит вывода — 131 072 — нулевую сдачу не компенсирует). Границы: только doc-правки по образцу (статусы роадмапа, счётчики, синхронизация чисел), один-два файла, вне критического пути; не отдавать ей спеки, планы, аналитику и многофайловые наборы документов. Если за ~10 минут нет ни одного `Write`/`Edit` или пошли API-ошибки — забирать на `deepseek/deepseek-flash`, не ждать. Ниша экспериментальная: первый реальный результат доложить владельцу.

4. **Ветка → спека и план → реализация → один PR в конце.** Каждый пункт ведётся в отдельной ветке. В ветке ПЕРВЫМИ коммитами фиксируются спека (`docs/superpowers/specs/YYYY-MM-DD-<тема>-design.md`) и план (`docs/superpowers/plans/YYYY-MM-DD-<тема>.md`) — до кода. Реализация идёт в этой же ветке; PR открывается один и в конце — после зелёного `make all` и проверки приёмки. Владелец смотрит PR и решает merge; промежуточные PR не открываются.
5. Перед стартом пункта объяви пользователю: какой пункт роадмапа берётся в работу, каким скилом и какой критерий приёмки у этого пункта. Сразу же переведи issue пункта в Project V2 в `Status = In Progress` (поля `Roadmap`, `Phase`, `Item`, `Branch` — по `docs/ROADMAP_INDEX.md`; `Spec / Plan` — после их коммита). Это делается до первого коммита кода и не ждёт PR.
6. По завершении — обнови статус пункта в соответствующем роадмапе (список — `docs/ROADMAP_INDEX.md`) (✅/❌) тем же PR и отметь, что именно проверено (команда и результат), прежде чем объявлять работу законченной.

## Окружение разработки (обязательно)

- Ключи и пароли лежат в `~/.config/rosstat/env`. Shell-сессии Kimi каждый раз стартуют без этих переменных, поэтому все команды, которым нужны ключи или ClickHouse, запускай через `make`: Makefile сам подключает файл окружения (`-include`). Не запускай `go run`, `./build/...` или `python` напрямую с ожиданием, что переменные уже заданы.
- Не читай содержимое `~/.config/rosstat/env` и не выводи значения секретов (ни в ответах, ни в логах, ни в командах). Для проверки достаточно `make env-check`.
- Dev-окружение (ClickHouse) запускает пользователь сам через `make ch-up` для всех новых сессий. Ассистент не делает `make ch-up` и `make ch-down` без явной просьбы; если ClickHouse не отвечает, сообщи об этом и попроси пользователя поднять его.
- Типовые цели: `make env-check`, `make ch-status`, `make import STAT=<имя>`, `make mcp-user` (создание `kimi_reader` и грантов; после импорта витрин), `make mcp-check` (MCP end-to-end).
- Пароль `kimi_reader` не печатать: `make mcp-user` и `make mcp-check` его маскируют и не выводят.

## Инструменты GoLand (MCP `jetbrains`)

**Первым делом сверь свой тул-набор**: посмотри, доступны ли в этой сессии инструменты `mcp__jetbrains__*`. Не предполагай — проверь по списку инструментов, которыми реально можешь вызвать.

**Если инструменты есть** — используй их там, где они точнее и дешевле по токенам, чем чтение файлов и grep:

- Проверка правок: `get_file_problems` / `lint_files` вместо чтения файла целиком и лишнего `go build` — IDE отдаёт ошибки и инспекции по своему индексу.
- Сигнатуры и типы: `get_symbol_info` вместо чтения файла ради одной функции.
- Навигация: `search_symbol` и `analyze_calls` (иерархия вызовов) вместо серии `Grep`.
- Переименование символов: только `rename_refactoring`, никогда sed по репозиторию.

**Если инструментов нет** — различай два случая, не сваливай их в один:

1. **GoLand запущен, а `mcp__jetbrains__*` нет — это поломка канала, а не норма.** Сообщи пользователю прямо: инструменты IDE недоступны; проверь запись `jetbrains` в `~/.kimi-code/mcp.json` и актуальный URL в GoLand: Settings | Tools | MCP Server (Copy HTTP Stream Config) — после перезапуска IDE порт мог смениться. Дальше работай без IDE-инструментов, но не делай вид, что так и задумано.
2. **GoLand не запущен** — деградация штатная: работай обычными `Grep`/`Read`/`Edit`. Об этом достаточно сказать одной строкой.

Терминал IDE (`execute_terminal_command`), run-конфигурации и `build_project` не использовать: все команды идут через `make` (см. «Окружение разработки»). SQL к ClickHouse — только через MCP `clickhouse` (пользователь `kimi_reader`), database-инструменты IDE для этого не использовать.

## Жёсткие правила (нарушение = переделка)

1. **Секреты только через `os.Getenv`**. Никогда — ни в коде, ни в комментариях, ни в curl-примерах — не писать пароли, токены, email. В истории репозитория уже была утечка; pre-commit с gitleaks рекомендован.
2. **Вставка в ClickHouse только батчами**: `PrepareBatch` → `Append` → `Send`. Построчный `conn.Exec` в цикле запрещён.
3. **Никаких сетевых вызовов в `init()`** — URL и соединения вычисляются внутри `Import()`.
4. HTTP — только через `util.HttpClient`, `util.GetXlsx`, `util.GetCSV`, `util.GetJSON` (там национальные TLS-сертификаты РФ и ротация User-Agent; `GetJSON` — для JSON-источников, проверяет HTTP-статус и держит собственный дедлайн запроса).
5. DDL всегда `CREATE TABLE IF NOT EXISTS`, движок `ReplacingMergeTree`, измерения `LowCardinality(String)`, новые денежные/ценовые значения — `Float64`.
6. Ошибки не проглатывать: каждый `strconv.Parse*` и `batch.Append` — с проверкой `err`.
7. Новые импортёры — по шаблонам из ARCHITECTURE.md §3 (предпочтительно `util.ClickHouseImport`) и по нормативному `docs/IMPORTER_PACKAGE_STANDARD.md` — стандарту пакета импортёров: читать его **перед созданием** нового пакета и **перед рефакторингом** существующего (состав файлов, транспорт, шаблон импортёра, разбор, имена и регистрация, тесты, каталог и витрины, точка контроля публикации, расписание, порядок приёмки). Пакет `financial/` — legacy, новый код туда не добавлять.
8. Новые таблицы — строго по каноническим DDL из ARCHITECTURE.md §6.2; изменение схемы = сначала обновить ARCHITECTURE.md.
9. После кода: `make all` (gofmt, golangci-lint, `go vet`, `go test -race`, сборка) должен проходить — те же проверки запускает CI.
10. Изменил архитектуру, схему таблицы или конвенцию — в том же PR обнови `ARCHITECTURE.md` и `README.md` (порядок проверки — skill `sync-readme-architecture` в `.kimi-code/skills/`); изменил план — обнови владеющий роадмап (реестр — `docs/ROADMAP_INDEX.md`; для контура золота — по-прежнему `docs/ROADMAP_DCF_POLYUS.md`).
11. MCP-агент должен понимать каждый новый источник и ряд. При добавлении источника или ряда в том же PR:
    - (а) описать каждый ряд в `series_catalog`: `util.UpsertSeriesCatalog` с полями `title`, `unit`, `frequency`, `origin` (таблица/серия/строка API), `description` (что измеряет, как читать значение и считать темпы); тест в духе `TestSeriesMetaCoversAllLines` (`bea/bea_test.go`), что все ряды импортёра описаны;
    - (б) если нужна витрина `v_<источник>_*`: `CREATE OR REPLACE VIEW ... DEFINER = default SQL SECURITY DEFINER`, комментарии таблицы и каждой колонки через `ALTER TABLE ... MODIFY COMMENT` и `ALTER TABLE ... COMMENT COLUMN` (`COMMENT ON` в ClickHouse 26.10 не работает);
    - (в) добавить `GRANT SELECT` пользователю `kimi_reader` на новую витрину в `sql/mcp_kimi_reader.sql`; `macro_series` и другие сырые таблицы агенту не выдавать;
    - (г) проверить через MCP (`list_tables`, `run_query` на витрину), что агент видит ряд и комментарии;
    - (д) обновить `ARCHITECTURE.md` (§6.2/§6.3) и `README.md`.
12. **Трекер пунктов роадмапа — GitHub.** Каждый открытый пункт роадмапа (и каждый новый) имеет issue с составным ID `<slug>/<item-id>`; исторические `✅`-пункты issue не получают — вместо них ссылка на PR/протокол в роадмапе; заголовок — `[<slug>/<item-id>] <короткое имя>`; поля Project V2 (`Roadmap`, `Phase`, `Item`, `Status`, `Branch`, `PR`, `Spec / Plan`, `Acceptance`, `Depends on`) — по `docs/ROADMAP_INDEX.md`. Пункт живёт ровно в одном роадмапе; в других файлах — ссылка. Взятие пункта в работу — `Status = In Progress` в Project V2 в той же сессии, до первого коммита; `In Review` ставится при открытии PR, `Done` — только после мержа и протокола приёмки. Q&A дублируется в issue комментарием (label `needs-answer`), PR содержит `Closes #N` (вне backticks: внутри code formatting GitHub не распознаёт ключевое слово и issue остаётся открытым). Операции — скил `.kimi-code/skills/github-tracker/SKILL.md`, модель — спека `docs/superpowers/specs/2026-10-17-github-tracker-design.md`. **После мержа PR, в котором менялся `docs/ROADMAP_INDEX.md` или владеющий файл роадмапа, агент обязан синхронизировать роадмап с issue:** в той же сессии, а если мерж был вне сессии — при следующем старте, обнаружив merge-коммит, создать отсутствующие issue для открытых пунктов и обновить заголовок/тело/поля Project V2; issue автоматически **не закрывать** — расхождения и кандидатов на закрытие выносить в отчёт владельцу. Повторный запуск идемпотентен; порядок — скил `github-tracker` §10. GitHub-операции — через MCP `mcp__github__*` (issue, поиск, Project, PR); `gh` CLI — фолбэк, если MCP-инструменты недоступны.

## Стиль коммитов и PR

- Коммиты: кратко, по-английски, в духе истории репозитория (`add fred importer`, `fix batch insert cbr_queries`).
- PR: одна фича = один импортёр/таблица; в описании — источник данных, схема таблицы, как запускать (`CLICKHOUSE_IMPORT_STAT=<name>`), пример проверки (`SELECT ... FROM <table> FINAL LIMIT 5`).
- В описании PR — роадмап и пункт (`<slug>/<item-id>`) и `Closes #N`; протокол живой приёмки — **комментарием в PR** того же пункта (состав, источник и порядок — `docs/IMPORTER_PACKAGE_STANDARD.md` §16.1 п. 8; связь с пунктом — правило 12; первое применение — PR #66, `cbr_int_rate_loans`).
- Логирование — logrus (`log.Infof("Imported %d rows of %s", ...)`), без fmt.Print в прод-коде импортёров.

## Календарь и приоритеты

Актуальный календарь триггеров — в ARCHITECTURE.md §7. Приоритет работ — фазы владеющего роадмапа (реестр — `docs/ROADMAP_INDEX.md`; для контура золота — `docs/ROADMAP_DCF_POLYUS.md` §7): сначала гигиена безопасности, затем импортёры данных для золота (fred → eia → lbma_gold → moex_iss), затем витрины и MCP.
