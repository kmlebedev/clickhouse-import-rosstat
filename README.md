# clickhouse-import-rosstat

Go-конвейер импорта российской макроэкономической и финансовой статистики в ClickHouse. Данные используются дашбордами Grafana и аналитическими моделями (сценарный прогноз золота, DCF и NAV акций ПАО «Полюс»). Один бинарник, конфигурация только через переменные окружения.

Подробная архитектура, схемы таблиц и конвенции — в [ARCHITECTURE.md](ARCHITECTURE.md). План развития — в [docs/ROADMAP_DCF_POLYUS.md](docs/ROADMAP_DCF_POLYUS.md). Правила для AI-ассистентов — в [AGENTS.md](AGENTS.md). Контур прогноза золота (витрины, календарь, ingest-endpoint, плагин `gold-nav`) — в разделе «Контур прогноза золота» и в [спецификации](docs/superpowers/specs/2026-10-10-gold-nav-plugin-design.md).

## Что импортируется

Каждый источник — импортёр, регистрируемый в общем реестре `chimport.Stats`; в пакетах `cbr/` и `rosstat/` регистрация одна на пакет — реестры `cbr/importers.go` и `rosstat/importers.go` (у каждого свой тест-энфорсер). Расписание задаёт Dagu (файлы в `dagu/`). Устройство пакета импортёров целиком — состав файлов, транспорт, шаблон, имена и регистрация, тесты, каталог и витрины, точка контроля публикации, расписание, порядок приёмки — описывает нормативный [docs/IMPORTER_PACKAGE_STANDARD.md](docs/IMPORTER_PACKAGE_STANDARD.md): читать его перед созданием нового пакета и перед рефакторингом существующего.

Импортёр `gold` — временный: производная цена, не LBMA. Официальный LBMA AM/PM пока не подключён, см. «Ограничения».

Импортёр `forecast_resolve` (пакет `forecast/`) закрывает обратную связь журнала прогнозов. Он читает `forecast_log FINAL` по `metric = 'xau_q_avg'` с наступившей `target_date`, берёт окно сверки — квартал, содержащий `target_date` (`[начало квартала, target_date]`), считает `actual` средним `gold_prices` в окне по приоритету `comex_front > moex_fix_usd` (площадка выбирается по количеству точек: среднее пустого окна — NaN, поэтому гейт по счётчику) и `error_pct = (predicted − actual) / actual × 100`. Записывает **одним батчем и только изменившиеся строки** — прогон ежедневный, перезапись того же значения не делается. `nav` и прочие метрики не резолвятся: факта для NAV нет, строка остаётся `is_resolved = 0`. Окно без точек цены — пропуск с предупреждением в логе; таблицу `forecast_log` резолвер не создаёт (её создаёт ingest при старте). Расписание — `dagu/forecast.yaml`, ежедневно 20:23 МСК (после `gold.yaml` и `moex.yaml`); разовый бэкфилл прогноза Q3-2026 — `sql/forecast_log_backfill.sql`. Результат виден в витрине `v_forecast_accuracy`.

Импортёр `dcf_mine_plans` (пакет `dcf/`) **сеет** `mine_plans` — LOM-планы активов Полюса: факт добычи последнего отчётного года он читает из `databook_polyus` (метрика `Total Dore gold output`, год берётся из колонки `date`), остальные числа (TCC, capex, срок службы, профиль проекта развития) берёт из версионных констант сида `dcf/mine_plans_seed.go` — снимка публичной отчётности Полюса. Актива с нулевой/отсутствующей добычей в датапаке пропускаются с предупреждением: сегодня так выпадают `TITIMUKHTA` и `ZAPADNOYE` (их россыпная добыча лежит в таблице `ALLUVIALS`), поэтому сид покрывает **6 активов из 8**. Ряды сида описаны в `series_catalog` (source `dcf_mine_plans`, 8 записей, частота `A`). Полная карта пробелов — [docs/DCF_DATA_COVERAGE.md](docs/DCF_DATA_COVERAGE.md).

**Поактивный AISC поверх Go-сида — ручной шаг `make dcf-aisc`.** Скрипт `scripts/extrapolation_aisc.py` (Python 3, только стандартная библиотека) разбирает поактивный AISC/TCC из четырёх закоммиченных PDF-пресс-релизов Полюса 4Q/FY 2018–2021 (`scripts/testdata/`), калибрует клин поддержания как **долю** от TCC за 2019–2021 (`r̄_i = mean((AISC − TCC)/TCC)`, грубые выбросы отсекаются правилом MAD), экстраполирует клин на 2025–LOM и увязывает его к групповому AISC замкнутой скалярной поправкой `m`. Скрипт **в ClickHouse не пишет** — он генерирует `sql/dcf_mine_plans_seed.sql` (77 строк = 5 активов × 10/13/24/15/15 лет) и `polyus_lom_reconciled_long.csv` (локальный артефакт контроля, в git не хранится). Сид применяется **вручную, отдельным шагом**: в `dagu/dcf.yaml` его нет — цепочка там остаётся двухшаговой (`dcf_mine_plans` → `dcf_engine`), потому что запланированный `make ch-sql` на staging не заработал бы (в релиз попадают только `README.md` и `dagu/*.yaml`, а `make`, Makefile и сам SQL-файл на хосте отсутствуют) и провал был бы **бесшумным**: `dcf_mine_plans` в той же цепочке пересеял бы ключи из Go-снимка, и расчёт прошёл бы на старом клине с зелёным логом. Порядок ручного применения — после `dcf_mine_plans`, до `dcf_engine`:

```bash
make dcf-aisc                                            # сгенерировать sql/dcf_mine_plans_seed.sql
make ch-sql FILE=sql/dcf_mine_plans_seed.sql             # применить (ReplacingMergeTree перезапишет 77 строк из 87)
DCF_RUN_ID=$(uuidgen | tr A-Z a-z) make import STAT=dcf_engine
```

Отличие от Go-сида — в структуре затрат, а не в горизонте: клин `(AISC − TCC)` у каждого рудника свой (доля `r̄` от ~0.49 у Куранаха до ~0.75 у Вернинского против единого «TCC + $698»), а `capex_sustaining` в этих строках равен **0**, потому что поддержание уже внутри `aisc` (Полюс определяет AISC как «TCC plus sustaining capital expenditures», а `npvLOM` вычитает и `aisc`, и `capex_sustaining` — ненулевое значение удвоило бы отток). Клин для глазной сверки виден только в CSV (`wedge_usd_per_oz`, `wedge_mn_usd`). Сухой Лог сид не трогает (проект развития, собственного AISC не раскрывает) — его 10 строк остаются от Go-сида. `VERNINSKOYE2` несёт консервацию карьера с сентября 2024: **нулевая добыча 2025–2028 при сохранённых строках**. Живая приёмка 2026-10-11: `mine_plans FINAL` — 87 строк (164 сырых = 87 + 77, затем 77 перезаписывают 77 по ключу), `dcf_engine` импортирует 36 строк (6 активов × 3 дека × 2 контура), невязка увязки 0.000000, `m` ≈ 1.992279; NAV Сухого Лога не изменился (54 887.40), Вернинского на `own_scenario`/`industrial` — 3 234.85 (было 3 435.34 под Go-сидом).

Импортёр `dcf_engine` (пакет `dcf/`) считает sum-of-parts LOM-NAV по активам: читает LOM-планы из `mine_plans` и цены из `price_decks` (на пустой таблице деков сеет её сама — спот из `gold_prices` плюс два задокументированных LT-якоря), считает NPV каждого актива по трём декам и двум контурам ставки и пишет `nav_by_asset` **одним батчем**. Агенту виден только результат — витрина `v_dcf_assumptions` (ARCHITECTURE.md §6.3); сырые `mine_plans`, `price_decks` и `nav_by_asset` не выданы. **Порядок запуска: сначала `dcf_mine_plans`, затем `dcf_engine`** — движок читает `mine_plans` как вход, и прогон ядра раньше сида посчитал бы по пустому или прошлогоднему плану. В расписании этот порядок ГАРАНТИРУЕТ `dagu/dcf.yaml`: `type: chain` исполняет шаги строго по порядку (`dcf_mine_plans` → `dcf_engine`), поэтому «сид раньше расчёта» — не пожелание, а свойство DAG-а. Запуск:

```bash
make import STAT=dcf_mine_plans                                  # сид mine_plans (до движка)
DCF_RUN_ID=$(uuidgen | tr A-Z a-z) make import STAT=dcf_engine   # пишет nav_by_asset
make import STAT=dcf_engine                                      # без DCF_RUN_ID ничего не пишет
```

`run_id` — клиентский и обязателен: строки `nav_by_asset` ссылаются на `model_runs`, а туда пишет только ingest-endpoint. Без `DCF_RUN_ID` движок считает, печатает в лог готовое тело `POST /v1/model_run` (его дописывает человек и отправляет в ingest) и **не пишет ничего** — `0` строк и запись в лог. Пока `mine_plans` пуста, прогон тоже успешен: предупреждение и `Imported 0 rows`. Строк на прогон — `активы × 3 дека × 2 контура`.

Отчётность Полюса даёт два импортёра в пакете `polyus/`: `databook_polyus` (xlsx-датапак) и `polyus_financial_metrics` (PDF-отчёты, пишет в общую таблицу `company_financials`). Текст извлекается `pdftotext -tsv`; полоса шапки финансовой таблицы собирается по ролям строк (маркер единиц, подписи периодов, подписи изменений), а подписи периодов, разбитые переносом строки («4Q» на одной строке шапки, «2019» на другой), склеиваются по X; значения раскладываются по колонкам, выведенным из шапки по X-координатам. Запуск: `make import STAT=polyus_financial_metrics` или `make import STAT=databook_polyus`; витрины над `company_financials` — `make import STAT=company_views` (в расписании — шаг после импорта метрик, см. `dagu/financial.yaml`). Пакет `news/` даёт импортёр `news_watch` — событийная лента РФ-канала: семь RSS-лент (Интерфакс, РБК, две ленты ЦБ РФ — `RssNews` и `eventrss`, TASS, две ленты smart-lab — `KonstantinLebedev` и `spydell-telegram` под общим `source='smartlab'`) пишутся в `news_events` (ключ `(date, source, title)` — повторный прогон идемпотентен), а агент читает витрину `v_news_events` с широким фильтром по стемам тезисов (дизель/нефть/НПЗ, санкции, ставка/ФРС, инфляция, золото/резервы, НДПИ, Полюс; у smart-lab — ещё вклады/депозиты/наличные/кредит/ОФЗ/RGBI/RUONIA/RUSFAR, стемы добавлены фазой 1.4) — сырая таблица ему не выдана. У лент smart-lab полный текст поста ложится в колонку `description` (`news_events` расширена идемпотентной миграцией `ALTER TABLE … ADD COLUMN IF NOT EXISTS`: существующая таблица не пересоздаётся, строки до миграции получают `''`; у новостных лент в `description` краткое описание позиции, `''` — описания нет), и при цитировании поста нужна атрибуция автора и smart-lab. Окна лент конечны (Интерфакс 25 позиций, РБК 30, ЦБ и TASS по 100, smart-lab ×2 по 20), поэтому расписание — каждые 30 минут (`dagu/news.yaml`, :07/:37 МСК), а режим расписания — `since`: прогон пишет **только отсутствующие** в `news_events` позиции (проверка наличия по ключу `(date, source, title)`, а не по дате-курсору), поэтому окно не переписывается целиком каждые полчаса, а опоздавшие позиции и второй фид ЦБ под тем же `source` не теряются; окно лент всё равно вычитывается целиком — у RSS нет «since»-параметра. Пропущенный прогон не теряет данные, пока следующее успешное чтение укладывается в окно ленты (простой дольше окна теряет её позиции безвозвратно — границы окон в «Ограничениях и известных проблемах»), и история копится с первого прогона (глубокой ретроспективы ленты не отдают). Дата позиции разбирается по формам `RFC1123Z`, той же форме без секунд и `RFC1123` (последняя — только для `GMT`/`UTC`: иначе аббревиатура зоны молча сдвинула бы время); позиция без распознанной даты или заголовка попадает в счётчик пропусков (ненулевое значение в логе — сигнал, что лента сменила форму), а ноль позиций в ленте или её сбой — ошибка ленты: остальные ленты при этом пишутся, итог собирается через `errors.Join`. Колонка `sentiment` пока остаётся NULL — канал записи для LLM-сессии это follow-up. Режимы переключаются переменной `NEWS_WATCH_MODE` (`all` по умолчанию):

```bash
make import STAT=news_watch                       # полный upsert окна всех лент (режим all — ручная пересборка)
NEWS_WATCH_MODE=since make import STAT=news_watch # режим расписания: только отсутствующие позиции (ключ date/source/title)
NEWS_WATCH_MODE=check make import STAT=news_watch # диагностика покрытия: окна источников и дыры, без записи
```

`check` читает ленты по HTTP и выполняет DDL `CREATE TABLE IF NOT EXISTS news_events` (и идемпотентные ALTER-ы схемы) (импортёр обязан отработать и на чистой базе), но **строк не пишет** и витрину не публикует; покрытие он берёт из сырой `news_events`; найденная дыра — ошибка прогона (режим ручной, «зелёный» отчёт с дырой никто не перечитает). Ограничение метода: дыру видно, пока сохранённый максимум источника старше начала окна его ленты, — после следующей успешной записи окно сдвигается вперёд, и `check` её больше не покажет, хотя пропущенные позиции так и не собраны. Отказ ленты виден и в `check`: список непрочитанных лент есть в отчёте, а окно помечено неполным — по неполному окну (например, выжила одна из двух лент ЦБ) дыра намеренно не объявляется, потому что промежуток могла закрывать упавшая лента.

Пакет `craw/` даёт импортёр `gost_vehicle_safety_certificate` — реестр СБКТС Росстандарта (свидетельства о безопасности конструкции ТС), прокси объёма импорта автомобилей: каждой ввезённой машине соответствует запись реестра, и дневной поток выданных сертификатов читается как поток импорта. **Транспорт — REST API портала `gost.ru`** (`/standards/rest-api/libraries/search`, заголовок `gtn.access.appid`), а не HTTP-листинг: портальная пагинация упирается в стену (`from=20000` ≈ 3 с, `from=100000` ≈ 10.7 с, `from=150000` и глубже — стабильный таймаут 60 с), а текстовый `query=DD.MM.YYYY` отдаёт те же документы плоским дневным срезом по дате публикации любой глубины. День читается целиком одним батчем, документы дедуплицируются по `id`, день с недобором — ошибка прогона, день с `count > 10000` отвергается (окно поиска ручки; исторический максимум дня ≈ 2.3 тыс.). Режим задаёт `GOST_MODE`: `since` (по умолчанию и режим расписания — хвост `[якорь − GOST_SETTLE_DAYS, сегодня МСК]`, дефолт `GOST_SETTLE_DAYS=3`; лаг «выдача → публикация» у источника ≈ 2 суток, поэтому хвост перечитывается каждый час, а верхняя граница — сегодня: часовой прогон ловит и дневной батч текущего дня), `full` (вся история, диапазон `GOST_FROM`/`GOST_TO`, по умолчанию `2016-01-01` … вчера МСК), `check` (read-only сверка `count` API против `uniqExact(certificate_number)` по дню публикации; расхождение — ошибка прогона). Неизвестный режим — ошибка до сети и до БД. Расписание — `dagu/craw.yaml`, раз в час (`:17` МСК), режим `since`; `full` и `check` — только вручную. Витрины `v_gost_vehicle_safety_certificate` (строки, без технического `uid`) и `v_gost_vehicle_safety_daily` (`date, mark, certificates = uniqExact(certificate_number)`) публикует сам импортёр в пишущих режимах. Запуск:

```bash
make import STAT=gost_vehicle_safety_certificate                        # since: хвост (штатный, этим ходит dagu)
GOST_MODE=full GOST_FROM=2016-01-01 GOST_TO=2026-10-11 make import STAT=gost_vehicle_safety_certificate
GOST_MODE=check GOST_FROM=2026-06-01 GOST_TO=2026-06-30 make import STAT=gost_vehicle_safety_certificate
```

`GOST_APP_ID` лежит в env-файле хоста: **dev** — `~/.config/rosstat/env`, **staging** — `/etc/clickhouse-import-rosstat.env` (тот же файл, что читает `deploy/staging/dagu.service`; образец — `deploy/staging/clickhouse-import-rosstat.env.example`). Значение — токен `gtn.access.appid` из JS-конфига страницы реестра (`standarts.adminsHeaders`); в репозитории не хранится, без него импортёр падает до сети.

**В env-файле держите только `GOST_APP_ID`.** Файл подключается Makefile через `-include`, а его переменные объявлены с `export`, поэтому значения из файла перекрывают префикс команды: `GOST_MODE=full make import STAT=gost_vehicle_safety_certificate` молча прочитает значение из файла, если `GOST_MODE` там есть. Режимные переменные (`GOST_MODE`/`GOST_FROM`/`GOST_TO`/`GOST_SETTLE_DAYS`) передавайте префиксом команды или в `env` шага DAG — как `GOST_MODE=since` в `dagu/craw.yaml`.

Полный прогон — часы работы (5–10 тыс. запросов), запускается **чанками по годам** (`GOST_FROM`/`GOST_TO`) и **резюмируем**: запись идемпотентна по ключу `ReplacingMergeTree`, неудачные дни перечисляются в ошибке и повторяются следующим прогоном; пустая таблица в режиме `since` даёт предупреждение «запустите `GOST_MODE=full`» и читает последние 7 дней, а если якорь отстал больше чем на 30 дней, окно обрезается последними 30 днями с тем же предупреждением — глубже 30 дней `since` историю не перечитывает, для неё нужен `full`. Ограничения данных: день с более чем 10 тыс. документов отвергается как нечитаемый; повторная публикация изменённого сертификата даёт вторую строку при том же номере (поэтому дневная метрика — `uniqExact`, а не `count()` строк); строки, записанные до бэкфилла, несут `publication_date = 1970-01-01` и в сверке `check` не участвуют (импортёр о них предупреждает); расхождение счётчиков портала (≈3.569 млн документов) и API (≈3.44 млн) — 3.6 % не объяснено (на проверенном окне наборы совпали).

Пакет `moex/` даёт третий импортёр — `keyrate_futures` (расчётный фьючерс на Индекс ключевой ставки MOEX KEYRATE): это рыночный контур ожиданий по ставке, единственный ряд, смотрящий на **будущие** решения ЦБ, а не на факт, поэтому он сравнивает модель с рынком (побить рынок трудно, измерить, добавляет ли модель информацию поверх него, — можно). Список серий **не хардкодится**: каждый прогон перечитывает поиск ISS (`/iss/securities.json?q=KEYRATE`; отбор — площадка `RFUD`, код с префиксом `KK`, `is_traded = 1`, поэтому индекс `KEYRATE` и календарные спреды `KKV6KKZ6` отсеиваются) — серии добавляются и экспирируются каждый квартал. Паспорт серии (`/iss/securities/<secid>.json`, блок `description`) даёт короткое имя (`SHORTNAME`, «KEYRATE-10.26»), начало обращения `FRSTTRADE` и дату экспирации `LSTDELDATE` — она же **дата заседания СД ЦБ**, по объявленной на нём ставке рассчитывается индекс (19:00 МСК — `EXPIRATION_TIME` паспорта ISS); дневные итоги приходят пагинацией `start` из `/iss/history/engines/futures/markets/forts/securities/<secid>.json`. Цена серии — расчётная цена дня `SETTLEPRICE` в пунктах, равных п.п. ставки (при ставке 14 % индекс = 14,00; шаг цены 0,01 п.п. = 10 ₽, то есть 1 п.п. = 1 000 ₽ — формула `100 − ставка` к KEYRATE **неприменима**). `LAST` не используется нигде: в дни без сделок ISS отдаёт по нему ноль, а расчётная цена дня есть всегда. Инкремент — по **каждой** серии от её `max(date) + 1 день` (`lastDate`), а не от общей даты: серии живут с разных дней (`KKG7` стартовала 12.10, остальные — 29.09). Сбой одной серии не роняет остальные (`log.Warnf` с `secid`, итог — `errors.Join`), но сбой **всех** серий (паспортов или дней) — ошибка импорта **до публикации**: пустой прогон не должен слать батчи, писать каталог и пересоздавать витрину. Таблицы — `keyrate_futures` (дневные итоги, ключ `(secid, date)`) и `keyrate_contract` (паспорта серий, `ORDER BY secid`), витрина — `v_keyrate_expectations`: дата, серия, дата заседания, `settle`/`close`, ликвидность серии и вменённое изменение к последней **известной** ставке `cbr_key_rate` — `expected_change_pp` (п.п.) и `expected_change_bp` (б.п.). Вменённое значение считается к последней известной ставке, а не к ставке на дату заседания, и равно NULL, пока `cbr_key_rate` пуста (`nullIf(…, 0)`: `argMax` по пустой таблице отдаёт `0`, и без обёртки изменение выродилось бы в `settle × 100` б.п.) — NULL здесь значит «неизвестно», а не нулевое изменение; `close`/`LAST` ожиданий не отражают, читать надо `settle`. ⚠️ Инструмент **низколиквиден** (открытые позиции — десятки контрактов, у дальней серии сделок может не быть вовсе), поэтому значение **индикативно**: это не прогноз рынка и не ценовое обязательство, а при нулевом объёме дня — не рыночное ожидание вовсе. Расписание — `dagu/moex.yaml`, ежедневно 19:13 МСК, шаг 3 (после `ofz_curve`); сырые `keyrate_futures`/`keyrate_contract` агенту **не выданы** — доступ даёт только витрина (`GRANT SELECT` — `sql/mcp_kimi_reader.sql`), описания серий — в `v_series_catalog` по `source = 'moex'`. Запуск:

```bash
make import STAT=keyrate_futures   # серии + паспорта + дневные итоги + каталог + витрина; повтор идемпотентен по (secid, date)
```

Пакет `cbr/` даёт и импортёр `cbr_mp_survey` — мониторинг предприятий Банка России (опросы нефинансовых компаний), главный канал ценовых ожиданий бизнеса в решениях ЦБ. XLSX `mp_survey_data.xlsx` (стабильный id 135603: имя файла при обновлении не меняется, поэтому скрейпинг страницы не нужен; в книге 31 лист, читаются 4) разбирается без ручного шага, 13 рядов пишутся в `macro_series` с `source = 'cbr_survey'`: ценовые ожидания бизнеса на следующие 3 месяца (баланс ответов, п. — главный канал ЦБ), индикатор бизнес-климата (ИБК; прокси разрыва выпуска — числового ряда разрыва ЦБ не публикует), условия кредитования предприятий (индекс, отрицательные значения — преобладает ужесточение), ожидаемый прирост отпускных цен в годовом выражении (вопрос анкеты с 2020 г., поэтому ряд короче остальных), загрузка производственных мощностей (%), обеспеченность предприятий персоналом и ожидания изменения численности (баланс ответов). У шести рядов есть сезонно сглаженная пара `…_sa` — именно с.к. значения ЦБ цитирует в комментариях; у `credit_conditions` пары нет (сезонной корректировки в источнике нет); единицы и знаки рядов различаются, поэтому перед использованием читать `v_series_catalog` по `(source='cbr_survey', series)`. **Дата точки — отчётный период, а не месяц публикации:** месячные ряды начинаются с 2002-01, квартальные — с 1к02, дата квартального ряда — 1-е число месяца, следующего за отчётным кварталом (конвенция `rosstat_vvp_kvartal`), поэтому последняя точка месячного ряда — 2026-08, тогда как справка ЦБ этой волны называется «сентябрь 2026»: ЦБ публикует волну в первую декаду следующего месяца (~10–15-го) и нумерует справки по месяцу волны — 22,7 п. в справке «сентябрь 2026» это точка отчётного периода август 2026 (с.к. ряд, +1,6 п. к июлю). Всего 2084 точки (1640 месячных + 444 квартальных) — живая приёмка 2026-10-13 совпала с публикацией ЦБ по всем четырём сверенным рядам (ИБК −2,3 п.; ожидаемый прирост отпускных цен 7,0 %; обеспеченность персоналом −19,7 п. в 2к26). Разбор — `cbr/mp_survey_parse.go` (`excelize/v2`: маркеры блоков и заголовки в фиксированных строках, только raw-значения ячеек, fail-fast на структуру листа и неоднозначную колонку), определения 13 рядов — `cbr/series_meta.go`, витрина — `cbr/views.go` (`cbrSurveyView`); тесты офлайн на фикстуре `cbr/testdata/mp_survey_data.xlsx` (урезанная копия реального файла: те же 4 листа из 31, ~226 КБ) и тест полноты каталога `cbr/mp_survey_series_meta_test.go`. Витрина `v_cbr_survey` (`source, series, date, value`) выдана агенту (`GRANT SELECT` — `sql/mcp_kimi_reader.sql`), а сырая `macro_series` ему закрыта: 13 рядов читаются только через неё, единицы, знаки и происхождение — в `v_series_catalog` (`source = 'cbr_survey'`, 13 записей).

Второй импортёр того же пакета — `cbr_mo_br` (макроэкономический опрос Банка России, шаг 1.5 контура ключевой ставки) — даёт **консенсус-бенчмарк**: медианы, интервалы (p10/p90), min/max и число ответов профессиональных аналитиков по 17 показателям (ИПЦ, ВВП, ключевая ставка, курс USD/RUB, нефть и др.). Файл волны — `full.xlsx` со страницы `cbr.ru/statistics/ddkp/mo_br/`: ссылку импортёр ищет по `a[href$="full.xlsx"]` (имя и id файла меняются с каждой волной), поэтому URL в коде не хардкодится. Волны выходят **~8 раз в год** (в книге — колонки-волны с 2021-05; дата точки — 1-е число месяца волны, публикация наступает через 2–6 дней), значит ежедневный прогон почти всегда видит тот же файл: перед скачиванием импортёр делает лёгкий **HEAD-префлайт** (`util.HeadFingerprint`) и сверяет отпечаток версии с общей служебной таблицей `source_publications` (`util.PublicationKnown`/`util.SavePublication`) — при известной версии и совпавшем числе точек это **no-op без скачивания файла и без записи в БД**; полный путь (~560 КБ: страница + XLSX, парсинг, батч всей истории) — только при смене версии. Новую версию импортёр записывает строкой в `source_publications` **после** успешной записи точек, публикации каталога и витрины, поэтому строка всегда означает «эти точки записаны и опубликованы». Ряды лежат в общей `macro_series` (`source = 'cbr_mo_br'`, имена `<показатель>_<год>_<статистика>`, у двух листов без прогнозного года — без года), описаны в `series_catalog` (генерация из разбора) и читаются витриной `v_cbr_mo_br`; сырая `macro_series` агенту по-прежнему не выдана. `source_publications` — служебная: агенту (`kimi_reader`) она тоже не выдана. С этого PR механизм — свойство общего шаблона `util.ClickHouseImport` (три опциональных поля, ARCHITECTURE.md §3), и точку контроля публикации объявили ещё 15 импортёров: десять импортёров ЦБ с месячной каденцией файла (`cbr_households_b_mes`, `cbr_m2`, `cbr_credit_m2x`, `cbr_loans_to_corporations`, `cbr_loans_to_individuals`, `cbr_bank_int_rate`, `cbr_int_rate_loans`, `cbr_indicators_cpd`, `cbr_infl_exp` и `cbr_mp_survey`), четыре Росстата (`rosstat_ipc_mes`, `rosstat_salaries_mes`, `rosstat_vvp_kvartal`, `rosstat_labour_force_mes`; имена с префиксом пакета — с шага 1 фазы 2 контура ключевой ставки, тогда же импортёры переведены на `util.GetPage`/`util.FindLink` и сведены в реестр `rosstat/importers.go`) и `sber_finansovie_rezultaty`; производные (каталог рядов и витрины) публикует сам шаблон — обёртка `publishedStat` упразднена (на 2026-10-17 объявлений 24 — шестнадцать в `cbr/` и восемь вне него: пять Росстата, `sber_finansovie_rezultaty`, а два добавил рефакторинг пакета `bank/` — `domrf_mortgage` и `rus_vtb_group_ifrs`; в `cbr/` объявления добавили шаги платёжного баланса `cbr_bop_est` и `cbr_bop_standard`, `cbr_dip_bulletin` — приложения ДИП, `cbr_mt_forecast` — среднесрочный прогноз ЦБ, `cbr_form101` — сырые остатки формы 101, а `rosstat_ipc_weeks_bulletins` — недельные ИПЦ до 2022; у `rosstat_ipc_weeks_bulletins`, `cbr_dip_bulletin`, `cbr_mt_forecast`, `cbr_form101` и `rus_vtb_group_ifrs` объявление есть, но no-op держит гейт по своей таблице — датам у первого, `release_id` у второго, `release_date` у третьего, `max(report_date)` у четвёртого, пофайловым версиям (basename + отпечаток) у пятого, — ARCHITECTURE.md §8 п. 13). Третий импортёр того же пакета — `cbr_mp_summary` (шаг 1.2 контура ключевой ставки) — **текстовый сигнал ЦБ**: резюме обсуждения ключевой ставки, в которых ЦБ сам называет, какие каналы взвешивал (~8 публикаций в год, лаг 7–13 дней после заседания). Импортёр идёт по **индексу материалов заседаний** `https://www.cbr.ru/dkp/mp_dec/decision_key_rate/` (карточки с датой публикации и относительной ссылкой; имя слага меняется с публикацией, поэтому путь страницы не хардкодится) и работает **дельтой**: известным документ считается, только если его адрес есть в шапке, по дате его заседания есть строки блоков **и** есть хотя бы одна regex-строка каналов (`method='regex'`; именно regex — иначе строки LLM-слоя замаскировали бы потерю всего слоя 1). Недописанный документ (сбой любого из трёх батчей слоя 1) перекачивается и перезаписывается целиком, повтор идемпотентен по ключам `ReplacingMergeTree`. Поэтому в обычный день скачивается только индекс (~116 КБ), а новое резюме подхватывается в день публикации; HEAD-префлайта у импортёра нет — артефакт у него не один (индекс и набор документов), и вопрос «какие резюме уже разобраны» решается адресами и полнотой документа, а не отпечатком страницы. Результат — три свои таблицы: `cbr_mp_summary` (шапка: `meeting_date` — дата заседания и ключ ряда, `published` — атрибут, `url`, `decision_action` (`hold`/`cut`/`hike`), `decision_rate`, `decision_delta_bp` — шаг к предыдущему решению в б.п., `effective_from`, `signal` — дословные предложения ЦБ), `cbr_mp_summary_block` (дословный текст абзацев и пунктов пяти фиксированных блоков) и `cbr_mp_summary_channel` (разметка по 11 каналам ДКП; реестр и определения — [docs/KEY_RATE_CHANNELS.md](docs/KEY_RATE_CHANNELS.md) §3), плюс три витрины `v_cbr_mp_summary`, `v_cbr_mp_summary_blocks` и `v_cbr_mp_summary_channels` (гранты `kimi_reader` — `sql/mcp_kimi_reader.sql`; сырые три таблицы агенту **не выданы**). **Разметка двухслойная:** слой 1 — детерминированные регексы (`method='regex'`, `model=''`, `prompt_version=0`; работает всегда, офлайн и без ключей), слой 2 — модель LLM (`method='llm'`: официальный SDK `anthropic-sdk-go`, Anthropic-совместимый `POST <base>/v1/messages`, ключ заголовком `x-api-key`, обязательный `max_tokens`). LLM-слой факультативен: переменные `LLM_BASE_URL`, `LLM_API_KEY`, `MP_SUMMARY_LLM_MODEL` (значения — только в `~/.config/rosstat/env`; ключ уходит заголовком и в логи не попадает); если хотя бы одна пуста или провайдер отказал — `warn`, документ остаётся с regex-слоем, а догон повторится следующим прогоном. Фактическое имя модели пишется в данные (`model`), а `model` + `prompt_version` входят в ключ таблицы: разметка другой модели или редакции промпта ложится рядом со старой, не затирая её. Цитаты модели обязаны дословно присутствовать в тексте резюме (иначе отбрасываются), `slug` канала — только из реестра 11 каналов. Кроме импортёра в том же PR появился DAG календаря: `dagu/calendar.yaml` (ежедневно 10:07 МСК) забирает даты заседаний с `cbr.ru/dkp/cal_mp/` и пишет канонические строки заседаний в `events_calendar` — рядом с ручными строками-триггерами сида (у них другой `title`, а значит другой ключ `ReplacingMergeTree`; различие рядов — ARCHITECTURE.md §7). Запуск:

```bash
make import STAT=cbr_mp_summary   # первый прогон — вся история резюме из индекса; повтор — чтения и no-op без вставок
make import STAT=events_calendar  # календарь заседаний из cbr.ru/dkp/cal_mp/ (ручные строки сида не трогает)
```

## Быстрый старт

Нужны Go 1.27, ClickHouse с нативным протоколом (порт 9000) и `CLICKHOUSE_URL`.

```bash
make all                                # lint, тесты, сборка
export CLICKHOUSE_URL="clickhouse://user:password@host:9000/database"
CLICKHOUSE_IMPORT_STAT=fred,gold_prices ./build/clickhouse-import-rosstat
```

`make build` собирает статический бинарник `linux/amd64` в `build/` (для сервера). Для запуска на Mac соберите нативный бинарник: `go build -o /tmp/rosstat-bin .`

Проверка результата в ClickHouse:

```sql
SELECT series, count(), max(date) FROM macro_series FINAL GROUP BY series;
SELECT venue, count(), max(date) FROM gold_prices FINAL GROUP BY venue;
```

| Переменная | Назначение |
|---|---|
| `CLICKHOUSE_URL` | DSN подключения (обязательна). Не выводится в логах |
| `CLICKHOUSE_IMPORT_STAT` | Фильтр импортёров через запятую по имени (`Name()`). Пусто — все импортёры |
| `LOG_LEVEL` | Уровень logrus: `debug`, `info`, `warn`, `error` |
| `CERT_FILES` | PEM-сертификаты через запятую (нац. УЦ РФ для gos-сайтов) |
| `BLS_API_KEY` | Регистрационный ключ BLS (необязателен; без него работает, но лимиты строже). Не выводится в логах |
| `BEA_API_KEY` | UserID BEA API (обязателен для `bea`; без него импортёр завершается ошибкой). Не выводится в логах |
| `EIA_API_KEY` | Ключ EIA API v2 (обязателен для `eia`; без него импортёр завершается ошибкой, ключ маскируется в текстах ошибок). Не выводится в логах |
| `LLM_BASE_URL`, `LLM_API_KEY`, `MP_SUMMARY_LLM_MODEL` | LLM-слой разметки каналов `cbr_mp_summary`: base URL Anthropic-совместимого API (**без** `/v1` — путь `v1/messages` дописывает официальный SDK `anthropic-sdk-go`, и `/v1` в base дал бы `/v1/v1/messages`; у DeepSeek такой base — `https://api.deepseek.com/anthropic`), ключ и имя модели. Нужны все три; пустая любая / отказ провайдера / невалидный JSON — `warn` и деградация до regex-слоя (импорт не падает, догон следующим прогоном). Значения — только в окружении (`~/.config/rosstat/env`), в репозиторий и логи не попадают: SDK шлёт ключ заголовком `x-api-key`, а не в URL/query |
| `INGEST_TOKEN` | Bearer-токен ingest-endpoint, обязателен для `cmd/ingest` (без него процесс не стартует). Не выводится в логах |
| `INGEST_ADDR` | Адрес HTTP-сервера `cmd/ingest`, по умолчанию `:8081` |
| `INGEST_RATE_PER_MIN` | Лимит запросов `cmd/ingest` в минуту (token bucket, burst 10), по умолчанию 60; превышение — `429` |
| `NEWS_WATCH_MODE` | Режим импортёра `news_watch`: пусто или `all` — полный upsert окна всех лент (ручная пересборка), `since` — режим расписания dagu: только отсутствующие в `news_events` позиции по ключу `(date, source, title)`, `check` — проверка дыр/окон без записи. Неизвестное значение — ошибка до сети и до БД |
| `ARCHIVE_BACKEND`, `ARCHIVE_YANDEX_TOKEN`, `ARCHIVE_YANDEX_DIR`, `ARCHIVE_LOCAL_DIR`, `ARCHIVE_ACTION`, `ARCHIVE_LIST_SOURCE`, `ARCHIVE_RECONCILE`, `ARCHIVE_REGISTRY_OUT`, `ARCHIVE_REGISTRY_ALLOW_EMPTY` | Винтажный архив версий файлов источников (пакет `archive/`, ARCHITECTURE §2–§3): `ARCHIVE_BACKEND` = `local` \| `yandex` \| пусто = архивация выключена; `ARCHIVE_YANDEX_DIR` — корень архива на Яндекс.Диске (по умолчанию `disk:/rosstat-archive`), `ARCHIVE_LOCAL_DIR` — корень локального бэкенда (dev-прогон, приёмка). `ARCHIVE_ACTION` = `registry` \| `list` \| `restore` (неизвестное значение — ошибка): `registry` — обновить git-зеркало реестра (`make archive-registry`; путь зеркала переопределяет `ARCHIVE_REGISTRY_OUT`; пустой реестр поверх непустого зеркала режим не пишет — затирание разрешает только `ARCHIVE_REGISTRY_ALLOW_EMPTY=1` с warn); `list` — напечатать версии реестра (`make archive-list`; фильтр `ARCHIVE_LIST_SOURCE=<источник>`, а с `ARCHIVE_RECONCILE=1` — сверка «объект без строки реестра», нужен бэкенд с листингом, сегодня `local`); `restore` — восстановление БД из архива (`make archive-restore STAT=<импортёр>`; процесс не завершается, а продолжает обычный путь импортёров, поэтому пустой `CLICKHOUSE_IMPORT_STAT` в этом режиме — ошибка). Токен — секрет: только в окружении, в репозиторий и логи не попадает; как получить и куда положить — «Ключи и окружение» |

Поведение при запуске: неизвестное имя в `CLICKHOUSE_IMPORT_STAT` даёт предупреждение; ошибка любого импортёра даёт код выхода `1`, остальные импортёры при этом выполняются.

Импортёр `financial` читает `TICKER`, `FINANCIAL_DATA_DIR`, `INVESTING_EMAIL`, `INVESTING_PASSWORD`; эти переменные устаревают вместе с legacy-контуром.

`DCF_RUN_ID` — переменная окружения **разового прогона** `dcf_engine`, а не строка конфигурации источника: UUID прогона, который уходит в `nav_by_asset.run_id` и связывает строки с записью `model_runs` (её создаёт ingest-endpoint). Передавайте её прямо в команде — `DCF_RUN_ID=$(uuidgen | tr A-Z a-z) make import STAT=dcf_engine`; в `~/.config/rosstat/env` её хранить не нужно. Без `DCF_RUN_ID` движок считает и печатает тело `POST /v1/model_run`, но не пишет ни строки (см. «Что импортируется»). Импортёр `dcf_mine_plans` переменных окружения не имеет (только `CLICKHOUSE_URL`).

Переменные стендов Grafana (`GRAFANA_TEST_URL`/`GRAFANA_TEST_TOKEN`, `GRAFANA_STAGING_URL`/`GRAFANA_STAGING_TOKEN`, `GRAFANA_ORG_ID`) к импортёрам не относятся — они нужны целям `make grafana-*` (дашборды как код, деплой и smoke). Значения живут в том же `~/.config/rosstat/env`, `make env-check` печатает только «задан/не задан»; описание — в разделе «Grafana».

## Оркестрация (Dagu)

Расписания описаны в `dagu/*.yaml`: `type: chain`, `overlap_policy: skip`, каждый шаг запускает бинарник с `CLICKHOUSE_IMPORT_STAT=<имя>`, ретраи — 3 попытки с паузой 300 с. Путь к бинарнику (`ROSSTAT_IMPORT_BIN`) и `CLICKHOUSE_URL` задаются в `base.yaml` Dagu; секреты лежат в файлах `/etc/dagu/secrets/` с правами `0600`, в репозитории их нет. Внутри домена зависимости задаются через `depends`; между DAG зависимостей нет (см. `gold.yaml`: шаг `cbr_currency_usd` стоит внутри DAG). Отдельный `dagu/dcf.yaml` использует именно это свойство DAG-а: `type: chain` исполняет `dcf_mine_plans` строго до `dcf_engine`, и «сид раньше расчёта» — гарантия расписания, а не только порядок ручных команд (Finding 3 финального ревью). **Шага уточнённого AISC-сида в `dagu/dcf.yaml` нет** — он применяется вручную (см. «Что импортируется» и «Ограничения»); DAG содержит ровно два шага, и придумывать третий не нужно.

Запуск одного DAG вручную: `dagu start dagu/gold.yaml` (dev-окружение Dagu должно видеть `ROSSTAT_IMPORT_BIN` и `CLICKHOUSE_URL` через `base.yaml`).

## Контур прогноза золота

Составные части контура (подробно — ARCHITECTURE.md §6.3 и §6.5):

- витрины `v_model_inputs`, `v_gold_dashboard`, `v_forecast_accuracy`, `v_imf_macro`, `v_eia_petroleum`, `v_gold_forecasts`, `v_gold_etf_flows`, `v_cb_gold_dynamics`, `v_gold_etf_flows_daily`, `v_gold_etf_funds_daily`, `v_news_events` и календарь `v_events_calendar` — читаются агентом через MCP (пользователь `kimi_reader`, только `v_*`); гранты — в `sql/mcp_kimi_reader.sql`;
- витрины метрик компаний сектора `v_company_financials`, `v_company_metric_sources`, `v_company_operating` (импортёр `company_views`) — читаются агентом через MCP; сейчас наполнены данными Полюса (ARCHITECTURE.md §6.3);
- витрина `v_dcf_assumptions` — NPV рудников Полюса по каждому (deck, контур ставки, актив) плюс суммарный NAV рудников; пишет её импортёр `dcf_engine` (пакет `dcf/`, `DCF_RUN_ID=<uuid> make import STAT=dcf_engine`), сырая `nav_by_asset` агенту не выдана;
- импортёр `forecast_resolve` (пакет `forecast/`, `dagu/forecast.yaml`, 20:23 МСК) — обратная связь журнала прогнозов: заполняет `actual`/`error_pct` в `forecast_log` сверкой `xau_q_avg` со средним `gold_prices` за квартал `target_date` (ARCHITECTURE.md §6.1);
- ingest-endpoint (`cmd/ingest`) — единственный путь записи прогонов модели, ручных рядов, цен COMEX и консенсус-прогнозов;
- плагин Kimi `gold-nav` — отдельный репозиторий, сценарная сессия прогноза и DCF NAV PLZL.

### Ingest-endpoint

Запуск: `make run-ingest` (нужны `CLICKHOUSE_URL` и `INGEST_TOKEN` в `~/.config/rosstat/env`; `INGEST_ADDR` по умолчанию `:8081`). При старте создаются `model_runs`, `forecast_log`, `macro_series`, `gold_prices`, `gold_forecasts`, если их ещё нет. Витрины `views/` создаются отдельно: `make import STAT=gold_views` после первого запуска ingest.

| Метод и путь | Тело | Ответ |
|---|---|---|
| `POST /v1/model_run` | JSON прогона: клиентский `run_id` (UUID), `trigger_type`, `price_deck`, `probabilities`, `gold_scenario` с `horizon`, значения NAV | `200 {"inserted": 1}`; `400` при ошибке валидации |
| `POST /v1/manual_series` | JSON-массив `{"series", "date": "YYYY-MM-DD" (диапазон Date32 [1900-01-01, 2299-12-31]), "value", "source"?}` → `macro_series`; `source` необязателен (по умолчанию `manual`), допустимы `manual`, `webbridge`, `imf` | `200 {"inserted": N}`; `400` при ошибке любой точки |
| `POST /v1/gold_prices` | JSON-массив `{"venue", "date": "YYYY-MM-DD" (диапазон Date32), "usd"}` → `gold_prices`; допустимая venue — `comex_front` (словарь расширяемый), `usd` > 0 | `200 {"inserted": N}`; `400` при ошибке любой точки |
| `POST /v1/gold_forecasts` | JSON-массив `{"author", "published": "YYYY-MM-DD" (диапазон Date32), "horizon", "scenario", "low", "high", "point", "probability"}` → `gold_forecasts`; `author`/`horizon` непусты, `scenario` ∈ {`point`,`range`,`bull`,`base`,`bear`}, `low`/`high`/`point` ≥ 0 и хотя бы одно > 0, `high ≥ low` (когда заданы оба), `probability` 0–100 (0 — «не задана») | `200 {"inserted": N}`; `400` при ошибке любой строки |

Все запросы — с заголовком `Authorization: Bearer <INGEST_TOKEN>`; без него или с неверным токеном — `401`. Сверх `INGEST_RATE_PER_MIN` (по умолчанию 60 в минуту) — `429`; тело больше 1 MiB — `413`; неизвестное поле в JSON — `400`. Повторный `POST /v1/model_run` с тем же `run_id` ничего не записывает. Формат тела — в `ingest/model_run.go` (структура `ModelRun`).

### Деплой на staging

Разворачивает три компонента на хост `palmshell`: бинарник `clickhouse-import-rosstat`, планировщик `dagu` v2.18.2 и MCP-сервер `mcp-clickhouse` 0.7.0 (HTTP, read-only). ClickHouse и Grafana на хосте не трогаются. Артефакты — `deploy/staging/`, порядок и отладка — `deploy/staging/README.md`.

```bash
# 1. Файл секретов на хосте (один раз; значения задаёт владелец). Токен: openssl rand -hex 32
ssh palmshell 'install -m 600 /dev/null /etc/clickhouse-import-rosstat.env'
#    вписать по образцу deploy/staging/clickhouse-import-rosstat.env.example

# 2. Развернуть и создать пользователя MCP
make deploy-staging
CH_SETUP_PASSWORD=<пароль default> make mcp-user-staging

# 3. Проверить end-to-end через туннель
ssh -N -L 8123:127.0.0.1:8123 palmshell &
CLICKHOUSE_PASSWORD=<пароль kimi_reader> make mcp-check MCP_CHECK_HOST=127.0.0.1 MCP_CHECK_PORT=8123
```

Переменные: `STAGING_HOST` (по умолчанию `palmshell`), `MCP_VERSION`, `DAGU_VERSION`. `deploy-staging` **падает**, если файла секретов нет, и никогда его не создаёт.

**Внимание:** после `make deploy-staging` `dagu` включается и **начинает выполнять DAG-и по расписанию** — это реальные запросы к внешним источникам. Порядок внутри цели защищает от запуска DAG-ов на неисправном бинарнике: сначала проверяются бинарь и DAG-файлы, потом сервисы включаются, потом идёт smoke.

Цель также удаляет из `/root/dagu/` DAG-файлы, снятые с репозитория: `scp` копирует, но не удаляет, а оставшийся файл продолжал бы выполняться по своему расписанию параллельно новой цепочке. Список удаляемых файлов — в Makefile, его пополняют при каждом удалении DAG из `dagu/`. Одноразовый шаг после деплоя — миграция таблицы домохозяйств (сверка `cbr_households_b_mes` со старой `households_b_mes` и удаление старой только при совпадении): см. `deploy/staging/README.md`, раздел «После деплоя».

Сервисы слушают только `127.0.0.1` (`dagu` :8080, MCP :8000): наружу ничего не публикуется, TLS/Caddy и публичный MCP-эндпоинт — следующая фаза.

### Ключи и окружение

Ключи и пароли лежат в одном файле вне репозитория: `~/.config/rosstat/env` (права `600`, каталог `700`). Формат:

```bash
export BEA_API_KEY=<your-key>
export EIA_API_KEY=<your-key>
# export GOST_APP_ID=<токен gtn.access.appid: JS-конфиг страницы реестра СБКТС, standarts.adminsHeaders>
export CLICKHOUSE_URL=clickhouse://localhost:9000/default
export CLICKHOUSE_PASSWORD=<kimi_reader-password>
# export CH_IMPORT_PASSWORD=<пароль пользователя, читающего сырые таблицы>
# export BLS_API_KEY=<your-key>
# export ARCHIVE_YANDEX_TOKEN=<OAuth-токен Яндекс.Диска: оба scope — cloud_api:disk.write и cloud_api:disk.read>
# ARCHIVE_BACKEND в этот файл НЕ добавлять: бэкенд выбирается аргументом make (см. «Винтажный архив»)
# export INGEST_TOKEN=<ingest-token>
# export INGEST_RATE_PER_MIN=60
# export GRAFANA_TEST_TOKEN=<токен сервис-аккаунта Editor локального стенда :3000>
# export GRAFANA_STAGING_TOKEN=<токен сервис-аккаунта Editor на staging, доступ через туннель :3001>
# export GRAFANA_ORG_ID=1
```

- `CLICKHOUSE_URL` — **основной** способ задать адрес: это DSN, из которого Go-код (`clickhouse.ParseDSN`) и `scripts/extrapolation_aisc.py` берут хост, порт, пользователя и базу. Дискретные `CLICKHOUSE_HOST`/`CLICKHOUSE_PORT`/`CLICKHOUSE_USER`/`CLICKHOUSE_DATABASE` в файле обычно **не задаются**; скрипт читает их как переопределение поверх DSN;
- `CLICKHOUSE_PASSWORD` — пароль **`kimi_reader`**, read-only пользователя витрин (`make mcp-check`). Сырые таблицы ему закрыты: чтение `databook_polyus` и подобных идёт под другим пользователем, поэтому у скриптов есть **`CH_IMPORT_PASSWORD`**. Если пользователь из DSN пароля не имеет (локальный `default`), переменную задавать не нужно — подставлять вместо неё `CLICKHOUSE_PASSWORD` нельзя, это чужой пароль и он даёт 401.

- Makefile подключает файл сам (`-include`), поэтому любая `make`-цель видит ключи без `export` в shell; путь можно переопределить: `make ROSSTAT_ENV=/путь/к/файлу ...`;
- в терминале: `set -a; . ~/.config/rosstat/env; set +a`;
- проверка без вывода значений: `make env-check`;
- локальный импорт одного источника: `make import STAT=bea` (собирает бинарник под macOS в `build/clickhouse-import-rosstat-native`);
- Kimi Code: ключи для MCP задаются в `~/.kimi-code/mcp.json` (блок `env`), для остальных команд Kimi вызывает `make`, поэтому файл окружения подхватывается автоматически;
- Dagu (расписания): секреты описаны в `~/dagu-dev/base.yaml` через provider `file`, каждый ключ — отдельный файл `~/dagu-dev/secrets/<name>` (`600`). Для BEA: `bea_api_key`; для EIA: `eia_api_key`; при добавлении ключа нового импортёра — новый файл и строка в `secrets:`;
- файлы `*.env`, `secrets/` и ключи в коде не коммитить; `CLICKHOUSE_PASSWORD` только в файле окружения (`~/.config/rosstat/env`), в `mcp.json` его нет.

#### Винтажный архив версий файлов источников (опция)

Винтажный архив — сохранённые версии скачанных файлов источников в объектном хранилище плюс реестр `registry.jsonl` (ARCHITECTURE.md §2–§3, стандарт пакета импортёров §9.6). Штатно архивация **выключена**: пустой `ARCHIVE_BACKEND` = архива нет. Версия сохраняется как объект в хранилище плюс строка реестра, и объект записывается при каждом сохранении — ключ версии выведен из отпечатка HEAD, который содержимое не покрывает, поэтому перезапись и есть условие того, что `sha256`/`size` строки описывают именно лежащие в хранилище байты.

Как получить токен Яндекса (OAuth, личная учётная запись):

1. создать OAuth-приложение ([oauth.yandex.ru](https://oauth.yandex.ru/)), отметить **оба** scope: `cloud_api:disk.write` — запись версий и `cloud_api:disk.read` — проверка наличия, чтение реестра и скачивание версий;
2. получить токен по implicit-flow: открыть `https://oauth.yandex.ru/authorize?response_type=token&client_id=<ClientID>` и подтвердить доступ — токен вернётся в адресной строке (`access_token=…`);
3. положить строку `export ARCHIVE_YANDEX_TOKEN=…` в `~/.config/rosstat/env` (dev) или в `/etc/clickhouse-import-rosstat.env` на staging (образец — `deploy/staging/clickhouse-import-rosstat.env.example`); на staging и включается сам бэкенд (`ARCHIVE_BACKEND=yandex`);
4. проверка без вывода значений: `make env-check` — строка `OK ARCHIVE_YANDEX_TOKEN задан`.

**Ловушка:** `ARCHIVE_BACKEND` — режимная переменная, и в `~/.config/rosstat/env` её дублировать нельзя (переменные файла экспортируются и перекрывают префикс команды). Бэкенд выбирается аргументом цели — так приёмка идёт на локальном хранилище, не трогая Диск:

```bash
# приёмка на локальном бэкенде: объект версии и registry.jsonl в build/archive-dev/
make import STAT=cbr_m2 ARCHIVE_BACKEND=local ARCHIVE_LOCAL_DIR=build/archive-dev   # повторный прогон → no-op
# живой архив на Диске (токен берётся из окружения) и обновление git-зеркала реестра
make import STAT=cbr_m2 ARCHIVE_BACKEND=yandex ARCHIVE_YANDEX_DIR=disk:/rosstat-archive
make archive-registry ARCHIVE_BACKEND=yandex
# листинг версий и сверка хранилища с реестром (листинг умеет локальный бэкенд)
make archive-list ARCHIVE_BACKEND=local ARCHIVE_LOCAL_DIR=build/archive-dev
make archive-list ARCHIVE_BACKEND=local ARCHIVE_LOCAL_DIR=build/archive-dev ARCHIVE_RECONCILE=1
# восстановление ряда из архива — ручное действие, сети не касается (нужны CLICKHOUSE_URL и бэкенд)
make archive-restore STAT=rosstat_ipc_weeks_bulletins ARCHIVE_BACKEND=local ARCHIVE_LOCAL_DIR=build/archive-dev
```

**Восстановление из архива** (`make archive-restore STAT=<импортёр>`) — ручное действие, в расписании dagu его нет: штатный конвейер наполняет таблицы из источников, а restore нужен, когда источник потерял версию (живой буфер Росстата вычищен, Wayback троттлит) или ряд надо наполнить на пустой базе. Режим `ARCHIVE_ACTION=restore` процесс не завершает, а переключает обычный путь импортёров: байты версии берутся из архива по паре «источник + URL» (`archive.LoadEntries` → строка реестра, самая свежая по `first_seen` → объект хранилища), sha256 полученных байтов сверяется со строкой реестра, HEAD-префлайт и повторная архивация не выполняются — **сеть источника восстановлением не вызывается вовсе** (сам архив может быть сетевым: Яндекс.Диск), источник не спрашивается. Отпечаток для строки `source_publications` берётся из строки реестра; пустой (версия под sha-ключом — HEAD при архивации был недоступен) — строка не пишется, как и в обычном пути. Границы: `CrawFunc`-импортёры (файл качает сам импортёр и в архив не попадает) в режиме дают ошибку с явным текстом, а пустой `CLICKHOUSE_IMPORT_STAT` — тоже ошибка, чтобы «восстановить всё» случайным прогоном было нельзя. Повторный restore идемпотентен: таблицы на `ReplacingMergeTree` перезаписывают те же точки, производные публикуются тем же путём, что у обычного прогона.

**`make archive-list`** печатает версии реестра по хранилищу (`ARCHIVE_ACTION=list`, ClickHouse не нужен): строки с одинаковым `sha256` помечаются дублем содержимого (один файл под sha- и fingerprint-ключом — две записи об одном содержимом). Фильтр — `ARCHIVE_LIST_SOURCE=<источник>`. С `ARCHIVE_RECONCILE=1` бэкенд с листингом (`local`) сверяется с реестром: объекты без строк печатаются, и прогон завершается кодом 1 — реконсиляция не должна выглядеть чистым зеркалом при находках; для `yandex` (листинг — остаток шага 1.2) выводится сообщение «реконсиляция недоступна для бэкенда yandex».

Коды ошибок в логе: `401` (`ErrAuth`) — токен не принят (отозван, истёк или выдан без нужного scope): действие — перевыпустить токен по шагам выше. `403` (`ErrQuota`) — **двоякий**: так Диск отвечает и при нехватке прав у токена (не отданы оба scope, либо архив заведён на `disk:/`, а токен выдан приложению с доступом к `app:/`), и при исчерпанной квоте; к `ErrQuota` сводятся ещё `413` (файл больше лимита), `423` (ресурс занят) и `507` (нет места). Причину различает фрагмент ответа Диска в тексте ошибки (`; ответ Диска: …`): если в нём про права — перевыпускать токен с обоими scope и сверять путь (`disk:/` против `app:/`), если про место — освобождать. Поэтому прежде чем идти освобождать место, прочитайте фрагмент: у `403` без прав места может быть сколько угодно. Импорт данных при любой из этих ошибок не останавливается, но версия файла в архив не сохраняется и строка версии не пишется — следующий прогон повторит полный импорт.

### CI и релизы

`.github/workflows/go.yml` на каждый push в `main` и на pull request:

- `test`: `gofmt`, `go vet`, `go test -race`;
- `lint`: `golangci-lint` v2.14.0 с конфигом `.golangci.yml`. Пакет `financial/` исключён из линта как legacy;

- `build`: `make build`, артефакт `build/`.

Все задания используют Go `1.27.x`: `govulncheck` проверяет стандартную библиотеку тулчейном, которым запущен, и на go1.27.1 находил уязвимости `net/http` и `crypto/tls`, исправленные в go1.27.2.

`.github/workflows/dashboards.yml` (`dashboards`) на каждый push в `main` и на pull request проверяет все три дашборда контура (`gold-thesis`, `key-rate-publications`, `finance-polyus`) как код: `go vet` и `go test` модуля `grafana/`, `make grafana-build`, `git diff --exit-code -- dashboard/` (все три артефакта совпадают со свежей сборкой — заодно ловит недетерминированную генерацию; легаси-экспорты сборкой не трогаются), установка пинуемой `gcx` v1.5.0 и офлайновый `gcx dev lint run` одним прогоном по всем трём файлам артефактов (два idiomatic-предупреждения генератора — `editable`-дашборд и отсутствие описаний панелей — отключены по именам, иначе был бы exit 4), затем upload всех трёх артефактов. Секретов и деплоя в workflow нет: на стенд дашборды уезжают только вручную (`make grafana-deploy-test` / `make grafana-deploy-staging`), серверная `gcx resources validate` остаётся ручной проверкой (нужны сервер, org-id и креды).

`.github/workflows/release.yml` на тег `v*` запускает тесты и `goreleaser` (архив `linux/amd64`, `SHA256SUMS`, файлы `README.md` и `dagu/*.yaml`). Конфиг — `.goreleaser.yaml`; проверка: `goreleaser check`. В релиз входит только основной бинарник импорта; `cmd/ingest` собирается локально через `make build-ingest`.

## Ограничения и известные проблемы

- **У эндпоинтов bold.report обязателен суффикс `.json`.** Источник — статика на S3 за CloudFront: объекта без расширения там нет, и CDN отвечает `403 AccessDenied` (не `404`). На этом упала первая живая приёмка 2026-10-12: в девяти константах путей `bold/parse.go` суффикса не было, оба импортёра писали `0` строк. Дефект жил с первого коммита контура (`5b2341a`) и был невидим офлайн-тестам: `httptest` отвечает на любой путь. Исправлено коммитом `bold: require .json suffix on api paths`; суффикс закреплён тестом `TestBoldEndpointsPinPaths` — путь без `.json` валит тест. Приёмка после фикса пройдена (`make mcp-check` — ПРОВЕРКА ПРОЙДЕНА): 3138 точек цены, 21054 точки + 73 строки пер-фондового среза; подробности — [docs/GOLD_THESIS_DATA_ROADMAP.md](docs/GOLD_THESIS_DATA_ROADMAP.md) (фаза 3, follow-up 4).
- **LBMA AM/PM не подключён.** Официальный LBMA JSON, Nasdaq Data Link `LBMA/GOLD` и stooq недоступны из этой сети (403 WAF, JS-проверка), FRED серии LBMA удалил. Временно используется `gold` (MOEX GOLDFIXME ÷ курс ЦБ).
- **Курс ЦБ без понедельников и новогодних праздников.** В `cbr_currency_usd` этих дат нет; `gold` берёт последний курс не позже даты и пропускает дни без курса старше 10 дней. Это дыра в источнике ЦБ.
- **Импортёры ЦБ/Росстата берут ссылку со страницы источника.** `cbr_infl_exp`, `cbr_credit_m2x`, `rosstat_vvp_kvartal`, `rosstat_salaries_mes`, `rosstat_labour_force_mes` не хардкодят URL XLSX, а читают актуальную ссылку со страницы источника общими хелперами `util.GetPage` + `util.FindLink` (`util/links.go`, goquery; селектор — константа пакета), которыми пользуются `cbr/` и `rosstat/`. Остальные источники ЦБ используют стабильные пути `vfs/statistics/...`. У четырёх переведённых на точку контроля публикации росстатовских импортёров (`rosstat_ipc_mes`, `rosstat_salaries_mes`, `rosstat_vvp_kvartal`, `rosstat_labour_force_mes`) порядок изменён: ссылка ищется **до** вызова шаблона («страница → DDL → префлайт»), иначе префлайту неоткуда взять URL для HEAD; полный путь и результат совпадают, но при недоступной странице таблица уже не создаётся. **Как стало у ВТБ:** раньше в этом списке стоял и `rus_vtb_group_ifrs`, но его страница даёт **список** отчётных файлов по периодам, а `util.FindLink` ищет одну ссылку — поэтому теперь страницу разбирает свой парсер `vtbIfrsXlsLinks` (goquery; фильтр PDF, дедуп, сортировка по дате отчёта), а качает её общий `util.GetPage`. От `util` это не отказ — отличается только разбор листинга (третий пакет со своим разбором страницы после `cbr/` и `rosstat/`).
- **`sber_finansovie_rezultaty`, `tbank_group_ifrs` — ссылка задана статически (у ДОМ.РФ — больше нет).** **Как стало:** страница аналитики ДОМ.РФ отдаёт обычный серверный HTML (прежняя запись про JS-challenge ServicePipe разведкой не подтвердилась), и `domrf_mortgage` берёт ссылку на книгу из JSON блока «Топ ипотечных банков» каждый прогон — имя файла несёт отчётный месяц, поэтому статичного URL в коде нет (прежний литерал отдаёт 404). **Как было:** у `domrf_mortgage`, `sber_finansovie_rezultaty` и `tbank_group_ifrs` ссылка обновлялась вручную. Статическая ссылка осталась у двух: у `sber_finansovie_rezultaty` (страница закрыта JS-challenge TSPD; имя файла не меняется) и у `tbank_group_ifrs` (адрес CDN с UUID ведёт на **PDF**, а не XLSX, — импорт падает до вставки). **Развязка Т-Банка (как стало):** у `tbank_group_ifrs` теперь **своя таблица** `tbank_group_ifrs` и свои `%s`-DDL/константы — прежнее совладение общей `rus_vtb_group_ifrs` с ВТБ (`bank/tbank_fin_rez.go` писал чужими `vtbIfrsTableDdl`/`vtbIfrsDataInsert`, и префлайт со `count()` одного импортёра считали бы точки другого) убрано; таблица заводится пустой, а шаг импортёра **вне расписания** до починки источника (`dagu/bank.yaml`; условие возврата — живая XLSX-ссылка). Точка контроля публикации у Т-Банка не объявлена: контролировать нечего, пока ссылка ведёт не на разбираемый файл. У `sber_finansovie_rezultaty` точка контроля публикации объявлена: ссылка статична и меняется вручную — это ровно случай «файл обновляется реже прогонов»; транспорт при рефакторинге стал шаблонным (`DataUrl` + `ImportFunc`), поэтому версия файла попадает и в винтажный архив (было: `CrawFunc` — вне архива).
- **Источник SberIndex: старый путь API мёртв, а живая выгрузка — «deprecated».** Обе таблицы потребительских расходов Сбера (`sber_consumper_spending_index`, `sber_izmenenie_trat`) годами были пусты **не** из-за пустого источника: импортёры качали `sberindex.ru/proxy/services/node-services/v1/...`, а этот путь теперь отдаёт HTML-оболочку SPA (`200`, `content-type: text/html`, `<div id="root"/>`) — так сервер отвечает на любой неизвестный путь. `util.GetCSV` HTTP-статус не проверял и HTML от CSV не отличал, поэтому первый же разбор падал до вставки — «0 строк» на живых данных. Живые выгрузки найдены 2026-10-15 кнопкой «Скачать» → пунктом «…в .csv» дашбордов: `/api/dataset/deprecated/csv/ru/consumper-spending-index-sa.csv` (470 точек = 5 категорий × 94 мес., 2018-12-01 … 2026-09-01, индекс, 100 = декабрь 2018) и `/api/dataset/deprecated/csv/ru/ver-izmenenie-trat-po-kategoriyam.csv` (7 038 точек = 46 категорий × 153 ISO-недели, 2023-11-12 … 2026-10-11, % г/г); формат — UTF-8 **с BOM**, LF, `date;category;value`, скачиваются обычным GET без cookie, а `util.GetCSV` в этом же PR получил снятие UTF-8 BOM (выгрузки приходят с BOM в шапке). Риски источника: слово «deprecated» в адресе — путь может исчезнуть, поэтому разбор падает громко и с понятным текстом (не «0 строк»), резервный ZIP-экспорт месячного набора документирован в коде (требует распаковки), а «Расширенный CSV» недельного дашборда отвечает `{"error":"File not found"}` — «deprecated»-файл единственная машиночитаемая выгрузка набора; `HEAD` у источника закрыт (`403`), `Last-Modified` на GET равен времени запроса (`cache-control: no-store`) — отпечаток версии непостроим, поэтому точка контроля публикации у обоих импортёров **не объявлена** (это не относится к `sber_finansovie_rezultaty` — у него объявление есть) и CSV качается на каждом прогоне; API данных SberIndex (`/api/dataset/v1/meta/...`, `/api/i18n`) закрыт TSPD (`403` и в curl, и при браузерной навигации) — данные дашборда доступны только этой выгрузкой, а её закрытие WAF-ом означало бы смену источника, что решает владелец (вне объёма правки). Обход и данные: ряды видны агенту через `v_bank_sber_spending` (7 508 строк, каталог 5 + 46 рядов), имена категорий с пробелами на конце (`Все категории `) нормализуются `strings.TrimSpace`, чтобы опечатка источника не заводила отдельный ряд.
- **Раскрытие банковских результатов: помесячный быстрый набор — только Сбер и ВТБ.** Помесячно публично раскрываются только Сбер (РСБУ) и ВТБ (МСФО); Т-Банк, Совкомбанк и МКБ — поквартально/по полугодиям. Машиночитаемый IR-календарь есть только у ВТБ; в этом PR даты обоих банков заводятся ручным сидом `sql/events_calendar_bank_results_q4_2026.sql`, автопарсер — отдельный пункт. Помесячный пресс-релиз Сбера по РСБУ ещё не импортируется: в витрине SBER `customer_loans` до 2026-06, сплиты — до 2026-09 (сид `sql/sber_ras_monthly_seed_2026_09.sql`); VTBR до 2026-08. Импортёр формы 101 ЦБ (RAR → DBF, остатки по счетам) заведён (issue #95): его pilot-1 маппинг пишет сплиты SBER `ras` за июль/август 2026 (июль — сид `sql/sber_ras_form101_mapped_2026_07.sql`, август — сам импортёр), поэтому `customer_loans` остаётся нетто-рядом пресс-релиза, а кредиты ЮЛ/ФЛ идут отдельными `ras`-рядами.
- **Росстат может отдавать HTTP 426.** Домен `rosstat.gov.ru` периодически отклоняет запросы из-за технических работ (`Upgrade Required`), включая уже работавшие `rosstat_ipc_mes`/`rosstat_ipc_weeks`; это ограничение источника/сети, а не кода. Импортёры падают с диагностикой «не найдена ссылка на …».
- **`financial/`.** Legacy-контур (database/sql, свой main). Новые импортёры туда не добавляются; отчётность Полюса вынесена в `polyus/`, в `financial/` остался `databook_ugk` (ЮГК) и мёртвый код металлургов.
- **Поактивный AISC Полюса применяется вручную, а не по расписанию.** Уточнённый сид `sql/dcf_mine_plans_seed.sql` (`make dcf-aisc`) намеренно **не входит в `dagu/dcf.yaml`**: запланированный шаг `make ch-sql` на staging не заработал бы — в релиз попадают только `README.md` и `dagu/*.yaml` (`.goreleaser.yaml`), а `make`, Makefile и сам SQL-файл на хосте отсутствуют. Хуже то, что провал был бы **бесшумным**: `dcf_mine_plans` в той же цепочке пересеял бы ключи из Go-снимка, и `dcf_engine` посчитал бы на старом плоском клине «TCC + $698» с зелёным логом. Поэтому цепочка в `dagu/dcf.yaml` остаётся двухшаговой (`dcf_mine_plans` → `dcf_engine`), а сид AISC применяется человеком: `make ch-sql FILE=sql/dcf_mine_plans_seed.sql` до `DCF_RUN_ID=<uuid> make import STAT=dcf_engine`. Автоматизация (доставка SQL как релизного артефакта + способ его применить) — отдельный пункт роадмапа, вне текущего объёма.
- **Сторож устаревания сида и Python-тесты не покрыты CI.** `TestCommittedSeedIsFresh` (`scripts/extrapolation_aisc_test.py`) сверяет тело коммитируемого `sql/dcf_mine_plans_seed.sql` с тем, что порождает генератор, но для точного воспроизведения ему нужна живая ClickHouse (факт добычи приходит из `databook_polyus`); при недоступной БД тест **пропускается** с явной причиной. Сам Python-набор не запускается в CI: `.github/workflows/go.yml` выполняет только Go-проверки (`gofmt`, `go vet`, `go test -race`, `golangci-lint`, сборку), поэтому правленый вручную сид ловится только локальным прогоном `python3 scripts/extrapolation_aisc_test.py`. Связка Python-тестов с CI — отдельный пункт: под тот же пробел попадает и офлайн-набор модели ключевой ставки (`scripts/key_rate_model_test.py`, команда — в «Разработке»), поэтому его прогон — ручной шаг приёмки.
- **AISC Полюса за 2025+ остаётся выведенной величиной.** Per-asset AISC и TCC публикуются только в пресс-релизах 4Q/FY **2018–2021**; начиная с 2022 отчётность перешла на полугодовой формат и даёт поактивный TCC, но AISC — только групповой. Поэтому калибровка клина-доли опирается на 2019–2021, а годы плана 2025–LOM **экстраполируются** с них: сид улучшает структуру затрат (взвешенную по активам вместо единого клина) и переносит в модель наблюдённые веса, но не создаёт поздних измерений. Ровно поэтому `aisc` в каталоге рядов и в [docs/DCF_DATA_COVERAGE.md](docs/DCF_DATA_COVERAGE.md) §2 остаётся `derived`, а увязка к групповому AISC «точна» только на групповом уровне (по построению, независимо от качества входов).
- **Отчётность Полюса: `unitsMarker` привязан к строке, а не к смыслу.** `polyus/columns.go` распознаёт шапку финансовой таблицы только по склеенным меткам `$млн`, `$mln`, `$million`. Отчёт, печатающий `US$ million`, оставит набор колонок пустым, и парсер вернёт **0 записей с `err == nil`** — молчаливо пустую страницу, не отличимую от «в отчёте нет метрик». (Форма `US$ million` — находка контролёра по другим релизам; у включённых релизов 2019–2024 фикстуры несут `$ million`, и оно совпадает, поэтому расширение маркера этой работой не потребовалось.) Это самое важное ограничение парсера Полюса; подробности и остальные — в [ARCHITECTURE.md](ARCHITECTURE.md) §6.6.
- **Отчётность Полюса: остальные ограничения колоночной модели.** `parsePeriod` не принимает форму `FY 2014` (год с пробелом); на МСФО-страницах допущение «первое число = отчётный период» выполняется на обеих текущих страницах, но во время прогона не проверяется, и отчёт со сравнительным столбцом первым молча поменяет периоды местами; счётчик значений вне периодных колонок (178 на приёмке релизов 2019–2024) подтверждён только живым прогоном — сквозного теста на итоговую строку нет; `pageOfLine` возвращает первую ненулевую страницу слова (корректно, т.к. строка всегда принадлежит одной странице, но тест-инварианта нет); словарь `metrics.go` содержит метку `"Earnings per share – basic (US\nDollar)"` со встроенным переводом строки, который не совпадает со склеенным текстом, — на фикстуре FY2024 записей `eps_*` нет. Перечень — ARCHITECTURE.md §6.6.
- **Отчётность Полюса: полоса шапки по ролям строк может расти вниз, а подъём вверх ограничен 8pt.** Вниз полоса продолжается, пока строки играют роль строк шапки, а роль «подпись изменения» опознаётся по словарю меток (`Y-o-Y`, `H-o-H`, `Q-o-Q`, `change`): строка с такой подписью в области данных попадёт в полосу, и её метрики не прочитаются — ни записей, ни нераспределённых значений, тот же тихий ноль, что и у ограничения с `unitsMarker`. Вверх полоса поднимается на строку кварталов («4Q 3Q 4Q» над якорем), но только если разрыв не больше `maxFragmentLiftGap = 8pt` (`polyus/columns.go`): настоящий обрывок дальше 8pt не поднимется, и «4Q 2020» с «3Q 2020» молча схлопнутся в два годовых `2020FY` — значения останутся на месте, сменится только ключ периода, и счётчик нераспределённых этого не покажет. Ловит это `TestKPIPeriodsAreUniquePerMetric`: дубликат ключа внутри страницы валит тест громко. На девяти включённых отчётах оба порога недостижимы (замерено: полосы обрываются на строке данных, настоящие подъёмы — ровно 5.40pt), но 2015–2018, включаемые следующим пунктом, несут подписи изменений в области данных. Остальные ограничения того же списка — отбор строки метрики по первому `Top` и прочее — в ARCHITECTURE.md §6.6.
- **Отчётность Полюса: 5 отчётов 2015–2018 и 2025H2 отключены.** Включены 9 отчётов (2014FY EN KPI, 2019FY…2024FY EN 4Q/FY, RU 1H2026, EN МСФО 1H2026). Причина отключения оставшихся — не выверка страниц, а тип документа: 2015–2017 — MD&A с консолидированной отчётностью, 2018FY — консолидированная МСФО-форма (у них нет шапки «Comparative financial results»), 2025H2 — англоязычный 2H25-релиз с двухшапочной таблицей. Включение 2015–2018 — следующий пункт работ. Снятые ограничения (потеря документа на ключе без измерения источника, недоступность данных агенту) — ниже.
- **Отчётность Полюса: ключ таблицы больше не теряет документ — дефект закрыт 2026-10-10.** Прежний ключ `(company, metric, period)` (таблица `polyus_financial_metrics`) не содержал измерения источника, поэтому два отчёта, печатающие один показатель за один период, конкурировали за одну строку. Модель, которой размечен документ, видна в колонке `model`, версия промпта — в `prompt_version` (обе входят в ключ таблицы, поэтому смена модели или промпта не затирает старую разметку).

- **Винтажный архив версий файлов источников — опция, и покрытие у него неполное.** При `ARCHIVE_BACKEND=local|yandex` шаблон `util.ClickHouseImport` сохраняет версию файла (объект в хранилище + строка в `registry.jsonl`) — но только у импортёров с объявленной точкой контроля публикации и файловым путём шаблона (`ImportFunc` — XLSX, либо `BodyFunc` — HTML-бюллетени): теперь таких 23 — пятнадцать в `cbr/`, пять в `rosstat/` (пятый — `rosstat_ipc_weeks_bulletins`: байты HTML качает и архивирует шаблон, как у XLSX-импортёров) и три в `bank/` (`sber_finansovie_rezultaty` и `domrf_mortgage` — HEAD-префлайт; `rus_vtb_group_ifrs` — пофайлово: гейт пофайловых версий, объявление ради архива и строк `source_publications`, ARCHITECTURE.md §8 п. 13). **Не архивируются:** `CrawFunc`-импортёры, качающие файл внутри себя (пример — `customs/vneshn_torg_countries.go`; импортёров с объявленной точкой контроля среди них больше нет — `bank/sber_fin_rez.go` переведён на `DataUrl` + `ImportFunc` и архивируется), остальные пакеты, `cbr_form101` (свой `Import()` читает RAR → DBF и шаблон не зовёт), PDF (в т.ч. отчёты Полюса), HTML-страницы и XML/JSON-фиды. **Первый прогон после включения архива — полный ре-импорт** всех 23 покрытых артефактов: текущие версии уже импортированы, но в архиве их ещё нет, поэтому no-op не наступает; дальше повторный прогон снова no-op. Исключение — выпуски `cbr_dip_bulletin`, `cbr_mt_forecast` и недели `rosstat_ipc_weeks_bulletins`: их повторный прогон шаблон не зовёт вовсе (дельту держит гейт по `release_id`, `release_date` и по датам соответственно), поэтому архив прошлых выпусков при включении архива задним числом не наполняется — архивируются только выпуски, импортированные при включённом архиве, и недолеченный выпуск сам не восстановится (причина — тот же гейт): сбой архива или строки версии на выпуске, как и включение архива после первого прогона, требует ручного вмешательства — удалить строки выпуска (недели) из таблицы и повторить прогон; правка файла выпуска под тем же `id`/`release_date` (или `publication_date` под тем же `id`) подхватится так же только вручную. Сбой архива прогон не роняет — версия не сохраняется и строка версии в `source_publications` не пишется, поэтому следующий прогон повторяет полный импорт (данные при недоступном Диске не теряются) — у всех покрытых артефактов, кроме выпусков `cbr_dip_bulletin`, `cbr_mt_forecast` и недель `rosstat_ipc_weeks_bulletins` (см. выше). Самолечение срабатывает по потере **объекта**; потерянная строка реестра при живом объекте сама не возвращается (no-op-путь до записи реестра не доходит) — для локального бэкенда её показывает реконсиляция `make archive-list ARCHIVE_RECONCILE=1` (шаг 1.2). Восстановление и наполнение БД из архива — срез шага 1.2 (`docs/ROADMAP_INFRA.md`): вход восстановления `make archive-restore STAT=<импортёр>` (байты из архива, без сети, без префлайта и повторной архивации; `CrawFunc`-импортёры вне границы) и листинг `make archive-list`; остаток пункта — `archive-get` (получение отдельной версии в файл) и листинг Яндекс.Диска. Сам механизм — ARCHITECTURE.md §2–§3, §8 п. 13 и стандарт пакета §9.6.
- **Платёжный баланс: заведены только верхние агрегаты, и единицы двух выгрузок разные.** Импортёры `cbr_bop_est` (оценка ЦБ, 51 ряд) и `cbr_bop_standard` (стандартная презентация, 34 ряда) покрывают 17 агрегатов внешнего сектора; 391 подстатья стандартной презентации (услуги по видам, финансовый счёт по секторам и инструментам) — вне объёма пункта (спека [2026-10-15-cbr-bop-design.md](docs/superpowers/specs/2026-10-15-cbr-bop-design.md) §6), как и соседние выгрузки ЦБ `bal_of_payments_standart_before_2022.xlsx` (методология до 2022) и `bal_of_payments_ap.xlsx` (аналитическое представление). Единицы: у оценки — млрд долларов США, у стандартной презентации — млн (в 1000 раз мельче), поэтому ряды двух выгрузок нельзя складывать и сравнивать без пересчёта; в витрине `v_cbr_bop` их различает `source` (имя таблицы), а единица, знак и привязка даты названы в `v_series_catalog` по `(source, series)`. **Ноль — настоящее значение** (сальдо нулевое), а не пропуск данных; пустая ячейка источника точкой не становится. ЦБ меняет в выпусках и подписи строк, и число колонок (выпуск 15.10.2026 переименовал половину агрегатов оценки: `Товары` вместо `Торгового баланса`, `Услуги` вместо `Баланса услуг`, `К получению` вместо `Доходов к получению`, `Резервные активы` вместо `Изменения резервных активов`, и оставил 10 колонок вместо 14), поэтому разбор принимает оба набора подписей по позиции строки, а имя ряда (`Товары`, `Услуги`, `Доходы к получению`, …) от выпуска не зависит и совпадает с именем того же агрегата в стандартной презентации; оба винтажа закоммичены фикстурами (`cbr/testdata/bop_est.xlsx` — 15.10.2026, 170 точек, `cbr/testdata/bop_est_prev.xlsx` — 14.09.2026, 238 точек). Файлы ЦБ обновляются раз в месяц (`bop_est.xlsx`) и раз в квартал (`bal_of_payments_standart.xlsx`), поэтому будничный прогон — HEAD-префлайт и no-op без скачивания, а новые данные появляются с задержкой темпа источника; значения оценки ЦБ ревизует следующим выпуском (ключ `(name, date)` перезаписывает точку — историю ревизий хранит только винтажный архив файлов).
- **У модели ключевой ставки v0 — локальные артефакты, консервативный as-of слой и прогноз «в стол».** Скрипт `scripts/key_rate_model.py` (цель `make key-rate-model`) считает выборку решений (108 заседаний, 2014-02-14 … 2026-09-11), бенчмарки B1–B3, методы №2–3 и walk-forward (84/68 фолдов), но **в ClickHouse не пишет**: отчёт, CSV прогнозов и JSON текущего прогноза лежат в корне репозитория и в git не коммитятся (`.gitignore`). Признаки берутся as-of **консервативными лагами публикации**, а не point-in-time слоем: ревизии объясняющих рядов и точные даты публикаций здесь не учтены (спека [2026-10-15-key-rate-model-v0-design.md](docs/superpowers/specs/2026-10-15-key-rate-model-v0-design.md) §4). **Качество модели бенчмарки не подтверждают:** на скользящем окне 40 правило Тейлора существенно хуже наивных бенчмарков (RMSE 464.57 б.п. против 164.38 у B1) — известный эффект линейной экстраполяции, числа и диагностика — в отчёте прогона; «сделан» у этого пункта значит «измерение готово». Запись прогноза в `forecast_log` (вместе с правкой ошибки в базисных пунктах и резолвером `cbr_rate`) и публикации — отдельные подпункты фазы 4 [docs/ROADMAP_KEY_RATE.md](docs/ROADMAP_KEY_RATE.md) §6.
- **У ML-трека (nowcast ИПЦ) — локальные артефакты, консервативный as-of, частичное окно недель и пока не подтверждённый выигрыш над elastic net.** Скрипт `scripts/cpi_nowcast.py` (цель `make cpi-nowcast`; спека [2026-10-16-cpi-nowcast-design.md](docs/superpowers/specs/2026-10-16-cpi-nowcast-design.md), план [2026-10-16-cpi-nowcast.md](docs/superpowers/plans/2026-10-16-cpi-nowcast.md)) считает nowcast месячного ИПЦ по недельным данным Росстата (выборка 57 месяцев 2022-01…2026-09, пропусков нет; CatBoost direct/bottom-up + бенчмарки B1–B3), но **в ClickHouse не пишет**: отчёт, CSV прогнозов и JSON текущего прогноза лежат в корне репозитория и в git не коммитятся (`.gitignore`). Признаки берутся as-of **консервативными правилами публикации** (недельная точка — регистрация +2 дня, месячный ИПЦ — конец месяца M+1, FAO — первые дни месяца публикации), а не point-in-time слоем: ревизии и точные даты публикаций не учтены, PIT-слой — отдельный подпункт фазы 4. Данные СберИндекса не используются: условия `sberindex.ru` не подтверждены ([KEY_RATE_MODEL.md](docs/KEY_RATE_MODEL.md) §4, юридическая оговорка) — трек построен только на недельном ИПЦ Росстата, курсе USD, ключевой ставке, ОФЗ и FAO; включение Сбера — отдельный пункт после юридического выяснения. **Живой nowcast может работать на частичном окне недель** (на прогоне 2026-10-16 — 1 неделя из 4): режим генерации признаков отличается от бэктест-режима (там окно строго 4 недели, и бэктест не меняется), а `gasoline_4w` нормирован к 4-недельному масштабу (сырая сумма за N недель × 4/N — модели обучены на четырёхнедельной сумме). B3 (ElasticNetCV) сходится не на всех фолдах: на 10 из 33 фолдов старта 24 координатный спуск не сошёлся (`ConvergenceWarning`), число недосходов публикуется в отчёте, а недосход живого фита помечает прогноз B3 в `note` JSON и в отчёте как индикативный. **Вывод «в ансамбль?»:** значимый выигрыш есть только над naive B1 (DM p = 0.0112), а над elastic net (B3) выигрыш **не значим** (p ≈ 0.78) — по правилу §4 [KEY_RATE_MODEL.md](docs/KEY_RATE_MODEL.md) **ML-трек в ансамбль пока НЕ входит**; ансамбль методов — отдельный подпункт фазы 4 [docs/ROADMAP_KEY_RATE.md](docs/ROADMAP_KEY_RATE.md) §6.
- **Приложения ДИП: винтажные ряды ревизуются, а гейт не видит подмены файла выпуска.** `cbr_dip_bulletin` хранит значение таким, каким его опубликовал выпуск (ключ `(series, date, release_id)` + `publication_date`), и это не «последняя версия ряда», а точка во времени: **сезонно сглаженные ряды ДИП ревизуются между выпусками** (SA-безработица за 2023-11 равна 2.885274 в выпуске 24-01 и 2.916127 в 26-06) — ровно поэтому таблица винтажная. Следствия для чтения: «последнее значение» без `release`/`publication_date` не определено, а число строк витрины `v_cbr_dip_bulletin` умножается на число выпусков (один месяц лежит столько раз, сколько выпусков его напечатало) — это «сколько точек набрано», а не «сколько месяцев наблюдений». **Замена файла выпуска под тем же `id` гейтом не отслеживается** (ЦБ публикует каждый выпуск под новым id, но полагаться на это нельзя): лечение ручное — удалить строки выпуска и повторить прогон (гейт его не увидит и импортирует заново). Первый прогон долгий: 49 приложений ≈1,5 МБ, ЦБ отдаёт ~60 КБ/с — ≈4–6 мин и ≈72 МБ архива; повторный прогон — один `SELECT DISTINCT release_id` по таблице без скачиваний.
- **Среднесрочный прогноз ЦБ: история диапазонов машиночитаемо начинается с 07.05.2026, а гейт не видит подмены файла выпуска.** `cbr_mt_forecast` хранит прогноз таким, каким его зафиксировал выпуск (ключ `(indicator, year, release_date)`), и это не «последняя версия ряда», а точка во времени: **следующий выпуск ревизует диапазоны** (по паре `(indicator, year)` сравнение двух выпусков и показывает сдвиг прогноза). Следствия для чтения: без `release_date` «прогноз» не определён — это разные редакции; `lo = hi` значит точечный прогноз, «среднее по диапазону» источник не публикует; горизонт прогноза меняется от выпуска к выпуску (3–4 года), а факт-колонка источника не импортируется — факты живут в своих рядах (`cbr_key_rate`, `rosstat_*`). **Машиночитаемый xlsx есть только у 2 новейших выпусков** (07.05.2026 и 05.08.2026) — 9 выпусков 2024-02 … 2026-02 только PDF, и до их бэкфилла (отдельный пробел роадмапа; у всех 11 заседаний есть PDF «Среднесрочный прогноз» с той же «Табл. 1») глубина ряда ограничена источником. **Замена файла выпуска под тем же `release_date` гейтом не отслеживается** (идентичность выпуска — дата публикации из слага страницы, а не имя файла): лечение ручное — удалить строки выпуска и повторить прогон. Витрина `v_cbr_mt_forecast` — не long-форма: диапазон отдаётся парой колонок `lo`/`hi` (распад на две long-строки потерял бы смысл «это один диапазон»). Повторный прогон — один `SELECT DISTINCT release_date` по таблице без скачиваний.

### Дашборд как код

- Источник истины — `grafana/` (отдельный Go-модуль): дашборды `gold-thesis` (9 панелей id 1–9 в 5 рядах), `key-rate-publications` (19 панелей id 1–19 в 4 рядах, «Ключевая ставка — публикации») и `finance-polyus` (19 панелей id 1–19 в 4 рядах id 31–34, «Полюс (PLZL) — финансы и прогноз»); все запросы — только по витринам `v_*`, датасорс каждой панели — константа uid `ch-rosstat`. CLI — флаги `-dashboard <uid>|all` (дефолт `all`) и `-out-dir` (дефолт `../dashboard`): файл артефакта — `<out-dir>/<uid>.json`. Артефакты `dashboard/gold-thesis.json`, `dashboard/key-rate-publications.json` и `dashboard/finance-polyus.json` (k8s-ресурс `dashboard.grafana.app/v1beta1`, uid = `metadata.name`) руками не правятся: `make grafana-build` перезаписывает их детерминированно, а CI падает, если артефакт разошёлся с кодом.
- `make grafana-validate` — `go vet` + тесты модуля (состав панелей всех трёх дашбордов и негативные правила `Validate`). Серверный `gcx resources validate` намеренно не входит в цель: он проверяет ресурс на живом инстансе (server-side dry-run) и требует кредов — рабочая форма записана в комментарии цели.
- Локальный стенд: `make grafana-up` (brew-Grafana; данные, логи и плагины в `$(GF_DIR)`, провижининг датасорса — `grafana/provisioning/datasources/clickhouse.yaml`, порт 3000) и `make grafana-down`. При первом входе в UI смените пароль `admin/admin`.

### Переменные окружения стендов

| Переменная | Назначение |
|---|---|
| `GRAFANA_TEST_URL` | адрес тест-стенда, по умолчанию `http://localhost:3000` |
| `GRAFANA_TEST_TOKEN` | токен сервис-аккаунта **Editor** на тест-стенде: `make grafana-deploy-test`, `make grafana-check` (в `gcx` уходит как `GRAFANA_TOKEN` — make-цели подставляют его сами; при ручных вызовах `gcx` подставляйте явно, см. «Цикл разработки и деплой») |
| `GRAFANA_STAGING_URL` | адрес staging, по умолчанию `http://localhost:3001` — **только через ssh-туннель** |
| `GRAFANA_STAGING_TOKEN` | токен сервис-аккаунта **Editor** на staging: `make grafana-deploy-staging` |
| `GRAFANA_ORG_ID` | org-id инстанса для `gcx` (on-prem без него отвергается), по умолчанию `1` |

Значения — только в `~/.config/rosstat/env`; `make env-check` печатает «задан/не задан» без значений. Версии: `gcx` 1.5.0 (`brew install gcx`), локальный стенд — Grafana 13.2.3 + плагин `grafana-clickhouse-datasource` 4.3.2 (ставится `make grafana-up`), staging — Grafana 13.1.1.

### Одноразовая настройка (владелец)

1. `brew install gcx`.
2. Локальный стенд: `make grafana-up` → войти `admin/admin` (первый запуск) → **Administration → Users and access → Service accounts** → аккаунт с ролью **Editor** → **Add service account token** → значение в `~/.config/rosstat/env` как `GRAFANA_TEST_TOKEN`; то же одной командой — `make grafana-test-token` (создаёт аккаунт `dashboards-cd` роли Editor и печатает строку для env-файла).

### Цикл разработки и деплой


Push идемпотентен: повторный прогон обновляет тот же ресурс (`metadata.name=<uid>` — uid дашборда из списка `DASHBOARDS`), дубль не создаётся. Перед публикацией — серверная проверка ресурса на живом инстансе (шаг ручной, нужны креды; по файлу на дашборд — `dashboard/<uid>.json`):

```bash
set -a; . ~/.config/rosstat/env; set +a             # источник значений; ничего не печатает
# если в env-файле нет адреса/токена — подставьте их: GRAFANA_TEST_URL=http://localhost:3000, GRAFANA_TEST_TOKEN=<токен Editor>
GRAFANA_SERVER="$GRAFANA_TEST_URL" GRAFANA_TOKEN="$GRAFANA_TEST_TOKEN" GRAFANA_ORG_ID=1 \
  gcx resources validate dashboards --path dashboard/gold-thesis.json   # пример вывода: ✔ No errors found
```

**Ручные вызовы `gcx`.** `gcx` читает креды только из `GRAFANA_SERVER`/`GRAFANA_TOKEN`/`GRAFANA_ORG_ID`; переменную `GRAFANA_TEST_TOKEN` он не знает — make-цели подставляют её в `GRAFANA_TOKEN` сами. Запуская `gcx` руками, подставляйте `GRAFANA_TOKEN` явно (как в примере выше), иначе push падает с `401 Unauthorized: the server has asked for the client to provide credentials` — это не признак недействительного токена.

Staging — через туннель `:3001` (порт не конфликтует с локальным стендом `:3000`):

```bash
ssh -N -L 3001:127.0.0.1:3000 palmshell &
make grafana-deploy-staging             # провижининг датасорса → push дашборда → smoke
```

**Ловушка staging:** Grafana (проверено на 13.1.1) применяет `provisioning/datasources` **только при старте** — сразу после первого `make grafana-provision-staging` датасорса `ch-rosstat` в инстансе ещё нет, и smoke упадёт. Активировать без рестарта сервиса:

```bash
curl -u admin:<пароль> -X POST http://localhost:3001/api/admin/provisioning/datasources/reload
```

(либо один `systemctl restart grafana-server`). Цель Grafana не перезапускает и сама печатает эту команду; подробности — `deploy/staging/README.md`.
