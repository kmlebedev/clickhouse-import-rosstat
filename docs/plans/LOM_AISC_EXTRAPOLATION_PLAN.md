## 1. Постановка и место в конвейере

Сегодня AISC по активам выводится одним грубым допущением (`dcf/mine_plans_seed.go`):

```go
groupTCC2025USDPerOz  = 739.0     // Годовой обзор 2025, стр. 31
groupAISC2025USDPerOz = 1437.0    // там же
sustainingWedgeUSDPerOz = 1437.0 - 739.0 = 698.0   // ОДИН клин на все активы
aisc = seed.TCC + sustainingWedgeUSDPerOz          // и плоско на весь LOM
```

Один клин $698/унц применяется к рудникам с разной структурой затрат: Олимпиада (TCC 773) и Куранах (TCC 925) получают одинаковую надбавку, хотя у Куранаха выше и вскрышные работы, и удельный capex. Далее AISC заводится **плоско на все годы** LOM — плато последним фактом.

Задача скрипта — заменить единый клин на **взвешенную по активам структуру затрат**, откалиброванную на единственном годе с per-asset раскрытием, и увязанную с групповым AISC МСФО на каждом году плана.

### Конвейер

```
databook_polyus (CH)  ──факт добычи 2021–2025──┐
политика TCC (константы, Годовой обзор)  ───────┤
                                               ▼
                              scripts/extrapolation_aisc.py
                                              │
              калибровка r̄_i (2018–2021)      │  DML-батчи
              экстраполяция r̄_i по ИПЦ          ▼
              увязка к групповому AISC     sql/dcf_mine_plans_seed.sql ──► make ch-sql
                                              │                             │
                                        CSV-артефакт                        ▼
                                                               mine_plans (5 активов × LOM)
                                                                           │
                                                                   dcf_engine ──► nav_by_asset
```

**Ключевое разделение:** скрипт **не пишет в ClickHouse**. Он читает факт, считает и печатает SQL-сид. «Расчёт» (Python, детерминирован, тестируется offline) отделён от «вставки» (SQL + `make`), поэтому Python-скрипту не нужен пароль и он не нарушает read-only контур `kimi_reader` (AGENTS.md, правило 11в).

## 3. Архитектура скрипта `scripts/extrapolation_aisc.py`

### 3.1 Стиль и конвенции

По образцу `scripts/mcp_setup_user.py` и `scripts/make_datapack_bad_cell_fixture.py`:

- `ROOT = Path(__file__).resolve().parent.parent`, module-level константы;
- `def main() -> int` + `if __name__ == "__main__": sys.exit(main())`;
- без `argparse` и без `logging` (репозиторий обходится без них в скриптах);
- русская проза в сообщениях; **пароль не печатать** (хелпер `mask`, как в `mcp_setup_user.py`);
- конфигурация — только из env (`CLICKHOUSE_HOST`, `CLICKHOUSE_PORT`, `CLICKHOUSE_USER`, `CLICKHOUSE_PASSWORD`, `CLICKHOUSE_DATABASE`, `CH_HTTP_PORT`). Сам файл env скрипт **не читает**: его экспортирует Makefile (`-include $(ROSSTAT_ENV)` + `export`), поэтому запуск — только через `make`.
- парсинг ответа ClickHouse — стандартная библиотека (`json`), HTTP — `urllib.request` (как `mcp_setup_user.py`). Новых зависимостей не вводить: `scipy` из rev.1 **не нужен** (§3.4).

### 3.4 Увязка: точное решение вместо SLSQP

Модель — **клин как доля от TCC** (см. спеку §3.1): `aisc_i = tcc_i · (1 + r̄_i · m)`, где `r̄_i` — калиброванная доля `(AISC − TCC)/TCC`, а `m` — общая увязочная поправка. Целевое ограничение — групповой AISC взвешен по добыче:

```
Σ_i aisc_i · w_i = AISC_group,   w_i = production_i / Σ_j production_j
```

Решение имеет замкнутую форму:

```
m = 1 + (AISC_group − Σ_j tcc_j·(1+r̄_j)·w_j) / (Σ_j tcc_j·r̄_j·w_j)
aisc_i = tcc_i · (1 + r̄_i · m)
```

**Почему доля, а не `tcc + δ`.** Фиксированный долларовый клин размывается относительно растущих затрат; доля сохраняет структуру. Проверено на FY2021: `r` по активам 0.52 (Куранах) … 0.80 (Вернинское) — единый клин $698 давал бы отношение 1.81 для Олимпиады против 1.23 для Куранаха, то есть искажал бы структуру, а не просто оценивал её неточно.

**Поправка `m` применяется к клину, а не к AISC целиком:** `tcc_i` — наблюдённая величина, её не трогаем; `r̄_i` — оценка, её и корректируем.

Свойства, из-за которых это лучше SLSQP:

- **Детерминировано** — нет `x0`, нет сходимости, нет локальных минимумов. Один и тот же вход даёт один и тот же выход всегда.
- **Точно увязывает** — невязка равна нулю по построению (до округления при записи), а не «< 1 % после оптимизации».
- **Объяснимо** — это одна скалярная поправка, которую можно назвать в отчёте («клин завышен на 3,4 %, групповой AISC выше расчётного»), в отличие от скрытых штрафов.
- **Не оставляет степеней свободы** — общая поправка `m` не перекладывает затраты между активами, а сдвигает всю структуру к групповому факту, сохраняя откалиброванные веса. Именно сохранение весов и есть смысл калибровки на 2018–2021.

**Вырожденный случай:** `Σ_j tcc_j·r̄_j·w_j → 0` (все клины нулевые) — вернуть `m = 1` с предупреждением, не делить на ноль.

**Оговорка о честности метода:** «точно увязано» здесь означает «точно увязано **на групповом уровне**» — по построению, независимо от качества входов. Это не «AISC по активам верен»: per-asset AISC остаётся **derived** (за 2025+ он не публикуется вообще), а сама увязка опирается на константы `ESCALATION` и на допущение о переносе доли клина с 2018–2021 на поздние годы. См. §3.6.

Опциональный режим сравнения с SLSQP (`--optimizer`) в первую итерацию **не входит**: он вносит недетерминизм без пользы, пока нет эталона для сравнения.

### 3.5 Калибровка vs план (разделение годов)

| Период | Роль | Проверка |
|---|---|---|
| **2018–2021** | Калибровка: ряд лет с публикуемым per-asset AISC (база долей `r̄_i`). | AISC каждого года в 400–1400 USD/oz; `r̄_i` в 0.3–1.0; **перекрёстная сверка** перекрывающихся лет (см. ниже). |

#### Источник per-asset AISC: пресс-релизы 4Q/FY Polyus

Ключевой вход (закрывает открытый вопрос №1): **per-asset AISC и TCC публикуются**, в отличие от утверждения rev.1 «AISC по активам не публикуется». Источник — пресс-релизы «Financial Results for 4Q and FY» в архиве [Results and reports](https://polyus.com/en/investors/results-and-reports/) по годам. В каждом релизе две таблицы — `TCC performance by mine, $/oz` и `All-in sustaining costs by mine, $/oz` — плюс прозаические абзацы с теми же числами за полный год.

| Год релиза | Документ | Перекрытие лет | Сверка |
|---|---|---|---|
| FY2018 | `2019_02_11_press_release_4q_fy2018_final-_1_.pdf` | 2018, 2017 | 2017 — график, сверка неполная |
| FY2019 | `press_release_4q-fy2019_final-_1_.pdf` | 2019, **2018** | проверяемо |
| FY2020 | `press_release_4q_fy2020.pdf` | 2020, **2019** | проверяемо (сверено, см. ниже) |
| FY2021 | [Financial Results for 4Q/FY 2021](https://polyus.com/en/media/press-releases/financial-results-for-the-fourth-quarter-and-full-year-2021/) | 2021, **2020** | проверяемо |

Пути — от корня `https://polyus.com`; прямые URL старых пресс-релизов теперь редиректят на список 2026 года, поэтому ссылаться надо на PDF из архива. **FY2017 годится только как справка:** в нём поактивные значения — в графиках, а не в таблице, и `pdftotext -layout` их не разбирает. Поэтому перекрёстно сверяемых лет три (2018, 2019, 2020), а не четыре, и ранняя граница ряда — **2018**.

#### Значения берутся из прозы, а не из таблицы-графика

Таблицы в этих релизах свёрстаны как **диаграммы**: подписи серий (`3Q 2020`, `4Q 2020`) стоят рядом с числами из соседнего графика, и `pdftotext -layout` их перемешивает. Прозаические абзацы дают те же числа однозначно и разбираются регулярным выражением:

> «In **2021**, AISC at **Olimpiada** increased to **$618** per ounce, …»

Правило для скрипта: **значение читается из прозы**; таблица-график используется только как перекрёстная сверка. Прозаический шаблон — `In (\d{4}), AISC at (\w+) (?:increased|decreased|remained\D{0,40}?)to \$([\d,]+) per ounce` плюс отдельные варианты для «remained almost flat at $N» (Kuranakh 2019) и «АISC at Alluvial increased to $1 277» (Alluvials, единственное число, без запятой).

#### Перекрёстная сверка перекрывающихся лет (обязательный guard)

Каждый год присутствует в **двух** релизах: как отчётный в одном и как сравнительный в следующем. Совпадение до доллара — проверка того, что ряд склеен верно. Сверено вручную на 2019 (из отчёта FY2019 против колонки 2019 в отчёте FY2020):

| Актив | FY2019 | FY2020 (колонка 2019) |
|---|---|---|
| Olimpiada | 455 | 455 |
| Blagodatnoye | 566 | 566 |
| Natalka | 605 | 605 |
| Verninskoye | 636 | 636 |
| Kuranakh | 777 | 777 |

Этот тест обязателен в скрипте: расхождение перекрёстного года — **ошибка**, а не предупреждение. Он ловит главный риск калибровки — опечатку при ручном переносе чисел из PDF.

#### Форма калибровки: тренд, а не одна точка

`r̄_i` оценивается по ряду 2018–2021, а не по единственному году: для каждого актива берётся средняя доля `(AISC − TCC)/TCC` за доступные годы, и только она экстраполируется на LOM. Это снимает риск «ошибка одиночного года размножится на весь LOM»: разброс доли по годам становится видимым (в скрипте — печатается как min/max по активу), а не скрытым в одной константе.

**Alluvials присутствует в таблицах TCC/AISC по всем годам** (2021: TCC $950, AISC $1 277) — поактивные затраты россыпи публикуются, в отличие от её добычи, которая уехала в отдельную таблицу датапака. Это дополнительный аргумент по пробелу №8, но сам актив в этот пункт не входит (§1 «Границы»).

### 3.6 Допущения (названы явно)

1. **Эскалация TCC — константы, а не `ipc_mes`.** Движок эскалирует AISC только если `Params.Ipc` непуст, а он пуст (`dcf/params.go`) — то есть ИПЦ в модель не входит вообще (пробел из `DCF_DATA_COVERAGE.md` §1). Скрипт считает эскалацию **сам**, по константам года; когда `ipc_mes` будет подключён к движку, источник констант заменяется чтением из БД, а формула — остаётся.
2. **Всё поддержание идёт в `capex_sustaining`; `SUSTAINING_SHARE` не вводится.** Прежняя редакция плана предлагала делить дельту на capex и SG&A по доле-допущению. Публичного разбиения «поддержание / SG&A» по активам нет, а доля клина `r̄_i` калибруется по факту — вводить допущение поверх калиброванной величины незачем. Единая доля `r̄_i` покрывает всю дельту `AISC − TCC`.
3. **USD/RUB** считаются только для справочной рублёвой колонки в CSV; в `mine_plans` не идут и на NPV не влияют.
4. **Per-asset AISC для 2025+ остаётся derived.** Измерение есть только за 2018–2021; поздние годы экстраполируются с них, поэтому в `mine_plans` значение по-прежнему производное. Сид улучшает *структуру* затрат (взвешенную вместо единого клина) и переносит в модель реальные наблюдённые веса, но не создаёт поздних измерений. В `docs/DCF_DATA_COVERAGE.md` статус `aisc` остаётся `derived` — меняется качество вывода и его опора на факт.
