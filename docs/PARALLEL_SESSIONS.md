# Параллельные сессии: регламент работы над репозиторием

**Дата:** 2026-10-14
**Спека:** [docs/superpowers/specs/2026-10-14-parallel-sessions-design.md](superpowers/specs/2026-10-14-parallel-sessions-design.md)
**План:** [docs/superpowers/plans/2026-10-14-parallel-sessions.md](superpowers/plans/2026-10-14-parallel-sessions.md)
**Для ассистента:** обязательные правила — [AGENTS.md](../AGENTS.md), раздел «Параллельные сессии».

Над репозиторием одновременно работают несколько сессий Kimi Code (Desktop и CLI) при одном инстансе GoLand. Документ описывает, как развести сессии по рабочим деревьям, как брать общие ресурсы по очереди и какие гарантии за это отвечают: `scripts/worktree.sh`, `scripts/lock.sh`, `.githooks/pre-commit`, `scripts/agent-guard.sh`.

## Зачем

Общее у параллельных сессий — больше, чем ветка. Шесть классов конфликтов, каждый с реальной ценой:

1. **Рабочее дерево, `HEAD`, индекс и `build/`.** В одном дереве `git checkout` одной сессии уводит контекст у другой, а `make all` падает на файле, который вторая сессия ещё дописывает; собранный бинарник в `build/` тоже один на всех.
2. **DDL внутри импорта.** DDL исполняется в общем цикле `Import()` — `util/clickhouse_import.go` (шаг `CreateTable` в `Import()`, сейчас строки 108–113), а витрины пересоздаются в `util/views.go:23-50` (`CreateView`: `CREATE OR REPLACE VIEW` плюс `ALTER TABLE … MODIFY COMMENT`). Импорты двух сессий по одной витрине пересекаются в одном ClickHouse, и это не ловится ни git-ом, ни сборкой.
3. **Гашение стенда.** `make ch-down` / `make grafana-down` (`Makefile:133-144` — рецепт `ch-down`) убивают сервер, на котором в этот момент считает соседняя сессия.
4. **Параллельный staging-деплой.** `make deploy-staging*` ходит по ssh на один хост (`STAGING_HOST`, по умолчанию `palmshell`), перезапускает systemd-сервисы и использует фиксированные `/tmp`-имена: два деплоя одновременно ломают staging.
5. **IDE: дерева нет в индексе — и выдача общая по всем открытым проектам.** `projectPath` в JetBrains MCP **не выбирает проект и не фильтрует выдачу**. Замер 2026-10-15, **до attach** (в GoLand одно окно, проект — корневое дерево, `.worktrees/parallel-sessions` проектом не открыто): `git_status` с `projectPath` своего дерева вернул ветку и dirty-файл **чужого, корневого** дерева (`source-file-archive`, `deploy/staging/dagu.service`), а `search_text` по фразе, уникальной для дерева («Параллельные сессии: регламент»), — `items: []`: файлов дерева в индексе нет **вовсе**, и все ответы проектно-зависимых вызовов принадлежат чужому дереву — без ошибки и без предупреждения. Замер **после attach** (владелец приаттачил папку; в дереве появились `.idea/modules.xml`, `parallel-sessions.iml`, `workspace.xml`): `git_status` дал **один и тот же** ответ при `projectPath` = корень и = дерево — два репозитория сразу (корень `source-file-archive` с `M deploy/staging/dagu.service` и `.worktrees/parallel-sessions` на `chore/parallel-sessions`, clean); `search_text` находит файлы дерева, но в **общей** выдаче и с префиксом `.worktrees/parallel-sessions/…`; `get_project_modules` → оба модуля; `get_run_configurations` → 15 конфигураций (объединение двух проектов). То есть attach необходим — без него дерева в индексе нет вовсе, — но недостаточен: свои результаты сессия отбирает сама по пути.
6. **Общий `.superpowers/sdd/<тема>/`.** Повторный прогон одной темы двумя сессиями перетирает брифы и `progress.md`: у артефактов SDD нет ключа дедупликации.

## Схема

**Дерево и ветка.** Одна сессия = одно рабочее дерево = одна ветка = один пункт роадмапа.

- дерево — `.worktrees/<slug>` (каталог в `.gitignore`, вне индекса репозитория);
- ветка — `<type>/<slug>`, создаётся от `BASE` (по умолчанию `main`);
- `git worktree` держит у каждого дерева свои `HEAD`, индекс и `build/` и не даёт двум деревьям встать на одну ветку — попытка получает `fatal: '<ветка>' is already checked out at '<путь>'`.

**Локи.** Общие ресурсы сериализуются хелпером `scripts/lock.sh <key> -- <команда>` (атомарный `mkdir`). Каталог локов — **вне репозитория**: `$HOME/.rosstat-locks` (переопределяется `ROSSTAT_LOCK_DIR`). Внутри репозитория лок был бы свой у каждого дерева, и защита исчезла бы. Внутри лока лежит файл `owner` с полями `tool`, `session`, `pid`, `host`, `since`, `cwd` — по нему видно, кто держит.

**IDE и агент.** Один инстанс GoLand обслуживает все деревья, а `projectPath` в вызовах JetBrains MCP — это **не фильтр по диску и не выбор проекта**: читающие инструменты возвращают **объединение по всем проектам, открытым в окне IDE**, а пути дают **относительно основного проекта**. Поэтому:

- дерево **обязательно** открывается (приаттачивается) в GoLand **отдельным проектом** — точное действие: `File → Open…` → путь `.worktrees/<slug>` (на запрос IDE — открыть в текущем окне как отдельный проект), а в Kimi Desktop — **отдельным workspace**; сессии Kimi хранятся по ключу рабочего каталога, разные деревья = разные наборы сессий;
- без этого шага дерева в индексе IDE нет **вовсе**: проектно-зависимые вызовы (`git_status`, `get_run_configurations`, `get_project_modules`, поиск по тексту и символам, проблемы файлов) молча отвечают про то дерево, что открыто в окне, — сессия в ворктри видит чужую ветку и чужой `git status`, а её собственные файлы в выдаче не появляются (замеры — класс конфликтов 5 выше);
- после attach `projectPath` выдачу **не сужает**: тот же `git_status` отдаёт оба репозитория сразу (корневой и свой), поиск находит файлы дерева, но в общей выдаче, `get_project_modules` возвращает оба модуля, `get_run_configurations` — объединение конфигураций обоих проектов. Поэтому `projectPath` передаётся в каждом вызове (признак, какой проект сессия считает своим), но свои результаты отбираются самому: в поиске, символах и конфигурациях — по префиксу пути `.worktrees/<slug>/…`, в `git_status` — по записи `repositoryPathRelativeToProject` своего дерева. Для инструментов, действующих на «текущий» проект (`execute_run_configuration`, `rename_refactoring`), поведение `projectPath` при двух открытых проектах **не проверялось**;
- исключение — чтение по абсолютному пути: `read_file` и `list_directory_tree` (например, `list_directory_tree --directoryPath <путь дерева>`) читают файлы дерева и **без** открытия проекта: каталог лежит в `.gitignore`, но файлы по явному пути доступны;
- две сессии в одном workspace запрещены: у них общий рабочий каталог, то есть ровно конфликты 1 и 5.

## Ресурс → общий? → чем закрыт

| Ресурс | Общий? | Чем закрыт |
|---|---|---|
| Рабочее дерево, `HEAD`, индекс | да (до правила) | `git worktree`: `.worktrees/<slug>`, ветка `<type>/<slug>` (`make wt-new`) |
| `build/` и собранные бинарники | да (до правила) | сборка внутри своего дерева (`BUILD_DIR := build` в `Makefile`) |
| Ветка | да | `.githooks/pre-commit` (ставится `make hooks-install`) — отказ на `main`, `master`, `main_worktree` и на detached `HEAD` |
| DDL и запись в локальный ClickHouse | да | лок `db` на `import`, `run`, `ch-sql`, `mcp-user`; источник пересечения — `util/clickhouse_import.go` (шаг `CreateTable` в `Import()`, строки 108–113) и `util/views.go:23-50` (`CreateView`) |
| ClickHouse-сервер `:8123`/`:9000`, каталог `~/clickhouse-dev` (`CH_DIR`) | да | тот же лок `db` на `ch-up`, `ch-down`: сервер и его данные — один ресурс, поэтому гашение не может совпасть с работающим импортом (было `stand`); гашение (`Makefile:133-144`) — только владелец стенда |
| Стенд Grafana `:3000`, каталог `~/grafana-dev` (`GF_DIR`) | да | лок `stand` на `grafana-up`, `grafana-down`, `grafana-deploy-test`, `grafana-test-token` |
| ingest-endpoint `:8081` (`INGEST_ADDR`) | да | лок **не берётся**: порт `:8081` сам не даст поднять второй экземпляр, а демон живёт часами — держать ресурс всё это время нельзя |
| Staging-хост `palmshell` (`STAGING_HOST`) | да | лок `staging` на `deploy-staging`, `deploy-staging-binary`, `deploy-staging-dagu`, `deploy-staging-mcp`, `upgrade-staging`, `mcp-user-staging`, `grafana-provision-staging`, `grafana-deploy-staging` (проверки `deploy-staging-preflight` и `deploy-staging-smoke` лок не берут — они ничего не мутируют) |
| Пользователь `kimi_reader` и его гранты | да | лок `db` на `mcp-user` |
| Каталог локов | общий для всех деревьев и **вне репозитория** | `$HOME/.rosstat-locks`, переопределяется `ROSSTAT_LOCK_DIR` |
| Индекс и MCP-эндпоинт GoLand | да (один инстанс IDE) | дерево открыто (приаттачено) отдельным проектом — иначе его файлов в индексе нет вовсе; `projectPath` своего дерева в каждом вызове, но выдачу он не сужает: свои результаты отбираются по префиксу `.worktrees/<slug>/…` |
| `.superpowers/sdd/<тема>/` и другие артефакты | да | один писатель на артефакт; тема SDD — одна сессия |
| `~/.config/rosstat/env` | да (секреты) | только чтение: файл подключается Makefile (`-include`), значения не печатать и не копировать в дерево |

Read-only цели лок **не** берут (иначе параллельная работа превратилась бы в очередь): `ch-status`, `lint`, `fmt`, `vet`, `test`, `test-parallel`, `build`, `build-ingest`, `all`, `mcp-check`, `env-check`, `dev-check`, `grafana-build`, `grafana-validate`, `grafana-check`, `run-ingest` (см. про `:8081` выше), `deploy-staging-preflight`, `deploy-staging-smoke`.

## Порядок работы сессии

1. **Создать дерево** из ветки-основания:
   `make wt-new NAME=<slug> TYPE=feat BASE=main` → `.worktrees/<slug>` на ветке `feat/<slug>`.
   Slug подходит под `^[a-z0-9][a-z0-9._-]*$`; повторный `new` тем же именем и занятая другим деревом ветка — отказ (это гарантия, а не помеха).
2. **Открыть (приаттачить) дерево** отдельным проектом в GoLand (`File → Open…` → путь `.worktrees/<slug>`; при запросе — открыть в текущем окне как отдельный проект) и отдельным workspace в Kimi Desktop. Это **условие**, без которого дерева в индексе IDE нет **вовсе**, и всё, что вернут проектно-зависимые вызовы (`git_status`, поиск, символы, run-конфигурации), относится к чужому дереву (класс конфликтов 5). Открытие — необходимое, но **не достаточное**: `projectPath` выдачу не сужает, инструменты отвечают объединением по всем открытым проектам. Поэтому проверка «дерево приаттачено» — это появление его файлов в выдаче `search_text` (с префиксом пути дерева) и записи с путём `.worktrees/<slug>` в `git_status`, а **не** «правильная ветка в ответе на свой `projectPath`»: та же ветка придёт и без attach, если она у другого дерева. Дальше все вызовы JetBrains MCP — с `projectPath` этого дерева и с отбором своих результатов по префиксу пути дерева; чтение по абсолютному пути (`read_file`, `list_directory_tree`) работает и без открытия проекта.
3. **Поставить git-хук** — один раз на клон: `make hooks-install` (`git config core.hooksPath .githooks` живёт в `.git/config`, поэтому действует сразу во всех деревьях; повторный прогон идемпотентен). Путь относительный — git разрешает его от корня того дерева, где идёт коммит, поэтому хук работает и в linked worktree (проверено), но только там, где в чекауте есть каталог `.githooks` (см. «Чего правило НЕ гарантирует»).
4. **Работать в своём дереве.** Первые коммиты ветки — спека и план пункта (порядок — [AGENTS.md](../AGENTS.md)).
5. **Проверить в своём дереве:** `make all` (gofmt, golangci-lint, `go vet`, `go test -race`, сборка) и `make test-parallel` (самотесты лок- и worktree-хелпера). Пишущие цели лок берут сами — оборачивать их руками не нужно, но и не запрещено: `scripts/lock.sh db -- make import STAT=rosstat_ipc_mes`.
6. **Провести приёмку** пункта и записать команды с результатом в роадмап (см. `docs/ROADMAP_DCF_POLYUS.md`).
7. **Один PR в конце.** После merge дерево убирается: `make wt-rm NAME=<slug>` (при незакоммиченных правках цель откажет; `FORCE=1` — осознанное действие, ветку цель не удаляет).

Полезное по ходу: `make wt-list` — деревья и пометка dirty, `make session-info` — путь дерева, ветка, dirty и активные локи с владельцами.

## Локи: ключи, цели, переменные

| Ключ | Что сериализует | Цели под локом |
|---|---|---|
| `db` | локальный ClickHouse целиком: и запись, и жизненный цикл сервера | `make import`, `make run`, `make ch-sql`, `make mcp-user`, `make ch-up`, `make ch-down` |
| `stand` | процессы локального стенда Grafana | `make grafana-up`, `make grafana-down`, `make grafana-deploy-test`, `make grafana-test-token` |
| `staging` | ssh-деплой и обновление на staging-хосте | `make deploy-staging`, `make deploy-staging-binary`, `make deploy-staging-dagu`, `make deploy-staging-mcp`, `make upgrade-staging`, `make mcp-user-staging`, `make grafana-provision-staging`, `make grafana-deploy-staging` |

`make run-ingest` лок не берёт: порт `:8081` сам не даст поднять второй экземпляр, а демон живёт часами — держать `db` всё это время нельзя (заблокировало бы все импорты). Проверки `deploy-staging-preflight` и `deploy-staging-smoke` тоже без лока: они только читают и ничего не мутируют.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `ROSSTAT_LOCK_DIR` | `$HOME/.rosstat-locks` | каталог локов; вынесен из репозитория, чтобы дерево не получало свой лок |
| `WAIT` | `900` | сколько секунд ждать занятый лок; `0` — не ждать, сразу выход с кодом `3` |
| `GRACE` | `5` | окно между `mkdir` лока и записью `owner`: пока оно не истекло, лок без `owner` не перехватывается |
| `ROSSTAT_LOCK_HELD_<key>` | не задан | выставляется хелпером внутри лока (`ROSSTAT_LOCK_HELD_db=1`); переменная ровно одна и названа по ключу как есть, поэтому `ROSSTAT_LOCK_HELD_DB` — это другой ключ, а не признак уже взятого лока; вложенный `make` внутри своего же лока не блокируется (reentrancy) |
| `ROSSTAT_SESSION` | basename рабочего дерева | имя сессии в `owner` — по нему вторая сессия видит, кто держит лок |
| `ROSSTAT_LOCK_TOOL` | сама команда | поле `tool` в `owner` (чем лок взят) |

Коды выхода `scripts/lock.sh`: код команды; `3` — лок занят и `WAIT` истёк (а также если брошенный лок не удалось перехватить за 3 попытки); `2` — ошибка вызова (ключ не задан/недопустим, команда не задана; сюда же нечисловые `WAIT`/`GRACE`, не удалось создать каталог локов и захват, который перехватили между `mkdir` и записью `owner` — то есть в `owner` оказался не наш pid, и работать под таким локом нельзя). Владельца занятого лока видно по `owner` (`key`, `tool`, `session`, `pid`, `host`, `since`, `cwd`) — хелпер печатает его в stderr вместе с фразой «жду до N с». Состояние всех локов печатает `scripts/lock.sh status` (возраст каждого лока, пометка «брошен» и поля `owner`; то же показывает `make session-info`).

**Перехват брошенного лока — только по мёртвому владельцу.** Возраст лока сам по себе не перехватывает ничего: живой владелец держит лок сколько нужно, а `kill -9` или долгий импорт не должны отдавать ресурс второму процессу. Лок считается брошенным, если pid владельца не отвечает (`kill -0` не проходит) **или** `owner`-файла нет и лок простоял ≥ `GRACE` секунд (окно между `mkdir` и записью `owner`). Сам перехват идёт под мьютексом `<lock>.takeover` (свой stale-таймаут): под ним владелец перечитывается, и только потом лок сносится — иначе два ожидающих могли снести свежий лок друг друга. Ручной `rm -rf` чужого лока, наоборот, снимает защиту у работающей сессии: при сомнении сначала `scripts/lock.sh status`.

Лок оборачивает **команду**, а не весь рецепт: сборка и подготовка внутри лока не нужны, под локом идёт только то, что пишет в общий ресурс.

## Что делать, когда лок занят

- **Ждать.** По умолчанию хелпер ждёт до 900 с и печатает владельца — это штатный путь: общий ClickHouse всё равно точка сериализации, второй тяжёлый импорт всё равно пойдёт по очереди.
- **Не ждать:** `WAIT=0 make import STAT=<имя>` — выход с кодом `3` без ожидания, если прогон нужен «сейчас или никогда».
- **Посмотреть, кто держит:** `make session-info` или `scripts/lock.sh status`; в `owner` есть pid, хост и рабочий каталог владельца.
- **Не трогать чужой лок руками.** Лок мёртвого владельца (pid не отвечает) или оставшийся без `owner` дольше `GRACE` перехватывается сам, с предупреждением. Удаление каталога лока вручную снимает защиту у работающей сессии.
- **Не поднимать второй ClickHouse.** Стенд один: `CH_HTTP_PORT`/`CH_TCP_PORT`/`CH_DIR` меняют только то, куда смотрит `make` из одного дерева, и расходятся с окружением MCP-пользователя.
- **Вложенные `make`** внутри уже взятого лока (агрегат вроде `deploy-staging` вызывает подцели) не дедлочатся: reentrancy через `ROSSTAT_LOCK_HELD_<key>`.

## Что делать при конфликте

- **Дерево и ветка.** `git worktree` не даст встать на ветку, занятую другим деревом, — это ожидаемая ошибка, а не поломка; своё дерево берётся через `make wt-new`.
- **Коммит в защищённую ветку.** Хук `.githooks/pre-commit` отказывает на `main`, `master`, `main_worktree` и на detached `HEAD`, печатая подсказку про `make wt-new`. Обход (`ALLOW_PROTECTED_COMMIT=1` или `git commit --no-verify`) — решение владельца репозитория, а не рядовой сессии.
- **Чужое дерево и чужая ветка.** `git worktree remove`, `git worktree prune`, `git branch -D` — только владелец: в дереве может лежать незакоммиченная работа. Свой `make wt-rm` отказывается удалять дерево с непустым `git status --porcelain` без `FORCE=1`.
- **Один писатель на артефакт.** `ARCHITECTURE.md`, `sql/*`, `dashboard/*.json`, `docs/archive/registry.jsonl`, `.superpowers/sdd/<тема>/` правит одна сессия; второй нужен отдельный файл или отдельная тема, а не параллельная правка одного.
- **Конфликт слияния.** В своей ветке подтяните `main` и разрешите конфликт обычным коммитом; force-push и `git reset --hard` по общей ветке запрещены (см. ниже).
- **Чужой стенд.** `make ch-down`, `make grafana-down` и `make ch-up` — только владелец стенда или по явной просьбе пользователя: стендом владеет сессия, которая его подняла.

## Личные хуки Kimi (страховка, в репозиторий не коммитится)

Хуки `[[hooks]]` Kimi Code читаются **только** из user-level `~/.kimi-code/config.toml` — проектного конфига у CLI нет, поэтому фрагмент не коммитится, а владелец добавляет его себе одной записью:

```toml
[[hooks]]
event = "PreToolUse"
matcher = "Bash"
command = "bash scripts/agent-guard.sh"
timeout = 10
```

Скрипт `scripts/agent-guard.sh` читает JSON события из stdin, работает только внутри этого репозитория — вверх по `cwd` ищется либо каталог `.githooks` с хуком, либо корень git-репозитория, у которого путь origin — ровно `…/clickhouse-import-rosstat(.git)` (см. «Где работают хук и гард» ниже) — и блокирует (`exit 2` с причиной в stderr):

- `make ch-down`, `make grafana-down`, `make ch-up` — «стендом владеет сессия, поднявшая его» (для `ch-up` исключение — прогон с `FORCE_STAND=1`); цель распознаётся и с глобальными флагами перед ней (`make -C <каталог> -j4 --no-print-directory ch-down`, `make VAR=1 ch-down`);
- `make deploy-staging`, `-binary`, `-dagu`, `-mcp`, `make upgrade-staging` без `FORCE_STAGING=1` — staging один на всех (лок `staging`, рестарт systemd-сервисов); `make deploy-staging-preflight` и `make deploy-staging-smoke` лок не берут и не блокируются;
- `git worktree remove`, `git worktree prune`, `git branch -D` — «дерево или ветка может принадлежать другой сессии»;
- `git checkout` / `git switch` на `main`, `master`, `main_worktree` — защищённая ветка;
- `git push --force`, `git reset --hard` — переписывание общей истории;
- `git clean` (кроме `-n`/`--dry-run`) и `git stash drop` — **только в корневом дереве**: там неотслеживаемые файлы и отложенная работа могут быть чужими; в своём `.worktrees/<slug>` это своё дело, и команда проходит;
- `rm`, у которого **путь-аргумент** лежит в `.worktrees`, и `find .worktrees … -delete` — снос чужих деревьев; `find … -delete` тоже блокируется только из корневого дерева, а `rm -rf build && ls .worktrees` не блокируется.

Корневое дерево гард отличает от linked worktree по `.git` (у корня — каталог, у worktree — файл-указатель): ближайший вверх каталог с `.git` и решает, cwd может быть и подкаталогом. Если определение не удалось, гард ведёт себя как раньше — блокирует (fail-closed: лишняя блокировка безопаснее ложного пропуска). Вне этого репозитория (чужой git-репозиторий, каталог без `.git` выше) гард молча выходит с кодом `0`.

### Где работают хук и гард

Признак у них разный, и от него зависит, в каких деревьях защита вообще есть.

- **Git-хук `.githooks/pre-commit` работает только в деревьях, где есть каталог `.githooks` в чекауте.** `core.hooksPath` относительный и разрешается от корня того дерева, где идёт коммит (в linked worktree это его собственный корень), поэтому дерево, созданное от `main`, куда ветка с `.githooks` ещё не влита, хука не получит — молча, без ошибки.
- **Гард `scripts/agent-guard.sh` активацию по чекауту не требует:** `cwd` поднимается вверх, и защита включается, если найден каталог `.githooks` с хуком (альтернативный признак — если origin переименуют) или корень git-репозитория, у которого путь `git remote get-url origin` — ровно `…/clickhouse-import-rosstat` или `…/clickhouse-import-rosstat.git` (хвост `.git` и завершающий слеш нормализуются, ssh-форма `git@host:owner/clickhouse-import-rosstat.git` подходит, а чужой форк `…-fork.git` — нет). Поэтому правила гарда — включая `git clean`/`git stash drop`/`find .worktrees -delete`, писанные именно под корневое дерево, — действуют и в корне, и в деревьях, созданных до этого правила.

**Владельцу при вливании ветки.** Обновить корневое дерево так, чтобы каталог `.githooks` в нём появился (`git -C <корень> pull` от `main`), и проверить `ls .githooks/pre-commit` — после этого хук получают все деревья, созданные от обновлённого `main`, а у гарда появляется второй (резервный) признак активации.

## Чего правило НЕ гарантирует

- **Хуки Kimi fail-open и user-level.** Ошибка разбора JSON, отсутствие записи в `config.toml`, новый инструмент вместо `Bash` — и команда пройдёт. Это страховка от случайности, а не барьер; барьеры — git-хук и лок.
- **Убитый владелец лока `kill -9`.** Перехват реагирует только на мёртвый pid и на отсутствие `owner` дольше `GRACE`, но у убитого холдера дочерняя команда (импортёр, сервер) может продолжать работу, уже без лока, — второй прогон тогда пойдёт параллельно с ней. Автоматики против этого нет: помогает ручное `rm -rf` каталога лока плюс повторный прогон (и `make ch-status`/`ps` — проверить, что прежний процесс действительно не работает). Отдельный случай того же класса — **переиспользование pid**: лок, оставшийся от убитого `kill -9` владельца, чей pid потом занял другой процесс, будет считаться живым (pid отвечает, возраст лока ни при чём) до ручного `rm -rf` каталога лока.
- **`core.hooksPath` видит только те деревья, где есть каталог `.githooks`.** Значение относительное и разрешается от корня того дерева, где идёт коммит (проверено в linked worktree: хук срабатывает), поэтому дерево, созданное от `main`, куда ветка с `.githooks` ещё не влита, хука не получит — молча, без ошибки. После вливания в `main` каталог есть во всех деревьях, созданных от него (порядок для владельца — «Где работают хук и гард»). Гард `scripts/agent-guard.sh` от чекаута не зависит: он активируется по origin этого репозитория, поэтому страховка есть и в деревьях без `.githooks`.
- **Один инстанс GoLand.** Порт MCP может смениться при перезапуске IDE; второй открытый проект удваивает индекс; пока дерево не приаттачено отдельным проектом, его файлов в индексе нет **вовсе** и git-ветка, `git status`, символы и run-конфигурации приходят по чужому дереву, а после attach `projectPath` выдачу **не сужает** — инструменты отдают объединение по всем открытым проектам, и чужие строки в ответе надо отсеивать по префиксу `.worktrees/<slug>/…` (в `git_status` — по записи своего дерева). Ни то, ни другое `projectPath` не лечит (замеры — класс конфликтов 5). Правило `projectPath` обязательно именно поэтому.
- **Общий ClickHouse — точка сериализации.** Лок не ускоряет работу, а расставляет очередь: два тяжёлых импорта идут по очереди (цена надёжности).
- **dagu на staging живёт по своему расписанию.** Scheduled-шаг и ручной `make import` того же стата друг о друге не знают: двойные вставки схлопнет `ReplacingMergeTree`, но лишняя нагрузка на источник и хост останется.
- **Лок — не распределённая блокировка.** Это каталог в `$HOME` на одной машине: вторую машину или общий NFS он не покрывает.
- **Read-only работа не координируется.** Лок берут только пишущие цели; `make test`, `make all`, `ch-status` и чтение витрин идут параллельно без ограничений.
