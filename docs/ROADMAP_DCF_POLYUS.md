## 1. Целевая постановка

Превратить ETL-проект в **аналитический контур замкнутого цикла**:

> Источники → ClickHouse (сырые ряды + витрины) → MCP-доступ для Kimi → регулярный сценарный прогноз золота → DCF → NAV акции PLZL → журналирование прогнозов и проверка точности.

Статья Q3-2026 уже содержит методологическое ядро: сценарную рамку с вероятностями (бычий 25% / базовый 40% / медвежий 35%), календарь триггеров (FOMC 9 декабря, CPI 10 ноября, истечение запрета на экспорт дизеля 1 ноября), дашборд верификации с порогами (crack spread >$50, запасы дистиллятов EIA, шансы FedWatch >80%) и практику проверки прошлых прогнозов. Дорожная карта институционализирует это: каждый индикатор из «дашборда верификации» становится таблицей в БД, каждый триггер — записью в календаре событий, каждый прогноз — версией в журнале.

## 3. Целевая модель данных

Канонические DDL — в [ARCHITECTURE.md](../ARCHITECTURE.md) §6.2 (единый источник истины, здесь не дублируются). Ключевые сущности:

- **Сырые ряды:** `macro_series` (FRED/EIA/WGC/CME + ручные ряды с `source='manual'`), `gold_prices`, `gold_forecasts` (версионированный консенсус + собственные сценарии), `events_calendar` (ядро оркестрации).
- **Модель:** `model_runs` (каждый пересчёт NAV — версия с триггером, сценариями, обоснованием), `forecast_log` (прогноз vs факт — автоматизация рубрики «проверка прошлого прогноза»).
- **Рыночный слой:** `news_events`, `index_weights`, `dividend_events`, `ofz_curve`, `mmf_aum`, `tax_events`.
- **Ресурсная база и peers:** `reserves_assets`, `reserves_dynamics`, `license_events`, `peers_nav`.
- **Sum-of-parts и price decks:** `mine_plans`, `nav_by_asset`, `price_decks`, `regime_states`.
- **Витрины для агента:** `v_model_inputs` (срез входов DCF одной строкой), `v_gold_dashboard` (дашборд верификации с флагами порогов), `v_forecast_accuracy`, `v_peers_comparison` (P/NAV по сектору), `v_gold_attribution` (GRAM-разложение); метрики компаний сектора — `v_company_financials` (разрешённое значение), `v_company_metric_sources` (все версии, включая проигравшую), `v_company_operating` (операционка по активам; схема общая для золотодобычи и металлургов, наполнена пока Полюсом — [docs/ROADMAP_DCF_METALS.md](ROADMAP_DCF_METALS.md)).

## 4. Дизайн DCF-модели Полюса

### 4.1 Структура (rev.2 — sum-of-parts)

```
NAV = Σ_asset NPV(LOM-план актива) − NetDebt − корп.затраты + опционность ресурсов вне LOM
Для каждого актива (Олимпиада, Благодатное, Вернинское, Наталка, Сухой Лог, …):
  FCF_t = Production_t(koz) × (Gold_deck_t − AISC_t) − НДПИ_t − налоги − capex_t ± ΔWC
  НДПИ = база + 10% × max(GoldPrice − 1900, 0)   ← ценовая надбавка, действует с 2025
  конец LOM: хвост closure_costs (отрицательный); perpetual TV у рудника НЕТ
Equity NAV/акция = (Σ NPV_активов − NetDebt) / shares; дивиденды приостановлены до 2030
```

Ключевые отличия rev.2 от первичной схемы: (1) модель считается **по активам** на life-of-mine планах (`mine_plans`), а не по компании в целом; (2) терминальная стоимость — отрицательный хвост закрытия, ресурсы вне LOM — опционно по EV/oz со стадийными haircut'ами; (3) ставка — двухконтурная (см. §13.1); (4) NAV считается на трёх price deck'ах (`price_decks`).

### 4.2 Ключевые связи макро → модель

| Макропараметр | Вход в модель | Источник ряда |
|---|---|---|
| Сценарная цена золота (прогноз $4,000–4,600, Q4-2026) | Выручка, основной сценарный рычаг | `gold_forecasts` (own) + `gold_prices` (факт) |
| USD/RUB | Трансляция рублёвых затрат в USD-себестоимость; чувствительность маржи | `cbr_currency_usd` |
| Ключевая ставка ЦБ / кривая ОФЗ | Локальный контур ставки (для RU-инвестора) | `cbr_key_rate`, `ofz_curve` |
| Ставка ФРС / реальные доходности | Драйвер сценарной вероятности золота; мировой дисконт | `macro_series` (FRED) |
| ИПЦ РФ | Эскалация TCC/AISC (зарплаты, ГСМ, взрывчатка) | `ipc_mes` |
| Дизельный crack (двойная роль!) | 1) индикатор инфляции США → ставка → золото; 2) прямой драйвер рублёвых топливных затрат Полюса | datasource `HO=F`; запасы дистиллятов — `macro_series` (`source='manual'`) |
| Brent | Прокси дизельного канала + бюджетное правило РФ (отсечка $59 → операции ФНБ с золотом) | `stock_prices`/новый ряд |

### 4.3 Выходы

- NAV/акция по трём сценариям **× трём price deck × двум ставкам** + вероятностно-взвешенная;
- **NAV-матрица чувствительности**: золото ($3,750–5,000, шаг $250) × USD/RUB (75–110) × ставка (±200 б.п.) — публикуется как Grafana-таблица;
- NAV- и EBITDA-бета к цене золота (рычаг);
- upside/downside к рыночной цене PLZL (MOEX ISS);
- журнал `model_runs` — полная история пересмотров с обоснованиями.

## 5. MCP-интеграция с Kimi

### 5.1 Готовый сервер — не писать свой

Официальный [mcp-clickhouse](https://github.com/ClickHouse/mcp-clickhouse) покрывает нужный минимум: `list_databases`, `list_tables`, `run_select_query`. Альтернатива — [Altinity MCP](https://github.com/Altinity/altinity-mcp) (написан на Go; есть JWE-аутентификация и OpenAPI-режим).

### 5.2 Рекомендуемая конфигурация

```bash
# Docker, HTTP-транспорт, токен-авторизация, read-only
docker run -d --name ch-mcp \
  -e CLICKHOUSE_HOST=clickhouse -e CLICKHOUSE_PORT=8123 \
  -e CLICKHOUSE_USER=kimi_reader -e CLICKHOUSE_PASSWORD=*** \
  -e CLICKHOUSE_MCP_SERVER_TRANSPORT=http \
  -e CLICKHOUSE_MCP_AUTH_TOKEN=<uuid> \
  -p 8000:8000 mcp/clickhouse
```

Правила безопасности:

1. Отдельный пользователь `kimi_reader` в ClickHouse: **только SELECT**, только база витрин; сырые таблицы и системные — закрыть.
2. MCP-сервер **строго read-only** — запись прогнозов (`model_runs`, `forecast_log`) делает не агент через MCP, а отдельный ingest-endpoint/скрипт по итогам сессии (контроль качества данных).
3. Токен в env, не в коде.

### 5.3 Чтобы агент понимал данные

- `COMMENT ON TABLE`/`COMMENT ON COLUMN` для каждой витрины — MCP отдаёт комментарии в `list_tables`, это и есть «документация для Kimi»;
- сниппет-шпаргалка (skill/prompt) с описанием модели: где лежат входы DCF, как считается NAV, какие пороги у триггеров, формат записи прогноза;
- представления с человекочитаемыми именами (`v_*`), чтобы агент не строил запросы по сырым таблицам.

## 6. Оркестрация обновлений: календарь + новости

### 6.1 Календарный контур

`events_calendar` наполняется один раз на квартал из известных расписаний (CPI 14 окт, PPI 15 окт, FOMC 28 окт и 9 дек, NFP 6 ноя / 4 дек, EIA — каждая среда, WGC GDT — конец октября, запрет дизеля — 1 ноя, совет директоров ЦБ РФ, отчётности Полюса). Планировщик:

- **ежедневный ETL** (cron → `make run` с фильтром `CLICKHOUSE_IMPORT_STAT` по дневным источникам: золото, DXY, USDRUB, crack, PLZL);
- **еженедельный**: по средам — EIA (запасы дистиллятов) и недельный ИПЦ Росстата (день недели сверить с календарём Росстата);
- **по событию**: в день `event_date` запускается соответствующий импортёр + сессия Kimi «обнови прогноз»: агент читает свежий релиз через MCP, сверяет с порогами из `events_calendar`, пересчитывает сценарные вероятности → новая запись `model_runs` → обновлённый NAV.

### 6.2 Новостной контур (в моменте)

1. **Простой (стартовый):** ручной триггер — новость в чат («запрет на дизель продлён», «FOMC повысил на 25 б.п.»), агент по MCP подтягивает текущие данные, пересчитывает сценарии и NAV, пишет в `model_runs` с `trigger_type='news'`.
2. **Продвинутый (фаза 5):** импортёр `news_watch` — RSS/парсинг ключевых лент (ЦБ РФ, Минфин, ФРС, WGC, EIA, IR Полюса) в `news_events`; свежие события сами становятся триггерами сессии пересчёта.

### 6.3 Петля обратной связи

После каждой контрольной даты агент сверяет `forecast_log.predicted` с фактом — «проверка прошлого прогноза» становится автоматической метрикой точности, её динамика — отдельной панелью Grafana. Ошибки атрибутируются к факторам GRAM (ставка / потоки / риск / импульс) через `v_gold_attribution`.

### 10.2 Что меняется в модели и процессе

1. **DCF корректируется фактом приостановки дивидендов до 2030**: дивидендная составляющая обнуляется на горизонте модели, NAV формируется чистым FCF/NAV-мультипликатором, а не DDM; в `model_runs` — поле `dividend_status`.
2. **Налоговая функция становится эндогенной**: НДПИ от сценарной цены золота — при медвежьем $3,750 нагрузка снижается вместе с выручкой, при бычьем $5,000 — растёт.
3. **Новый выход модели — «рыночный мост» NAV → целевая цена**: NAV ± корректировки по каналам (отрицательный дивидендный спред к ОФЗ → дисконт; начало перетока из фондов ликвидности → снятие дисконта; всплеск негативного sentiment → тактический дисконт). Каждая корректировка фиксируется в `model_runs` для верификации. С rev.2 мост декомпозируется на страновой дисконт (~75% к EM-пирам — рыночная константа, не ошибка модели) и компанейский (см. §13.6).
4. **`events_calendar` дополняется**: заседания ЦБ РФ (23 октября и 18 декабря 2026 — ближайшие), ребалансировки индексов MOEX (третьи пятницы квартала), дедлайны бюджета и налоговых поправок в ГД, даты СД Полюса по дивидендам.

## 11. Интеграция с Kimi Work: оркестрация и персональная панель

### 11.1 Почему это лучший слой оркестрации

**Kimi Work** — десктопный локальный агент Moonshot AI (запущен 03.06.2026, Beta, macOS/Windows; ядро Kimi Code/K3, длительные задачи, планировщик cron, WebBridge-автоматизация браузера, Goal-режим, виджеты и дашборды). Проект изначально строится «Kimi ↔ ClickHouse через MCP» — Kimi Work добавляет исполнительную среду той же модели без переконтекста.

| Возможность Kimi Work | Применение в проекте |
|---|---|
| **Cron-планировщик** (бесплатно 2 задачи; исполнение локально, компьютер должен быть включён) | Ежедневный ETL-прогон, по средам — запасы дистиллятов/недельный ИПЦ (день недели сверить с календарём Росстата), 10-е — ETF-потоки, дни FOMC/CPI/ЦБ; статус, история и отчёт по итогу прямо в UI — прозрачнее crontab |
| **Goal-режим** (многошаговые задачи с критериями приёмки) | Сценарные сессии пересчёта NAV: «обнови прогноз при пробитии $4,800» — цель + приёмка (вероятности нормированы, запись в `model_runs`, выжимка в `forecast_log`) |
| **WebBridge** (браузер локальной машины, переиспользует логин-сессии) | Сбор рядов без API: FedWatch (CME), ETF-потоки WGC, СЧА фондов ликвидности, составы индексов MOEX; заодно снимает TLS/ГОСТ-проблемы gos-источников |
| **Нативные финансовые БД** (плагины) | Кросс-проверка данных Полюса/IMOEX по запросу, без API-ключей |
| **Виджеты + Dashboard** (динамическое обновление из локальных данных/плагинов) | Персональная панель «Прогноз золота → NAV PLZL»: спот, сценарии, вероятности, NAV-матрица, календарь триггеров, sentiment; пин на рабочий стол |

### 11.2 Архитектура контура

```
ClickHouse (витрины v_*)
      │  ① MCP (mcp/clickhouse, read-only, HTTP, токен)
      │
Kimi Work (десктоп): Dashboard + Widgets  ←  ② локальные скрипты/CSV из CH
      │                                      ③ WebBridge (FedWatch, WGC, СЧА фондов)
      │  ④ Cron: ETL + триггерные сессии → model_runs/forecast_log (ingest-скрипт)
      ▼
Grafana остаётся как серверная/веб-витрина (24/7, без участия десктопа);
Kimi Work Dashboard — личная панель аналитика, дублировать её функции Grafana не нужно.
```

**Принцип:** Kimi Work — оркестратор и персональный интерфейс; **источник истины данных — ClickHouse** (все рассчитываемые ряды пишутся в БД и в Grafana, виджеты лишь отображают).

### 11.4 Ограничения и риски

1. **Локальность** — планировщик и дашборд работают, только пока включён десктоп с запущенным Kimi Work; ClickHouse+Grafana остаются системой записи и серверной витриной. Для 24/7-алертов — Grafana-alerts, для личной панели — Kimi Work.
2. **Beta-статус** — продукт итерируется быстро, интерфейсы могут меняться; интеграцию держать тонкой (локальные CSV/скрипты и MCP, не глубокие привязки к UI).
3. **Лимиты тарифа** — 2 cron-задачи на бесплатном плане, сверху — платный; внешние MCP-подключения read-only (`kimi_reader`).

### 11.5 Проверено на спайке 2026-10-10 (v3.2.15): datasource и шаринг

Спайк в запущенном Kimi Work подтвердил возможности, на которых держится пересмотр роадмапа (детали и таблицы покрытия рядов — в [спеке плагина](superpowers/specs/2026-10-10-gold-nav-plugin-design.md) §2):

- **Плагины и маркетплейс есть** (Featured/Finance/…), с кнопкой «+ Создать плагин» → встроенный агент Plugin Builder; формат — тот же `kimi.plugin.json`, что в Kimi Code; типы `skill-only | mcp | mcp+skills`; регистрация в **персональный маркет** официальным CLI, горячее подключение без перезапуска.
- **Remote MCP по URL поддержан** — значит mcp-clickhouse автора подключается напрямую; предположение «в Kimi Work нет своего MCP и datasource» **опровергнуто**.
- **Datasource-эквиваленты доступны**: `yahoo_finance` («Global Finance Data» — золото `GC=F`, DXY, ULSD), `imf`, `world_bank_open_data` и др. FRED-плагина нет, но ставка/доходности покрываются Yahoo (`^TNX`) и IMF; в Kimi Code тот же слой даёт плагин `kimi-datasource`.
- Отсюда — **datasource-first**: мировые ряды берутся в сессии из плагинов среды, в ClickHouse не дублируются; Go ETL хранит РФ-контур, исторический базлайн (fred/bls/bea/moex/gold) и журнал модели (см. §7, фаза 1).

**Модель шаринга — «хостинг у автора».** Получателю (в т.ч. не-программисту из РФ) Go-проект не нужен: он ставит плагин `gold-nav` одной командой (`/plugins install` в Kimi Code; Plugin Builder → персональный маркет в Kimi Work) и задаёт свой `GOLD_NAV_MCP_TOKEN`. mcp-clickhouse крутится в HTTP-режиме на стороне автора и выдаёт получателям **read-only** токен (`kimi_reader`, только витрины `v_*`); **ingest-токен записи `model_runs` остаётся только у автора**. Токены в репозиторий плагина не зашиваются — только `${ENV}`-плейсхолдеры.

Не проверено на спайке (стоит кредитов, входит в приёмку): живой end-to-end запрос данных в сессии Kimi Work.

**Проверено 2026-10-10 (второй спайк, живой `kimi-datasource` в Kimi Code): РФ-эмитенты в datasource НЕ покрыты.** Пробы `stock_finance_data_get_financial_statements`:

| Проба | Результат |
|---|---|
| `ticker=600223.SH`, `financial_parameter=20251231` | ✅ 83 колонки, 35 заполнены (`ths_operating_total_revenue_stock` = 3 650 898 043,82) |

Следствия для роадмапа: (а) datasource **не заменяет** собственный ETL по Полюсу, ЮГК, Селигдару и металлургам ни в одной части — тезис «datasource-first» относится только к мировым рядам (перевод металлургов — отдельная дорожная карта [docs/ROADMAP_DCF_METALS.md](ROADMAP_DCF_METALS.md)); (б) форма данных datasource — **широкая строка на отчётную дату с колонками-метриками**, где эмитент задаётся значением (`thscode`), а период — параметром запроса; эта форма подтверждает решение заводить общую `company_financials` вместо набора витрин на компанию (спека [2026-10-10-company-financials-views-design.md](superpowers/specs/2026-10-10-company-financials-views-design.md) §2.2). Ограничения API: ≤3 тикера, диапазон ≤3 года, обязательный `file_path`; суффиксы `.SH/.SZ/.BJ`, `.HK`, `.O/.N/.A.N/.B.N`, `.US`; `.RU` отвергается ошибкой `PARAMETER_ERROR`.

## 12. Запасы, ресурсы, лицензии и относительная оценка по сектору (P/NAV peers)

### 12.1 Почему запасы — отдельный блок модели

NAV Полюса — это дисконтированные **запасы в недрах**, а не только поток текущего производства. В DCF-модель добавляются три входа:

1. **Reserves & resources по месторождениям** (koz, по годам): запасы P&P, ресурсы M&I+Inferred, среднее содержание г/т (для Полюса — JORC-оценка).
2. **Прирост запасов и конверсия ресурсов** (%, koz/год): ГРР-программа и её стоимость ($/oz added) — реальный драйвер long-term value; без него TV систематически занижается.
3. **Портфель лицензий**: даты окончания/продления по ключевым активам (Олимпиада, Благодатное, Сухой Лог…), риск продления, «спящие» активы (опционная стоимость вне запасов).

### 12.2 Таблицы

Канонические DDL — [ARCHITECTURE.md](../ARCHITECTURE.md) §6.2: `reserves_assets` (с полями `standard` и `stage`), `reserves_dynamics`, `license_events`, `peers_nav` (с `peer_universe`); витрина `v_peers_comparison`.

### 12.3 Профили компаний-сверок (реперные точки)

| | **Полюс (PLZL)** | **Южуралзолото ГК (ЮГК)** | **Селигдар (SELG)** |
|---|---|---|---|
| Запасы | **106,8 млн унций** P&P (2025, +1,5% г/г); Сухой Лог — 43,3 млн унций из них | ~**40,7 млн унций** Au-eq по JORC (вторая в РФ); рост за счёт Томинского и Кочкарского ГОКов | **285 т золота** (~9,2 млн унц) + 412 тыс. т олова (РФ-классификация, не JORC — пересчёт обязателен) |
| Ключевой драйвер запасов | Сухой Лог (ввод — главный каскад NAV), Благодатное +35% за 2025 | Кочкарское: 99,5 млн ₽ ГРР в 2025, ресурсы 46 млн унций | Хвойное (новая ЗИФ ₽15 млрд, 2,5 т/год), цель 20 т/год к 2030 |
| Производство | ~2,5 млн унций (2025), цель 6 млн к концу 2030 | 12 т (~0,39 млн унц), +13% в 2025 | 8,1 т (2025), план 9–10 т в 2026 |
| Особенности для модели | дивиденды приостановлены до 2030, реинвест в Сухой Лог | двойной металл (Cu-Au-Ag-Mo), лицензионные риски Томинского → дисконт/премия к NAV | полиметаллический (Au+Sn); запасы по РФ-классификации → пересчёт в JORC-эквивалент для P/NAV |

### 12.4 Метрика сектора: P/NAV и EV/oz

Витрина `v_peers_comparison` (из `peers_nav` + `reserves_dynamics`):

- **P/NAV** каждой компании к собственной NAV (полная модель для PLZL; упрощённая по AISC×production для peers) — **на одинаковом price deck** (`consensus_lt`), иначе сравнение некорректно;
- **EV/унция запасов** ($/oz) — «рыночный ценник недр»;
- **дисконт к лидеру** — внутри российского контура (`peer_universe='ru'`, все несут одинаковый страновой дисконт); глобальные пиры — только для измерения странового дисконта.

Гипотеза для проверки: рынок даёт PLZL премию за масштаб и Сухой Лог, но дисконтирует за отсутствие дивидендов до 2030 — значит валютная NAV важнее рублёвой dividend-yield-логики, и в мосте NAV→цена дивидендный канал (§10) взвешен меньше, чем у ЮГК/Селигдара.

## 13. Стейт-оф-зе-арт: корректировки по мировой практике (обзор академии, sell-side, buy-side)

Исследованы: отраслевые стандарты (KPMG Insights into Mining, опросы CIM/L.D. Smith), sell-side (Scotiabank price deck, BMO LT-assumption, BofA NAV-leverage, J.P. Morgan gold research), buy-side (Schroders), WGC (Qaurum/GVF, GRAM, Gold Outlook 2026), академия (Erb–Harvey «The Golden Dilemma»; Schwartz 1997 / Schwartz–Smith 2000; Brennan–Schwartz real options; Markov-switching-литература по золоту). Семь корректировок уже внесены в модель (§4, §6.4 ARCHITECTURE.md), здесь — обоснование.

### 13.1 Ставка: конвенция 5% real USD, а не WACC от ставки ЦБ

Для золота отраслевой стандарт NAV — **реальная 5% USD** (базовые металлы 8–10%), с надбавками за юрисдикцию/стадию по опросам CIM (до 10%); CAPM/WACC не применяется — бета золотодобытчиков около нуля или отрицательна, ценовой риск уже в консервативном deck. Наша схема «WACC от ЦБ 14%» смешивала рублёвую доходность с USD-потоками. Решение: **двухконтурная ставка** — индустриальная (5% real + надбавки; сопоставима с глобальным P/NAV) и локальная (ОФЗ + премии; объясняет локальную цену). Обе — в `model_runs`.

### 13.2 Sum-of-parts LOM вместо корпоративного DCF

Мировой стандарт: NAV = сумма NPV рудников по life-of-mine планам (добыча, содержание, strip ratio, AISC, capex по годам из техотчётов) − net debt − корп. затраты. Сухой Лог — отдельный девелопмент-актив со своей ставкой/стадийным дисконтом, а не часть усреднённого потока. Таблицы: `mine_plans`, `nav_by_asset`.

### 13.3 Никакого perpetual TV

Рудник истощаем: в конце LOM — **отрицательный хвост** (закрытие, рекультивация, выходные пособия; рекультивация налогово вычитаема). Ресурсы вне LOM — не в DCF, а опционно: EV/oz × stage haircut (construction 0,7–0,9 / DFS 0,5–0,7 / PEA 0,2–0,4; рыночный P/NAV девелоперов 0,3–0,7 против 0,8–1,3 у производителей). NAV публикуется в двух разрезах: «LOM-only» и «с опционностью».

### 13.4 Price deck ×3

Sell-side считает NAV на deck: ближние годы — консенсус/форварды, хвост — LT-оценка (системно ниже спота: Scotia LT $2,600 с 2029; BMO поднял до $3,000); buy-side меряет «какая цена заложена в котировке» (Schroders: производители закладывают золото значительно ниже спота). У нас — `price_decks`: `spot_flat` / `consensus_lt` / `own_scenario`; каждый run считается на всех трёх; LT-хвост own-сценария сходится к обоснованной LT-оценке. P/NAV против пиров — только на одинаковом deck.

### 13.5 Золотой слой: GRAM-атрибуция, сценарии WGC, режимы

- `v_gold_attribution` — разложение движения золота по факторам WGC GRAM (экспансия / риск / альтернативная стоимость / импульс); ошибки `forecast_log` атрибутируются к фактору.
- Сценарии — в формате WGC Gold Outlook (квантифицированные пути ставки ФРС, доходностей, USD, риск-позиционирования по каждому сценарию).
- `regime_states` (скрытая марковская модель): связь «реальные ставки → золото» (корреляция −0,82 с TIPS) хрупка на длинных окнах (Erb–Harvey), знаки коэффициентов меняются между режимами; MS-модели точнее (MAPE 2,6% vs 7,3%). Сценарные вероятности согласуются с текущим режимом; смена режима — триггер пересчёта.
- ML-ансамбль (XGBoost+SHAP / EEMD-ансамбли / BiLSTM) — **конкурентный трек** в `forecast_log` с rolling-валидацией и Diebold–Mariano против экспертного прогноза, а не его замена (фаза 5+).

### 13.6 Декомпозиция дисконта: страновой vs компанейский

Российские акции торгуются с дисконтом ~75% к EM-аналогам (2025; было ~40% в 2021, MOEX/Advance Capital). Дисконт PLZL к глобальной NAV на 5%-конвенции — в основном страновой; сравнение P/NAV с ЮГК/Селигдаром (`peer_universe='ru'`) — корректная относительная рамка, глобальные пиры — для измерения странового дисконта. Дополнительный вывод run'а — NAV-/EBITDA-бета к золоту (эталон BofA: EBITDA-бета ~14% на +10% Au).

### 13.7 Что осознанно НЕ внедряем сейчас

- Полноценный real options / LSM Monte Carlo (Brennan–Schwartz, Cortazar–Schwartz) — академически эталон, но избыточен для старта; stage haircut'ы покрывают 80% эффекта. Возврат в фазе 5+ при наличии времени.
- Стохастические модели цены (Schwartz–Smith two-factor) — для симуляции распределения NAV вместо точечных сценариев; кандидат в фазу 5+ вместе с ML-треком.
