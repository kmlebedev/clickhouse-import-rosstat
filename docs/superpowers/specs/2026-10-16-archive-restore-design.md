# Спека: восстановление БД из винтажного архива (`ARCHIVE_ACTION=restore`) — срез инфра-пункта 1.2

**Дата:** 16 октября 2026 г.
**Пункт роадмапа:** [ROADMAP_INFRA.md](ROADMAP_INFRA.md) шаг 1.2 «Восстановление и наполнение БД из архива» — срез: вход восстановления (`make archive-restore`), листинг (`make archive-list`) и локальная реконсиляция «объект без строки реестра». Первый потребитель — нестабильный источник `rosstat_ipc_weeks_bulletins` (живой буфер Росстата может быть вычищен, Wayback троттлит; документы уже лежат в архиве).
**План:** [2026-10-16-archive-restore.md](../superpowers/plans/2026-10-16-archive-restore.md).
**Статус документа:** спека дизайна; нормы не пересказываются — ссылки вида «стандарт §9.6», «ARCHITECTURE §8 п. 13». Дизайн архива — [спека 2026-10-14](2026-10-14-source-file-archive-design.md) §1.3 (восстановление названо follow-up'ом шага 1.1).

---

## 1. Зачем

Шаг 1.1 (PR #62) сохраняет версию каждого скачанного файла в хранилище + `registry.jsonl`, но **читателя у архива нет**: восстановить ряд из архива сегодня нечем, а именно это делает архив полезным при потере источника. Нестабильный источник найден живым: буллетени Росстата — живой буфер и Wayback оба отдают 429/заглушки в произвольные моменты, а 71 документ уже заархивирован. Пункт 1.2 реализуется **сначала на этом источнике**: пустая таблица `rosstat_ipc_weeks_bulletins` наполняется из архива без единого сетевого обращения к источнику, «прогон на пустой БД доходит до витрин» (критерий приёмки пункта).

## 3. Решения по дизайну

### 3.1 Режим `ARCHIVE_ACTION=restore` (вход восстановления)

`main.go`: `ARCHIVE_ACTION` может быть `registry` (как раньше), `list` (новый) и `restore` (новый). `registry` и `list` — самостоятельные действия: делают своё и завершают процесс. `restore` **не завершает**, а переключает обычный путь импортёров: дальше обязательны `CLICKHOUSE_URL` и `CLICKHOUSE_IMPORT_STAT=<импортёр(ы)>`, и каждый выбранный импортёр работает в режиме восстановления. Неизвестное значение — по-прежнему фатальная ошибка (опечатка не должна превращаться в полный импорт).

Семантика режима (в `util.ClickHouseImport.Import`, одна точка на все шаблонные импортёры):

1. **Байты — из архива, сети нет вообще.** Вместо `GetFileBytes(DataUrl)` версия резолвится по реестру: строки `(source, url)` → самая свежая по `first_seen` → `Store.Get(key)`. Не найдена — ошибка с URL (fail-fast).
2. **Целостность проверяется:** sha256 полученных байтов обязан совпасть с `sha256` строки реестра; расхождение — ошибка (реестр и объект перестали быть самодостаточной парой).
3. **Префлайт не выполняется** (HEAD некуда делать — источник не спрашиваем вовсе); версия для строки `source_publications` берётся из строки реестра (её `fingerprint`); пустой отпечаток строки — строка версии не пишется (существующее правило шаблона).
4. **Архивация повторно не выполняется** — версия уже в архиве (объект и строка на месте по построению резолва).
5. `CrawFunc`-импортёры в режиме восстановления — ошибка с явным текстом (их байтов шаблон не видит и в архив они не попадают — граница шага 1.1; в срезе только шаблонные пути `ImportFunc`/`BodyFunc`).
6. Идемпотентность: повторный restore перезаписывает те же точки (`ReplacingMergeTree`), число строк не меняется; гейты импортёров (например, гейт бюллетеней по датам) продолжают работать как обычно — восстановление платит только за то, чего в таблице нет.

### 3.2 Листинг и реконсиляция

- `archive.LoadEntries(ctx, store)` — публичное чтение `registry.jsonl` из хранилища (существующий приватный разбор переиспользуется; без ClickHouse — как и задумано пунктом).
- `make archive-list` печатает строки «источник · имя · версия(8) · размер · first_seen · url»; строки с одинаковым `sha256` помечает как дубли содержимого (обязательный подпункт 1.2: один файл под `sha-`- и fingerprint-ключом — это две записи об одном содержимом).
- `ARCHIVE_RECONCILE=1`: для бэкенда с листингом (`LocalStore.List` — обход каталога, `*.tmp` и сам `registry.jsonl` пропускаются) печатает объекты, которых нет в реестре («есть объект — нет строки»), и завершает работу ненулевым кодом при находках — реконсиляция не должна молча выглядеть как чистое зеркало. Для бэкендов без листинга — явное сообщение «реконсиляция недоступна» (yandex — остаток пункта).
- `LocalStore.List` возвращает ключи (`<источник>/<файл>`) — та же форма, что в реестре.

### 3.3 Makefile

```make
archive-list:      # сборка бинарника + ARCHIVE_ACTION=list (+ARCHIVE_LIST_SOURCE=, +ARCHIVE_RECONCILE=1)
archive-restore:   # STAT=<импортёр> обязателен; ARCHIVE_ACTION=restore CLICKHOUSE_IMPORT_STAT=$(STAT)
```

Оба по образцу `archive-registry`: окружение подключает `$(ROSSTAT_ENV)`, секреты не печатаются.

### 3.4 Тесты и приёмка

- `archive/`: `LocalStore.List` (tmp и registry.jsonl пропущены), `LoadEntries` (roundtrip через `Registry.Ensure`).
- `util/`: `RestoreVersion` — успех, «в архиве нет версии», расхождение sha256, архив не настроен; импорт шаблона в режиме restore на фейковом соединении — байты берутся из архива, сеть не вызывается (URL заведомо нерезолвимый), батч получает строки из архивных байтов.
- Живая приёмка (критерий 1.2): пустая `rosstat_ipc_weeks_bulletins` → `make archive-restore STAT=rosstat_ipc_weeks_bulletins` → **6 106 точек, 71 неделя** без обращений к сети; spot-значения совпадают с протоколом PR #78 (Сметана 100,48; Картофель 103,0; агрегат 71 точка); `AfterImport` дошёл до витрины — `make mcp-check` ПРОВЕРКА ПРОЙДЕНА; повторный restore — идемпотентен (число строк не меняется).

## 4. Отступления от стандарта

Нет. Режим — свойство общего шаблона (одна точка на все шаблонные импортёры), CrawFunc-границы наследуются от шага 1.1 и названы в §2/§3.1.

## 6. Границы скоупа

- Не трогаем механики шага 1.1 (префлайт, ключи, self-heal) — кроме точки подключения restore.
- `archive-get`, листинг Яндекс.Диска, реконсиляция yandex — названы остатком пункта (роадмап).
- Одноразовый исследовательский сбор документов 2017–2019 (кладёт найденные версии в локальный архив и реестр) — **вне репозитория** (инструмент в игнорируемом `build/`), но именно он делает приёмочный сценарий «наполнение из архива» полноценным: восстановление работает и для версий, у которых живого источника уже нет.

## 7. Риски

1. **Расхождение ключей restore и будущих импортов** (отпечаток при живом импорте может отличаться от записанного в строке реестра) → срез резолвит **по URL**, а не по отпечатку; расхождение отпечатков влияет только на no-op-путь будущих живых прогонов (полный импорт — деградация, не ошибка).
2. **Смешение бэкендов** (реестр local против yandex) → листинг/restore работают с тем бэкендом, что задан `ARCHIVE_BACKEND`; приёмка — на локальном dev-хранилище, прод-хранилище в restore-пути не участвует.
3. **Дубли содержимого** (`sha-` и fingerprint-ключи) → реестр остаётся источником версий; restore выбирает самую свежую по `first_seen`; листинг называет дубль дублем.
