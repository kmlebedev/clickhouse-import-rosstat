# WGC ETF Flows: автоматизация сбора через JSON API fscdn — design

Дата: 2026-10-12. Пункт: `docs/GOLD_THESIS_DATA_ROADMAP.md`, «Фаза 3 — follow-up: WGC-импортёры» — новый follow-up
«WGC ETF Flows: автоматизация через JSON API fscdn».
Ветка: `feat/wgc-etf-flows-api`. Следующий пункт (не в этом PR): ежедневный прокси-ряд потоков по топ-4 US ETF (T+1).

Приёмка пункта: `make import STAT=wgc_etf_flows` пишет **5462** точки из API без ручного шага; потоки и AUM совпадают с
прежней xlsx-историей 1:1, а `holdings_tonnes` — до 0,01 т (округление самого источника, §3); невозможность API уводит
импорт на локальную выгрузку `wgc/data`; `make all` зелёный; `make mcp-check` — ПРОВЕРКА ПРОЙДЕНА.

## 1. Пробел

ETF-потоки WGC (20 рядов `etf_<метрика>_<регион>`, `source='wgc'`) наполняет импортёр `wgc_etf_flows` из локальной
выгрузки `ETF_Flows_*.xlsx` в `wgc/data`. Выгрузка скачивается **вручную браузером** (gold.org отдаёт боту `403`),
а джоба идёт по понедельникам — то есть помимо собственного лага публикации WGC (месячный отчёт, ~10-е число, 7–10 дней)
проект добавляет до недели ожидания. Итог: свежий месяц появляется в ClickHouse тогда, когда руки дошли, — а не тогда,
когда вышел отчёт.

При этом тот же ряд WGC отдаёт **машинно** — как JSON без ключа и без 403 (`403` у goldhub относится только к HTML
и скачиванию файлов). Ручной шаг не нужен.

## 2. Источник (проверено 2026-10-11 живыми запросами)

- `https://fscdn.gold.org/api/v11/charts/etfv2/revised/flows-chart2` — 242 КБ JSON
- `https://fscdn.gold.org/api/v11/charts/etfv2/revised/holdings-chart2` — 209 КБ JSON

Обе отдают `HTTP 200` обычному браузерному User-Agent, без ключа, `system.cached = false`,
`chartData.asOfDate = "2026-09-30"`. Параметр `?break-cache=11Oct26` (формат сайта goldhub) принимается — используется
против кэша CDN.

Структура:

- `flows-chart2` → `chartData.data.Monthly.series.{usd,tonnes}` — **список из 5 элементов**: `North America`, `Europe`,
  `Asia`, `Other` и **`Gold Price (rhs)`** (цена, а не регион). Элемент = `{name, data: [[ms, value], …]}`, у каждого
  ровно 284 точки (2003-02-28 … 2026-09-30). `usd` — **абсолютные доллары**.
- `holdings-chart2` → `chartData.data.Monthly.{tonnes,usd}` — `{columns: ["Date","North America","Europe","Asia","Other","Gold, US$/oz"], set: [[ms, …], …]}`,
  284 строки. `usd` — абсолютные доллары. **Отсутствие данных — `null`** (в потоках вместо этого явный `0`).

## 3. Правила пересчёта и совпадение с xlsx

| ряд | источник | преобразование |
|---|---|---|
| `etf_flow_usd_mln_*` | `flows.Monthly.series.usd` | ÷ 1e6 |
| `etf_flow_tonnes_*` | `flows.Monthly.series.tonnes` | как есть |
| `etf_holdings_tonnes_*` | `holdings.Monthly.tonnes` | как есть, `null` → точки нет. **Источник отдаёт тоннажные стоки округлёнными до 0,01 т** |
| `etf_aum_usd_bn_*` | `holdings.Monthly.usd` | ÷ 1e9, `null` → точки нет |
| `etf_*_world` | четыре региона | сумма 4 регионов, только если есть все 4 (существующие хелперы) |

`world` в JSON **нет** — как и в xlsx, он считается суммой четырёх регионов.

Совпадение с текущей xlsx-историей: потоки и AUM — **1:1 до 1e-9** (сверено 2026-10-11 через `v_gold_etf_flows` за
2026-08-31 и 2026-09-30): `asia` = `2255.40929756` млн $ / `16.18610771` т / `75.594060865` млрд $;
`north_america` = `3961.93761905` / `27.72232162` / `284.088446499`; `etf_flow_tonnes_world` 2026-09-30 = `67.28075855`.

А вот `holdings_tonnes` совпадает только **до 0,01 т**: тоннажные стоки в `holdings-chart2` приходят округлёнными до
второго знака (проверено 2026-10-12: из 1076 значений колонки `tonnes` ни одно не имеет больше двух знаков после запятой,
тогда как в потоках — до восьми). Значения источника: Asia `541.88`, North America `2115.88`, Europe `1521.36`,
Other `76.54`, сумма `4255.66` — против xlsx-точек `541.88460453` / `2115.88373719` / `1521.36429276` / `76.53717906` /
`4255.66981354` (то есть «record 4 256 t» публикации WGC). Расхождение ≤ 0,01 т на регион и не более 0,01 т на мир.

**Решение (принято владельцем решения контура):** принимаем округление источника как есть — тонажный сток это уровень,
и 0,01 т на 500–4255 т (≤ 2·10⁻³ %) ниже любой аналитической потребности; поток (сигнал ETF-цикла) и AUM приходят полной
точности. Цена решения: ручная выгрузка в фолбэке даёт полную точность, поэтому при переключении транспорта значение
одного и того же месяца может колебаться в пределах 0,01 т. Округление описывается в каталоге рядов (правило 11),
чтобы агент не считал расхождение с прежней историей дефектом импорта.

## 4. Расширение истории (решение владельца: дополнять как в API)

В потоках нули **явные**, а в xlsx соответствующая ячейка была пуста, поэтому импорт из API добавляет месяцы, которых
в `macro_series` сейчас нет:

- потоки регионов — 284 точки у каждого (сейчас `asia` 235, `europe` 274, `north_america` 283, `other` 283);
- `world`-потоки — 284 точки с 2003-02-28 (сейчас 235, с 2007-03-31). В месяцах до 2007-03 `world` = NA + EU + Other:
  азиатских фондов ещё не было — их **запасы `null`**, а `Asia`-поток приходит явным `0`;
- стоки и AUM — глубина **не меняется**: `world` 235 месяцев с 2007-03-31 (Азия в holdings `null` до 2007-03);
  регионы NA 284, EU 274, Asia 235, Other 283.

Значения в пересечении диапазонов не меняются, кроме `holdings_tonnes` (округление источника из §3) — история только
дополняется. Расхождение глубины потоков и стоков — не дефект, а свойство источника; оно описывается в каталоге (правило 11).

## 5. Дизайн кода

### 5.1 `util.GetJSON(url string, out any) error` (`util/json.go`)

`util.GetFile` ротует User-Agent, но **не смотрит HTTP-статус**: тело `403` вернулось бы «успехом» и всплыло как
`invalid character '<'`. `GetJSON` повторяет стиль `GetCSV` (`http.NewRequest`, `User-Agent: randomUA`, `HttpClient.Do`),
но проверяет статус: не-200 → ошибка вида `http status %d: <фрагмент тела ≤512 байт>`. URL в текст ошибки **не
подставляется** — хелпер общий, и у будущих вызывающих ключ может быть в URL (урок `eia`); контекст (имя эндпоинта)
добавляет вызывающий. Пустое тело — ошибка (как в `GetFile`).

### 5.2 `wgc/etf_api.go` — разбор JSON в точки

- `etfAPIBaseURL = "https://fscdn.gold.org/api/v11/charts/etfv2/revised/"`, пути `etfAPIFlowsPath = "flows-chart2"`,
  `etfAPIHoldingsPath = "holdings-chart2"`, `break-cache` = дата в формате `02Jan06`.
- `etfAPIScale` (`flow_usd_mln: 1e6`, `aum_usd_bn: 1e9`; тоннажные метрики — без делителя).
- `etfPointsFromAPI(baseURL string, now time.Time) ([]seriesPoint, error)` — база и часы параметрами (в `Import` — константа
  и `time.Now()`, в тестах — `httptest`-сервер и фиксированное время).
- Регион распознаётся существующим словарём `etfRegionsByName`. В списке рядов потоков всегда есть пятый элемент —
  ценовой ряд `Gold Price (rhs)`: он пропускается **по имени** (известный ожидаемый элемент, не регион). Любое другое имя
  вне словаря — **ошибка**, не молчаливый пропуск (симметрия с xlsx-парсером, где регион вне словаря тоже ошибка):
  иначе в `macro_series` появился бы ряд вида `etf_flow_tonnes_gold price (rhs)`.
- `null` в `holdings` → точки нет (не 0). Дата: `monthEnd(time.UnixMilli(ms))`.
- `world` и регионы — существующими `appendRegionPoints` / `allEtfRegionsPresent` / `etfWorldValue`; новой логики мира нет.
- Ноль точек или пустой ответ — ошибка (fail-fast, урок `eia`): тихий `Imported 0 rows` оставил бы dagu зелёным, а ряды —
  без обновления. В лог — `asOfDate` и число точек.

### 5.3 `wgc/etf.go` — API канонический, файл — фолбэк

- `etfFlowsStat` получает поле `apiBase string` с тем же смыслом, что `dir`: пустое → `etfAPIBaseURL`. Это шов для тестов
  без подмены пакетных переменных.
- `etfPointsFromFile(dir string) ([]seriesPoint, error)` — текущий разбор выгрузки; файла нет → sentinel `errNoEtfFile`
  (вызывающий превращает его в warn + 0 строк, как сейчас).
- `writeEtfPoints(ctx, conn, points)` — единый путь записи: сортировка, DDL, `PrepareBatch` → `Append` → `Send`, каталог.
- `Import`: (1) `etfPointsFromAPI` → запись; (2) ошибка API → `log.Warnf` с причиной + `etfPointsFromFile` → запись.
  **Транспорты не смешиваются в одном прогоне.**
- Guard устаревшего ответа CDN: `etfStoredMaxDate(ctx, conn)` → `max(date)` по `macro_series FINAL` (`source='wgc'`,
  ряды `etf_*`); если максимум из API меньше сохранённого — `log.Warnf`. **Не ошибка**: перезапись тех же значений
  идемпотентна, а ложный отказ оставил бы ряды без обновления.

### 5.4 Правило 11 (MCP-агент обязан понимать ряды)

- `wgc/series_meta.go`: `origin` — API (`fscdn.gold.org`, `flows-chart2` / `holdings-chart2`), фолбэк — файл `ETF_Flows_*.xlsx`;
  `etfCatalogImportNote` — канонический канал автоматический; `etfCatalogWorldSince` **разделяется по метрикам**
  (потоки — с 2003-02 и почему; стоки/AUM — с 2007-03).
- `wgc/series_meta_test.go`: тест пинит «origin называет лист выгрузки» и «описание `_world` содержит 2007-03» —
  оба утверждения обновляются: origin обязан называть эндпоинт метрики, `_world` потоков — `2003-02`, стоков — `2007-03`.
- `views/gold_etf_flows.go` (`Comment`): транспорт и глубина; логика приоритета `wgc > webbridge > manual` не меняется.
- `sql/wgc_etf_flows_catalog.sql` — **не меняется**: описывает `source='webbridge'` (сессионный фолбэк) и остаётся верным.

### 5.5 Расписание

`dagu/wgc.yaml`: `17 20 * * 1` → `17 20 * * *`. Ручного шага больше нет, и недельный интервал теряет смысл: ежедневный
прогон ловит публикацию в день выхода (проектный лаг → почти нулевой; собственный лаг публикации WGC 7–10 дней остаётся).
Шаг по-прежнему за 6 минут до `dagu/forecast.yaml` (20:23). Выгрузки ЦБ остаются ручными.

## 6. Приёмка

1. `make import STAT=wgc_etf_flows` → `Imported 5462 rows`; повторный прогон — идемпотентен; в логе `asOfDate = 2026-09-30`.
2. `v_gold_etf_flows` за 2026-08-31 / 2026-09-30 — потоки и AUM как в §3 (до 1e-9), `holdings_tonnes` — до 0,01 т:
   `asia` `541.88`, `world` `4255.66` (округление источника, а не xlsx-точки `541.88460453` и `4255.66981354`).
3. Глубина: регионы потоков 284 точки с 2003-02-28, `world`-поток 284 с 2003-02-28, `world`-стоки/AUM 235 с 2007-03-31.
4. Фолбэк: тест «API 500 → импорт из `wgc/data`» зелёный (живая проверка фолбэка — только тестом: подменять URL в проде нельзя).
5. `make all` — зелёный; `make mcp-check` — ПРОВЕРКА ПРОЙДЕНА (34 ряда `wgc`, витрина читается; правок скрипта не нужно).
6. `ARCHITECTURE.md` / `README.md` / роадмап синхронизированы.

## 7. Отклонённые варианты (зафиксировано, чтобы не возвращаться)

- **Прямой парсинг котировок через брокера Finam/Transaq (идея «свой парсер топ-5 ETF»).** Брокерские и биржевые данные —
  цена, сделки, стакан; **`Shares Outstanding` / AUM / тонн в них нет** ни в Transaq, ни в hosted Finam Trade API
  (в схеме `/v1/assets` таких полей нет). Без Δshares или Δtonnes чистый поток не считается: creation/redemption публикует
  эмитент, а не биржа. Плюс покрытие: `transaq-clickhouse-exporter` работает по бордам MOEX (`TQBR`/`TQCB`/`FUT`) — US-листингов
  там нет вовсе; на finam.ru из золотых ETF есть только `GLD` и `IAU` (борда `BATSNS`), `GLDM`/`IAUM`/`SGOL` и европейские — нет.
- **Некоммерческие агрегаторы (`etf.com`, `etfdb.com`, `stockanalysis.com`, Yahoo, stooq).** `etf.com`/`etfdb.com` → `403`
  боту; `stockanalysis.com` — данных в HTML нет, публичного JSON нет; Yahoo `quoteSummary` → `429` с этой сети (уже
  зафиксировано в ARCHITECTURE §6.1 по `lbma_gold`); stooq → JS proof-of-work challenge вместо CSV; SEC N-PORT → квартально,
  лаг 50–60 дней.
- **Ежедневный прокси по эмитентам как замена мировой величины** (для этого пункта). Эмитенты дают T+1
  (SPDR `api.spdrgoldshares.com/api/v1/historical-archive` → XLSX с `Tonnes of Gold`; BlackRock `varnish-api` → JSON `tonnes`),
  но топ-4 US ETF = 1810 т из 4255,67 т (**42,5 % мира**) — это прокси, а не мировой итог. Идёт следующим пунктом
  честным частичным рядом с пометкой покрытия.
- **Недельные региональные ряды WGC** (доступны в тех же эндпоинтах). Последняя weekly-точка на 11.10.2026 — 2026-09-25:
  лаг ~16 дней, то есть по свежести **хуже** месячного отчёта. Не берём.

## 8. Вне объёма

Ежедневный прокси-ряд по топ-4 US ETF (следующий пункт роадмапа); расширение покрытия на Европу
(iShares EU `SGLN`, Xetra-Gold `4GLD`, Invesco `SGLD` — ~60 % мира); `SGOL` (машинного ежедневного эндпоинта нет);
недельные региональные ряды; выгрузки резервов ЦБ (`wgc_cb_reserves`) — остаются ручными, машинного эквивалента нет.
