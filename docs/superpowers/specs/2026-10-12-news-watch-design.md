# news_watch — design

Дата: 2026-10-12. Пункт: `docs/GOLD_THESIS_DATA_ROADMAP.md` §2, «Фаза 4 — РФ-канал и контекст
(по мере надобности)», шаг «сбор».

## Пробел

`news_events` в коде нет: решения и сделки (кабмин/ЦБ/санкции) не покрыты ни рядом, ни календарём —
единственный класс входов статьи §6 без следа в БД. Пример: ключевой триггер квартала — истечение
запрета РФ на экспорт дизеля (01.11; п. 3 дашборда §6); внеплановые события (сюжет о поставках
российского дизтоплива на мировой рынок — разрешено лицензией Минфина США до 07.04.2027; в лентах
фоном 12.10) не оставляют в контуре ничего.

## Цель и объём

Импортёр `news_watch` (пакет `news/`, `Name()` = `news_watch`): 5 RSS-лент РФ-канала → `news_events`
(`sentiment` пока всегда NULL), витрина `v_news_events` для агента, расписание dagu каждые
30 минут, три режима работы. Критерий приёмки пункта: «тезис „геополитика работает через
нефть/ставку“ имеет событийный след в БД».

**Вне объёма** (зафиксировано follow-up 1–4 в роадмапе): канал записи от сессии
(`POST /v1/news_events` + заполнение `sentiment`), `v_gold_attribution` (GRAM), `regime_states`
(HMM), расширение источников (первичка кабмина `government.ru`/`pravo.gov.ru` — с этой сети
недоступны, IR Полюса, Коммерсант, Минфин).

## Источники (живые пробы 2026-10-12, все 200)

| `source` | Лента | Окно позиций |
|---|---|---|
| `interfax` | `https://www.interfax.ru/rss` | 25 |
| `rbc` | `https://rssexport.rbc.ru/rbcnews/news/30/full.rss` | 30 |
| `cbr` | `https://www.cbr.ru/rss/RssNews` | 100 |
| `cbr` | `https://www.cbr.ru/rss/eventrss` | 100 |
| `tass` | `https://tass.ru/rss/v2.xml` | 100 |

Оба фида ЦБ пишутся под одним `source = 'cbr'`, различаются `url`. Дата публикации у всех пяти
лент — RFC1123 с офсетом `+0300` («Mon, 12 Oct 2026 13:43:00 +0300»). Окна лент конечные:
история копится **с первого прогона** (в комментарии витрины это фиксируется).

## Три режима (env `NEWS_WATCH_MODE`; пусто → `all`; неизвестное значение → ошибка до сети)

### `all` — «получить всё» (ручной полный прогон / пересборка)

Все 5 лент, в одной транзакции батча пишутся **все** позиции текущего окна (upsert; повторный
прогон идемпотентен — ключ `(date, source, title)`). В расписании не используется: 30-минутный
dag — это `since` (только отсутствующие). Ручной полный прогон полезен как пересборка — записать
окно заново, не дожидаясь, пока `since` увидит его позиции новыми.

### `since` — «только отсутствующие» (этим режимом работает dagu)

Пишутся только те позиции окна, которых ещё нет в `news_events` — по ключу
`(date, source, title)`. Существующие ключи читаются из `news_events FINAL` по источнику и с
нижней границей окна (`SELECT date, title … WHERE source = ? AND date >= ?`). Ничего нового →
`0 строк` и спокойный лог (семантика no-op, как у `bold_*`).

Решение — о **наличии позиции**, а не о её дате: дата-курсор (`max(date)`) молча терял бы
опоздавшие позиции — RSS не обязан быть упорядочен по времени, а у ЦБ под одним `source = 'cbr'`
лежат ДВА фида (`RssNews` и `eventrss`) с независимыми фронтами, и пресс-релиз с датой раньше
фронта новостного фида не записался бы никогда. Окно лент при этом вычитывается целиком: у RSS
нет «since»-параметра, лента — это всегда последние N позиций; меняется только состав записи.

### `check` — «дыры/окна» (без записи)

По каждой ленте сверяются границы ленты (min/max/кол-во) с сохранённым покрытием
(`min/max/count` по `source` из `news_events FINAL`):

- **дыра** = `min(лента) > max(сохранённое)` — окно между ними ротация ленты уже съела
  (пропущенный прогон); печатается диапазон дыры `[max(сохранённое) … min(лента))` и
  возвращается ошибка (громко, не молчаливое старение);
- иначе — сводка покрытия по источнику (`сохранено N, min…max; в ленте M, min…max`);
- сохранённых строк по источнику нет → «первый прогон не выполнялся», не дыра.

Свойство метода (документируется): дыру видно только пока сохранённый максимум источника
не перешагнул её — после следующего успешного `all` она уже «залечена» новыми окнами. Диагностика
ручная (runbook в README), автопрогон не ставится.

Во всех режимах сначала идемпотентно исполняется DDL таблицы (`CREATE TABLE IF NOT EXISTS`);
витрина в пишущих режимах (`all`, `since`) создаётся/пересоздаётся в начале прогона — до чтения
лент (как у `eia`), поэтому публикуется и в ветке no-op; режим `check` витрину не трогает.

## Транспорт и разбор

- **`util.GetXML(url string, out any) error`** — зеркало `util.GetJSON` (`util/json.go`):
  общий `util.HttpClient`, проверка HTTP-статуса (`http status %d: <фрагмент тела ≤512 б>` через
  существующий `errorSnippet`), пустое тело — ошибка, дедлайн запроса 60 с переменной
  `xmlTimeout` (подмена в тестах). `util.GetFile` не годится: статус не проверяет.
  Разбор — `xml.Decoder` с `decoder.Entity = xml.HTMLEntity` (ленты встречаются с `&nbsp;`,
  и одна такая сущность не должна обнулять ленту целиком).
- **Разбор RSS 2.0** (`encoding/xml`): `item → {date, source, title, url}`; дата — `time.RFC1123Z`.
  Позиция без даты или заголовка — пропуск со счётчиком (печатается в итоговой строке импорта,
  как `values outside period columns` у `polyus`). URL позиции не обязателен (пустой url
  сохраняется как есть). `description` не хранится — канонический DDL §6.2 его не содержит.
- **Изоляция лент:** сбой одной ленты (транспорт/разбор/0 позиций — признак ретайра URL)
  не блокирует остальные: успешные ленты пишутся, по итогам возвращается агрегированная ошибка
  (DAG краснеет → retry 3 × 300 с; повтор идемпотентен). Ноль позиций у ленты — ошибка ленты,
  а не «пустой успешный» прогон (урок eia: ретайр кода/ленты ловится громко).
- URL-ы лент — пакетные переменные (`feedInterfaxURL` и т. п.), список лент собирается функцией
  из них; тесты подменяют их на `httptest.Server` (конвенция проекта).

## Схема и витрина

- `news_events` — канонический DDL из ARCHITECTURE.md §6.2 (копия в `news/schema.go` обязана
  совпадать, как у `gold_prices`/`gold_forecasts`):

```sql
CREATE TABLE IF NOT EXISTS news_events (
    date DateTime,
    source LowCardinality(String),
    title String,
    url String,
    sentiment Nullable(Float32)      -- -1..1, заполняет LLM-сессия (follow-up 1)
) ENGINE = ReplacingMergeTree ORDER BY (date, source, title);
```

- `v_news_events` — создаётся импортёром (образец — `eia/eia.go`: `CREATE OR REPLACE VIEW …
  DEFINER = default SQL SECURITY DEFINER` + `ALTER TABLE … MODIFY COMMENT` / `COMMENT COLUMN`):

```sql
SELECT
    date,
    toDate(date, 'Europe/Moscow') AS date_msk,   -- день по МСК для группировок
    source, title, url, sentiment
FROM news_events FINAL
WHERE match(title, <фильтр>)                     -- см. ниже
ORDER BY date DESC
```

- **Фильтр витрины** — широкая эвристика по стемам тезисов (RE2, регистронезависимо; строка —
  константа Go, из неё собирается SQL витрины, тест пиннит список):

```text
(?i)дизел|бензин|керосин|дистиллят|нефтепродукт|топлив|НПЗ|переработк|нефт|Brent|ОПЕК|Ормуз|Иран|
санкц|поставк|эмбарго|сделк|Трамп|перемири|пошлин|ставк|ФРС|Федрезерв|инфляц|дефляц|CPI|PPI|ИПЦ|
золот|драгметалл|XAU|ETF|резерв|Банк России|ЦБ|Минфин|бюджет|НДПИ|налог|отсечк|Полюс|Сухой Лог|PLZL
```

  В коде — одна строка; переносы здесь только для читаемости. Осознанно широкий: ложные пропуски дороже ложных срабатываний (напр. «доставка» на стем
  «ставк», «полюс» в географическом смысле); ложные срабатывания снимаются в запросе сессии,
  а список уточняется пересозданием витрины по всей истории — сырые данные хранятся полностью.
- Правило 11: (а) не применяется — новости не ряд `macro_series` (прецедент `bold_fund_snapshot`);
  (б) комментарии таблицы и каждой колонки — да; (в) `GRANT SELECT ON default.v_news_events
  TO kimi_reader` в `sql/mcp_kimi_reader.sql`, сырая `news_events` агенту не выдаётся;
  (г) проверки в `scripts/mcp_check.py` (витрина читается; `SELECT count() FROM news_events`
  под `kimi_reader` → ACCESS_DENIED); (д) ARCHITECTURE.md §2/§3/§5/§6.1/§6.2/§6.3/§7 и README.

## Расписание

`dagu/news.yaml`: один шаг `news_watch`, `schedule: "7,37 * * * *"` (каждые 30 минут; минуты
разнесены, как у остальных DAG), `overlap_policy: skip`, retry 3 × 300 с,
`env: NEWS_WATCH_MODE=since` — прогон пишет только отсутствующие позиции по ключу
`(date, source, title)` (окно лент всё равно читается целиком: у RSS нет «since»-параметра; см.
§`since`). Режим `all` остаётся для ручного полного прогона (пересборка). На staging
раскладывается вручную (как DAG фаз 2–4).

## Тесты (офлайн, без БД и сети)

- `util/xml_test.go`: успешный разбор; не-200 с фрагментом тела; пустое тело; битый XML;
  `&nbsp;` (HTMLEntity) не валит разбор.
- `news/parse_test.go`: фикстуры 5 лент (`news/testdata/*.rss`, реальные окна, обрезанные) —
  маппинг `{date, source, title, url}`, разбор даты `+0300`, счётчик пропусков (позиция без
  даты/заголовка), пустая лента → ошибка, битый XML → ошибка. Тест конфига: у каждой ленты
  есть фикстура, все позиции фикстур разбираются.
- `news/news_test.go`: логика режимов на чистом шве (без БД): `all` — все позиции; `since` —
  только отсутствующие по ключу `(date, source, title)` (включая опоздавшую позицию и два фида ЦБ
  под одним `source`); `check` — построение сводки и обнаружение дыры; изоляция лент (одна
  500 → позиции остальных + записанный сбой); неизвестный режим → ошибка. Композиция `Import()` —
  на фейковом соединении (без БД и сети): `check` не пишет строк и не публикует витрину, но
  объявляет дыру ошибкой; `all` пишет все позиции окна одним батчем в `news_events`; `since` пишет
  только отсутствующие ключи (кейс ЦБ: позиция «отставшего» фида с датой между фронтами
  записывается, позиция с уже сохранённым ключом — нет).

Шов тестируемости: выборка позиций по режиму и детекция дыр — чистые функции; сетевой слой
(`fetchFeeds`) тестируется через `httptest`; запись батчем проверяется офлайн на фейковом
соединении (состав и число строк), а на живой БД — приёмкой.

## Приёмка

1. `make all` зелёный (gofmt, golangci-lint, vet, `go test -race`, обе сборки).
2. `make import STAT=news_watch` (режим `all`): 5/5 лент в логе со счётчиками; повторный прогон
   идемпотентен.
3. `NEWS_WATCH_MODE=since make import STAT=news_watch` (штатный режим расписания) — пишутся
   только отсутствующие позиции; повтор команды без новых позиций в лентах → `0 строк` (no-op);
   `NEWS_WATCH_MODE=check make import STAT=news_watch` → сводка покрытия, дыр нет;
   `NEWS_WATCH_MODE=bogus …` → ошибка до сети.
4. MCP (`kimi_reader`): `v_news_events` читается; событийный след РФ-канала — запрос по
   `дизел|поставк|сделк|санкц` за последнюю неделю (фиксируем фактическое покрытие);
   `SELECT count() FROM news_events` → ACCESS_DENIED.
5. `make mcp-check` зелёный (добавлены проверки витрины и запрета сырой таблицы).
6. Статус фазы 4 в роадмапе обновлён (✅ шаг «сбор», приёмка; follow-up 1–4 остаются ⏳).

## Ограничения

- Фильтр витрины — эвристика (см. выше); полнота достигается тем, что сырая таблица хранит весь
  поток, а список меняется пересозданием витрины по всей истории.
- Дыра видна в `check` только до «залечивания» следующей успешной записью (свойство метода) —
  и только у той ленты, окно которой уже прошло мимо сохранённого максимума: пока максимум старше
  начала окна, дыра видна; после успешной записи окно сдвигается вперёд, и пропущенное больше не
  показывается.
- Лаг ленты: RSS отдаёт только текущее окно, и оно у лент разное — Интерфакс/РБК/TASS покрывают
  ~1–2 часа публикаций, фиды ЦБ — дни (`cbr_news` ≈12 дней, `cbr_press` ≈83 дня). Простой дольше
  окна ленты теряет её позиции безвозвратно (событийный след фиксируется из других источников).
- government.ru / pravo.gov.ru с этой сети недоступны (таймаут) — первичка кабмина отложена
  (follow-up 4), решения покрываются Интерфакс/РБК.
