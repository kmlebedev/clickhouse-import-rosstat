# Параллельные сессии Kimi Code на одном проекте — дизайн

**Дата:** 2026-10-14
**Ветка:** `chore/parallel-sessions`
**Статус:** спека (первый коммит ветки)

## Проблема

Над репозиторием одновременно работают две и больше сессий Kimi Code (Desktop и CLI). У всех — один рабочий каталог, один инстанс GoLand с одним MCP-эндпоинтом, один локальный ClickHouse, один стенд Grafana и один staging-хост. Ветку и коммит каждая сессия делает свою, и на этом совпадения не заканчиваются:

- рабочее дерево, `HEAD`, индекс и `build/` — общие: две сессии правят одни файлы, `git checkout` одной ломает контекст второй, `make all` одной падает на недописанном файле другой;
- DDL витрин исполняется **внутри** `Import()` (`util/clickhouse_import.go:118-123`, `util/views.go:23-51`) — `CREATE OR REPLACE VIEW` и `ALTER TABLE … MODIFY COMMENT` двух сессий на одной витрине пересекаются;
- `make ch-down` / `make grafana-down` одной сессии гасят стенд другой (`Makefile:118-129`);
- параллельный `make deploy-staging*` (ssh на один хост, systemd, фиксированные `/tmp`-имена) ломает staging;
- IDE-инструменты без `projectPath` возвращают проблемы и рефакторинги по чужому дереву;
- `.superpowers/sdd/<тема>/` при повторном прогоне темы перетирает брифы и `progress.md`.

## Цель

Довести параллельную работу до предсказуемой: сессии не мешают друг другу ни в git, ни в IDE, ни в БД; общие ресурсы берутся по очереди; правила зафиксированы в `AGENTS.md`, а гарантии — в git-хуке, lock-хелпере и структуре рабочих деревьев.

## Не-цели

- Изменения в импортёрах, DDL таблиц, витринах, `sql/mcp_kimi_reader.sql`.
- Изоляция стенда на сессию (свой ClickHouse/Grafana на каждое дерево) — отложено: общий стенд + лок закрывает тот же риск дешевле.
- Правки CI (`go.yml`), релизного процесса, dagu.
- Автоматизация запуска сессий и любая оркестрация агентов за пределами описанного протокола.

## Что уже есть (проверено 2026-10-14)

- `.worktrees/` существует и игнорируется (`.gitignore:11`); три живых дерева на `main_worktree`, `feat/mine-plans-seed`, `docs/tanker-freight-sources`. Соглашения «кто и как создаёт дерево» нет: планы и SDD-леджеры решают это по-разному.
- Сессии Kimi хранятся по ключу рабочего каталога (`~/.kimi-code/sessions/<workDirKey>/`, `~/.kimi-code/workspaces.json`) — **разные деревья = разные наборы сессий**.
- `jetbrains` MCP объявлен только в user-level `~/.kimi-code/mcp.json` (`http://127.0.0.1:64422/stream`), инструмент принимает `projectPath`; `clickhouse` MCP — в проектном `.kimi-code/mcp.json` (порт `8123`).
- Хуков Kimi нет (`~/.kimi-code/config.toml` без `[[hooks]]`), git-хуков нет (`core.hooksPath` не задан, `.githooks/` отсутствует).
- Переменные стенда в `Makefile` уже параметризованы (`CH_DIR`, `CH_HTTP_PORT`, `CH_TCP_PORT`, `GF_DIR`, `GF_PORT` — `Makefile:10,14,15,25,26`).
- Lock-утилит под macOS нет (`flock` отсутствует); есть атомарный `mkdir`.

## Решение

Четыре слоя, каждый закрывает свой класс конфликтов.

### 1. Разделение дерева — git worktree

Одна сессия = один worktree = одна ветка = один пункт роадмапа. `git worktree` не даёт двум деревьям встать на одну ветку и держит отдельные `HEAD`/индекс/`build/`. Хелперы: `make wt-new NAME=<slug> [TYPE=feat] [BASE=main]`, `make wt-list`, `make wt-rm NAME=<slug> [FORCE=1]`, `make session-info`.

### 2. Общие ресурсы — lock-хелпер

`scripts/lock.sh <key> -- <команда>` на атомарном `mkdir`; ключи: `db` (локальный ClickHouse), `stand` (ClickHouse-сервер, Grafana, ingest `:8081`), `staging` (ssh/деплой). Лок-каталог — **вне репозитория** (`$HOME/.rosstat-locks`, переопределяется `ROSSTAT_LOCK_DIR`), иначе каждое дерево получило бы свой лок и защита исчезла бы. Внутри лока — `owner` (инструмент, slug дерева, pid, host, время, cwd): второй агент видит, кто держит, и не гасит чужое. Занятый лок ждёт `WAIT` секунд (по умолчанию 900), `WAIT=0` — падает сразу. Stale-lock (pid мёртв или возраст больше `STALE`) перехватывается с предупреждением. Reentrancy — через `ROSSTAT_LOCK_HELD_<key>`: вложенный `make` внутри уже взятого лока не блокируется.

### 3. Git-хук — ветка

`.githooks/pre-commit` отказывает в коммите на защищённых ветках (`main`, `master`, `main_worktree`) и при detached `HEAD`, сообщая, что делать (`make wt-new`). Ставится `make hooks-install` → `git config core.hooksPath .githooks` (значение живёт в `.git/config`, поэтому действует сразу во всех worktree; глобальный конфиг не трогаем). Хук fail-closed для коммита — это единственное место, где нужна жёсткая гарантия.

### 4. Личная страховка — хуки Kimi (в репозиторий не коммитится)

`[[hooks]]` читаются только из user-level `~/.kimi-code/config.toml` (project-level конфига у CLI нет), поэтому в репозитории лежит скрипт `scripts/agent-guard.sh`, а владелец подключает его одной записью у себя. Скрипт читает JSON события из stdin и блокирует (`exit 2`) гасящие и разрушительные команды. Хуки fail-open — это страховка от случайности, а не барьер; барьеры — в git-хуке и локе.

### 5. Протокол в `AGENTS.md`

Раздел «Параллельные сессии» фиксирует шесть правил (дерево, ветка, лок, `projectPath`, один писатель на артефакт, сборка в своём дереве) и ссылается на `docs/PARALLEL_SESSIONS.md`. Правило должно попасть в `main`, иначе сессия в чужом дереве прочитает свой снимок файла.

## Ограничения и риски

- Один инстанс GoLand на оба дерева: порт MCP может смениться при перезапуске IDE; второй открытый проект удваивает индекс; без `projectPath` тихо приходят результаты по чужому дереву — поэтому правило 4 обязательное.
- Хуки Kimi fail-open и user-level: не строить на них гарантий.
- Общий ClickHouse остаётся точкой сериализации: два тяжёлых импорта идут по очереди (цена надёжности).
- dagu на staging со `schedule` не координируется с ручным прогоном того же стата — двойные вставки схлопнет ReplacingMergeTree, но нагрузка лишняя.
- `make ch-up`/`ch-down` под локом `stand`: сессия, поднявшая стенд, владеет им; гашение — только по явной просьбе пользователя.

## Приёмка

1. `make wt-new NAME=probe-a` и `NAME=probe-b` → два дерева с разными ветками в `git worktree list`; `git checkout` ветки соседа во втором дереве падает (гарантия git).
2. `make test-parallel` — самотесты lock-хелпера (взаимное исключение, ожидание, stale-takeover, reentrancy) и worktree-хелпера в одноразовом клоне; зелёные.
3. `make all` зелёный в рабочем дереве.
4. `make hooks-install` + коммит на `main` → отказ с понятным сообщением; коммит в своей ветке проходит.
5. Два одновременных `make import STAT=<разные>`: второй в логе называет владельца лока и ждёт, оба завершаются, данные в ClickHouse корректны.
6. `make ch-down` под чужим локом `stand` не проходит.
7. IDE: `get_file_problems` с `projectPath` своего дерева отдаёт проблемы своего файла.
8. README.md и ARCHITECTURE.md синхронизированы с новыми целями и файлами; пункт отмечен в `docs/ROADMAP_DCF_POLYUS.md`.
