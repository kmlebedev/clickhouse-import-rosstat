## 1. Зачем

Таблица `cbr_mt_forecast` — «эталон ЦБ» контура ключевой ставки: диапазоны среднегодовой ставки и прогноза инфляции, винтажно по выпускам. С 2026-10-17 в ней лежат **2 выпуска** (07.05.2026 и 05.08.2026) — те, у которых есть машиночитаемый xlsx. Остальные **9 PDF-комментариев** 2024-02 … 2026-02 импортёр пропускает со счётчиком, а **11 PDF «Среднесрочный прогноз»** (по одному на каждое опорное заседание) не читаются вовсе. Итог: история винтажей обрывается на мае 2026, и PIT-бэктест прогноза ЦБ до этой даты невозможен.

Пункт §4.2 №19 требует закрыть оба пробела **отдельным пунктом** (PDF-парсер — не хвост xlsx-импортёра). После работы:

- 22 винтажа, 1216 точек: 11 комментариев (9 PDF + 2 xlsx) и 11 прогнозов;
- у каждого заседания появляется **самая ранняя** точка PIT — PDF «Среднесрочный прогноз» публикуется в день заседания, комментарий — через 11–17 дней;
- схема таблицы, витрина, каталог и расписание не меняются.

## 3. Решения по дизайну

### 3.1 Импортёр, таблица, схема — без изменений

Расширяется существующий импортёр `cbr_mt_forecast` (`cbr/mt_forecast.go`):

- `Name()` = `TableName` = `cbr_mt_forecast`, запись реестра и шаг `dagu/cbr.yaml` не меняются (стандарт §7.2, §8);
- DDL, ключ `(indicator, year, release_date)`, витрина `v_cbr_mt_forecast`, каталог 16 рядов и грант `kimi_reader` не меняются;
- новый импортёр, таблица или `Name()` не заводятся: источник тот же индекс, артефакт — тот же набор выпусков, дельту уже считает гейт по `release_date` (стандарт §9.3, прецедент `cbr_dip_bulletin`).

`mtForecastRelease` получает вид выпуска:

```go
type mtForecastKind string
const (
    mtForecastKindComment  mtForecastKind = "comment"
    mtForecastKindForecast mtForecastKind = "forecast"
)
type mtForecastRelease struct {
    MeetingDate time.Time
    ReleaseDate time.Time
    URL         string
    Kind        mtForecastKind
    PDF         bool // артефакт — PDF (нет xlsx-страницы)
}
```

`release_date` документируется как **дата публикации артефакта** (комментария или прогноза); у прогноза она равна дате заседания. Комментарии витрины (`release_date`, `url`, текст таблицы) обновляются тем же PR.

### 3.2 Оба корпуса, один цикл импорта

Решение владельца (2026-10-19): импортируются оба корпуса. В цикле `Import` выпуск идёт одной из двух веток:

- **страница + xlsx** (как сейчас): `local.DataUrl = cbrUrl + href`, `local.ImportFunc = mtForecastAppendPoints(release)`;
- **PDF**: `local.DataUrl = release.URL`, `local.BodyFunc = mtForecastPDFAppendPoints(ctx, release)`.

Обе ветки проходят один и тот же шаблон `util.ClickHouseImport`: DDL → префлайт → байты/книга → точки → архив версии → `source_publications`. Для PDF это принципиально: шаблон сам качает байты и кладёт **тот же срез** в винтажный архив (стандарт §9.6), поэтому версия каждого PDF видна в `registry.jsonl` и в `source_publications`.

### 3.3 Транспорт PDF — `pdftotext` (Poppler)

Извлечение текста — внешняя утилита `pdftotext` с ключами `-layout -enc UTF-8 -nopgbrk`, stdin — байты PDF, stdout — текст:

```
pdftotext -layout -enc UTF-8 -nopgbrk - -
```

Обоснование:

- `polyus/` уже использует `pdftotext` (`polyus/source.go`), и [исследование 2026-10-10](../../research/2026-10-10-pdf-extractors-go.md) признало его эталоном: строго лучшей чистой Go-замены нет, главный выигрыш нативной библиотеки — «CI без poppler»;
- `-layout` для нашей таблицы достаточен: прототип разобрал все 20 PDF без координатной модели (проверено 2026-10-19);
- тесты офлайн: парсер работает по тексту, `pdftotext` в тестах не вызывается (как у `polyus`), поэтому CI без poppler остаётся зелёным.

**Отступление от стандарта §4 (названо по §1.5):** таблица транспорта нормирует HTTP-хелперы `util` и не содержит PDF; извлечение текста внешней утилитой — новое взаимодействие. Оно вынесено в один файл `cbr/mt_forecast_pdf.go`, сеть по-прежнему идёт через `util.GetFileBytes` (шаблон), а `exec` — только для локального преобразования уже скачанных байтов. Стандарт §4 в этом PR не меняется: PDF-транспорт остаётся названным отступлением.

**Runtime-зависимость:** `poppler-utils` (`pdftotext`) на хосте, где идёт импорт. Она уже нужна `polyus_financial_metrics`; в README и `deploy/staging/README.md` добавляется явный prerequisite. No-op-прогоны бинарник не вызывают: `pdftotext` запускается только при импорте нового PDF-выпуска.

**Ошибки:** нет `%PDF-` в первых 1024 байтах (WAF/HTML-заглушка) — ошибка до `exec`; `pdftotext` отсутствует/упал — ошибка с именем утилиты, выпуска и подсказкой `poppler-utils`; пустой stdout — ошибка. Таймаут — 2 минуты на файл (PDF ≤ 1 МБ, фактически ~0,1 с).

### 3.4 Индекс: два типа карточек

`mtForecastIndexReleases` читает обе карточки в одном проходе (структура карточек и селекторы даты/титула — общие, `mpSummaryCardSel`/`mpSummaryNameSel`/`mpSummaryDateSel`):

- титул «Комментарий к среднесрочному прогнозу Банка России» + href с `comment_`;
- титул «Среднесрочный прогноз Банка России» + href с `forecast_`.

Дата заседания — из шапки ближайшего `div.dropdown` (`Заседание Совета директоров от DD.MM.YYYY`) для **обоих** типов (сейчас PDF-комментарии возвращаются без неё — это меняется). Дата публикации — из карточки; для страницы комментария дополнительно сверяется со слагом `comment_<ДДММГГГГ>/` (как сейчас; расхождение — ошибка).

Правила fail-fast меняются:

- **было:** «ни одной страничной карточки — ошибка» (PDF нечем импортировать);
- **стало:** «ни одной карточки комментария — ошибка» (источник сломан или подменён); отсутствие forecast-карточек — `warn` (комментарии импортируются, пробел виден в логе и счётчиках).

Счётчики для no-op-сообщения: `комментариев N (страниц A, PDF B), прогнозов M, в таблице K выпусков`.

### 3.5 Разбор «Табл. 1» из текста

Чистая функция `mtForecastParsePDF(text []byte) ([]mtForecastPoint, error)`; сеть и `exec` — снаружи (стандарт §6.1). Алгоритм:

1. **Нормализация строки:** удалить soft hyphen `U+00AD`; заменить пробелы-двойники (`U+00A0`, `U+2002`, `U+2009`, `U+200A`, `U+202F`, `\t`, `\f`) пробелом; склеить разрезанные диапазоны: `([\d)])\s+[–—]\s+(\(?-?\d)` → `$1–$2` (RE2 не поддерживает lookbehind, поэтому захват соседних символов; в таблице это только диапазоны).
2. **Якорь:** первая строка, которая после удаления soft hyphen содержит `ОСНОВНЫЕ ПАРАМЕТРЫ ПРОГНОЗА БАНКА РОССИИ` (регистронезависимо; в комментарии — капсом, в прогнозе — с заглавной). Якорь один на документ (проверено на 20 PDF), поэтому поиск по всем страницам безопасен.
3. **Шапка годов:** первая строка после якоря, в которой после разбиения по `\s{2,}` не менее 2 токенов-годов (`mtForecastYear`: целое 1900–2100). Факт-год стоит отдельной строкой выше и в прогнозные годы не попадает. Годы обязаны возрастать и не повторяться; число годов — 3–4 (источник), но жёсткого потолка нет.
4. **Строки таблицы:** до строки `Источник: Банк России` или строки-сноски (`^\d+\s` или `^[¹²³⁴⁵⁶⁷⁸⁹]\s`). Строка разбивается по `\s{2,}`: первый токен — подпись, остальные — значения.
5. **Подпись** нормализуется общей `mtForecastNormalizeLabel` (в неё добавляются снятие надстрочных цифр и хвостового двоеточия — см. §3.6) и ищется в реестре 16 показателей (`mtForecastIndicatorByLabel`).
6. **Значения:** ожидается ровно `1 + len(years)` токенов: первый — факт-колонка (не импортируется, как и в xlsx), остальные — прогнозные годы по возрастанию. Каждый проходит `mtForecastBounds` (точка/диапазон, скобочные отрицательные, приклеенная сноска, `lo <= hi`).
7. **Контракт полноты** — как у xlsx: неизвестная подпись — `warn` и продолжение (стандарт §6.6); пропажа core-показателя — ошибка; пропажа не-core — `warn`; число значений ≠ `1 + годы` — ошибка; ноль точек — ошибка.

Проверка на корпусе: 16/16 строк и ожидаемое число точек в каждом из 20 файлов; spot-значения `key_rate_avg` зашиты в тест (см. план §1). Известные ловушки: `ПРОГ­НОЗА` с soft hyphen, `13,5 – 14,5¹` (диапазон в трёх «колонках»), `(-0,5) – 0,5`, `19,2¹`, `15,51` (= 15,5 + сноска), `– к населению, в том числе:` с двоеточием.

### 3.6 Нормализация подписи

`mtForecastNormalizeLabel` расширяется: перед срезанием хвостовых цифр снимаются надстрочные `¹²³` (существующая `mtForecastStripSuperscripts`), после — хвостовое двоеточие. Для xlsx это no-op (там обычные цифры и нет двоеточия); поведение закрепляется существующими тестами и новым тестом PDF-формы.

## 4. Фикстуры и тесты

**Фикстуры** — дословный вывод `pdftotext` страницы с таблицей (стандарт §11.1, прецедент `polyus/testdata/*.tsv`):

- комментарии — страница 2: `cbr/testdata/mt_forecast_pdf/comment_<ДДММГГГГ>.txt` (8 файлов);
- `comment_27022024_p1p2.txt` — страницы 1–2 (обложка + таблица): проверяет поиск якоря после страницы без таблицы и soft hyphen в якоре;
- прогнозы — страница 1: `forecast_<ДДММГГ>.txt` (11 файлов).

Команда снятия: `curl -sS <url> | pdftotext -f N -l N -layout -enc UTF-8 -nopgbrk - - > <file>`. PDF-байты в git не коммитятся (3,7 МБ); извлечение проверяется живым прогоном.

**Тесты** (`cbr/mt_forecast_pdf_test.go`):

1. корпус: 20 фикстур → ожидаемые годы, 16 строк, 1104 точки; spot `key_rate_avg` по каждому выпуску (таблица в плане §1); суммы 496 (комментарии) и 608 (прогнозы);
2. fail-fast: пустой текст, нет якоря, нет строки годов, неверное число значений, нет core-строки;
3. предупреждения: неизвестная подпись, пропажа не-core строки;
4. извлечение: HTML-байты → ошибка до `exec`; подменённый `mtForecastPDFTool` → ошибка с подсказкой `poppler-utils`;
5. `mtForecastNormalizeLabel` для PDF-формы (`валюте³`, `…в том числе:`).

**Существующие тесты** (`cbr/mt_forecast_test.go`) обновляются: 22 карточки в живой фикстуре `mp_summary_index.html` (11 комментариев + 11 прогнозов; фикстура уже содержит forecast-карточки), даты/URL/`Kind`, гейт пропускает 20 новых выпусков, правило «нет страничных карточек» заменяется на «нет комментариев — ошибка».

## 7. Риски и оговорки

- **`pdftotext` на staging.** Первый прогон после релиза упадёт, если пакета нет; ошибка это называет, prerequisite — в deploy/README. No-op-прогоны утилиту не вызывают.
- **Дрейф вёрстки PDF.** Разбор валидирует 16 строк и число значений; смена вёрстки — громкая ошибка, а не тихая потеря. Незнакомая подпись — warn (стандарт §6.6).
- **Дубли значений** forecast/comment — осознанны: разные даты публикации и провенанс; названо в комментариях витрины.
- **Размер фикстур** ≈ 170 КБ — приемлемо (в репозитории есть xlsx на 0,46–1,5 МБ).
- **Grep-чистота `cbr/`:** `colly`/`fmt.Print*` не добавляются; `exec` изолирован в одном файле.
- **Проверка `pdftotext` в CI не нужна:** тесты читают текстовые фикстуры; извлечение проверяется живой приёмкой.

## 8. Вне объёма

- «Табл. 2–4» и «Рис. 1» PDF (платёжный баланс, дневной ряд ставки).
- Переимпорт двух xlsx-выпусков и изменение их винтажей.
- Point-in-time слой, ансамбль, дашборды.
- Изменение нормативного стандарта §4 (PDF-транспорт остаётся названным отступлением).
