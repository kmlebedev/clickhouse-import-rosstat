# Дефекты данных Полюса из публикации 2026-11-01 — протокол

> **Пункт:** `dcf-polyus/phase-3-remaining-data-defects-2026-11`, issue [#484](https://github.com/kmlebedev/clickhouse-import-rosstat/issues/484), `role:go`.
> **Статус:** решения записаны до кода; WGC-часть вынесена в отдельный пункт `gold-thesis/phase-3-followup-8` и делается после мержа этого PR (WIP=1).

## 1. Зачем

Публикация о Полюсе 2026-11-01 вскрыла два дефекта, из-за которых DCF-модель могла читать не тот факт, и два пробела в покрытии отчётности. Проверки выполнены на staging (публичный MCP `rosstat-staging` и прямой ClickHouse-доступ):

1. **Сдвиг года в DCF.** `polyus/datapack.go:164` хранит годовое наблюдение как первое число месяца после конца периода: FY2024 → `2025-01-01`, FY2025 → `2026-01-01`. `dcf/mine_plans_import.go:69` ищет год через `toYear(date)`, поэтому для `reportingYearBase = 2025` находит FY2024. На staging `mine_plans` OLIMPIADA 2025 = `1 265,7` (FY2024) вместо `926,5` (FY2025); база четырёх действующих активов завышена на 12,9 %, Олимпиада — на 36,6 %.
2. **Границы блоков датапака.** В датапаке 1H25 блок называется `VERNINSKOYE**`; его нет в `datapackTables`, и парсер продолжает относить строки к предыдущему блоку `TITIMUKHTA`. На staging 208 строк `TITIMUKHTA` с `date >= 2021-01-01` повторяют `VERNINSKOYE2`. Текущий FY2025-файл чист, но `ReplacingMergeTree` не удаляет старые ключи, поэтому дефект виден только на накопленных данных.
3. **2H25-отчёт.** `polyus/pages.go:172` (`2026_03_16_2h25-_-tu-mda-eng.pdf`) отключён: двухшапочная таблица. Значения 2025H2 приходят только сравнительной колонкой 1H26; перекрёстной проверки нет.
4. **1H26-датапак и метрики.** В `v_company_financials` `adjusted_ebitda`, `net_debt_including_derivatives`, `operating_profit`, `cash_and_cash_equivalents` заканчиваются на 2024H2. В KPI-релизе 1H26 этих строк нет; расширение словаря `polyus/metrics.go` само по себе не поможет.

## 2. Решения

### 2.1. Дата: конвенция остаётся у импортёра, исправляется потребитель

Конвенция `databook_polyus` — **первое число месяца, следующего за концом периода**. Она уже согласована для кварталов и полугодий (`4Q'07 → 2008-01-01`, `2H'24 → 2025-01-01`) и закреплена тестом. Менять её — переписать 8 484 строки и всех потребителей; это дороже и рискованнее, чем исправить один запрос.

`actualProductionSelect` переходит на точную дату:

```sql
AND date = makeDate({year:UInt16} + 1, 1, 1)
```

Точная дата, а не `toYear(subtractMonths(date, 1))`: она не матчит случайную строку с другим месяцем и использует ключ сортировки `(table, name, data, date)`. Комментарии в `dcf/mine_plans_import.go`, `views/company.go` и `ARCHITECTURE.md` §6.1/§6.3 приводятся к фактической конвенции.

### 2.2. Границы блоков: alias + fail-fast + дубли

В `polyus/datapack.go`:

- нормализация метки блока: верхний регистр, trim, снятие хвостовых `*`, схлопывание пробелов;
- alias `VERNINSKOYE` → `VERNINSKOYE2` (покрывает `VERNINSKOYE**` из 1H25-датапака);
- неизвестная all-caps метка после первого известного актива — ошибка разбора с номером строки и меткой; секции `Mining`/`Processing`/`Mill`/`Heap-leach` и сноски (`*`, `1 - …`) блоками не считаются;
- после разбора — проверка дублей ключа `(table, name, data, date)`; дубль — ошибка. Это страховка от будущих переименований, которые не покрыты alias.

Источник данных не меняется: 1H25-датапак с `VERNINSKOYE**` не импортируется в прод, он остаётся доказательством дефекта и тест-кейсом (модификация FY2025-фикстуры во временном файле).

### 2.3. Staging: TRUNCATE + полный reimport

`databook_polyus` на staging содержит 208 устаревших строк `TITIMUKHTA` (`date >= 2021-01-01`), которые текущий импортёр не порождает. Точечный `DELETE` оставил бы риск других stale-ключей; по решению владельца таблица очищается и датапак импортируется заново. Это разрушающая операция на общей БД, поэтому:

- окно — вне расписания `financial` (пн 10:23 МСК) и `wgc` (ежедневно 20:17 МСК);
- до TRUNCATE фиксируются `count()` и SHA-256 файла, после — `count()`, крайние даты и отсутствие **ненулевых** значений `TITIMUKHTA` после 2020 (нулевые полугодовые строки — штатные, их пишет чистый датапак);
- `v_company_operating` пересоздаётся шагом `company_views`.

### 2.4. 2H25 и 1H26 — отдельные follow-up

- **2H25**: нужен разбор двухшапочной таблицы; новых периодов документ не даёт, только перекрёстную проверку 2025H2. Отдельный пункт роадмапа, не код этого PR.
- **1H26**: KPI-релиз 1H26 не содержит `adjusted_ebitda`, `net_debt`, `operating_profit`, `cash`; нужен MD&A/презентация или новый датапак. Расширение словаря `polyus/metrics.go` без источника строки даст ложное «покрытие». Отдельный пункт роадмапа.

Оба решения фиксируются комментарием в issue #484 и в `docs/ROADMAP_DCF_POLYUS.md`.

## 3. Границы

- Не меняются DDL, имена таблиц/рядов, витрины и гранты.
- Не импортируется 1H25-датапак и не включается 2H25-отчёт.
- Не добавляются новые метрики `company_financials` и новый датапак.
- WGC (`working_dir`, доставка выгрузок, fail-loud) — отдельный issue/PR `gold-thesis/phase-3-followup-8`, зависит от этого.

## 4. Критерий приёмки

1. Тест конвенции даты: FY2024 → `2025-01-01`, 4Q'07 → `2008-01-01`, 2H'24 → `2025-01-01`.
2. Тест формы запроса: `actualProductionSelect` использует точную дату, не голый `toYear(date)`.
3. Тест границ: FY2025-фикстура с `B84 = VERNINSKOYE**` даёт `VERNINSKOYE2` `Ore processed` 2021-01-01 = 3277, у `TITIMUKHTA` нет **ненулевых** значений после 2020 (нулевые полугодовые строки допустимы), дублей в затронутых блоках нет; неизвестная all-caps метка — ошибка.
4. `make all`, `make docs-check`, `dagu validate dagu/financial.yaml dagu/dcf.yaml` — зелёные.
5. На staging после TRUNCATE + reimport: `databook_polyus` — 8 484 строки, `TITIMUKHTA` без **ненулевых** значений после 2020, `VERNINSKOYE2` без изменений.
6. На staging `dcf_mine_plans`: `OLIMPIADA — факт базы 926.5 koz (2025)`, `Imported 87 rows`; `dcf_engine` — 36 строк; NAV до/после зафиксирован в протоколе (чистое сравнение — на dev).
7. `make mcp-check` — ПРОВЕРКА ПРОЙДЕНА; `v_company_operating` и `v_dcf_assumptions` читаются через MCP.
8. По 2H25 и 1H26 — решение в issue и роадмапе (отдельные follow-up).
