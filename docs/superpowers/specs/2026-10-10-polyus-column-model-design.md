# Колоночная модель разбора PDF в пакете `polyus/` — Design

**Дата:** 2026-10-10
**Пункт роадмапа:** фаза 1 «Данные для золота» — качество извлечения текста из отчётности Полюса.
**Сопутствующие документы:** [ARCHITECTURE.md](../../../ARCHITECTURE.md) §6.2 (DDL), §6.6 (ограничения `polyus/`); [ROADMAP §8.1](../../ROADMAP_DCF_POLYUS.md) (три отложенных дефекта).

## 1. Проблема

Разбор отчётности Полюса опирается на `pdftotext -layout` и **позиционное** сопоставление значений с периодами: `parseKPIPage` строит список колонок из шапки и затем присваивает числа строки по порядку. Как только между периодами в шапке оказывается колонка-изменение, порядок ломается.

**Проверенный корень** (найден в фикстуре FY2014, файл `polyus/testdata/press_release_hist_p1.txt`):

```
строка 3:                                              y-o-y
строка 4:  $ mln (if not mentioned otherwise)   FY 2014   FY 2013        2H 2014   1H 2014
строка 5:                                              change
строка 7:  Total gold production (koz)            1,696     1,652     3%      950       746
```

Шапка объявляет **четыре** периода, а в строке данных **пять** значений: `3%` — это `change` (отдельная строка шапки, периодом не является). Позиционное присваивание сдвигает всё после `change`: `3%` попадает в слот `2014H2`, `950` — в `2014H1`, а `746` теряется. Живое следствие в ClickHouse: `2014H2` содержит `revenue` 2 329, `capex` 1 440, `gold_sold` 1 631 — это цифры FY2013.

То же в русском релизе 1H2026: шапка `1 п/г 2026 | 1 п/г 2025 | Изм. за год | 2 п/г 2025 | Изм. за п/г`, где «Изм. за год» — колонка **без года** (X ≈ 358), поэтому периодом не распознаётся, но её значение всё равно вычитывается позиционно. Следствие: `gold_output 2025H2 = -2` (это процент изменения `(2%)`, а не добыча).

Позиционность — причина всех трёх отложенных дефектов, зафиксированных в ROADMAP §8.1: сдвиг колонок, `2014H2` с чужими данными и тот факт, что guard вынужден грубо отбрасывать последнюю колонку вместо точного определения принадлежности.

## 2. Цель

Перейти к **колоночной модели**: колонки таблицы определяются по X-координатам из шапки, каждое значение строки относится к колонке по своей X-координате, а не по порядку следования.

**Критерий приёмки:**
- `2014H2` не содержит данных FY2013 (значения этой колонки либо верны, либо колонка не читается вовсе);
- русский релиз 1H2026 отдаёт корректное значение слота `2 п/г 2025` (`1 218`), а не процент `(2%)`;
- контрольные значения `2026H1` сохраняются: `gold_output` 1287, `tcc_per_ounce` 1069, `total_revenue` 4674, `profit_for_period` 829, `stripping_capex` 397;
- `make all` зелёный; живые тесты подтверждают результат на реальных отчётах;
- модель **проверена на восьмиколоночной шапке** (2024FY, §3.1) — на ней колонки-изменения без года (`Y-o-Y`, `H-o-H`) не читаются как периоды. Сам отчёт при этом не включается: проверка берётся фикстурой без записи в ClickHouse, чтобы ядро было готово к следующему пункту.

## 3. Границы

**Входит:**
- переход `polyus/source.go` с `-layout` на `-tsv` (координаты слов);
- новый файл разбора TSV и группировки слов в строки;
- новый файл колоночной модели (колонки из шапки по X, значение по X);
- перевод `parseKPIPage` и `parseIFRSPage` на построчный вход с координатами;
- сохранение guard как резервной защиты (см. §7);
- TSV-фикстуры вместо текстовых слепков.

**Не входит:**
- смена источника координат: `pdftotext` остаётся, нативная библиотека (pdfcpu и др.) не подключается — проверено, что pdfcpu извлечение текста не поддерживает вовсе, а `-tsv` уже даёт нужные координаты;
- изменение схем таблиц (`databook_polyus`, `polyus_financial_metrics`) — ключ `(company, metric, period)` не трогается;
- неоднозначность `revenue` ≡ `total_revenue` — это свойство ключа без измерения источника, отдельная задача;
- **включение 11 отключённых отчётов** (2015FY…2025H2) — выносится в следующий пункт, см. §3.1.

### 3.1 11 отключённых отчётов: почему не в этой итерации

Отключённый набор — непрерывная история **2015FY…2025H2**, то есть весь ряд между включённым 2014FY и текущим 1H2026. Заявленная в `pages.go` причина («номера страниц не выверены») верна, но неполна; проверка двух файлов на живом сайте показала более существенное препятствие.

**Шапки этих отчётов шире, чем различает позиционная модель.** Пример — 2024FY, страница 4:

```
Comparative financial results
$ million (if not mentioned otherwise)   2024   2023   Y-o-Y   2H 2024  1H 2024   H-o-H   2H 2023   Y-o-Y
```

Восемь колонок: **5 периодов и 3 колонки-изменения**, причём метки `Y-o-Y` и `H-o-H` **не содержат года вообще**. Позиционная модель различает не более 3 колонок (`maxPeriodTokens`) и не может отличить такую метку от периода никаким способом — значения неизбежно перепутаются.

Колоночная модель (§5) снимает именно эту причину: колонка без распознанного периода не читается, а её место по X сохраняется. Но остаются два препятствия, которые модель не снимает:

1. **Номера KPI-страниц.** Проверено: у 2024FY операционной таблицы на первых страницах нет — она на странице 4 внутри «Comparative financial results», тогда как страницы 9–10 несут другие таблицы. Правило «одна страница на отчёт» для этого набора не действует; каждый файл требует ручного прогона `pdftotext` и выверки.
2. **Разные типы документов.** Часть набора — консолидированные IFRS-формы без колоночной периодики (например 2018FY, `polyus-group-ifrs-cons-fs-18_e_signed.pdf`), то есть `Kind: "ifrs"`, а не `kpi`; часть — двухшляпочные релизы 4Q/FY. Набор неоднороден, и `Kind`, `Lang` и `Pages` для каждого файла определяются отдельно.

Поэтому работа разделена: **эта спека** доводит колоночную модель и закрывает три дефекта на уже включённых отчётах; **следующий пункт** на готовом ядре выверяет и включает историю 2015–2025. Такое разделение даёт проверяемый результат раньше и не смешивает риск смены модели разбора с риском ручной выверки 11 файлов.


## 4. Модель данных извлечения

### 4.1 Word и Line

```go
type Word struct {
    Text   string
    Left   float64 // x минимума
    Top    float64 // y минимума
    Width  float64
    Height float64
    Block  int // block_num из TSV
    Line   int // line_num из TSV
}

type Line struct {
    Top   float64
    Words []Word // отсортированы по Left
}
```

`pdftotext -tsv` печатает уровни: `1` страница, `3` flow, `4` line, `5` word. Разбираются только строки уровня `5`; служебные маркеры (`###PAGE###`, `###FLOW###`, `###LINE###`) отбрасываются.

### 4.2 Группировка в строки

Проверено на живых файлах: у слов одной визуальной строки `Top` совпадает **точно** (пример — `Выручка`, `4`, `674` все при `Top = 434.80`). Поэтому группировка идёт по точному `Top`, а не по допуску; сортировка внутри строки — по `Left`.

Допуск не нужен для штатной разметки, но нужен как страховка от дрейфа базовой линии (например, слово с другим кеглем в той же строке). Поэтому `groupByLine` принимает `deltaTop` и считает слова одной строкой, если `|Top − опорный Top| ≤ deltaTop`; при `deltaTop = 0` поведение строго точное. Опорным берётся `Top` первого слова группы. Значение по умолчанию — 0; подбор значения для конкретных отчётов фиксируется в коде с комментарием, а не подбирается «на глаз» без проверки.

## 5. Колоночная модель

```go
type Column struct {
    Period string  // "2026H1", "2014FY"; пусто, если колонка не период
    Type   string  // "H", "Q", "FY"
    Left   float64 // x начала колонки по шапке
    Right  float64 // x конца колонки по шапке
}
```

Правила:
1. Шапка распознаётся тем же словарём метрик (`matchMetric` с определением `period`), что и сейчас, — формат `$ млн (если не указано иное)` / `$ mln (if not mentioned otherwise)`.
2. Периоды в шапке ищутся многословно (`parsePeriod` для окон до 3 токенов — как в `matchPeriodAt` сейчас), а их границы по X берутся от первого до последнего слова периода.
3. Колонка, для которой период не распознан, всё равно попадает в набор как `Column{Period: ""}` — **она нужна, чтобы занять своё место по X** и не дать значениям справа сдвинуться влево. Значения из неё не читаются.
4. Значение строки относится к колонке по `Left` значения: берётся колонка, в чьём диапазоне `[Left, Right]` (с расширением до середины промежутка до соседней колонки) лежит начало числа.
5. Если ни одна колонка не накрывает значение по X — значение игнорируется (и это видно в счётчике пропусков), а не присваивается ближайшей.

Ключевое отличие от текущего кода: принадлежность определяется координатой, а не индексом в списке. Именно это чинит сдвиг на колонке-изменении.

## 6. Источник текста и фикстуры

`extractPage` меняет флаг: вместо `-layout` вызывается `-tsv`. Остальные параметры сохраняются (`-f N -l N -nopgbrk -enc UTF-8`), проверка непустого результата и ошибки `pdftotext` — без изменений.

**Фикстуры коммитятся как TSV-снимки** реального вывода `pdftotext -tsv`. Страницы: русский пресс-релиз 1H2026 (стр. 1), английская МСФО 1H2026 (стр. 6 и 7), исторический английский отчёт FY2014 (стр. 4) и — для проверки широкой шапки (§3.1) — страница 4 отчёта 2024FY (восемь колонок). Существующие текстовые слепки (`.txt`) удаляются вместе с переходом — держать два формата фикстур незачем.

Фикстура 2024FY нужна как **тест-кейс модели**, а не как источник данных: сам отчёт остаётся `Enabled: false` (§3.1), в ClickHouse ничего не пишется.

Тесты не вызывают `pdftotext`: они разбирают TSV-снимок. Это сохраняет возможность прогонять тесты там, где утилиты нет (CI), — свойство, которое уже действует и должно сохраниться.

## 7. Guard как резерв

По решению заказчика guard **сохраняется**, но меняет роль: раньше он был единственным механизмом против сдвига (грубо отбрасывал последнюю колонку), теперь — резервной защитой.

Новое поведение: guard считает **нераспределённые** значения — числа строки, которые не попали ни в одну колонку по X (см. §5.5), и числа, попавшие в колонку, чей период не распознан. Если такие есть, строка помечается как частично неразобранная: распознанные значения записываются, нераспознанные — нет, в лог идёт `Warnf` со счётчиком.

Важно: «не распределилось никуда» и «попало в непериодную колонку» — это ожидаемая ситуация для колонок-изменений (`Изм. за год`, `change`), поэтому такие числа **не** считаются ошибкой. Ошибкой считается только число, не накрытое ни одной колонкой вообще: это признак того, что шапка разобрана не полностью или разметка страницы нестандартна.

Это уже не «отбросить последнюю колонку», а «принять только то, что однозначно отнесено к периоду, и сообщить об остальном».

Функция `untrustworthyPeriod` и её позиционная эвристика удаляются: колонка-изменение теперь распознаётся по отсутствию периода в шапке, а не по признаку «последняя».

## 8. Тестирование

**Разбор TSV** (`words_test.go`): на TSV-снимке — число слов уровня 5, отсутствие служебных маркеров, корректные координаты конкретного слова; группировка в строки даёт ожидаемое число строк; внутри строки слова упорядочены по `Left`; `deltaTop` склеивает слова с дрейфом базовой линии.

**Колоночная модель** (`columns_test.go`): на шапке русского релиза 1H2026 — три колонки-периода (`2026H1`, `2025H1`, `2025H2`) плюс непериодная колонка «Изм. за год» с пустым `Period`; значение `1 069` из строки TCC относится к колонке `2026H1`, а `(2%)` — к непериодной и потому не читается; на шапке FY2014 — четыре колонки-периода и непериодная `change`; на шапке 2024FY — **пять** колонок-периодов (`2024`, `2023`, `2H 2024`, `1H 2024`, `2H 2023`) и **три** непериодные (`Y-o-Y`, `H-o-H`, `Y-o-Y`), причём метки без года не становятся периодами (регрессия §3.1).

**Сквозные регрессии** (`kpi_test.go` / `ifrs_test.go`): сохраняются все существующие проверки значений, плюс новые:
- `TestKRIPeriodsFullCoverage` (регрессия «Изм. за год»): строка TCC русского релиза даёт значения для всех трёх периодов, включая `2025H2` = `1 218`, и **не** даёт `−2`;
- `TestFY2014NoColumnShift` (регрессия сдвига): строка `Total gold production` даёт `1,696` для `2014FY`, `1,652` для `2013FY`, `950` для `2014H2`, `746` для `2014H1`, и ни одно значение не попадает в чужой период;
- `TestAmbiguousRowRejected` (резерв guard): строка, которую нельзя разложить по колонкам, не порождает записей и увеличивает счётчик.

**Живая приёмка:** `make import STAT=polyus_financial_metrics`, затем проверка через `make ch-sql`: контрольные значения `2026H1`; отсутствие записей `2014H2` с цифрами FY2013; корректный `2025H2` русского релиза.

## 9. Что чинится и что остаётся

| Дефект (ROADMAP §8.1) | Статус после работы |
|---|---|
| Guard отбрасывает последнюю колонку, теряя слот `2025H2` | **чинится**: колонка-изменение распознаётся по шапке, слот `2025H2` читается корректно |
| `2014H2` содержит данные FY2013 | **чинится**: `change` не становится колонкой периода, значения раскладываются по X |
| Неоднозначность `revenue` ≡ `total_revenue`, ключ без источника | **не чинится** — свойство ключа таблицы, отдельная задача |
| 11 отключённых отчётов 2015FY…2025H2 | **не включаются** в этой работе — выверка выносится в следующий пункт (§3.1); модель к их шапкам готовится и проверяется фикстурой 2024FY |

Отдельно: `splitLabelAndValues` (латентное искажение при слипании сноски с меткой) — кандидат на проверку в рамках этой работы, так как с координатами сноска определяется по X, а не по эвристике «цифра вплотную к скобке». Включать или нет — фиксируется на этапе плана.

## 10. Риски

| Риск | Митигация |
|---|---|
| Разметка `-tsv` иная, чем ожидает модель, на каком-то из отчётов | Все координаты берутся с живых файлов; модель проверяется на пяти реальных страницах (RU 1H2026, EN МСФО ×2, FY2014, 2024FY) до перевода парсеров |
| Слова с разным кеглем в одной строке разъезжаются по `Top` | `groupByLine` принимает `deltaTop`; проверяется на живом отчёте, при расхождении значение фиксируется с комментарием |
| Сноска, слипшаяся с меткой (`… унцию ($)4`), после перехода читается как часть периода | С координатами сноска отделена по X; отдельный тест на строку TCC русского релиза |
| TSV-объём фикстур (852 строки на страницу русского релиза) | Приемлемо: это текст, пять файлов; альтернатива — резать фикстуру до нужных строк — отвергается, так как ломает проверку координат по всей странице |
| Восьмиколоночная шапка (2024FY) выявляет предел модели, не покрытый проверками | Она входит в критерий приёмки (§2) и в фикстуры наравне с остальными |
| CI без `pdftotext` | Тесты работают на TSV-снимках и утилиту не вызывают; живой прогон — ручная приёмка |
