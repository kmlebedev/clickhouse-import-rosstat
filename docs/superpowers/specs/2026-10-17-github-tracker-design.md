**Связанные документы:** [ROADMAP_INDEX.md](../../ROADMAP_INDEX.md) (реестр роадмапов и правила ID), [AGENTS.md](../../../AGENTS.md) правило 12, скил [`.kimi-code/skills/github-tracker/SKILL.md`](../../../.kimi-code/skills/github-tracker/SKILL.md).

## 1. Зачем

В репозитории пять роадмапов, и они устроены по-разному:

- `docs/ROADMAP_DCF_POLYUS.md` — фазы 0–5, шаги `3.1`–`7.3`, подпункты `7.1`–`7.3`;
- `docs/GOLD_THESIS_DATA_ROADMAP.md` — фазы 0–5, прозаические `follow-up N`, таблица витрин, шаги CatBoost;
- `docs/ROADMAP_DCF_METALS.md` — шаги `1`–`8`, маркеров статуса нет;
- `docs/ROADMAP_KEY_RATE.md` — фазы 1–5, `1.1`–`1.11`, пункты фазы 2 прозой;
- `docs/ROADMAP_INFRA.md` — фазы 1–2, `1.1`–`1.5`, `2.1`–`2.2`.

Одномаршрутная модель «issue = пункт роадмапа» ломается на четырёх вещах:

1. **ID не уникальны.** `1.1` есть и в `ROADMAP_INFRA`, и в `ROADMAP_KEY_RATE`; фазы `1–5` повторяются у четырёх файлов.
2. **Гранулярность разная.** Где-то таблица шагов, где-то проза, где-то таблица витрин; единого «номера пункта» нет.
3. **Статусы разные.** `✅` / `❌` / `⏳` / `🔶` / «не начато» / «план, не начато»; в `ROADMAP_DCF_METALS` маркеров нет.
4. **Пересечения.** `ROADMAP_DCF_POLYUS` фаза 1 перечисляет `fred`/`bls`/`bea`/`wgc`/`eia`, принадлежащие `GOLD_THESIS`; `ROADMAP_KEY_RATE` 3.1 ссылается на банковский рефакторинг; `ROADMAP_DCF_METALS` продолжает `company_financials`; `ROADMAP_INFRA` обслуживает все треки.

Цель — одна конвенция и один GitHub Project V2 на репозиторий, в которых все пять роадмапов читаются без коллизий и дублей. Источник истины остаётся в файлах роадмапов; GitHub — журнал и вид.

## 2. Границы

**Входит:**

- реестр роадмапов и правило владения;
- составной ID пункта и шаблон заголовка issue;
- контракт тела issue и шаблон GitHub Issue Form;
- поля и виды Project V2;
- отображение статусов роадмап → Project;
- sub-issues, Q&A, междокументные зависимости;
- порядок синхронизации роадмап ↔ GitHub;
- правило бэкфилла и триажа существующих issue;
- операционный скил и шаблон PR.

**Не входит (отдельный шаг 3.2):**

- выдача scope `project` и включение toolset `projects` в `~/.kimi-code/mcp.json`;
- создание живого Project V2, полей и видов;
- бэкфилл открытого фронта и раскладка существующих issue;
- автоматизация через GitHub Actions.

## 3. Реестр роадмапов

Слаги фиксированы и совпадают с именами файлов:

| Слаг | Файл | Роль / граница владения | Схема item-id |
|---|---|---|---|
| `dcf-polyus` | `docs/ROADMAP_DCF_POLYUS.md` | золото → DCF → NAV PLZL; DCF-модель, парсеры Полюса, остаток фазы 3 | `0`–`5`, `3.1`–`7.3`, `phase-3-remaining-<тема>` |
| `gold-thesis` | `docs/GOLD_THESIS_DATA_ROADMAP.md` | данные и витрины тезисов по золоту; WGC/EIA/bold/news/фрахт/аналитические витрины | `phase-N`, `phase-N-followup-M`, `analytics-<витрина>` |
| `dcf-metals` | `docs/ROADMAP_DCF_METALS.md` | CHMF/MAGN/NLMK в `company_financials`; металлурги и `dashboard/chmf.json` | `step-1`–`step-8` |
| `key-rate` | `docs/ROADMAP_KEY_RATE.md` | контур прогноза ключевой ставки; ЦБ-источники, модель ставки, news-ленты контура | `1.1`–`1.11`, `phase-2-<тема>`, `phase-4-<тема>` |
| `infra` | `docs/ROADMAP_INFRA.md` | общая инфраструктура, не принадлежит ни одному треку | `1.1`–`1.5`, `2.1`–`2.2`, `3.1`–`3.2` |

Реестр — `docs/ROADMAP_INDEX.md`. На него ссылаются `AGENTS.md` (правило 1 и правило 12) и шапки роадмапов.

**Правило владения:** пункт живёт ровно в одном роадмапе — том, чья шапка или §1 объявляет его своим. В других файлах — только ссылка. Если работа упомянута в двух файлах, канонический владелец определяется по этому правилу, а второй файл получает ссылку на issue владельца.

Примеры:

- `fred`/`bls`/`bea`/`wgc`/`eia`/`bold` — владелец `gold-thesis`; `dcf-polyus` фаза 1 ссылается, своих issue не заводит.
- Прогноз ставки — владелец `key-rate`; `dcf-polyus` §13.1 потребляет его как вход.
- Металлурги — владелец `dcf-metals`; `dcf-polyus` §12 (peers) ссылается.
- Архив, приёмка, дашборды, деплой — владелец `infra`; трековые роадмапы ссылаются.

## 4. Составной ID и заголовок issue

Канонический ключ пункта: `<slug>/<item-id>`.

Примеры формата:

- `infra/1.1`, `key-rate/1.9`, `dcf-polyus/7.3`, `dcf-metals/step-4`;
- `gold-thesis/phase-3-followup-2`;
- `gold-thesis/analytics-v-gold-floor`;
- `dcf-polyus/7.1`.

Заголовок issue: `[<slug>/<item-id>] <короткое имя пункта>`.

- `[key-rate/1.9] Telegram-молния Интерфакса и винтажные версии`
- `[infra/1.1] Винтажная база: архив версий файлов источников`
- `[dcf-metals/step-4] Парсер CHMF + NLMK`

Слаг в заголовке обязателен: он снимает коллизию `1.1` и делает issue читаемой без Project.

## 5. Контракт тела issue

Шапка issue — машинно-читаемая:

```text
Roadmap: key-rate
File: docs/ROADMAP_KEY_RATE.md
Item: 1.9
Phase: 1
Acceptance: <критерий из роадмапа>
Spec: docs/superpowers/specs/...
Plan: docs/superpowers/plans/...
Depends on: #...
```

Тело:

- цель пункта;
- критерий приёмки;
- ссылки на спеку и план;
- Q&A — комментариями;
- протокол живой приёмки;
- `Closes #N` — в PR.

Полные спеки и планы в тело issue не копируются: только ссылки. Иначе неизбежен дрейф.

## 6. Project V2: поля

Один проект на репозиторий.

| Поле | Тип | Значения / смысл |
|---|---|---|
| `Roadmap` | single select | `dcf-polyus`, `gold-thesis`, `dcf-metals`, `key-rate`, `infra` — ровно одно |
| `Phase` | text | `3`, `follow-up 2`, `step 4` |
| `Item` | text | `7.3`, `1.9`, `step-4` |
| `Status` | single select | `Todo` / `In Progress` / `In Review` / `Done` / `Blocked` |
| `Branch` | text | `feat/...` |
| `PR` | text | номер или URL |
| `Spec / Plan` | text | пути к файлам |
| `Acceptance` | text | короткий критерий + ссылка на протокол |
| `Depends on` | text | номера issue |
| `Priority` | single select | `P0` / `P1` / `P2` (опционально) |
| `Target date` | date | опционально |

Отдельный `Track`/`Contour` не нужен: вид «Gold» собирается фильтром по двум значениям `Roadmap`.

## 7. Project V2: виды

- `Все пункты` — table, group by `Roadmap`, затем `Status`.
- `dcf-polyus`, `gold-thesis`, `dcf-metals`, `key-rate`, `infra` — по одному виду на файл.
- `Gold` — `Roadmap = dcf-polyus OR gold-thesis`.
- `В работе` — `Status = In Progress OR In Review`.
- `Ждут ответа` — label `needs-answer`.
- `Inbox` — `Roadmap` пуст.
- `Roadmap` — roadmap-layout по `Target date` (опционально, после бэкфилла дат).

## 8. Отображение статусов

| В роадмапе | В Project |
|---|---|
| `❌`, «не начато», «план, не начато», нет маркера | `Todo` |
| `⏳`, `🔶`, «срез сделан», «остаток пункта», «в работе» | `In Progress` |
| PR открыт, «статус финализируется после мержа PR» | `In Review` |
| `✅` + протокол приёмки в PR + PR смержен | `Done` |
| внешний блокер | `Blocked` |

Правило `Done`:

1. критерий приёмки с командой и результатом;
2. зелёный `make all`;
3. смерженный PR;
4. статус в роадмапе обновлён тем же PR.

`✅ сделан этим PR` до мержа — это `In Review`, не `Done`. Частичный пункт («срез») остаётся `In Progress`, остаток становится sub-issues или отдельным пунктом, если владелец вынес его из объёма.

## 9. Sub-issues и срезы

- Issue = пункт роадмапа (эпик).
- Sub-issue = задача плана: `[<slug>/<item-id>] Task N: ...`, один уровень вложенности.
- Если роадмап сам называет срез или follow-up отдельным пунктом — это отдельный issue со своим ID, а не sub-issue.
- «Остаток пункта» в роадмапе → sub-issues или отдельный пункт.

## 10. Q&A

Формат комментария:

```text
### Q<N>: <вопрос>
**Контекст:** ...
**Варианты:** A / B / C
**Решение:** ... (заполняется после ответа)
**Обоснование:** ...
```

Labels: `roadmap:<slug>` — группировка до появления Project V2; `needs-answer` — пока в issue есть открытый вопрос Q&A.

- Пока вопрос открыт — label `needs-answer`.
- После ответа — резолюция в тот же комментарий, label снимается.
- Если ответ меняет состав или порядок фаз — правка роадмапа тем же PR, ссылка на issue в правке.

## 11. Междокументные зависимости

- Native GitHub «blocked by», где доступно; иначе строка `Depends on: #N` в теле и поле `Depends on` в Project.
- Типовые цепочки:
  - `gold-thesis` → `dcf-polyus` (данные и витрины → DCF);
  - `key-rate` → `dcf-polyus` (прогноз ставки → ставка дисконтирования);
  - `dcf-polyus (company_financials)` → `dcf-metals` (общая схема → металлурги);
  - `infra` → все (архив, приёмка, дашборды, деплой).
- Зависимость не дублирует пункт: issue зависимого трека ссылается на issue владельца.

## 12. Синхронизация роадмап ↔ GitHub

- Источник истины — файлы роадмапов. GitHub — журнал и вид.
- Старт пункта: issue создан/обновлён, `Status = In Progress`, заполнены `Branch`, `Spec/Plan`.
- PR: `Closes #N`, `Status = In Review`, заполнен `PR`.
- Мерж + приёмка: `Status = Done`, статус в роадмапе с командой и результатом, протокол — комментарием в PR.
- Периодический аудит — чек-лист скила `github-tracker`: «нет issue / нет пункта в роадмапе / дубль / статус разошёлся». Скрипт не обязателен на первом этапе.
- Правило «один пункт = одна ветка = один PR» не меняется; срезы, названные в роадмапе отдельными пунктами, ведут свои ветки и PR.

## 13. Бэкфилл и триаж

1. Завести поля и виды Project.
2. Бэкфилл **открытого фронта** (ориентир): `infra` (~3), `key-rate` (~17), `gold-thesis` (~16), `dcf-polyus` (~10), `dcf-metals` (8).
3. Исторические `✅`-пункты issue не получают; вместо них — ссылка на PR/протокол в роадмапе.
4. Существующие 19 issue добавить в Project; каждому выбрать `Roadmap` или оставить в `Inbox`.
5. `Inbox`-правило: sub-issue существующего пункта, новый пункт во владеющем роадмапе (с правкой файла) или закрытие. Шестой роадмап не заводить.
6. Для 2–3 активных пунктов создать sub-issues из их планов.

## 14. Критерий приёмки пункта 3.1

- Все пять роадмапов описаны в `docs/ROADMAP_INDEX.md`: слаг, файл, граница владения, схема item-id.
- `AGENTS.md` правило 12 ссылается на индекс, спеку и скил; порядок начала сессии упоминает индекс.
- Скил `.kimi-code/skills/github-tracker/SKILL.md` содержит операции issue/sub-issue/Q&A/PR/Project и чек-лист аудита.
- Шаблоны `.github/ISSUE_TEMPLATE/roadmap-item.yml` и `.github/pull_request_template.md` существуют и валидны.
- `docs/ROADMAP_INFRA.md` содержит пункт 3.1 (✅) и 3.2 (не начато).
- `README.md` и `ARCHITECTURE.md` синхронны: ссылка на индекс и конвенцию.
- `make all` зелёный; изменений кода нет.

## 15. Риски

| Риск | Митигация |
|---|---|
| Дубли пунктов между роадмапами | Правило владения + аудит скила; при сомнении — ссылка, а не копия |
| `✅ сделан этим PR` принимают за `Done` | Явный `In Review` до мержа и протокола |
| Бэкфилл historical `✅` даёт шум | Заводить issue только на открытый фронт |
| Project V2 требует scope/toolset и ломается без них | Пункт 3.2 отдельно; до него работают labels и issue |
| Расхождение статусов в файле и Project | Статус в файле канонический; аудит сверяет |
| Сломали шаблон issue form | Валидация YAML и живая проверка формы в 3.2 |

## 16. Что не делать

- Не заводить issue на каждый исторический `✅`.
- Не дублировать пункт в двух роадмапах.
- Не считать `✅ сделан этим PR` статусом `Done` до мержа и протокола.
- Не вводить отдельный `Track`-селект с произвольными значениями: `Roadmap` — единственный источник группировки.
- Не переносить спеки и планы в тело issue.
- Не использовать `GITHUB_TOKEN` Actions для записи в Projects V2.
- Не заводить шестой роадмап без решения владельца.
