## 1. Контекст и границы

T1/T2 дали сырые ИЦП Росстата: совокупный ряд по ВЭД (`rosstat_ppi_ved`, m/m с 1998) и товары/ОКПД2 (`rosstat_ppi_product`, m/m с 2021, 1 327 кодов). T3 построил versioned mapping `ОКПД2 → КИПЦ` (`okpd2-kipc-2026-v2`), веса КИПЦ и измерил паритет с 10 текстовыми якорями «Инфляции в России»: **±0,3 п.п. не достигнут** (primary MAE KIPC 1,728 п.п.; лучшие специализированные ряды — non-food 1,122, `core` 1,338). T4 добавляет производный слой: сезонно скорректированные ИЦП `ppi_sa` с явными версиями спецификации и таксономии.

**В объёме T4:** таблица `ppi_sa`, 5 рядов (`total`, `food`, `nonfood`, `all`, `core`), `sa`/`m/m_sa`/`saar`/`saar3`, X-13 `seats_log_cal`, версии, идемпотентность, каталог `series_catalog`, паритетный отчёт, `dagu/ppi.yaml` (предварительное расписание), тесты и документация.

**Вне объёма:** витрина `v_rosstat_ppi`, `GRANT SELECT` и MCP-проверки витрины — T5 #280; ежемесячное окно «после 16-го рабочего дня», свежесть и staging-приёмка расписания — T6 #281; data request в ЦБ (mapping, веса, PPI-спецификация) — T7 #282. Т4 не заявляет паритет с ЦБ.

## 2. Входы и версии

| Вход | Что берём | Версия / период |
|---|---|---|
| `rosstat_ppi_ved` | `m/m`, код `1323500.029.31`, с 2013-01 | винтаж 08-2026; таблица T1 |
| `rosstat_ppi_product` | `m/m`, листья mapping v2 | 2021-01…2026-08; таблица T2 |
| mapping ОКПД2→КИПЦ | `kipc_group`, `is_leaf`, `status` | `okpd2-kipc-2026-v2` (PR #307) |
| Полная панель весов КИПЦ | `period,code,weight` по всем группам mapping | 2012–2022, `2022-04`, 2023–2026 |
| X-13 | `seasonal` (R), baseline `seats_log_cal` | R 4.x, `seasonal` 1.11.x |

**Почему нужна полная панель.** Handoff-панель T3 (`2026-10-20-ppi-kipc-weights-panel.csv`, 469 строк / 60 кодов) фильтрована по scope-группам и не содержит весов `01.2.1`…`01.2.6` и `09.3.2`, в которые mapping v2 маппит листья (соки, кофе, чай, воды, безалкогольные напитки, корм для животных). T3-пилот считал по полному листу КИПЦ, а handoff-панель — нет; для продакшена нужна панель по всем группам mapping v2 (ожидаемо 66 кодов, ≥469 строк). Экспорт — `scripts/ppi_sa_weights_panel.py`, артефакт — `docs/research/2026-10-21-ppi-sa-weights-panel.csv`.

**Какие веса использует primary.** Фиксированные веса **2026** для всех месяцев — так считал research/T3, и это не создаёт разрыва состава: структура КИПЦ меняется в 2023 г. (новые группы `04.3.1.1`, `05.2`, `07.2.1`, `08.1`, `09.2`, `09.7`, `13.1.2`, `13.2` и др. появляются в весах), а годовые веса 2021–2022 неполны и дали бы скачок агрегата на 2023-01. Полная панель (2012–2022, `2022-04`, 2023–2026) встраивается и публикуется для provenance и будущей sensitivity-абляции «годовые веса»; primary T4 её не использует. Выбор `2022-04`/годовых весов — отдельный будущий пункт, не T4.

**PIT/винтажи.** XLSX Росстата — последняя версия; ревизии перезаписываются `ReplacingMergeTree`. T4 хранит `loaded_at` (когда собрана derived-строка) и `published_at` (as-of появления входного винтажа в конвейере), но PIT-слой не заявляет.

## 3. Агрегация (v2)

Повторяет `scripts/ppi_sa_mapping.py` v2 (`_group_series`) с полной панелью:

1. **Листья.** Берутся только `is_leaf=1` и `status=mapped`; у каждого есть `kipc_group`.
2. **KIPC-иерархия — только точка** (`_is_kipc_child`: `code.startswith(parent + ".")`). `04.3.1.1.1` и `04.3.1.1.10` — соседи, а не родитель/ребёнок.
3. **Группы scope** (константы кода, копия v2):
   - `food`: `01.1.1`–`01.1.5`, `01.1.8`, `01.1.9`, `01.2`;
   - `alcohol`: `02.1`; `tobacco`: `02.3`;
   - `nonfood`: `04.3.1.1`, `03.1`, `03.2`, `05.1`–`05.6`, `06.1`, `07.1`, `07.2.1`, `08.1`, `09.1`, `09.2`, `09.3`, `09.7`, `13.1.2`, `13.2`;
   - `fuel`: `07.2.2`;
   - вычитания: `03.1.4` из `03.1`, `03.2.2` из `03.2`, `05.6.2` из `05.6`.
   - `all` = food + alcohol + tobacco + nonfood + fuel; `core` = food + nonfood.
4. **Группировка.** Листья группируются по точному `kipc_group`; из выбранных групп удаляются те, что являются KIPC-детьми другой выбранной группы (`_dedupe_members`). У v2 mapping родительских листьев `04.3.1.1` нет — остаются дочерние.
5. **Вес.** Primary использует фиксированный период **`2026`** для всех месяцев (полный лист КИПЦ; у каждой mapped-группы вес есть — тест полноты). Группы без m/m в конкретном месяце пропускаются, веса нормируются на доступную сумму (как в v2). Историческая панель (`2022-04`, 2012–2022) в primary не участвует — она встроена для provenance и будущей sensitivity-абляции; группа, у которой нет веса 2026, — ошибка конфигурации.
6. **m/m группы** — среднее m/m mapped-листьев группы за месяц; **m/m scope** — взвешенное среднее групповых m/m по весам 2026 с нормировкой.
7. **Уровень** — цепочка от базы 100 в первом месяце: `level_t = level_{t−1} · (m/m_t / 100)`. Для `total` первый месяц — 2013-01 (m/m 2013-01 не применяется, как в research); для потребительских рядов — 2021-01. Уровни разных рядов несопоставимы по абсолюту (разные базы), сравнивать можно темпы.
8. **Непрерывность.** Месяцы каждого ряда обязаны идти подряд; пропуск — ошибка, а не «пустой месяц».

## 4. X-13ARIMA-SEATS и формула

Спецификация `seats_log_cal` (research #275):

```r
fit <- seas(x, transform.function = "log", outlier = "", regression.aictest = "td")
sa  <- as.numeric(final(fit))
```

SEATS, авто-ARIMA, авто-выбросы, календарный тест, лог-преобразование. R-скрипт — production-версия (`ppi/data/ppi_sa_x13.R`), один вариант вместо четырёх research-вариантов. Вход — `series,date,level`, выход — `series,date,sa`; скрипт проверяет ≥36 точек, непрерывность месяцев и положительные уровни, при ошибке одной серии завершается ненулевым кодом без частичного результата.

Метрики считаются в Go (единственный источник формулы, тестируется без R):

- `mm_sa = (sa_t / sa_{t−1} − 1) · 100`;
- `saar = ((1 + mm_sa/100)^12 − 1) · 100`;
- `saar3` = среднее трёх `saar` (t−2…t); `mm_sa` первого месяца, `saar` первого и `saar3` первых двух — `NULL`.

**Версии.**

| Поле | Значение | Смысл |
|---|---|---|
| `method` | `x13arima-seats` | реализация/семейство метода |
| `spec_version` | `ppi-sa-2026-v1` | точная спецификация: SEATS, log, auto-outliers, calendar td, mean3_saar, старт 2013-01/2021-01 |
| `taxonomy_version` | из mapping, ожидается `okpd2-kipc-2026-v2` | mapping + полная панель весов |

`spec_version` пересматривается раз в год (по образцу методики ЦБ); изменение любого элемента спецификации — новый `spec_version`. SHA-256 встроенного R-скрипта и файлов данных пинится в коде: правка без bump версии валит тест.

## 5. Схема `ppi_sa`

```sql
CREATE TABLE IF NOT EXISTS ppi_sa (
    date             Date,
    series           LowCardinality(String),   -- total | food | nonfood | all | core
    method           LowCardinality(String),   -- x13arima-seats
    spec_version     LowCardinality(String),   -- ppi-sa-2026-v1
    taxonomy_version LowCardinality(String),   -- okpd2-kipc-2026-v2
    sa               Float64,                  -- SA-уровень, 100 = первый месяц ряда
    mm_sa            Nullable(Float64),        -- % м/м SA
    saar             Nullable(Float64),        -- % SAAR
    saar3            Nullable(Float64),        -- % SAAR, среднее трёх месяцев
    published_at     Nullable(Date),           -- as-of входного винтажа
    loaded_at        DateTime DEFAULT now()
) ENGINE = ReplacingMergeTree(loaded_at)
ORDER BY (date, series, method, spec_version, taxonomy_version);
```

- `taxonomy_version` в ключе: смена mapping/весов не затирает прошлую версию — параллельные строки читаются с фильтром по версии.
- `published_at` — `toDate(max(first_seen))` из `source_publications` по входу: для `total` — `rosstat_ppi_ved`, для потребительских рядов — `rosstat_ppi_product`; `NULL`, если версии нет. Это **не** официальная дата публикации Росстата, а момент, когда конвейер впервые увидел винтаж; оговорка — в `LIMITATIONS.md` и комментарии каталога.
- `loaded_at` — версия `ReplacingMergeTree`; повтор с теми же ключами перезаписывает строки.

## 6. Транспорт и импортёр

**Пакет `ppi/`, импортёр и таблица `ppi_sa`.** Новый пакет, а не `rosstat/`: энфорсер `rosstat/` требует префикс `rosstat_` у имени и таблицы и двустороннюю сверку `dagu/rosstat.yaml`; derived-слой с внешним R — отдельный домен. Имя `ppi_sa` соответствует префиксу пакета `ppi_`.

**Цикл `Import()`:**

1. DDL `ppi_sa` (идемпотентно).
2. Чтение `rosstat_ppi_ved` (m/m, код `1323500.029.31`) и `rosstat_ppi_product` (m/m) с `FINAL`; ошибка, если таблиц/точек нет.
3. Парсинг встроенных mapping и полной панели; проверка `taxonomy_version` и полноты весов.
4. Агрегация и цепочка уровней; проверка непрерывности.
5. Отпечаток входов: SHA-256 по канонически отсортированным `(date, code, value)` + `spec_version` + `taxonomy_version`.
6. Гейт `source_publications` (`source='ppi_sa'`, `name='ppi_sa'`): если версия известна и `count() FROM ppi_sa FINAL` сходится с записанным — `no-op` без R; расхождение count — self-heal полным прогоном.
7. Запись входа во временный CSV (0600), вызов `Rscript` с встроенным скриптом (`exec.CommandContext`, timeout 15 мин, temp-каталог удаляется); ошибка R возвращается с stderr.
8. Парсинг `series,date,sa`; проверка полноты и порядка.
9. Расчёт `mm_sa`/`saar`/`saar3`; один `PrepareBatch` → `Append` → `Send` строк `ppi_sa`.
10. `series_catalog` (5 рядов, `source='ppi_sa'`) — после точек и до строки версии.
11. Строка версии в `source_publications` последней.

**Сеть в `init()` отсутствует.** R-скрипт и данные встроены через `//go:embed`, поэтому бинарник на staging не зависит от `scripts/` и `docs/`; внешняя зависимость — только `Rscript` + `seasonal`, как `pdftotext` у PDF-импортёров.

## 7. Каталог рядов

5 записей `series_catalog` (`source='ppi_sa'`): `total`, `food`, `nonfood`, `all`, `core`. `title` — что за ряд и база; `unit` — «индекс (100 = первый месяц ряда); mm_sa/saar/saar3 — %»; `frequency='M'`; `origin` — `rosstat_ppi_ved`/`rosstat_ppi_product` + X-13 `seats_log_cal` + версии; `description` — как читать колонки, что `saar3` — среднее трёх SAAR, что уровни разных рядов несопоставимы, что паритет с ЦБ не заявлен. Витрина и грант — T5.

## 8. Расписание

`dagu/ppi.yaml`: `type: chain`, `schedule: "17 14 * * 4"` (четверг 14:17 МСК, после цепочки `dagu/rosstat.yaml` 12:17), `overlap_policy: skip`, один шаг `ppi_sa` с `retry_policy` 3×300 с. Шаг в собственном DAG в хвосте общего расписания: падение derived-шага не лишает данных сырые импортёры. Окно «после 16-го рабочего дня» и проверка свежести — T6.

## 9. Паритет

10 текстовых якорей «Инфляции в России» (4 food, 4 non-food, 2 all → `core`) — [`2026-10-21-ppi-sa-anchors.csv`](../research/2026-10-21-ppi-sa-anchors.csv). `scripts/ppi_sa_parity.py` читает `ppi_sa` read-only через `scripts/lib/clickhouse.py`, берёт `saar3` на target-месяц и считает MAE/max/bias/corr по рядам и overall; результат — `docs/research/2026-10-21-ppi-sa-parity.json` и таблица в отчёте. Цель ±0,3 п.п. не достигнута в T3; T4 **публикует расхождение** с числами, без подгонки весов.

## 10. Тесты

- Go: парсинг mapping/панели; полнота весов 2026 для всех mapped-групп; KIPC-иерархия (соседи `04.3.1.1.1`/`.10`); вес 2026 (панель содержит `2022-04`); агрегация против эталонного CSV; цепочка/непрерывность; формула SAAR и краевые `NULL`; парсинг выхода R; пины SHA-256; версии в каждой строке; стабильность отпечатка; решение гейта; реестр/dagu; каталог 5 рядов; ошибка «Rscript не найден» через подменяемый runner.
- Python: экспорт полной панели (фикстура/скип без XLSX); паритетная математика и моки запроса.
- `make all` (включает `go test -race ./...`), `make docs-check`, `dagu validate dagu/ppi.yaml`; Python-наборы — отдельными командами.

## 11. Приёмка

Ожидаемо **≈436 строк** `ppi_sa`: `total` 164 (2013-01…2026-08) + `food`/`nonfood`/`all`/`core` по 68 (2021-01…2026-08). Первый прогон — `Imported 436 rows`; повтор — no-op по отпечатку без вызова R; `count() FINAL` не меняется; spot-значения записаны в протокол. Паритет — числа MAE в JSON и PR. `make mcp-check` — регрессия (витрина `v_rosstat_ppi` — T5).

## 12. Риски и ограничения

| Риск | Проявление | Что делаем |
|---|---|---|
| `Rscript`/`seasonal` нет в CI/staging | шаг падает до записи | Go-тесты R не вызывают; live — ручной; staging ставит `r-base`+`seasonal` (инструкция в `deploy/staging/README.md`), шаг последний в своём DAG |
| Локальный main отстаёт от #307 | v1-mapping/неполная панель | ветка от `origin/main` после `git fetch`; `taxonomy_version` читается из файла и сверяется |
