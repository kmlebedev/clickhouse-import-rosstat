# Дата оперативной справки инФОМ в `series_publication` — #624

Пункт `key-rate/phase-4-series-publication-spravka`, role:go. Контекст — дефект Ф1 бэктеста
`economist-oracle` (#622, отчёт [2026-11-16-economist-oracle-backtest-data-gaps.md](../../research/2026-11-16-economist-oracle-backtest-data-gaps.md), PR #623).

## Дефект

`v_series_publication.published_at` у волн «наблюдаемая/ожидаемая инфляция» (`source='cbr'`,
`cbr_infl_exp`) — дата **полного комментария** ЦБ, а не **оперативной справки инФОМ**.
Разрыв постоянный, ~7 дней: справка 2026-07-21 → `published_at` 2026-07-28; 2026-09-22 →
2026-09-29; 2026-03-18 → 2026-03-25. Скил отбрасывает свой якорный вход в день, на который
рассчитан.

Причина в коде: `writeSeriesPublications` → `buildSeriesPublications` берёт дату из
`data-tooltip-content` архива версий (`Infl_exp_YY-MM.xlsx` / `inFOM_YY-MM.pdf`); ЦБ ставит
туда дату полного комментария. `period_date` волны (14-е) — дата опроса, а не публикации.

## Источник правильной даты

`cbr_publication_calendar` уже содержит отдельную строку аналитического блока:

```
title  = Оперативная справка по результатам исследования «Измерение инфляционных ожиданий
         и потребительских настроений на основе опросов населения»
topic  = analytics
period = YYYY-MM   (месяц волны)
```

На dev такие строки есть за каждый месяц 2025-01 … 2026-11, ровно за 7 дней до строки
«Инфляционные ожидания и потребительские настроения» того же блока. Импортёр пишет календарь
в том же прогоне (`writeCalendarDelta` до `writeSeriesPublications`), поэтому источник свежий,
новых сетевых вызовов и DDL нет.

## Правило

1. Читать `cbr_publication_calendar FINAL` по префиксу
   `Оперативная справка по результатам исследования` (отсекает «…по результатам мониторинга
   предприятий»), `topic='analytics'`, `period` вида `YYYY-MM`.
2. Дату брать как `max(publication_date)` среди строк месяца, но только если она
   **не в будущем** относительно сегодня (MSK, по компонентам даты): `published_at` не должен
   оказаться впереди какого-либо as-of среза. Строка `planned=1` допустима — флаг отражает
   снимок, а не факт; на день публикации backfill отстаёт максимум на сутки.
3. Приоритет для `Archive == cbr_infl_exp`: **справка → tooltip архива → fallback конец M+1**.
   Справка принимается, только если её дата не раньше `period_date` волны (страховка от
   сдвига месяца в блоке календаря).
4. `quality='date'`, `published_at = 23:59:59 MSK` даты справки, `source_url` — ссылка строки
   календаря (`…/analytics/dkp/inflationary_expectations/#a_…`). `quality` не меняется:
   точность по-прежнему «дата», различие «справка/комментарий» видно по `source_url`.
5. Месяцы, закрытые справкой, не запрашиваются в релизном архиве (не качаем `Infl_exp_*.xlsx`
   зря). Месяцы без строки справки идут прежним путём (tooltip → fallback).
6. `cbr_indicators_cpd` и `cbr_survey` не меняются: у мониторинга предприятий оперативная
   справка выходит не каждый месяц, и текущая дата полного релиза для этих рядов корректна.

Дельта не меняется: `seriesPublicationChanged` разрешает смену даты при том же `quality`,
поэтому существующие строки `date` переписываются на более раннюю дату, повторный прогон —
no-op.

## Покрытие и остаток

Ряды — 2023-01 … 2026-10 (46 месяцев × 2). Точная дата закрывается для **2025-01 … 2026-10**
(21 месяц × 2 = 42 строки; 2026-10 уже равен дате справки и не переписывается). Календарь ЦБ
начинается 2025-01-10; волны 2023-01 … 2024-12 (48 строк) остаются с датой полного
комментария. Это консервативно (дата позже факта, утечки будущего нет), фиксируется как
остаток; машинно-читаемого источника справки за те годы нет — отдельный research.

## Что не меняется

DDL и `ReplacingMergeTree`-ключ `series_publication`, грант `kimi_reader`, расписание
`dagu/cbr.yaml`, состав источников. Витрина пересоздаётся тем же `util.CreateView`; правится
только текст её комментария.
