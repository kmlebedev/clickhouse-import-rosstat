# Пакет `polyus/` — парсеры отчётности Полюса (вынос из legacy `financial/`) — Design

**Дата:** 2026-10-10
**Пункт роадмапа:** самостоятельный пункт перед фазой 3 («DCF-движок»); после завершения — вход для `mine_plans` фазы 3.
**Сопутствующие документы:** [ARCHITECTURE.md](../../../ARCHITECTURE.md) §3 (шаблоны импортёров), §6.2 (DDL); [AGENTS.md](../../../AGENTS.md) правило 7 (пакет `financial/` — legacy).

## 1. Проблема

Отчётность Полюса парсится двумя файлами в пакете `financial/`, куда AGENTS.md запрещает добавлять новый код:

| Файл | Что делает | Состояние |
|---|---|---|
| `financial/gold_polyus.go` (123 строки) | xlsx-датапак: поквартальные операционные результаты по активам с 2007 (`CONSOLIDATED OPERATING RESULTS`, `OLIMPIADA`, `BLAGODATNOYE`, `TITIMUKHTA`, `VERNINSKOYE2`, `ALLUVIALS`, `KURANAKH`, `ZAPADNOYE`, `NATALKA`, `Sukhoi Log`) | Работает; таблица `databook_polyus`; тестов нет |
| `financial/gold_polyus_finance.go` (517 строк) | PDF-отчёты: `pdftotext -layout` по KPI-странице + регулярки; список URL → номер страницы в `init()` | Работает; половина исторических отчётов закомментирована; тестов нет |

Оба используют общий движок `financial/databook.go` (`FinDataBook`): скачивание PDF, `pdftotext`, батч-вставка.

Известные дефекты, которые надо закрыть в этом цикле:

1. **Историю видно только в коде.** Список отчётов и номеров KPI-страниц зашит в `init()` (строки 469–517 `gold_polyus_finance.go`), причём у большинства исторических отчётов строки закомментированы (`// "https://polyus.com/...": 4`). Непонятно, какие периоды реально разобраны, а какие нет.
2. **Свежий отчёт отсутствует.** Последний разобранный период — не 1H2026. Нужен парсинг пресс-релиза 1H2026: [press_reliz-1h26-_tu_mda_2.pdf](https://polyus.com/upload/iblock/80e/press_reliz-1h26-_tu_mda_2.pdf) (рус.). Английская версия релиза недоступна, английский файл `otchetnost-6m2026_eng.pdf` — это МСФО-отчётность без операционных KPI (см. §4.0).
3. **Нет тестов.** Ни xlsx-, ни PDF-парсер не покрыт; ошибка регулярки обнаруживается только на живом прогоне.
4. **Прод-код печатает в stderr.** `fmt.Fprintf(os.Stderr, "downloaded %d bytes...")` и `fmt.Printf` в парсерах — нарушение стиля (logrus).
5. **Парсер бросает работу на первой ошибке.** `finDataBookTableImport` возвращает `err` на любом нечисловом значении — одна битая ячейка в датапаке роняет весь импорт.

## 2. Цель

Вынести парсеры Полюса в самостоятельный пакет `polyus/`, привести их к конвенциям проекта (батч-вставка, logrus, проверка ошибок по правилу 6), сделать список разбираемых отчётов данными, добавить 1H2026 и закрыть тестами.

**Критерий приёмки:** `make all` зелёный; `make import STAT=polyus` пишет операционные и финансовые ряды Полюса, включая русский пресс-релиз 1H2026; в `financial/` кода Полюса не осталось; тесты парсеров работают без сети и покрывают оба языка.

## 3. Границы

**Входит:**
- новый пакет `polyus/` с xlsx- и PDF-парсерами, перенесёнными из `financial/`;
- таблица разбираемых отчётов как данные (`pages.go`), с 1H2026;
- тесты обоих парсеров на локальных фикстурах (без сети);
- закрытие дефектов 4 и 5;
- удаление кода Полюса из `financial/`, обновление импортёров/`main.go`, `ARCHITECTURE.md`, `README.md`.

**Не входит (отдельные пункты):**
- вынос остального содержимого `financial/` — пакет остаётся legacy целиком, кроме кода Полюса; см. §4.1 (карта переноса);
- построение `mine_plans` из распарсенных данных — это фаза 3;
- русские версии **принимаются** так же, как английские: парсер двуязычный (§4.0). Источники — `https://polyus.com/en/investors/results-and-reports/` (англ.) и раздел русских пресс-релизов; свежие релизы выходят только на русском;
- рефакторинг общих утилит HTTP/скачивания (`util.HdBase`, `util.GetCSV`) сверх того, что нужно парсерам Полюса.

## 4. Структура пакета

Пакет назван по компании, потому что парсит только её отчётность. Общая на несколько компаний структура появится, когда в контур войдут пиры (`peers_nav`, фаза 3/12) — тогда `polyus/` станет одним из источников наряду с будущим пакетом для ЮГК/Селигдара, а не «общим золотодобывающим» пакетом.

```
polyus/
  polyus.go          типы (Report, MetricDefinition), регистрация импортёров (init(), Name())
  datapack.go        xlsx-парсер операционных результатов   (перенос gold_polyus.go, 123 строки)
  kpi.go             PDF-парсер KPI пресс-релизов EN/RU      (перенос gold_polyus_finance.go, 517 строк)
  ifrs.go            PDF-парсер МСФО-форм (P&L, баланс) — новый режим разбора
  pages.go           таблица «отчёт → тип → KPI-страницы → парсить да/нет» как данные
  metrics.go         словарь метрик KPI (EN + RU)
  ifrs_metrics.go    словарь статей МСФО (EN)
  periods.go         разбор обозначений периода (EN «1H 2026» / RU «1 п/г 2026»)
  source.go          скачивание PDF + pdftotext (выделено из financial/databook.go)
  datapack_test.go   тесты xlsx-парсера на локальной фикстуре
  kpi_test.go        тесты KPI-парсера на слепках (EN и RU)
  ifrs_test.go       тесты МСФО-парсера на слепке EN
  testdata/          фикстуры (xlsx + текстовые слепки pdftotext)
```

Разделение по файлам отвечает разным скоростям изменения:

- `kpi.go` / `metrics.go` — разбор пресс-релизов: код разбора стабилен, словарь `Prefix`-строк растёт с каждым отчётом на двух языках.
- `ifrs.go` / `ifrs_metrics.go` — разбор МСФО: другая схема (статья + два столбца периодов), поэтому отдельный файл, а не ветка внутри KPI-парсера. Это защищает работающий KPI-парсер от регрессий.
- `periods.go` — разбор обозначений периода. Сейчас логика в `gold_polyus_finance.go` жёстко английская: `periodMatch = ([1-4][HQ])\s+(\d{4})` и `reH = ^([12])H(\d{4})$`. Русские пресс-релизы используют другой формат («1 п/г 2026»), МСФО — третий (номер года без H/Q). Разбор выносится отдельно и покрывается тестами на все три формы.
- `source.go` — минимальный вынос нужной части `FinDataBook`: скачивание с проверкой `%PDF-` заголовка и `pdftotext -f N -l N -layout -nopgbrk -enc UTF-8`.

### 4.0 Двуязычность и два типа документов (требование, а не опция)

Проверено на живых файлах 1H2026:

| Документ | Содержимое | Валюта / формат |
|---|---|---|
| `press_reliz-1h26-_tu_mda_2.pdf` (пресс-релиз + MD&A, рус.) | добыча руды, производство золота (koz), TCC, прогноз — **операционные KPI** | «1 п/г 2026», «2 п/г 2025» |
| `otchetnost-6m2026_eng.pdf` (МСФО, англ.) | выручка, прибыль, налог, EPS, баланс — **финансовые формы** | `in millions of US Dollars`; заголовки периодов `2026 / 2025` |
| `msfo-pao-polyus-za-6m2026.pdf` (то же, рус.) | те же формы | `в миллионах российских рублей` |

**Выбор языка МСФО — английский.** Обоснование: датапак `polyus_datapack_*.xlsx` англоязычный, а английская МСФО отчитывается в долларах США (`Total revenue 4 674`) — та же система координат, что и у исторических рядов. Русская МСФО даёт рубли (`Итого выручка 352 667`), которые в одну таблицу с датапаком не лягут без пересчёта по курсу. Дополнительно английские заголовки уже покрыты словарём `metrics` в `gold_polyus_finance.go` и регулярками периода.

**Двуязычность пресс-релизов остаётся обязательной:** свежие релизы (в т.ч. 1H2026) выходят только на русском, а русский формат периода (`1 п/г 2026`) не разбирается текущими регулярками `([1-4][HQ])\s+(\d{4})`.

**Два типа документов — два режима разбора.** МСФО-отчётность не содержит KPI, а пресс-релиз не содержит форм; это разные схемы парсинга, а не один алгоритм с разными словарями:

| Режим | Документы | Что разбирает | Разбор |
|---|---|---|---|
| KPI | пресс-релизы (EN/RU) | добыча, производство золота, TCC, AISC, прогноз | таблица «метрика + строки периодов» |
| МСФО | `otchetnost-*_eng.pdf` | выручка, прибыль, налог, EPS, статьи баланса | таблица «статья + два столбца (отчётный / прошлый)» |

Поэтому в `pages.go` отчёт получает поле `Kind` (`"kpi"` / `"ifrs"`), а `metrics.go` — отдельный словарь для МСФО-статей. Существующий парсер KPI при этом не ломается: МСФО-ветка — новый код, а не переделка старого.

Что это даёт для контура: пресс-релиз закрывает операционные входы DCF (добыча, TCC), МСФО — финансовые (выручка, долг для `NetDebt`, налог).

## 6. Таблица отчётов как данные (`pages.go`)

Вместо закомментированных строк в `init()` — явный список:

```go
type Report struct {
    URL      string
    Period   string // "FY2025", "2026H1"
    Kind     string // "kpi" | "ifrs" — режим разбора (см. §4.0)
    Lang     string // "en" | "ru" — набор префиксов и разбор периода
    Pages    []int  // KPI-страницы в PDF (для ifrs — страницы форм)
    Enabled  bool   // false — отчёт известен, но страницы не выверены
}

var reports = []Report{ ... }
```

Правила:
- у каждого отчёта заполнены `Period`, `Kind`, `Lang` и `Pages`; отчёт, который не парсится, остаётся в списке с `Enabled: false` и комментарием причины — история отчётов видна целиком, «выключенное» не теряется;
- русский пресс-релиз 1H2026 добавляется с `Enabled: true`, `Kind: "kpi"`, `Lang: "ru"` после выверки страниц на живом PDF (номер страницы определяется прогоном `pdftotext`, а не угадывается);
- английская МСФО 1H2026 добавляется с `Enabled: true`, `Kind: "ifrs"`, `Lang: "en"` тем же порядком;
- импортёры пропускают `Enabled: false` с логом `log.Infof("skip report %s (%s): disabled", ...)`.

## 7. Обработка ошибок (дефект 5)

xlsx-парсер сейчас падает на первой нечисловой ячейке. Новое поведение:
- ячейки `-`, `N/A`, пустые — пропускаются (как сейчас);
- значение, не поддающееся разбору, — пропуск строки с `log.Warnf` (не `return err`), счётчик пропусков пишется в итоговый лог;
- жёсткая ошибка остаётся для структурных сбоев: лист/таблица не найдены, файл не открылся, `batch.Append`/`Send` не прошли.

Правило 6 AGENTS.md («каждый `batch.Append` с проверкой `err`») сохраняется без исключений.

## 8. Тестирование

**xlsx-парсер** (`datapack_test.go`): фикстура — копия `financial/data/polyus_datapack_fy2025_new.xlsx` в `polyus/testdata/`. Проверяется: число разобранных строк > 0; добыча конкретного актива за конкретный квартал равна ожидаемому числу (значение берётся из файла и фиксируется как эталон); отрицательные значения в скобках разбираются со знаком минус; ячейка `N/A` пропускается, импорт не падает.

**PDF-парсер KPI** (`kpi_test.go`): фикстуры — сохранённые текстовые слепки `pdftotext -layout` KPI-страниц (сеть в тестах не используется):

- английский релиз (исторический, из текущего рабочего списка) — проверяет, что перенос не сломал существующее поведение: метрика `gold_output` распознана, период и значения совпадают с ожидаемыми;
- русский пресс-релиз 1H2026 — проверяет двуязычность: период `1 п/г 2026` разобран в `2026H1`, метрика производства золота распознана по русскому префиксу, значение равно `1287` (koz).

**PDF-парсер МСФО** (`ifrs_test.go`): фикстура — слепок `отчет о прибылях`/`statement of profit or loss` из `otchetnost-6m2026_eng.pdf` (англ.). Проверяется: `total_revenue` = `4674`, `profit_for_period` = `829`, `eps_basic` = `0.87`; период определён как `2026H1`; русская МСФО-версия в этот пункт не входит (парсим английскую, см. §4.0).

**Тесты разбора периода** (`periods_test.go` или кейсы внутри `kpi_test.go`): таблица «вход → ожидаемый Period/Type» на все три формы — `1H 2026` → `2026H1`/`H`, `1 п/г 2026` → `2026H1`/`H`, `2 п/г 2025` → `2025H2`/`H`, `2025` → `2025FY`/`FY`, `4Q 2022` → `2022Q4`/`Q`, МСФО-шапка `2026 / 2025`; неизвестный формат → ошибка, а не тихий пропуск.

**Живой прогон (ручная приёмка):** `make import STAT=polyus` — скачивает русский пресс-релиз 1H2026 и английскую МСФО с сайта, парсит, пишет в ClickHouse; проверка `SELECT period, metric, value FROM polyus_financial_metrics FINAL WHERE period LIKE '%2026%' ORDER BY metric LIMIT 10` — ожидаются и операционные (добыча, производство), и финансовые (выручка, прибыль) метрики.

## 9. Совместимость и документация

- `main.go`: добавляется blank-импорт `polyus`; существующий импорт `financial` **сохраняется** — в нём остаются `databook_ugk` (ЮГК), мёртвые парсеры металлургов и утилиты, а также используемый ими общий движок `databook.go`. - `CLICKHOUSE_IMPORT_STAT` для нового пакета: `polyus` (один импортёр на оба парсера) — уточняется на этапе плана по фактической структуре `Name()`.
- `ARCHITECTURE.md` §6.1 (таблица импортёров) и `README.md` — новый пакет, состав таблиц, команда запуска.

## 10. Риски

| Риск | Митигация |
|---|---|
| Разметка PDF 1H2026 отличается от исторических отчётов, регулярки не срабатывают | Формат английского релиза и агрегатная форма (значения столбцом, а не строками с периодом) — разные вещи; разбор проверяется на живом файле до включения отчёта `Enabled: true`, тест на слепке фиксирует разметку |
