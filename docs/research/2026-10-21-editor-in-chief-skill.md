> **Объект:** контур публикаций по ключевой ставке — `docs/publications/2026-10-18-key-rate.md` (PR [#199](https://github.com/kmlebedev/clickhouse-import-rosstat/pull/199), merged 2026-10-18 13:43) и шаблон [KEY_RATE_PUBLICATIONS.md](../KEY_RATE_PUBLICATIONS.md).
> **Задача:** спроектировать ролевой скил `.kimi-code/skills/editor-in-chief/SKILL.md`, который собирает числа из витрин через MCP, перепроверяет утверждения статьи, собирает/обновляет публикацию на текущую дату и выдаёт рекомендации к шаблону.
> **Метод:** рецензия статьи 2026-10-21 (MCP `mcp__clickhouse__run_query`, пользователь `kimi_reader`, ClickHouse 26.10.1.1853, `now()=2026-10-21 11:52 +05:00`), разбор PR #199 и три внешних редакционных стандарта (BBC, NYT, Reuters), прочитанных 2026-10-21.

## 1. Короткий вывод

**Go.** Скил нужен, и он должен быть отдельной **ролью** («главный редактор»), а не разделом `ml-engineer` или `research-engineer`: его работа — не считать прогноз и не исследовать источник, а **удерживать соответствие текста данным на дату выпуска**. Кейс #199 показывает, почему: статья, собранная дисциплинированно (снимок, версия данных, 26 сносок, чек-лист §9), за **три дня** накопила 12 классов расхождений с витринами — от устаревших чисел до перепутанной семантики бюджетных рядов. Это не небрежность автора, а отсутствие шага «перепроверить перед выпуском» и требования «каждое число воспроизводится SQL».

Минимальный набор возможностей скила:

1. **Снимок на дату** (`version()`, `timezone()`, `now()`, `data_version`) и инвентарь входов с `max(date)`.
2. **Семантика ряда** — из `v_series_catalog` (`title`, `unit`, `frequency`, `description`), а не из названия.
3. **Таблица «утверждение → SQL → пересчёт → вердикт»** для каждого числа статьи, включая сноски.
4. **Пересчёт производных** (г/г, реальная ставка, спреды, вменённая вероятность, суммы вероятностей).
5. **Отчёт рецензии** с severity: блокер / важное / мелкое.
6. **Рекомендации к шаблону** — не правки «попутно».

### 2.3. Корневые причины

1. **Нет повторной верификации на дату выпуска.** Снимок 18.10 и выпуск — один проход; за 3 дня обновились USD, золото, RUONIA, KEYRATE, ОФЗ, бюджет, опросы предприятий, появился недельный ИПЦ за 12.10.
2. **«Нет обновления» проверялось один раз и стало ложным.** Ряд недельного ИПЦ обновился после снимка, но текст остался.
3. **Семантика бралась из названия, а не из `v_series_catalog`.** Отсюда `minfin_mesyats` как «кумулятивный» и два разных ряда депозитов под одним числом.
4. **Текст и сноски сверялись не построчно.** 68,14 в тексте и 70 937 232 в сноске — один и тот же «факт» из разных рядов.
5. **Статусы инфраструктуры брались по памяти.** «Витрины нет» при существующей витрине; статус журнала не сверен с `v_key_rate_dashboard`.
6. **Даты периодов и дубли строк не проверялись.** Квартальный ряд прочитан как месячный: «I кв. +0,95 %» — это IV кв. 2025, I кв. 2026 = −0,15 %. Недельная статистика считалась по 218 строкам вместо 111 — доля подорожавших 71,6 % вместо 72,1 %.
7. **Не было адверсариального прохода.** Автор проверял, что числа есть; никто не проверял, что они значат. Более новый прогон журнала (19.10) не сверен с опубликованным (18.10).

## 3. Практики больших изданий → шаги скила

| Практика | Источник | Что требует | Шаг скила |
|---|---|---|---|
| Due accuracy; «well sourced, based on sound evidence, and where possible corroborated»; честно говорить, чего не знаешь | [BBC Editorial Guidelines §3 Accuracy](https://www.bbc.co.uk/editorialguidelines/guidelines/accuracy) (прочитано 2026-10-21) | каждый факт — с источником; несопровергнутое — атрибутируется | §4 шаги 3–6: инвентарь, семантика, SQL-воспроизведение, verdict |
| «Serious factual errors should normally be acknowledged and corrected quickly, clearly and appropriately»; accuracy важнее скорости | BBC §3.2.4–3.2.5 | исправление видимо, не задним числом | §6 «no silent rewrite», журнал исправлений; §7 отчёт |
| Integrity, independence, freedom from bias; «unbiased and reliable news» | [Reuters Trust Principles](https://www.thomsonreuters.com/en/about-us/trust-principles.html) (2026-10-21) | не выбирать удобный трек; публиковать расхождение | §6: три трека и расхождение — обязательны; никакого «усреднения» |
| «Imagine the perspective of a fair-minded but skeptical reader… knows everything about how we reported, wrote, edited» | [NYT Ethical Journalism Handbook, ch. 1](https://www.nytimes.com/editorial-standards/ethical-journalism.html) (2026-10-21) | текст должен выдерживать взгляд скептика, знающего процесс | §4 шаг 6: адверсариальная таблица; §7 severity |
| Числа и единицы по стайлгайду | класс практик AP/Economist (не читались: подписка/403) | единицы, округления, «б.п.» vs «%» | §5 матрица: units/rounding/sign |

Три принципа, которые repo добавляет к этому:

- **Provenance числа** = ряд + дата ряда + единица + дата снимка (а не только «Росстат, 05.10»).
- **Show your work** — каждый тезис воспроизводится SQL; SQL сохраняется в отчёте рецензии.
- **Публикация — событие, а не файл.** Один файл на дату; правки — с пометкой «обновлено» и записью в журнал исправлений.

## 4. Дизайн скила

### 4.1. Роль и триггеры

`editor-in-chief` — ролевой скил (как `ml-engineer`/`research-engineer`), а не процессный: он маршрутизирует задачи «подготовить / обновить / отревьюить публикацию» и задаёт границы. Триггеры:

- предзаседание, постзаседание, «после резюме», недельный разбор, опорное заседание;
- пост-апдейт и сверка факта после решения;
- ревью/факт-чек существующей статьи;
- предложение изменений в `KEY_RATE_PUBLICATIONS.md`.

### 4.2. Границы

| Делает | Не делает |
|---|---|
| Читает витрины через MCP `kimi_reader`, пересчитывает, пишет статью и чек-лист | Не пишет прод-код, DDL, GRANT, не меняет импортёры |
| Проверяет журнал через `make ml-live-check` | Не пишет в `forecast_log` и не публикует пост |
| Готовит рекомендации к шаблону | Не правит шаблон «попутно» — отдельный пункт |
| Требует артефакты треков из файлов | Не пересчитывает ML/LLM-модели и не подставляет их вместо статистики |

### 4.3. Рабочий цикл (12 шагов)

**Режим ревью** (только чтение): шаги 2–6 и 8–10; шаг 1, 11 и 12 не выполняются.

| # | Шаг | Выход |
|---|---|---|
| 1 | Пункт, issue, формат публикации, дата заседания | шапка отчёта |
| 2 | Снимок: `version()`, `timezone()`, `now()`, пользователь | строка снимка |
| 3 | Инвентарь входов: ряд → `max(date)` → `last_value` → свежесть vs естественный цикл; дедупликация `SELECT DISTINCT series, date, value` | таблица входов |
| 4 | Семантика: `v_series_catalog` (`title`, `unit`, `frequency`, `origin`, `description`); привязка даты (квартал = 1-е число следующего квартала; волна опроса ≠ месяц данных) | таблица «ряд → что значит» |
| 5 | Пересчёт производных: г/г, реальная ставка, спреды, `P(cut)`, E[step], суммы вероятностей; недельная медиана — по 111 дедуплицированным рядам без агрегата | таблица пересчётов |
| 6 | Таблица «утверждение статьи → SQL → значение → вердикт»; каждый блокер подтверждается вторым запросом | отчёт рецензии |
| 7 | Три трека: статистика/LLM/ML из артефактов; канонический артефакт — `forecast_date` = дата среза | блок §7 |
| 8 | Рыночный контур: settle, volume, OI, шаг, `P(cut)` — только на `max(date)`; ликвидность рядом | блок §4 |
| 9 | Пороги: пересчитать против текущих значений; что сработало | блок §6 |
| 10 | Журнал: `make ml-live-check` или `v_key_rate_dashboard` (`forecast`): `as_of` + `data_version`; новый прогон назвать | строка статуса |
| 11 | Сборка по §4 шаблона: заголовок, подзаголовок, 8 разделов, сноски | статья |
| 12 | Чек-лист §9 + повторный снимок за 24 ч до выпуска | checklist |

### 4.4. Матрица проверок

| Класс | Проверка | Пример из #199 |
|---|---|---|
| Свежесть | `max(date)` каждого ряда на дату выпуска, не на дату снимка | USD, KEYRATE, ОФЗ |
| «Нет обновления» | перед публикацией повторить запрос; если данные появились — снять пометку | недельный ИПЦ 12.10 |
| Существование ряда | `v_series_catalog` и `system.tables`; не утверждать «ряда нет» по памяти | агрегат недельного ИПЦ, `v_key_rate_dashboard` |
| Семантика | `description` ряда: охват (федеральный/консолидированный), период (месяц/накопление), группа (физлица/ИП) | `minfin_mesyats`, депозиты |
| Единицы | % vs п.п. vs б.п.; млн vs млрд vs трлн | депозиты 68,14 vs 70,94 трлн |
| Дата периода vs публикации | волна опроса ≠ месяц данных; дата ряда — не дата публикации | ИБК SA |
| Текст ↔ сноска | одно число — один ряд в тексте и сноске | депозиты |
| Производные | пересчитать формулу, а не переписать число | г/г кредита, реальная ставка, P(cut) |
| Вероятности | сумма 100 ± 0,1; округление объяснено; E[step] — взвешенное среднее, не обещание | 81,65/16,24/2,12 |
| Статусы | «готово/не готово» проверяется запросом, а не памятью | `v_key_rate_dashboard` |
