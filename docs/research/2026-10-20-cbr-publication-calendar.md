# График публикаций ЦБ как источник `published_at` и as-of (2026-10-20)

> **Объект:** график публикаций Банка России `https://www.cbr.ru/calendar/`, его ICS-выгрузка и релизные архивы трёх рядов контура ставки — `cbr_infl_exp`, `cbr_indicators_cpd`, `price_expectations`/`cbr_survey`.
> **Задача:** решить, может ли календарь дать исторические `published_at` для этих рядов, и каким должно быть правило as-of по дате/времени заседания (включая запас 2 дня для заседания 23.10.2026).
> **Метод:** live-пробы 2026-10-20 (`curl`, разбор HTML/ICS на Python), сверка дат календаря с релизными страницами ЦБ, чтение текущих витрин ClickHouse через MCP `kimi_reader`.
> **Границы:** не проверялись staging, полный перебор всех релизных страниц 2016–2024 (только выборка), 2014–2015 и pre-2022 survey, фактические времена аналитических релизов, ревизии рядов, платный доступ/лицензия, поведение календаря через +1 и +3 дня. ML-прогоны не выполнялись.

## 1. Короткий вывод

1. **Календарь — `go` как forward-расписание публикаций** (статистическая таблица + ICS) и как **исторический слой 2025–2026** (22 месячных аналитических блока). Он не требует авторизации, отдаётся server-rendered HTML и ICS, пригоден для ежедневного импорта.
2. **Календарь — `no-go` как единственный исторический источник `published_at`.** Статистическая таблица смотрит только вперёд; аналитическая история ограничена 22 месяцами (январь 2025 … октябрь 2026); в ICS 790 событий только на 2026-09-29 … 2027-12-30. Историческая глубина контура ставки (2014+) им не покрывается.
3. **Исторические даты — из релизных архивов по каждому ряду:**
   - `cbr_infl_exp` — 383 элемента списка версий, 197 уникальных дат, **2013-07-11 … 2026-09-29** (XLSX с 2016, PDF с 2013);
   - `cbr_indicators_cpd` — версии «Динамики потребительских цен» **2016–2026** (HTML-страницы 2021–2026, PDF 2016–2022);
   - `price_expectations`/`cbr_survey` — версии «Мониторинга предприятий» **2022-05 … 2026-10** (точки — до 2026-09).
   Для более старых точек — только консервативный fallback «конец месяца M+1», помеченный в данных как fallback, а не как точная дата.
4. **Единый `available_from_cpd` для всех рядов — `no-go`.** У рядов разные даты публикации; нужен per-series lookup `published_at` + признак качества (`exact_time` / `date` / `fallback`).
5. **As-of:** дата+время заседания **13:30 МСК**, строгое `published_at < cutoff`; для даты без времени — `23:59 МСК`; для заседания **23.10.2026** — предзарегистрированный запас **2 дня** (cutoff `21.10.2026 23:59 МСК`). Это отдельный pre-registered прогон, не post-hoc правка #296.

**Форма календаря.** `form action="/calendar/" method="get"` с `UniDbQuery.year` (в разметке только 2026 и 2027), `UniDbQuery.period` (1/3/6/12 месяцев), `UniDbQuery.pID` (тема) и `UniDbQuery.SSRD`. Произвольные годы (`2014`, `2019`, `2024`, `2025`) игнорируются: выдача совпадает с текущей (618 строк дат в статистической таблице при `period=4`; 230 209 байт против 230 017 байт по умолчанию — разница только в текущей дате/состоянии страницы). Историю через `year` получить нельзя.

**Термины.** Страница прямо предупреждает: «В календарях публикаций официальной статистической и аналитической информации могут происходить изменения. Следите за обновлениями». Значит, календарь — **план**, а не журнал фактических публикаций. Юридические условия использования на странице не выделены; данные публичные, но это не заменяет проверку terms перед промышленным использованием.

## 4. Винтажи, ревизии, PIT

- **Календарь — не винтажный лог.** Он не говорит, когда значение фактически появилось и как оно ревизовалось; он говорит, когда публикация запланирована (и, для прошедших месяцев, когда состоялась). Ревизии SA-рядов (например, сезонно сглаженные ряды ДИП) календарь не отслеживает.
- **Точность даты.** Релизные страницы дают день, но не время; ICS/статистическая таблица дают время для части статистических публикаций. Аналитические релизы времени не имеют.
- **Правило среза (предложение):**
  - `meeting_datetime` = `events_calendar.event_date` + `event_time` (13:30 МСК) для заседаний СД; для остальных событий — по их времени, иначе 23:59 МСК.
  - `cutoff` = `meeting_datetime`; для заседания **23.10.2026** — `meeting_datetime − 2 дня` = **21.10.2026 23:59 МСК** (предзарегистрированный запас, а не подгонка).
  - Точка доступна, если `published_at < cutoff` (строгая граница; публикация ровно в 13:30 не участвует).
  - Если известна только дата, `published_at` трактуется как `23:59 МСК` этой даты — консервативно; если время известно из ICS/таблицы, используется точное время.
- **Качество.** Для каждой точки — `exact_time` (время из ICS/таблицы), `date` (дата релиза), `fallback` (консервативный конец M+1). `fallback` не должен выглядеть как точная дата в отчётах и в `forecast_log.data_version`.
- **Почему не один `available_from_cpd`.** Сейчас `scripts/key_rate_model.py` (`available_from_cpd`, `available_from_survey`) использует конец M+1 для всех месячных рядов. Это теряет информацию в заседаниях, которые проходят после фактической публикации, но до конца M+1, и одновременно может быть слишком оптимистичным для рядов, опубликованных позже. Нужен per-series lookup.

## 5. Риски и режимы отказа

| Риск | Проявление | Митигация |
|---|---|---|
| DDoS-Guard / WAF | 403/503, cookies, капча | обычный `util.HttpClient` с ретраями, без параллельного flood; кэш последней удачной версии |
| Смена разметки | пропали `dropdown_title`, `table.data`, `data-tooltip-content` | тесты на фикстурах; fail-fast при нуле строк; логировать селекторы |
| `year` игнорируется | запрос «2014» отдаёт текущую выдачу | не использовать `year` для истории; история — только релизные архивы |
| ICS только вперёд | 2026-09-29 … 2027-12-30 | ICS — для forward-расписания; история — из релизных страниц |
| Planned ≠ actual | дата в календаре сдвинулась | при импорте сверять с релизной страницей; хранить `planned` и `actual` отдельно |
| 404 / кривые ссылки | `CPD_2025-4/5`, `CPD_2022-6` | fallback: PDF-архив, затем календарь; помечать `quality` |
| Нет времени у аналитики | нельзя отличить 10:00 от 18:00 | date-only → 23:59 МСК; для 23.10.2026 — запас 2 дня |
| Праздники/переносы | дата публикации сдвинута | брать фактическую дату релиза, не правило «N-й день» |
| MSK/UTC | ICS в UTC, страницы в МСК | хранить `DateTime` с таймзоной Europe/Moscow; в ICS конвертировать |

## 6. Рекомендация и критерий приёмки

### 6.1. Go/no-go

| Решение | Вердикт | Обоснование |
|---|---|---|
| Календарь как forward-расписание публикаций | **go** | HTML/ICS, без авторизации, ежедневно, время для части строк, 22 месяца истории для валидации |
| Календарь как единственный исторический `published_at` | **no-go** | статистическая история отсутствует, аналитика — 22 месяца, planned ≠ actual |
| Релизные архивы как исторический источник | **go** | `infl_exp` 2013+, `cpd` 2016+, `survey` 2022-05+; точные даты, дешёвый HTML-разбор |
| Единый `available_from_cpd` для всех рядов | **no-go** | разные даты публикации; нужен per-series lookup |
| ML-прогоны в research-PR | **no-go** | ролевая граница; отдельный pre-registered ML-прогон |

### 6.2. Handoff

| Слой | Что сделать | Критерий приёмки |
|---|---|---|
| Go — календарь | импортёр `cbr_publication_calendar` (таблица `cbr_publication_calendar`: `publication_date Date`, `publication_time Nullable(String)`, `title String`, `topic LowCardinality(String)`, `period String`, `source_url String`, `planned UInt8`, `loaded_at DateTime`; `ReplacingMergeTree ORDER BY (publication_date, title, period, source_url)`), витрина `v_cbr_publication_calendar`, `GRANT SELECT`; ежедневный шаг в `dagu/cbr.yaml` | 173+ строк статистического окна и 22 аналитических блока; повтор — no-op; `make all`, `make mcp-check` |
| Go — `published_at` | generic `series_publication` (`source`, `series`, `period_date`, `published_at DateTime`, `quality LowCardinality(String)`, `source_url`) + витрина `v_series_publication`; backfill из релизных архивов: `cbr_infl_exp` 2013+, `cbr_indicators_cpd` 2016+, `cbr_survey` 2022-05+; fallback — конец M+1 с `quality='fallback'` | точные даты на проверенных месяцах; 404/кривые ссылки не роняют прогон; повтор идемпотентен; `make all` |
| Python — as-of | заменить `available_from_cpd`/`available_from_survey` на lookup `published_at`; `meeting_datetime` 13:30 МСК; `published_at < cutoff`; date-only → 23:59; для 23.10.2026 — `cutoff = meeting − 2 дня`; флаг включает новый режим, baseline без флага не меняется | тесты на границы (13:30, 23:59, 2 дня); артефакты baseline без флага побайтно те же; отчёт с покрытием `exact/date/fallback` |
| ML — pre-registered rerun | отдельный прогон rate model/channel fan и CPI-эксперимента с календарным as-of; гипотезы, окна, метрики (RMSE/MAE, CRPS, coverage 80 %, DM-HLN, CI) и правила остановки зафиксировать до запуска; сравнить с baseline; не править #296 | отчёт с числами и CI; вывод «значимо/не значимо»; паспорт прогона; без `forecast_log` |

**Оценка объёма (person-days, грубо):** research — 1–2; Go (календарь + `published_at`) — 3–5; Python (as-of) — 2–3; ML (rerun) — 2–3. Итого 8–13; критические зависимости — Go → Python → ML.

**Критерий приёмки research-пункта:** документ с покрытием, as-of правилом, go/no-go и handoff; `make docs-check` зелёный; issue/роадмап обновлены; прод-код, схема и ML-артефакты не менялись.

## 7. Что не проверено

- staging и продакшн-окружение; поведение DDoS-Guard при длительной серии запросов.
- Полный перебор всех HTML-страниц `CPD_2016…2024` и всех PDF: проверена выборка; часть страниц может отсутствовать или иметь иные даты.
- 2014–2015 для `cbr_indicators_cpd` и pre-2022 для `cbr_survey`: точных дат в архивах не найдено; остаётся fallback.
- Фактические времена аналитических релизов (страницы дают только дату); ICS их не содержит.
- Ревизии рядов и винтажи (кроме `cbr_dip_bulletin`) — не проверялись; календарь их не покрывает.
- Лицензия/terms и допустимость промышленного использования; платный доступ/API.
- Повторная проба через +1 и +3 дня; стабильность разметки на горизонте.
- Полнота Wayback для пропущенных месяцев.
