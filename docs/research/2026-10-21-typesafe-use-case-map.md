# TypeSafe (Jev, System One): применимость и пилот для контура ключевой ставки (2026-10-21)

> **Объект:** TypeSafe Jev — «System One» модель типизированных решений: `Choice`, `Score`, `Noul` над `state`, без генерации текста.
> **Задача:** какие задачи `clickhouse-import-rosstat` модель может закрыть, где она не подходит, и что она даёт приоритетному пункту `key-rate/phase-4-first-publication` (#191).
> **Метод:** desk research официальной документации TypeSafe (use-case map, primitives, confidence, models, how-to-build), сверка с роадмапом, витринами и публикационным контуром; живых вызовов API не было.
> **Границы:** не проверены латентность, фактический расход токенов, качество на русском языке, калибровка на наших классах и условия хранения данных. Всё, что ниже помечено «оценка», — расчёт по документации, а не измерение.

---

## 1. Короткий вывод

1. **TypeSafe — не ещё одна LLM, а слой типизированных суждений.** Он возвращает выбранный вариант, полное распределение вероятностей и `confidence`, а не текст. Это ровно то, чего не хватает `forecast_log`: числа, которые можно писать в журнал, сравнивать по Brier/log loss и пропускать через gate.
2. **Цена почти не имеет значения.** В прайсе `$42` — за **Btok** (миллиард токенов), то есть **$0.042 за 1M** входных токенов; выход бесплатный ([models](https://docs.typesafe.ai/models)). Один прогон трека ставки — примерно **$0.0015**, год из восьми заседаний — **$0.012**. Даже массовая разметка 200 новостей в день — около **$0.25/мес**. Ошибка «$42 за миллион» завысила бы цену в 1000 раз.
3. **Главная ценность — контур ставки:** независимый вероятностный трек cut/hold/hike, пост-заседание «факт против прогноза», семантический QA статьи до выпуска и вектор 11 каналов ЦБ как признаки.
4. **Второй по ценности — типизированные новостные признаки:** event type, `cb_channel`, policy-event (тарифы, эмбарго, топливо, бюджет) для CPI-nowcast. Это не замена GLM-разметке: TypeSafe не пишет `summary`, поэтому GLM остаётся, а TypeSafe может стать вторым слоем там, где нужны вероятности, а не текст.
5. **Чего он не закрывает:** генерацию объяснений и `summary`, детерминированный разбор PDF/XLSX, числовые проверки свежести и нормализации, DDL/запись в ClickHouse. Это не «замена LLM-треку», а его вероятностная половина.
6. **Главные риски:** английский — основной язык, русский «handled but not equally well»; калибровка на наших классах не доказана; вендор молодой, SLA нет; черновик статьи до публикации — чувствительный текст, который уходит внешнему API.
7. **Рекомендация:** **go на ограниченный пилот** в контуре ставки после #191; **no-go** на замену GLM-разметки, детерминированных парсеров и на production без 22-заседания бэктеста, RU/EN-теста и shadow/canary.

## 2. Что такое TypeSafe

### 2.1. Примитивы и ответы

Модель принимает `state` (текст или JSON) и один или несколько вопросов; каждый вопрос оценивается независимо и параллельно, ответы ограничены заданными вариантами ([primitives](https://docs.typesafe.ai/primitives)):

| Тип | Что спрашивает | Что возвращает |
|---|---|---|
| `Choice` | «Какой из этих вариантов?» | `choice`, полное распределение `probabilities`, `confidence` |
| `Score` | «Какой уровень по упорядоченной шкале?» | `score`, `legend`, `probabilities`, `confidence` |
| `Noul` | «Верно ли утверждение?» | `noul` — вероятность «да» (0…1), без отдельного `confidence` |

Важные свойства:

- **Ответ не парсится из прозы.** Распределение всегда по нашим вариантам; значение вне схемы вернуть нельзя.
- **Вопросы независимы.** Один ответ не становится скрытым контекстом для другого; композиция — в коде.
- **`confidence` — не вероятность правильности.** Это статистика формы распределения: 1 при всей массе на одном варианте, 0 при равномерном распределении ([confidence](https://docs.typesafe.ai/confidence)). Для `Noul` отдельного `confidence` нет; если нужен порог, используют `|2p − 1|`.
- **Заявленная калибровка** — свойство модели на её тренировочном распределении (RLCD), а не гарантия для наших классов и русского текста. Это надо измерять.
- **Скорость** — «most queries complete in about 100 ms» по документации; в нашем окружении не измерялась.
- **Батчинг:** число вопросов не ограничено, ограничен объём; 13 вопросов в одном запросе ≈12× дешевле и ≈10× быстрее 13 отдельных вызовов ([parallel questions](https://docs.typesafe.ai/cookbooks/parallel_questions)).

### 2.2. Цена, лимиты, язык

| Параметр | Значение | Следствие для нас |
|---|---|---|
| Цена | `$42 / Btok` = **`$0.042 / Mtok`** входных токенов; выход бесплатный | трек ставки — доли цента; массовая разметка — центы |
| Контекст | 64k на запрос / 32k на вопрос; long context 262k по заголовку | наш state 6–10k токенов помещается с запасом |
| Язык | английский — основной; другие языки «handled but not equally well» | русские цитаты ЦБ требуют отдельного теста |
| Дообучение | нет; домен задаётся `instructions`/`criteria` | правила каналов и классов — в criteria, а не в весах |
| Данные | не обучаются на запросах; ZDR — enterprise | черновик статьи до публикации — отдельное решение владельца |
| Алиасы | `jev-latest` двигается; версия в ответе | пинить `jev-1.14.0` и писать `model` в журнал |
| Rate limits | per-org, 429, SDK ретраит | для 8 заседаний/год не проблема |

### 2.3. Чего модель не делает

- Не генерирует объяснения, `summary` и связный текст — это не её примитив.
- Не считает числа, не проверяет арифметику и не заменяет SQL/детерминированные проверки.
- Не разбирает таблицы PDF/XLSX — это не structured extraction из таблиц.
- Не пишет в ClickHouse; путь записи остаётся прежним — ingest endpoint.
- Не гарантирует калибровку на наших классах и не гарантирует качество на русском.

### 2.4. Десять форм решений из use-case map

[Use-case map](https://docs.typesafe.ai/concepts/use-case-map) перечисляет: classification, detection, scoring, routing, search, retrieval, ranking, verification, ML feature extraction, structured data extraction. Для нас это переводится так:

| Форма | Наши задачи |
|---|---|
| Classification | класс решения ЦБ, `cb_channel`, тип новости, тип корпоративного события |
| Detection | изменился ли сигнал ЦБ, есть ли policy-event, emergency-заседание |
| Scoring | ястребиность резюме, сила риска, релевантность новости |
| Routing | алерт vs дайджест, ручная проверка при низком `confidence` |
| Search / retrieval | поиск по резюме и новостям, контекст для статьи |
| Ranking | исторические аналоги заседания, приоритизация новостей |
| Verification | поддержка цитатой утверждения статьи, сверка разбора с текстом |
| ML feature extraction | вероятности как признаки для CatBoost/ordered logit |
| Structured data extraction | поля из нового формата пресс-релиза (fallback) |

## 4. Ранжирование и go/no-go

### 4.1. P0 — контур ставки

1. **Внутренний QA статьи #191 до выпуска.** Citation-check: для каждого утверждения/числа — `Noul` «поддерживает ли `source_excerpt` утверждение в том виде, как оно написано». Плюс `Noul` «не заявляет ли формулировка большую определённость, чем распределение». Это не правка статьи, а отчёт владельцу.
2. **Пост-заседание 23.10.** `Noul` «изменился ли сигнал ЦБ», `Score` «ястребиность резюме», `Choice` «доминирующий канал», `Choice` «факт против прогноза». Это структурированный черновик пост-апдейта, входящего в критерий #191.
3. **Shadow-трек `cbr_rate:jev` на 23.10 и 18.12**, затем canary 1 и production после калибровки. Shadow-строки не публикуются и не входят в `v_key_rate_dashboard` — контур #184 это уже умеет.

### 4.2. P1 — признаки и второй слой

4. **22-заседания бэктест** (2024-02 … 2026-09): Brier, log loss, калибровочная кривая против `ordered_logit` и базовой частоты. Это условие production, а не отдельная хотелка.
5. **Вектор 11 каналов ЦБ** по 22 резюме: `Choice` на канал + порог, сравнение с regex/GLM; вероятность канала как признак для `ordered_logit`/CatBoost.
6. **Типизированные теги новостей** как второй слой поверх GLM: event type, `cb_channel`, sentiment; GLM оставляет `summary`. Проверить на 100 документах против GLM/человека.

### 4.3. P2 — после появления данных/продукта

7. **Policy-event признаки для CPI**: тарифы ЖКУ, эмбарго, топливные демпферы, бюджетные решения. Ценность высокая, но история `news_events` короткая (окно с 2026 г.), поэтому бэктест на 2013–2026 невозможен без бэкфилла новостей и PIT.
8. **Аналоги заседаний**: `Choice` по 108 заседаниям с описаниями; проверить на известных эпизодах (2022, 2024).
9. **Triage новостей**: `Noul` «меняет ли это прогноз ставки» + `confidence`-порог; только после появления алертов/дайджеста.

### 4.4. No-go

- **Замена GLM-разметки целиком**: TypeSafe не пишет `summary`; текущая схема `news_annotation` содержит текст, который нечем заполнить.
- **Детерминированные проверки**: нормализация вероятностей, свежесть рядов, арифметика, уникальность дат — это SQL/код, а не модель.
- **Shock-классификатор**: 6 положительных меток, AUC 0,247; калибровка невозможна.
- **Парсинг таблиц**: PDF/XLSX — `pdftotext` + детерминированный разбор.
- **DDL/запись в ClickHouse**: только ingest endpoint.

## 5. Приоритетная задача #191

### 5.1. Рамка

`key-rate/phase-4-first-publication` (#191) — первая публикация на smart-lab к заседанию **23.10.2026** (опорное). По очереди `ml-engineer` §9 это пункт №1 после закрытого #184. Критерий приёмки включает:

- производственные строки `forecast_log` до публикации;
- вероятности нормированы, каждое число — с источником и датой;
- ML-паритет с CB_COMP назван «не близок»;
- чек-лист `KEY_RATE_PUBLICATIONS.md` §9;
- пост-апдейт после 23.10 и сверка через `forecast_resolve`.

Статья уже влита (PR #199) и **заморожена**: `KEY_RATE_PUBLICATIONS.md` §2 запрещает переписывать прогноз задним числом. Поэтому TypeSafe не «улучшает» уже написанное; он закрывает **QA до выпуска** и **пост-публикационный контур**.

### 5.2. Что закрывает и что нет

| Что | TypeSafe | Почему |
|---|---|---|
| Production-строки `forecast_log` | ❌ | нужен перезапуск ingest (#196), не модель |
| Свежий снимок недельного ИПЦ/Сбера | ❌ | данные, не суждение |
| Публикация поста и ссылка в #191 | ❌ | действие владельца |
| Переписывание статьи | ❌ | запрещено §2 |
| QA утверждений/чисел до выпуска | ✅ | citation-check по источнику |
| Пост-апдейт «факт против прогноза» | ✅ | `Noul`/`Score`/`Choice` по пресс-релизу и резюме |
| Shadow-трек к 18.12 | ✅ | `cbr_rate:jev` в shadow/canary |
| Четвёртый трек в следующей статье | ✅ после gate | калибровка, RU/EN, shadow/canary |

### 5.3. State для пилота

Компактный JSON, ~6–10k токенов:

```
as_of, meeting_date, rate_before,
cpi (m/m, y/y, core, SAAR), expectations (expected, observed, business),
labor (unemployment, real wages, staffing), credit (stock, rates, M2),
budget (deficit, oil_gas, expenditures), fx (USD/RUB, Brent),
ofz (1y, 3y, 5y, 10y), ruonia, keyrate (settle, oi, volume),
consensus (2026/2027 medians), cb (last decision, signal, 11 quotes),
calendar (next meeting)
```

Для текущего прогона источник — `build/key-rate-publication-2026-10-18/snapshot.json` (gitignored) и витрины `v_key_rate_dashboard`, `v_cbr_mp_summary_blocks`, `v_keyrate_expectations`, `v_ofz_curve`, `v_cbr_mo_br`. Для бэктеста — as-of реконструкция: `published_at`, где он есть; иначе fallback «конец M+1» с флагом `quality` (по research #240).

### 5.4. Вопросы (предрегистрируются до прогона)

1. **`step_joint`** — один `Choice` по совместным вариантам: `cut_50plus`, `cut_25`, `hold`, `hike_25`, `hike_50plus`, `other`. Joint-вопрос лучше двух независимых: не возникает несогласованности «P(cut)=0.8, P(step=0)=0.7».
2. **`decision_class`** — `Choice` {cut, hold, hike}; cross-check к joint.
3. **`step_bucket`** — `Choice` {−50, −25, 0, +25, +50, other}; cross-check.
4. **11 каналов** — по одному `Score` {−1 = дезинфляционный, 0 = нейтральный, +1 = проинфляционный}; 11 вопросов.
5. **11 каналов, binding** — по одному `Noul` «является ли канал связывающим для решения»; 11 вопросов.
6. **`signal_changed`** — `Noul`.
7. **`budget_risk`**, **`labor_risk`**, **`expectations_risk`** — три `Noul`.
8. **`cb_dominant_channel`** — `Choice` по 11 каналам + `none`.

Всего ~29 вопросов. `instructions` и `criteria` фиксируются в JSON-файле предрегистрации; менять их после первого прогона нельзя.

### 5.5. Композиция и запись

- **Primary** — `step_joint`; агрегируем в `cut/hold/hike` для `probabilities`, полное распределение шага — в артефакт.
- **Ожидаемый шаг** — `Σ p_bucket × bucket_mid`; `predicted = rate_before + E[step]/100`.
- **Cross-check** — взвешенная сумма 11 каналов с весами из `KEY_RATE_CHANNELS.md` §3, замороженными до прогона; расхождение primary и cross-check — метрика, а не повод выбрать удобный.
- **`confidence`** — только порог «публиковать/не публиковать», не вероятность.
- **3 повтора**; медиана вероятностей и разброс — в отчёт.
- **Запись:** `metric='cbr_rate:jev'`, `model='jev-1.14.0'`, `prompt_version='typesafe-key-rate-v1'`, `data_version='typesafe:<sha256 snapshot>'`, `probabilities` — JSON cut/hold/hike. Первый прогон — `--stage shadow`, 2 заседания; затем canary 1; production — после gate.

**Чего не хватает в коде (handoff, не research):**

- `ingest/key_rate_forecast.go`: `keyRateTracks` — закрытый список; нужно добавить `"jev": true` и тест. Схема `forecast_log` не меняется.
- `scripts/key_rate_forecast_log.py`: путь `--llm-payload` принимает только `cbr_rate`/`cbr_rate:llm`; нужен `--typesafe-payload` или обобщение на `cbr_rate:<track>` с проверкой суммы.
- Новый Python-скрипт `scripts/models/key_rate/key_rate_typesafe_forecast.py`: сборка state, вызов API, 3 повтора, артефакт + `--log` payload; в ClickHouse не пишет.
- `docs/CONFIGURATION.md`: `TYPESAFE_API_KEY`, `TYPESAFE_MODEL`, при необходимости `TYPESAFE_BASE_URL`; ключ только через env.

### 5.6. Калибровка и RU/EN

**Бэктест:** 22 заседания 2024-02 … 2026-09, где есть резюме ЦБ и исход. Для каждого — state as-of, 3 повтора, медиана.

**Метрики:**
- Brier (сумма по трём классам), log loss, калибровочная кривая;
- сравнение с `ordered_logit` (fold-предсказания из `ml_predictions`) и базовой частотой классов;
- блочный бутстрап 95% CI разницы Brier/log loss; без CI — никаких заявлений;
- разброс трёх повторов: max |Δp| по классам.

**RU/EN:** 5 заседаний; оригинальный русский state против английского перевода (перевод фиксируется с версией). Приёмка: одинаковый argmax минимум в 4/5 и max |Δp| ≤ 0.10. Если не проходит — либо английский state как обязательный слой, либо отказ от пилота; решение владельца.

**Критерий production:** Brier не хуже `ordered_logit` на 22 заседаниях (или явно названное расхождение с CI), RU/EN и repeat-stability пройдены, shadow 2 + canary 1. Отрицательный результат — допустимый результат; паритет не заявляется.

### 5.7. Стоимость

## 6. Другие применения в проекте

### 6.1. CPI-nowcast: policy-event признаки

`phase-4-cpi-extra-channels` (#223) уже назвал «policy-теги в `news_watch`» дешёвым кандидатом. TypeSafe может дать не теги, а вероятности: `Noul` «объявлено изменение регулируемых тарифов», «введён экспортный барьер», «изменён топливный демпфер», «принято бюджетное решение с прямым влиянием на цены». Это признаки для `cpi_monthly`/`cpi_monthly_v3`, с датой публикации и `prompt_version`.

**Блокер:** истории `news_events` недостаточно для бэктеста 2013–2026; без бэкфилла и PIT это только forward-фича. Поэтому P2, а не P1.

### 6.2. Новости: типизированные теги и triage

Текущая `news_annotation` — GLM: `summary` + теги. TypeSafe не пишет `summary`, но может дать `Choice` по типу события, `Score` по релевантности и `Noul` по «меняет ли это прогноз ставки». Цена — центы в месяц. Ценность — вероятности и `confidence` для маршрутизации, а не текст.

**Пилот:** 100 документов, сравнение с GLM/человеком по event type и `cb_channel`; RU/EN не нужен, если документы русские и качество проверяется напрямую. Если качество не хуже GLM — второй слой для high-value подмножества, не замена.

### 6.3. Каналы ЦБ

Сейчас `v_cbr_mp_summary_channels` — regex + GLM (879 строк на 22 документа). TypeSafe `Choice` по 11 каналам + `none` на документ или абзац даёт вероятность каждого канала; порог > 0.2 даёт multi-label. Это признаки для `ordered_logit`/CatBoost и материал для панели «Карта каналов».

**Пилот:** 22 документа, сравнение с regex/GLM; цена ~$0.007. Если вероятность канала улучшает Brier ставки — включать в модель; если нет — оставить визуализацией.

### 6.4. Золото/DCF: текстовая атрибуция

`v_gold_attribution` и GRAM-факторы (ставка / потоки / риск / импульс) сейчас опираются на рыночные ряды; текстовая лента `news_events` — отдельный слой. TypeSafe может размечать новости по этим четырём факторам (`Noul`), но приоритет gold-трека — C1–C4, а не текст. P2/P3.

### 6.5. Edisclosure

Корпоративные раскрытия: дивиденды, capex, guidance, M&A. `Choice` по типу события + `Noul` «есть ли изменение дивидендной политики» — полезно для `company_financials`/DCF. Но объём высокий, GLM дешевле; TypeSafe — только для high-stakes подмножества. P2.

### 6.6. Поиск аналогов заседания

`Choice` по 108 заседаниям с краткими описаниями (~200 токенов каждое) — ~$0.02 за прогон. Проверить на известных аналогах: 2014-12, 2022-02, 2024-07. Если модель выбирает те же эпизоды, что и человек, — использовать в статье для «исторических аналогий». P2.

## 7. Риски и режимы отказа

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Русский текст обрабатывается хуже английского | Высокая | Среднее/высокое | RU/EN-тест на 5 заседаниях; при провале — английский state с фиксированным переводом или отказ |
| Калибровка не переносится на наши классы | Высокая | Высокое | 22-заседания бэктест, Brier/log loss + CI; production только после gate |
| `jev-latest` двигается | Средняя | Среднее | пинить `jev-1.14.0`; писать `model` в `forecast_log` |
| Вендор недоступен перед заседанием | Средняя | Высокое | TypeSafe — дополнительный трек; fallback на статистику/LLM; публикация не блокируется |
| Черновик статьи уходит вендору | Средняя | Среднее/высокое | решение владельца; ZDR/договор; отправлять только публичные фрагменты |
| Модель «уверена», но ошибается | Средняя | Высокое | `confidence` — не вероятность; порог + human review; не публиковать без бэктеста |
| Rate limits | Низкая | Низкое | 8 заседаний/год; SDK ретраит |
| Нет fine-tuning | Средняя | Среднее | criteria/instructions; тест на наших документах |
| Оценка стоимости по прайсу не совпадёт с счётом | Средняя | Низкое | замерить tokens usage в первом прогоне; лимит на пилот |
| Контаминация оценки (подбор вопросов по тесту) | Средняя | Высокое | предрегистрация; holdout; не менять criteria после результатов |
