# GitHub-трекер пунктов роадмапа

**Назначение.** GitHub — журнал и вид работ по роадмапам: issue хранит пункт и его Q&A, Project V2 — статусы и срезы, PR — реализацию и протокол приёмки. **Источник истины — файлы роадмапов**: состав, объём и канонический статус пункта решают они, а GitHub обязан с ними сходиться.

**Что прочитать перед стартом.** Реестр роадмапов, слаги, правило владения и карту статусов — [docs/ROADMAP_INDEX.md](../../../docs/ROADMAP_INDEX.md); обязательная норма — правило 12 [AGENTS.md](../../../AGENTS.md); модель трекера, поля и виды Project V2 — [спека](../../../docs/superpowers/specs/2026-10-17-github-tracker-design.md) §6–§7; шаблоны — [issue](../../../.github/ISSUE_TEMPLATE/roadmap-item.yml) и [PR](../../../.github/pull_request_template.md).

## 1. Реестр

| Слаг | Файл |
|---|---|
| `dcf-polyus` | `docs/ROADMAP_DCF_POLYUS.md` |
| `gold-thesis` | `docs/GOLD_THESIS_DATA_ROADMAP.md` |
| `dcf-metals` | `docs/ROADMAP_DCF_METALS.md` |
| `key-rate` | `docs/ROADMAP_KEY_RATE.md` |
| `infra` | `docs/ROADMAP_INFRA.md` |

Пункт живёт ровно в одном роадмапе. Если работа упомянута в двух файлах, issue заводится у владельца, а второй файл получает ссылку на этот issue. Шестой роадмап не заводится без решения владельца.

## 2. Создание issue

Заголовок: `[<slug>/<item-id>] <короткое имя пункта>` — слаг обязателен, он снимает коллизию одинаковых номеров.

Через `gh`:

```bash
gh issue create \
  --title "[<slug>/<item-id>] <короткое имя>" \
  --body-file /tmp/roadmap-item.md
```

Или через MCP `issue_write` (создание issue в репозитории). Поля формы можно взять из шаблона [`.github/ISSUE_TEMPLATE/roadmap-item.yml`](../../../.github/ISSUE_TEMPLATE/roadmap-item.yml), но заголовок и шапку тела проверить глазами: форма не подставляет слаг и item-id автоматически.

Шапка тела — машинно-читаемая:

```text
Roadmap: docs/ROADMAP_KEY_RATE.md
Item: 1.9
Phase: 1
Contour: key-rate
Acceptance: <критерий из роадмапа>
Spec: docs/superpowers/specs/...
Plan: docs/superpowers/plans/...
Depends on: #...
```

Дальше — цель пункта, критерий приёмки со ссылкой на роадмап, ссылки на спеку и план, Q&A комментариями и протокол живой приёмки. Полные спеки и планы в тело issue не копируются: только ссылки.

Labels: `roadmap:<slug>` (создать при первом использовании) и `needs-answer` — пока в issue есть открытый вопрос Q&A. Обязательных labels у шаблона нет: до шага `infra/3.2` форма должна работать без предварительной настройки репозитория.

## 3. Project V2

1. `projects_get` — узнать ID проекта, полей и опций. Не угадывать ID и не хардкодить их в текстах: они принадлежат живому проекту.
2. `projects_write` метод `add_project_item` — добавить issue в проект.
3. `projects_write` метод `update_project_item` — заполнить поля.

| Поле | Значение |
|---|---|
| `Roadmap` | слаг: `dcf-polyus`, `gold-thesis`, `dcf-metals`, `key-rate`, `infra` — ровно одно |
| `Phase` | фаза роадмапа: `3`, `follow-up 2`, `step 4` |
| `Item` | item-id без слага: `7.3`, `1.9`, `step-4` |
| `Status` | `Todo` / `In Progress` / `In Review` / `Done` / `Blocked` |
| `Branch` | имя ветки пункта |
| `PR` | номер или URL PR |
| `Spec / Plan` | пути к файлам |
| `Acceptance` | короткий критерий + ссылка на протокол |
| `Depends on` | номера issue |

Отображение статусов: `❌`/«не начато»/нет маркера → `Todo`; `⏳`/`🔶`/«срез»/«остаток» → `In Progress`; открытый PR → `In Review`; `✅` + протокол + мерж → `Done`; внешний блокер → `Blocked`. `✅ сделан этим PR` до мержа — это `In Review`, не `Done`.

## 4. Sub-issues

- Issue пункта — эпик; sub-issue — задача плана.
- `sub_issue_write` метод `add`; родитель — issue пункта.
- Заголовок sub-issue: `[<slug>/<item-id>] Task N: <короткое имя>`.
- Вложенность — один уровень. Если роадмап сам называет срез или follow-up отдельным пунктом, это отдельный issue со своим ID, а не sub-issue.
- «Остаток пункта» в роадмапе → sub-issues или отдельный пункт, если владелец вынес его из объёма.

## 5. Q&A

Формат комментария:

```text
### Q<N>: <вопрос>
**Контекст:** ...
**Варианты:** A / B / C
**Решение:** ... (заполняется после ответа)
**Обоснование:** ...
```

Пока вопрос открыт — label `needs-answer`. После ответа резолюция дописывается в тот же комментарий, label снимается. Если ответ меняет состав или порядок фаз — правка роадмапа тем же PR, со ссылкой на issue в правке.

## 6. PR

1. В описании PR — роадмап и пункт `<slug>/<item-id>` и `Closes #N` (см. [шаблон PR](../../../.github/pull_request_template.md)).
2. При открытии PR: `Status = In Review`, поле `PR` заполнено, ветка — в `Branch`.
3. Статус пункта в роадмапе обновляется тем же PR, что и реализация; до мержа формулировка `✅ сделан этим PR` остаётся `In Review`.
4. Протокол живой приёмки — **комментарием в PR** (состав и порядок — `docs/IMPORTER_PACKAGE_STANDARD.md` §16.1 п. 8).
5. После мержа и протокола: `Status = Done`, статус в роадмапе — `✅` с командой и результатом.

## 7. Аудит

Периодически сверить каждый файл роадмапа с issue:

1. Выписать открытые пункты файла (без исторических `✅`) и их составные ID.
2. Сопоставить с открытыми issue по заголовкам и полю `Item`.
3. Отчёт — четыре категории: **нет issue** (пункт есть, issue нет), **нет пункта** (issue есть, в роадмапе пункта нет), **дубль** (два issue на один пункт), **статус разошёлся** (файл и Project говорят разное).
4. Статус в файле канонический: расхождение исправляется в Project, а не в файле, если файл обновлён по приёмке.

## 8. Чего не делать

- Не дублировать пункт в двух роадмапах и не заводить два issue на один пункт.
- Не заводить issue на исторические `✅` пункты: вместо них — ссылка на PR/протокол в роадмапе.
- Не переносить спеки и планы в тело issue — только ссылки.
- Не считать `✅ сделан этим PR` статусом `Done` до мержа и протокола.
- Не вводить отдельный `Track`-селект: `Roadmap` — единственный источник группировки.
- Не заводить шестой роадмап без решения владельца.
- Не использовать `GITHUB_TOKEN` GitHub Actions для записи в Projects V2.

## 9. До шага `infra/3.2`

Живой Project V2, его поля и виды заводятся шагом `infra/3.2`. Пока Project недоступен, работа не блокируется: issue, заголовок с составным ID, шапка тела и labels `roadmap:<slug>`/`needs-answer` уже несут всю информацию. Когда Project появится, issue добавляются в него и поля заполняются по этой же таблице.
