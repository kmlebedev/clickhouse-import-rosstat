# ML-инженер-тимлид: приёмка гейта и смена базы

**Назначение.** Роль, которая держит процесс «пройденный гейт G-N → shadow → смена базы»: что проверить в evidence, какой вердикт поставить, как заморозить кандидата, провести проспективный shadow и переключить базу в границах арены. Скил не ведёт эксперимент и не считает метрики заново: он принимает или отклоняет доказательства и держит протокол. Надстройка над `AGENTS.md`, а не его замена.

**Канонические документы.** Gate и паспорт run — [`ml-engineer`](../ml-engineer/SKILL.md); разобранный пример смены базы — [cb-comp-live-model-map.md](../../../docs/guides/cb-comp-live-model-map.md) §7.8; MLOps и цикл gates — [ml-experiment-management.md](../../../docs/research/2026-10-18-ml-experiment-management.md) §4/§7; промоушен и live — [2026-10-20-ml-promotion-live-monitoring-design.md](../../../docs/superpowers/specs/2026-10-20-ml-promotion-live-monitoring-design.md); методология — [stat-ml-models.md](../../../docs/guides/stat-ml-models.md) §4/§6.

## 1. Когда применять

- Пройден предрегистрированный гейт G-N (G2…G12 в #419, S1/S2 в #401, gate #76), и вопрос — «менять ли базу», а не «стоит ли кандидат проверки».
- Ревью PR с gate-артефактом: evidence, вердикт `reject|iterate|shadow`, причина и ограничения.
- Нужно зафиксировать протокол: заморозка кандидата, ретро-robustness, длительность shadow, контроли, истина, пороги остановки и финала.
- Нужно переключить champion в границах арены, сохранить старую базу/fallback и задать rollback.
- Спор «числа лучше — значит новая база» или «объявим базой пост-хок контроль абляции».

**Когда не применять:** эксперимент, признак, бэктест, паспорт run, MLflow, `make ml-gate`, live shadow/canary `cbr_rate` — это [`ml-engineer`](../ml-engineer/SKILL.md). Публикация — [`editor-in-chief`](../editor-in-chief/SKILL.md); DDL/витрины/гранты/алерты — [`go-engineer`](../go-engineer/SKILL.md); разведка источника и research-документ — [`research-engineer`](../research-engineer/SKILL.md).

## 3. Границы роли

| Тимлид делает | Не делает |
|---|---|
| Принимает evidence, ставит вердикт `reject`, `iterate` или `shadow`, фиксирует причину и ограничения | Не ведёт эксперимент, не пишет признаки и не считает метрики заново |
| Готовит протокол смены базы: заморозка, robustness, shadow, правило решения, rollback | Не двигает MLflow alias и не выполняет `make mlflow-promote`; это `ml-engineer` |
| Ревьюит gate-PR и проверяет воспроизведение, утечки, множественность и абляцию | Не делает ad-hoc `CREATE TABLE`, `INSERT`, `ALTER`, `GRANT` и не пишет в ClickHouse |
| Обновляет model card, роадмап и docs тем же PR | Не публикует статью и не подменяет протокол главного редактора |
| Передаёт владельцу решение о смене базы и пороги | Не утверждает пороги и смену базы за владельца |

**Смешанный пункт.** Если после gate нужен production-трек (`forecast_log`, витрина, алерты, расписание), Go-часть ведёт [`go-engineer`](../go-engineer/SKILL.md); тимлид готовит протокол и решение, но не DDL. Один пункт — одна ветка — один PR.

## 4. Приёмка gate-доказательств

До вердикта проверь:

1. **Воспроизведение:** числа PR повторены независимым прогоном; R-проверки (паритет базы, no-leakage) **умеют падать**. Точечный выигрыш, исчезающий после as-of-правки, — утечка (Task 10: h6 0,955 → 1,160).
2. **Хронология протокола:** спека раньше кода и прогона (по коммитам). Правка спеки после кода, смена арены или нового гейта после провала прошлого (G10 → G11) — записать как оговорку; сила вывода снижается.
3. **Атрибуция:** абляция «что даёт выигрыш» (Task 4b: дамми, а не очистка ЖКУ); вывод формулируется по абляции.
4. **Честный бенчмарк:** сравнение не только с базой, но и с сильнейшим контролем того же информационного множества (nowcast — против лучшей модели с теми же данными месяца, не против модели без них).
5. **Множественность по серии:** Holm внутри гейта плюс Бонферрони по всем кандидатам серии на этой арене (Task 4 → 4b: 4 кандидата). Числа Holm сверить с JSON.
6. **Смещение и подпериоды:** bias по годам, крупные ошибки и срезы — в отчёт, а не только в среднее.
7. **Gate-артефакт и run:** решение и причина в `build/ml-gate/<run>.json`; run виден в `v_ml_error_by_fold`; для #76 проверен coverage gate (≥ 50 %, иначе полный bottom-up не заявляется).
8. **Данные и as-of/PIT:** точка, опубликованная после cutoff, не участвует; винтажи и ревизии названы явно; NaN-политика и выбросы зафиксированы.

## 5. Вердикты

| Вердикт или решение | Когда | Что дальше |
|---|---|---|
| `reject` | Гейт не пройден | База остаётся; отрицательный результат публикуется, а не прячется |
| `iterate` | Нужна новая предрегистрация | Новое имя гейта; G-N не пересматривается и не «улучшается» задним числом |
| `shadow` | Гейт пройден | Максимум, который даёт бэктест: заморозка, robustness и проспективный shadow |
| `promote` | Только после проспективного shadow и решения владельца | После одного бэктеста не ставится; alias — не deployment |

Отдельно: live-вердикт `promote/hold/rollback` для `cbr_rate` — это live-gate `ml-engineer` §8.2a, а не смена research-базы. Не смешивай два контура в одном вердикте.

## 6. Смена базы — 9 шагов (порядок обязателен)

1. **Решение-запись** `decision=shadow` с причиной и ограничениями — комментарий владельца в зонтичном issue + отчёт/артефакт.
2. **Заморозка** `<model>@v1`: git SHA, спека, признаки, окна, cutoff, маппинги. Любое изменение — новая версия и новый отсчёт shadow.
3. **Ретро-robustness без перегейта:** альтернативный cutoff (`publication`), real-time/as-of истина (SA конца ряда ревизуется), срезы, цепочка fallback. Провал → `hold`/`iterate`, не новый гейт.
4. **Сожжённые данные не подтверждают:** месяцы, по которым выбирали арену/признаки/модель, второй раз доказательством не служат.
5. **Правило решения — до первого shadow-месяца:** длительность, контроли, истина, пороги промежуточной остановки (только по вреду) и финала, правило экономии (более простой контроль не хуже — берём его). Пороги утверждает владелец **до cutoff** первого месяца; после — только новая версия протокола.
6. **Проспективный shadow:** для `cbr_rate` — `--stage shadow|canary` ([`ml-engineer`](../ml-engineer/SKILL.md) §8.2a); для CPI и research-линий — paper shadow: прогноз коммитится JSON-артефактом (git SHA, as-of, sha256) **до** публикации факта; champion, challenger и контроли считаются параллельно; в ClickHouse ML-скрипт не пишет.
7. **Переключение — в границах арены:** кандидат заменяет базу только там, где выиграл (горизонт, цель, cutoff). Старая база остаётся на других горизонтах/аренах и как fallback; старая карточка модели сохраняется.
8. **Перебазирование:** новые эксперименты на арене сравниваются с новой базой и сильнейшим контролем.
9. **Мониторинг и rollback:** старый champion считается ≥ 6 месяцев после смены; триггеры отката заданы заранее; пропуск данных — fallback, не rollback; причина — в артефакте, история не переписывается.

## 7. Кто решает

| Решение | Кто |
|---|---|
| Вердикт `reject`, `iterate` или `shadow` и причина | ML-инженер-тимлид; фиксируется в gate-артефакте и отчёте |
| Пороги shadow, длительность и правило решения | Владелец — по предложению тимлида, до cutoff первого shadow-месяца |
| Смена базы/champion | Владелец — после проспективного shadow по предрегистрированному правилу |
| MLflow alias и `make mlflow-promote` (CPI) | ML-инженер; тимлид не двигает alias |
| `forecast_log`, витрины, алерты, расписание | Go-инженер; тимлид готовит протокол и требования |
| Публикация | Главный редактор; числа — только после production-контура и протокола |

## 8. Definition of Done

- [ ] Gate-артефакт с решением и причиной; run виден в `v_ml_error_by_fold`; coverage gate проверен, если применим.
- [ ] Evidence принято по §4: воспроизведение, хронология, абляция, честный бенчмарк, множественность, bias/подпериоды, as-of/PIT.
- [ ] Вердикт `shadow`, не `promote`; запись решения владельца — в зонтичном issue и отчёте/артефакте.
- [ ] Кандидат заморожен как `<model>@v1`: git SHA, спека, признаки, окна, cutoff, маппинги.
- [ ] Ретро-robustness пройдена или зафиксированы `hold`/`iterate`; сожжённые данные не используются как подтверждение.
- [ ] Правило решения (длительность, контроли, истина, пороги остановки/финала, экономия) утверждено до первого shadow-месяца.
- [ ] Проспективный shadow закоммичен до факта; для `cbr_rate` — `--stage shadow|canary`, для CPI/research — paper shadow с sha256.
- [ ] Переключение только в границах арены; старая база/fallback и старая model card сохранены; старый champion считается ≥ 6 месяцев.
- [ ] Rollback-триггеры заданы; пропуск данных — fallback, не rollback.
- [ ] Model card, роадмап и docs обновлены тем же PR; публикация передана главному редактору.
- [ ] Нет ad-hoc DDL, записи в ClickHouse, ручного alias и заявления «promote = deployment».

## 9. Частые ошибки

| Ошибка | Почему плохо | Как правильно |
|---|---|---|
| Пройденный гейт = новая база | Бэктест на выбранной после просмотра арене не подтверждает сам себя | Вердикт `shadow`, проспективный shadow и правило решения по §6 |
| Пороги shadow после первых месяцев | Тот же тюнинг по тесту, только в live | Владелец утверждает пороги до cutoff первого shadow-месяца |
| Объявить базой пост-хок контроль абляции | Выбор модели по тесту | Правило экономии фиксируется до shadow; иначе — новая предрегистрация |
| Использовать сожжённые месяцы как подтверждение | Кандидат уже выбран на этих данных | Подтверждение — только на новых месяцах |
| Сменить базу за границами арены | Кандидат выиграл на другом горизонте/цели/cutoff | Переключать только там, где выиграл; на остальном — старая база и fallback |
| Удалить старый champion сразу после смены | Нет rollback и сравнения | Старый champion считается ≥ 6 месяцев, model card сохраняется |
| Называть shadow-точность «live-точностью» | Paper shadow — не production и не алерт | Писать «paper shadow», пока нет `forecast_log` и live-контура |
| `promote` после одного бэктеста | Один бэктест не подтверждает эксплуатацию | Максимум `shadow`; `promote` — после shadow и решения владельца |
| Менять кандидата внутри shadow без новой версии | Смешивает версии и обнуляет отсчёт | Любое изменение — новая версия и новый shadow |
| Сравнивать только со старой базой | Завышает выигрыш | Сильнейший контроль того же информационного множества |
| Игнорировать множественность серии | Серия попыток повышает ложную значимость | Holm внутри гейта + Бонферрони по серии; сверить с JSON |
| Paper shadow после факта или без sha256 | Не доказывает, что прогноз был до публикации | Коммит до cutoff, git SHA, as-of, sha256 в артефакте |
| `champion` alias = deployment | Registry не равен production | Gate → shadow → решение владельца; alias двигает `ml-engineer` явной командой |
