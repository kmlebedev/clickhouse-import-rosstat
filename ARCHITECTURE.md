## 1. Что это за проект

Go-конвейер (ETL) импорта российской макроэкономической статистики и финансовых данных в **ClickHouse** для дашбордов **Grafana** и аналитических моделей (сценарный прогноз золота → DCF → NAV акции PLZL). Монолитный репозиторий: основной бинарник импорта и отдельный бинарник `cmd/ingest` (ingest-endpoint контура прогноза, §6.5); конфигурация только через env.

- Репозиторий: `github.com/kmlebedev/clickhouse-import-rosstat`
- Go 1.27, сборка: `make build` → статический linux/amd64 бинарник (CGO_ENABLED=0, ldflags `-s -w`); `make build-ingest` → `build/ingest`
- Драйвер БД: `github.com/ClickHouse/clickhouse-go/v2` (native protocol)
- Ключевые библиотеки: `excelize/v2` (XLSX), `xlsReader` (legacy XLS), `colly/v2` + `goquery` (скрейпинг), `unipdf/v3` (PDF), `cenkalti/backoff/v5` (ретраи), `logrus` (логи, `log.Infof/Errorf/Fatal`)

## 3. Ключевой паттерн: реестр импортёров

Каждый источник — импортёр, который регистрирует себя в глобальном реестре `chimport.Stats`; `main.go` импортирует пакеты вслепую и запускает всех (или фильтр по `CLICKHOUSE_IMPORT_STAT`). Регистрация — на пакет: в большинстве пакетов её делает `init()`, а в `cbr/` все импортёры собраны в один реестр `cbrImporters` (`cbr/importers.go`, 15 записей, единственный `init()` пакета) — персональных `init()`-append по файлам импортёров там больше нет. Полноту и префиксы реестра держит тест `TestCbrImportersPrefixedAndRegistered`: префикс `cbr_` у имён и таблиц, уникальность имён, каждая строка `dagu/cbr.yaml` присутствует в реестре (расписание — единственный продакшн-вызов, и его опечатка иначе не видна ничем).

```go
// chimport/stats.go
type ImportStat interface {
    Name() string
    Import(ctx context.Context, conn driver.Conn) (count int64, err error)
}
var Stats []ImportStat
```

**Конвенция имени:** `Name()` возвращает имя таблицы ClickHouse (`ipc_mes`, `cbr_key_rate`). Фильтр запуска: `CLICKHOUSE_IMPORT_STAT=ipc_mes,cbr_key_rate`.

### Шаблон А — ручной импортёр (скрейпинг страницы → ссылка на XLSX → парсинг)

Эталон: `rosstat/ipc_mes.go`. Скрейпер colly ищет ссылку на актуальный XLSX на странице источника → `util.GetXlsx(url)` → якорная строка в таблице → сбор `[][]string` → DDL + INSERT.

Это **предпочтительный** способ для источников, где имя файла или id в URL меняются при обновлении (`cbr_infl_exp`, `cbr_credit_m2x`, `vvp_kvartal`, `salaries_mes`, `rus_vtb_group_ifrs`). В пакете `cbr/` для этого служит связка `util.GetFile` + `findLink` (goquery, `cbr/links.go`) — colly там больше не используется, и те же `getPage`/`findLink` переиспользуются тестами на HTML-фикстурах. Ссылку вычислять внутри `Import()` (не в `init()`), иначе регистрация импортёра делает сетевой вызов. Если после `c.Wait()` URL пуст — вернуть понятную ошибку, а не вызывать `GetXlsx("")`.

Ограничение: страницы, закрытые JS-challenge (`domrf_mortgage` — ServicePipe; `sber_finansovie_rezultaty` — TSPD) или не имеющие листинга ссылок (`tbank_group_ifrs` — CDN с UUID), colly распарсить не может — там ссылку обновляют вручную.

### Шаблон Б — `util.ClickHouseImport` (декларативный, предпочтительный)

Единый шаблон для XLSX-источников и краулеров. Встраивается в обёртку-структуру пакета; `Import()` обёртки вычисляет `DataUrl` и делегирует в шаблон, а производные (каталог рядов, витрина) объявляются полем `AfterImport` — их публикует шаблон после точек и **до** записи строки версии (§8 п. 13), поэтому обёртка их не публикует и не имеет шанса отменить порядок.

```go
type myStat struct {
    util.ClickHouseImport
}

// Сеть — только здесь, не в init(). Производные шаблон публикует сам (AfterImport).
func (s *myStat) Import(ctx context.Context, conn driver.Conn) (count int64, err error) {
    if s.DataUrl = myGetDataUrl(); s.DataUrl == "" {
        return count, fmt.Errorf("my: не найдена ссылка на xlsx на %s", myPageUrl)
    }
    return s.ClickHouseImport.Import(ctx, conn)
}

func init() {
    chimport.Stats = append(chimport.Stats, &myStat{ClickHouseImport: util.ClickHouseImport{
        TableName:   "cbr_m2",
        CreateTable: []string{`CREATE TABLE IF NOT EXISTS %s (...);`},  // несколько DDL — допустимо
        ImportFunc:  myImportFunc,   // func(xlsx *excelize.File, batch driver.Batch) error
        // CrawFunc: func(url string, conn driver.Conn) (int64, error) — альтернатива для краулеров
        // BeforeImport: func(ctx, conn) error — вычислить DataUrl внутри шаблона
        // AfterImport: func(ctx, conn) error — производные (series_catalog + витрина) после точек
        // PublicationCountPoints: "SELECT count() FROM cbr_m2 FINAL" — включает префлайт (§8 п. 13)
        // PublicationSource у cbr_m2 не нужен (ключ версии = TableName); его задают только владельцы
        // общей macro_series, чей Name() != TableName — cbr_mp_survey и cbr_mo_br
    }})
}
```

Поля: `TableName`, `CreateTable []string` (`%s` подставляется `TableName`), `DataUrl`, `ImportFunc` **или** `CrawFunc` (или `BeforeImport` + `ImportFunc`); ровно один режим обязателен — иначе `Import()` вернёт ошибку «no CrawFunc or ImportFunc configured». Полный цикл шаблона: DDL → `BeforeImport` → префлайт → точки → `AfterImport` → строка версии (§8 п. 13). Механизм точек контроля публикации включается тремя опциональными полями: `PublicationCountPoints` (SQL числа точек ряда; непустое значение включает точку контроля — HEAD-префлайт по `DataUrl`, no-op известной версии, строка версии в `source_publications` последней), `PublicationSource` (ключ версии в `source_publications` и префикс лога префлайта; пусто → `TableName`; нужен импортёрам, чей `Name()` не равен `TableName`, — `cbr_mo_br` и `cbr_mp_survey` пишут в общую `macro_series`) и `AfterImport` (производные: каталог и витрина). Метод `PublicationKey()` отдаёт объявленный ключ версии, `Publication()` — объявление целиком (`Source`/`Url`/`CountPoints`): по нему тест-энфорсер реестра отличает «объявление забыли» от «объявление не нужно» (§3, §8 п. 13). Поля опциональны: у импортёров, которые их не задают, поведение `Import` не меняется ни на шаг.

Эталон краулера (`CrawFunc` + colly: листинг ссылок, пагинация, XLSX с каждой страницы) — `customs/vneshn_torg_countries.go`; XLSX с `DataUrl` в рантайме — `cbr/Infl_exp.go`, `cbr/indicators_cpd.go`, `minfin/fedbud_mes.go`; подстановка даты в URL — `cbr/ruonia.go`. Эталон объявления точки контроля публикации — `cbr/m2.go` (`AfterImport: afterCbrMacro(<мета>)` + `PublicationCountPoints`); эталон префлайта у импортёра со ссылкой со страницы — `cbr/mo_br.go`; эталон производных вне `cbr/` — `rosstat/ipc_mes.go` (`AfterImport: afterRosstatMacro(<мета>)`); эталон импортёра без `Name()`-таблицы — `bank/sber_fin_rez.go` (объявлен только `DataUrl`/`CrawFunc`/`PublicationCountPoints`).

### Общие хелперы `util/`

- `util.HttpClient` — единый HTTP-клиент: системные CA + `CERT_FILES` (нац. сертификаты РФ), cookie-jar с `redirect_cookie` для rosstat.gov.ru
- `util.GetXlsx(url)` / `util.GetCSV(url)` (разделитель `;`) / `util.GetFile(url)` — скачивание с ротацией User-Agent; запрос `GetFile` ограничен дедлайном 2 мин (`fileTimeout` — с запасом на многомегабайтные XLSX, которые он же и тянет; `GetXlsx`/`GetXls` наследуют его через `GetFile`), потому что `HttpClient` создан без `Timeout`, и зависший ответ ЦБ иначе не дал бы ошибки вовсе — регрессия `cbr_key_rate`, потерявшего десятисекундный таймаут colly при переводе на общий хелпер (§6.1)
- `util.GetJSON(url, out)` — скачивание JSON тем же `HttpClient`: **сначала проверяется HTTP-статус** (не-200 → ошибка `http status %d: <фрагмент тела ≤512 байт>`; URL в текст не подставляется — у вызывающих в query бывает ключ), пустое тело и ошибка `json.Unmarshal` — тоже ошибка, запрос ограничен дедлайном 60 с. Отличие от `GetFile`, который статус не проверяет и вернул бы тело `403` «успехом»: фолбэк `wgc_etf_flows` срабатывает по ошибке API, а не по ошибке разбора (§6.1)
- `util.GetXML(url, out)` — скачивание XML тем же `HttpClient`: **сначала проверяется HTTP-статус** (не-200 → ошибка `http status %d: <фрагмент тела ≤512 байт>`; URL в текст не подставляется — у вызывающих в query бывает ключ), пустое тело — ошибка, запрос ограничен дедлайном 60 с (`xmlTimeout`), разбор — `xml.Decoder` с подменённой таблицей сущностей на `xml.HTMLEntity` (ленты встречаются с `&nbsp;`: именованная сущность иначе роняет разбор всей ленты, а не одного поля). Контракт приёмника: структура обязана пинить корень через `XMLName` (`xml:"rss"`) — без пина 200-страница HTML (заглушка WAF) разберётся в нулевую структуру без ошибки. Отличие от `GetFile`, который статус не проверяет: у лент РФ-канала (§6.1) заглушка читалась бы «успехом»
- `util.PostJSON(url, headers, request, out)` — POST JSON тем же `HttpClient` (случайный User-Agent, `Content-Type: application/json`): тело маршалится из `request`, ответ разбирается в `out`; **сначала проверяется HTTP-статус** (не-2xx → ошибка `http status %d: <фрагмент тела ≤512 байт>`; URL в текст не подставляется — конвенция `GetJSON`), пустое тело — тоже ошибка (пустой ответ неотличим от «разметка без каналов»), запрос ограничен дедлайном 65 с (`postJSONTimeout`: вызов LLM генерирует разметку десятков цитат и отвечает заметно дольше обычного фида, а на зависший ответ импортёр обязан получить ошибку и уйти в деградацию). Заголовки накладываются поверх — ключ LLM едет в `Authorization`, а не в query, поэтому в тексты ошибок не попадает (ошибки транспорта приходят `*url.Error` и содержат URL, но не заголовки). Транспорт LLM-слоя `cbr_mp_summary` (§6.1)
- `util.ParseXML(body, out)` + `util.charsetReader` (`util/xml.go`) — разбор XML тем же `xml.Decoder`, что и у `GetXML` (таблица сущностей `xml.HTMLEntity`, контракт приёмника — пин корня через `XMLName`), с перекодировкой по объявленной в декларации кодировке: `windows-1251`/`cp1251` через `charmap`, `utf-8`/`utf8` — как есть, любая другая — ошибка (а не «разберём как получилось»). Так читаются ленты ЦБ — `XML_dynamic.asp` (курс USD) и `xml_metall.asp` (учётные цены металлов): обе объявляют `windows-1251`, поэтому `util.GetXML` = fetch + `ParseXML`, а вызывающий с уже скачанными байтами (тест, локальная выгрузка) зовёт `ParseXML` напрямую
- `util.MonthsToNum` — map русских названий месяцев (все падежи + сокращения + опечатка «авугст»)
- `util.HeadFingerprint(url)` / `util.EnsurePublications(ctx, conn)` / `util.PublicationKnown(ctx, conn, source, name, fingerprint)` / `util.SavePublication(ctx, conn, p)` / `util.PublicationPreflight(ctx, conn, source, url, countPoints)` / `util.CountPoints(ctx, conn, query)` (`util/publications.go`) — точки контроля публикаций для источников, чей файл обновляется реже прогонов. `PublicationPreflight` — весь префлайт одним вызовом (HEAD → известна ли версия → количественный чек), им пользуется шаблон `util.ClickHouseImport` (§3), объявивший механизм своими полями, поэтому фактический список потребителей ведёт §8 п. 13, а не этот пункт. `HeadFingerprint` делает HEAD через `HttpClient` (дедлайн `fileTimeout`, как у `GetFile`) и возвращает md5 от «имя|ETag|Last-Modified|Content-Length»: композит меняется ровно при смене файла, пропажа отдельного заголовка его не ломает, а не-2xx или ошибка сети — ошибка (отпечаток «из пустых заголовков» превратил бы битую ссылку в валидную версию). `EnsurePublications` идемпотентно создаёт общую таблицу `source_publications` (канонический DDL — §6.2), `PublicationKnown` отвечает «версия уже импортирована и сколько точек записала» (отсутствие строки — штатное «версия новая», а не ошибка), `SavePublication` пишет строку версии последней — после успешной записи точек, публикации каталога и витрины. `CountPoints` выполняет запрос импортёра (`SELECT count() … FINAL`); один и тот же запрос служит и чеком известной версии, и значением `points` записываемой версии — `batch.Rows()` для этой роли не годится (у `cbr_households_b_mes` 9030 ячеек листа против 7350 точек ряда, и чек не сошёлся бы никогда). Сбой `CountPoints` — в префлайте и при записи версии — ошибка прогона, а не деградация к полному импорту: без числа точек не сходится ни чек, ни `points` будущей записи (спека §3.4), причём недоступный HEAD и сбой `SELECT` версии, наоборот, дают warn и полный импорт. Механизм не защита от подмены, а ответ на вопрос «это тот же файл, что импортировали?»; таблица внутренняя — агенту (`kimi_reader`) не выдаётся
- `util.Import(ctx, conn, ddl, insert, *[][]string)` — DDL + батч из таблицы строк (колонки: name, y, m, value)

## 4. Конвенции БД ClickHouse

- Движок: **`ReplacingMergeTree`**, ORDER BY = естественный ключ (`(name, date)`, `(code, quarter, name)`)
- Типы: `LowCardinality(String)` измерения, `Date` даты, значения — **для новых таблиц Float64** (legacy — Float32, не трогать)
- DDL всегда `CREATE TABLE IF NOT EXISTS`; идемпотентный реимпорт — норма
- ⚠️ Вставка — **только батчами**: `conn.PrepareBatch(ctx, "INSERT INTO t")` + `batch.Append(...)` + `batch.Send()`. Построчный `conn.Exec` в цикле — антипаттерн (есть в legacy, не копировать)
- ⚠️ Дашборды/запросы к ReplacingMergeTree — с `FINAL` или дедупликацией

-- source_kind различает вид документа (kpi/ifrs), но не документ — два пресс-релиза

-- МСФО-страниц, где шапки нет по устройству отчёта, период приходит параметром отчёта.
-- Колоночная модель (2026-10-10) схему не меняла; включение релизов 2019–2024 (2026-10-10)

CREATE TABLE IF NOT EXISTS company_financials
(
    company     LowCardinality(String),               -- 'PLZL','UGK','SELG','CHMF','MAGN','NLMK'

    value       Nullable(Float64),
    unit        LowCardinality(String),
    source_url  LowCardinality(String),               -- документ-источник, часть ключа
    source_page UInt16,

ENGINE = ReplacingMergeTree(loaded_at)
ORDER BY (company, metric, period, source_kind, source_url);

`mine_plans`, `price_decks` и `nav_by_asset` заведены в коде пакетом `dcf/` (DDL — копии блока выше в `dcf/schema.go`) и создаются импортёрами идемпотентно. Наполнение: `mine_plans` **сеет импортёр `dcf_mine_plans`** из публичной отчётности Полюса (§6.1) — факт последнего отчётного года из `databook_polyus` и версионные константы сида `dcf/mine_plans_seed.go`; `nav_by_asset` пишет `dcf_engine` (при заданном `DCF_RUN_ID`), `price_decks` он же сеет на пустой таблице. Оба шага и их порядок (сид → расчёт) задаёт `dagu/dcf.yaml`. Год плана вне окна `[minPlanYear, maxPlanYear)` (`dcf/seed.go`) не сеется и не считается покрытым (§6.1): мусорный год — дефект данных, и план из одних мусорных лет даёт ошибку до расчёта (на пустой `price_decks` — `seedPriceDecks`, на непустой — `checkYearCoverage`), а не успешный прогон с бессмысленным NAV. Сид `mine_plans` **не покрывает все 8 моделируемых активов**: он заводит **6 из 8** — `TITIMUKHTA` и `ZAPADNOYE` пропускаются с `log.Warn`, потому что их добыча в датапаке равна нулю (россыпное золото учтено отдельной таблицей `ALLUVIALS`), а ноль на месте факта молча занизил бы NPV актива. `closure_costs` у всех засеянных активов равен `0` — это означает **«не задано»** (per-asset провижен на рекультивацию Полюс не публикует), а не «закрытие бесплатно». Полная карта пробелов — [docs/DCF_DATA_COVERAGE.md](docs/DCF_DATA_COVERAGE.md). На пустых `mine_plans` движок по-прежнему прогоняется вхолостую: `log.Warn` и `Imported 0 rows`.

    date Date,                                   -- дата выдачи СБКТС (МСК)
    certificate_number String,                   -- номер СБКТС («ТС RU …»)
    ecoclass LowCardinality(String),             -- экологический класс; '-' — не применимо
    enginetrademark String,                      -- двигатель: модель, топливо (дизель/бензин/электро)
    yearofmanufacturing UInt16,                  -- год выпуска; 0 — не указан / строка до бэкфилла

    publication_date Date                        -- дата батча публикации (провенанс/резюмируемость)

-- Паспорт серии KEYRATE: одна строка на серию (`ORDER BY secid`), пишется на каждую
-- обнаруженную серию, в том числе без дневных итогов. `series_name` — SHORTNAME ISS

- `v_events_calendar` — **реализован** (`calendar/events.go`): `events_calendar FINAL`: календарь событий-триггеров прогноза золота/NAV (дата, категория, заголовок, пороги-триггеры в JSON, статус pending|done|verified); сид Q4-2026 — `sql/events_calendar_q4_2026.sql`
- `v_gost_vehicle_safety_certificate` — **реализован** (`craw/gost_views.go`, импортёр `gost_vehicle_safety_certificate`): строки реестра СБКТС — `gost_vehicle_safety_certificate FINAL`, одна строка на сертификат, колонки `date` (дата выдачи, МСК), `publication_date` (дата среза публикации у источника), `mark`, `type`, `certificate_number`, `ecoclass`, `enginetrademark`, `yearofmanufacturing`, `nameofmanufacturer`; технического `uid` в выдаче нет (это провенанс импортёра), `ORDER BY` в определении тоже нет — сортировка ~3,4 млн строк на каждом запросе не нужна, поэтому фильтровать надо по `date` (комментарий витрины это и советует). `FINAL` схлопывает вытесненные копии `ReplacingMergeTree`, но amendment-строку не убирает: изменение сертификата с новой датой выдачи — **вторая строка при том же номере**. Оговорки в комментариях: `publication_date` отстаёт от `date` на ≈2 суток (по дню публикации и собирается срез), у строк до бэкфилла `publication_date = 1970-01-01`, `yearofmanufacturing = 0` — год не указан или строка до бэкфилла. Витрину публикует сам импортёр (`CREATE OR REPLACE VIEW … DEFINER = default SQL SECURITY DEFINER`) в пишущих режимах (`since`/`full`), в `check` — не трогает; комментарии таблицы и каждой колонки — там же (`gostViewStatements`)
- `v_gost_vehicle_safety_daily` — **реализован** (`craw/gost_views.go`): дневной поток выдачи СБКТС — одна строка на (день выдачи × марка), `certificates = uniqExact(certificate_number)` (не `count()` строк: amendment даёт вторую строку при том же номере), `ORDER BY date DESC, mark` (свежий день сверху, внутри дня — стабильный порядок марок). Пустой день в выдаче отсутствует (не `0`). Агрегация — по дню **выдачи**, а не публикации: это метрика выпуска, прокси импорта авто (канал №7 §10.1 [docs/ROADMAP_DCF_POLYUS.md](docs/ROADMAP_DCF_POLYUS.md)); разбивка по моделям — `GROUP BY mark` по строковой витрине. Сырая `gost_vehicle_safety_certificate` агенту **не выдана**: доступ дают только обе витрины (`GRANT SELECT` — `sql/mcp_kimi_reader.sql`), проверки — `scripts/mcp_check.py` (§6.5)
- `v_news_events` — **реализован** (`news/schema.go`, импортёр `news_watch`): событийная лента РФ-канала — позиции RSS пяти лент (`interfax`, `rbc`, `cbr` ×2, `tass`) из `news_events FINAL`, одна строка на позицию. Определение — `CREATE OR REPLACE VIEW v_news_events DEFINER = default SQL SECURITY DEFINER`: колонки `date` (момент публикации — `pubDate` источника со своим офсетом времени), `date_msk` (`toDate(date, 'Europe/Moscow')` — для группировок по дням), `source`, `title`, `url`, `sentiment` (сейчас всегда NULL — заполняет LLM-сессия, канал записи — follow-up); порядок строк — `date DESC`. Фильтр тезисов живёт в определении витрины: `match(title, newsFilter)`, где `newsFilter` — константа Go, широкий набор стемов RE2 с флагом `(?i)` (дизель/бензин/НПЗ/нефть/Brent/ОПЕК/Ормуз/Иран, санкции/поставки/эмбарго/сделки/Трамп/перемирие/пошлины, ставка/ФРС/Федрезерв/инфляция/дефляция/CPI/PPI/ИПЦ, золото/драгметаллы/XAU/ETF/резервы, Банк России/ЦБ/Минфин/бюджет/НДПИ/налог/отсечка, Полюс/Сухой Лог/PLZL). Фильтр осознанно широкий: лишнее снимает запрос сессии, а сужение списка делается пересозданием витрины по всей истории — сырая `news_events` хранит ленту целиком и агенту не выдана. История копится с первого прогона: окна лент конечны (25–100 позиций) и задним числом не «залечиваются». Сырая `news_events` агенту **не выдана** — доступ и фильтр даёт только витрина: `GRANT SELECT` — `sql/mcp_kimi_reader.sql`, а комментарии таблицы и каждой колонки ставит сам импортёр в `news/schema.go` (`newsViewStatements`: `ALTER TABLE … MODIFY COMMENT` / `COMMENT COLUMN`)

Правила витрин:
- создаются через `CREATE OR REPLACE VIEW ... DEFINER = default SQL SECURITY DEFINER AS ...` — определение может меняться, и агент читает сырые таблицы через definer, без прав на `macro_series`;
- комментарии ставятся через `ALTER TABLE v_x MODIFY COMMENT '...'` и `ALTER TABLE v_x COMMENT COLUMN col '...'`: синтаксис `COMMENT ON TABLE/COLUMN` в текущей версии ClickHouse (26.10) не поддерживается;
- `CREATE OR REPLACE` для витрин — отступление от правила «DDL всегда `IF NOT EXISTS`» (то правило относится к таблицам);
- для каждой новой витрины — `GRANT SELECT` пользователю `kimi_reader` в `sql/mcp_kimi_reader.sql`;
- витрины контура прогноза (`views/`, импортёр `gold_views`) создаются `util.CreateView` и пропускаются, пока не существуют все их исходные таблицы. `v_model_inputs` требует 9 таблиц, в том числе `ipc_mes` и `ipc_weeks` (Росстат) и `model_runs` (ingest). Гейт проверяет только наличие таблиц (`system.tables`), не заполненность: `ipc_mes` и `ipc_weeks` создаются до загрузки Росстата, поэтому при его сбое витрина создаётся, а колонки `ipc_mes_last` и `ipc_week_ytd` дают NULL или устаревшие значения (ориентироваться по `*_date`). Запускать `make import STAT=gold_views` после первого запуска ingest
- витрины метрик компаний (`views/company.go`, импортёр `company_views`) создаются тем же `util.CreateView`, но не в единственном шаге: импортёр **сначала исполняет DDL таблицы** `company_financials` сырым `conn.Exec` (`companyViewsDDL()`), и лишь затем создаёт витрины. Порядок обязателен: гейт `CreateView` считает таблицы-источники в `system.tables` и **молча пропускает** витрину (created=false, err=nil), если хоть одной нет, — на пустой БД это пропустило бы и `v_company_financials`, и `v_company_metric_sources`, потому что таблицу создаёт тот же импортёр. `v_company_operating` гейтится по `databook_polyus` и на пустой БД будет пропущена (правильно: до импорта датапака она всё равно нечитаема). Затем импортёр пишет описания рядов Полюса в `series_catalog` (18 релизных + 19 датапак = 37 строк; `util.UpsertSeriesCatalog` идемпотентен). Гранты импортёр не выдаёт — их меняет владелец БД (`make mcp-user`, `sql/mcp_kimi_reader.sql`). Запуск: `make import STAT=company_views`; шаг стоит в `dagu/financial.yaml` после `polyus_financial_metrics`
- групповые витрины legacy-источников (`v_cbr_macro`, `v_rosstat_macro`, `v_minfin_budget`, `v_gold_prices`) создаются через `util.CreateView`: витрина появляется, только когда все таблицы её группы уже импортированы, поэтому её создаёт последний импортёр группы; описания рядов группы пишутся в `series_catalog` каждым импортёром своими записями.

Каноническое определение витрины `v_keyrate_expectations` — `var keyrateView` в `moex/keyrate.go` (импортёр `keyrate_futures`, §6.1); копии обязаны совпадать. `util.CreateView` собирает из полей этой переменной `CREATE OR REPLACE VIEW … DEFINER = default SQL SECURITY DEFINER AS <Select>`, `ALTER TABLE … MODIFY COMMENT '<Comment>'` и `ALTER TABLE … COMMENT COLUMN <колонка> '<Columns[колонка]>'`:

```sql
-- Select: util.CreateView оборачивает его в CREATE OR REPLACE VIEW v_keyrate_expectations
-- DEFINER = default SQL SECURITY DEFINER AS <Select>. Алиас обязан стоять ДО FINAL:
-- форма `keyrate_futures FINAL f` — SYNTAX_ERROR code 62 (проверено DESCRIBE, 26.10).
SELECT f.date AS date, f.secid AS secid, c.series_name AS series_name,
       c.last_trade AS decision_date, f.settle AS settle, f.close AS close,
       f.volume AS volume, f.openposition AS openposition,
       round(f.settle - nullIf((SELECT argMax(rate, date) FROM cbr_key_rate FINAL), 0), 4) AS expected_change_pp,
       round((f.settle - nullIf((SELECT argMax(rate, date) FROM cbr_key_rate FINAL), 0)) * 100, 1) AS expected_change_bp
FROM keyrate_futures AS f FINAL
INNER JOIN keyrate_contract AS c FINAL ON f.secid = c.secid
```

### 6.4 DCF-модель Полюса (ключевые допущения, rev.2 по мировой практике)

```
СТРУКТУРА: sum-of-parts, не корпоративный DCF
NAV = Σ_asset NPV(LOM-план актива из mine_plans) − NetDebt − CorpCosts + Опционность ресурсов
LOM-DCF актива: FCF_t = Production×(Gold_deck_t − AISC_t) − НДПИ − налоги − capex ± ΔWC;
  в конце LOM — хвост closure_costs (ОТРИЦАТЕЛЬНЫЙ, perpetual TV у рудника НЕТ)
НДПИ = база + 10%×max(gold−1900,0)  ← надбавка с 2025; AISC_t = AISC_base × эскалация(ИПЦ РФ)

ПОАКТИВНЫЙ AISC (реализовано 2026-10-11, `scripts/extrapolation_aisc.py`, цель `make dcf-aisc`):
  Полюс публикует поактивный AISC/TCC только в пресс-релизах 4Q/FY 2018–2021; с 2022 —
  поактивный TCC, но AISC только групповой. Поэтому клин поддержания калибруется как ДОЛЯ
  от TCC: r̄_i = mean_t((AISC_i,t − TCC_i,t) / TCC_i,t), t ∈ 2019–2021 (2018 исключён: в FY2018
  нет годового AISC по Вернинскому). Грубые выбросы отсекаются правилом MAD (k = 6).
  В плане AISC_i,t = TCC_i,t × (1 + r̄_i × m), где m — замкнутая скалярная поправка,
  увязывающая взвешенный по добыче AISC к групповому (1 437 USD/oz, Годовой обзор 2025):
  m = 1 + (AISC_group − Σ_j tcc_j·(1+r̄_j)·w_j) / (Σ_j tcc_j·r̄_j·w_j), w_j = добыча_j / Σ добычи.
  Приёмка 2026-10-11: m ≈ 1.992279, невязка 0.000000 USD/oz.
  CAPEX_SUSTAINING = 0 в этих строках: поддержание УЖЕ ВНУТРИ aisc (Полюс определяет AISC как
  «TCC plus sustaining capital expenditures»), а npvLOM вычитает и aisc (в выручке),
  и capex_sustaining (в opCash) — ненулевое значение удваивало бы отток. Клин для глазной
  сверки лежит в CSV (`wedge_usd_per_oz`, `wedge_mn_usd`), НЕ в оттоке модели.
  КОНСЕРВАЦИЯ: у VERNINSKOYE2 карьер законсервирован с сентября 2024 — нулевая добыча
  2025–2028 при СОХРАНЁННЫХ строках (пропуск годов сдвинул бы нумерацию лет плана и дисконт).
  Сухой Лог сид не трогает (проект развития, своего AISC не раскрывает) — его строки
  остаются от Go-сида с плоским клином «tcc + 698».

СТАВКА (двухконтурная):
  1) индустриальная: 5% real USD + страновая/стадийная надбавка (CIM-сurvey: до 10% для рисковых
     юрисдикций) — сопоставима с глобальным P/NAV; CAPM/WACC для золотодобычи НЕ использовать
     (бета сектора ≈ 0 или отрицательная)
  2) локальная (для RU-инвестора): ОФЗ-кривая (ofz_curve) + премии — объясняет локальный дисконт
Оба результата пишутся в model_runs

PRICE DECK (обязательно 3 контура, price_decks):
  spot_flat / consensus_lt (LT-якорь системно ниже спота: Scotia $2,600 с 2029, BMO $3,000) /
  own_scenario (gold_forecasts; LT-хвост обязан сходиться к обоснованной LT-оценке)
Сценарии золота Q4-2026 (база из docs/): bull $4,600–5,000 (25%), base $4,000–4,600 (40%), bear $3,750–4,050 (35%);
вероятности согласуются с regime_states (HMM); формат сценариев — по WGC Gold Outlook

РЕСУРСЫ ВНЕ LOM: не в DCF, а опционно — EV/oz × stage_haircut (construction 0.7–0.9 / DFS 0.5–0.7 /
PEA 0.2–0.4); Сухой Лог (43 млн унц из 106,8) — отдельная строка со стадийным дисконтом

РЫНОЧНЫЙ МОСТ: дисконт к NAV декомпозируется: страновой (RU-акции ≈ −75% к EM-пирам в 2025) +
компанейский (див.спред к ОФЗ, переток ликвидности, индексные потоки, sentiment)
Peers-сверка (peer_universe='ru': PLZL/ЮГК/SELG) — относительная рамка; глобальные пиры — только
для измерения странового дисконта. Выводы run'а: NAV/акция по 3 deck × 2 ставки + NAV- и EBITDA-бета
к золоту (эталон BofA: EBITDA-бета ~14% на +10% золота)
```

**Реализация:** чистый расчёт этой конвенции — пакет `dcf/` (`ndpiPerOz`, `npvLOM`, `escalate`; порог $1 900 и надбавка 10% — поля `Params`, ставки контуров — `DiscountRates` в `dcf/params.go`), вход `mine_plans` сеет импортёр `dcf_mine_plans` (§6.1), выход считает `dcf_engine` (§6.1) — `nav_by_asset` и витрина `v_dcf_assumptions` (§6.3). **Поактивный AISC поверх Go-сида** добавляет отдельный скрипт `scripts/extrapolation_aisc.py` (цель `make dcf-aisc`): он генерирует `sql/dcf_mine_plans_seed.sql` (77 строк, ключ `(company, asset, year)` — `ReplacingMergeTree` перезаписывает 77 строк из 87, строки Сухого Лога выживают). Сид **применяется вручную** (`make ch-sql FILE=sql/dcf_mine_plans_seed.sql`) и **в `dagu/dcf.yaml` НЕ входит** — цепочка там остаётся двухшаговой (`dcf_mine_plans` → `dcf_engine`), см. §6.1 и «Ограничения» README; запланированный `make ch-sql` на staging не заработал бы (нет ни `make`, ни Makefile, ни SQL-файла) и провалился бы бесшумно, потому что `dcf_mine_plans` в той же цепочке пересеял бы ключи из Go-снимка. Что из конвенции **ещё не реализовано**: эскалация AISC/TCC по ИПЦ (`Params.Ipc` пуст — скрипт эскалирует по собственным константам `ESCALATION`, §3.6 плана), стадийные haircut'ы ресурсов вне LOM (`stage_haircut` всегда NULL), рублёвый NAV (`usdrub_path` пуст — все деньги USD), мост NAV → цена акции и NAV-матрица в Grafana. Остаток фазы 3 перечислен в [docs/ROADMAP_DCF_POLYUS.md](docs/ROADMAP_DCF_POLYUS.md) §7.

| `CLICKHOUSE_MCP_BIND_HOST` / `_PORT` | `127.0.0.1` / `8000` | слушает только loopback; наружу не публикуется |

`GET /health` намеренно **без** аутентификации (для проб); проверка авторизации — запросом к `POST /mcp`, который без заголовка `Authorization` обязан вернуть `401`. Инструменты сервера: `list_databases`, `list_tables` (читает `system.tables`/`system.columns`, видит только то, на что есть гранты; комментарии колонок попадают в `create_table_query`), `run_query`.

Сырые таблицы (`macro_series`, `gold_prices`, ...) агенту недоступны: проверено `497 ACCESS_DENIED`. Создание и гранты — `sql/mcp_kimi_reader.sql` (пароль подставляется вручную). #### Ingest-endpoint (пакет `ingest/`, бинарник `cmd/ingest`)

**Реализован.** Единственный путь записи в `model_runs`, `forecast_log`, `macro_series`, `gold_prices` и `gold_forecasts` со стороны контура прогноза.

- Сборка и запуск: `make build-ingest` → `build/ingest`; `make run-ingest`. Нужны `CLICKHOUSE_URL` и `INGEST_TOKEN` (см. §5); `INGEST_ADDR` по умолчанию `:8081`; `INGEST_RATE_PER_MIN` по умолчанию 60.
- Старт: ping ClickHouse, затем `EnsureTables` — идемпотентное создание `model_runs`, `forecast_log`, `macro_series`, `gold_prices`, `gold_forecasts` по DDL §6.2 (копии в `ingest/schema.go`).
- Авторизация: заголовок `Authorization: Bearer <INGEST_TOKEN>`, сравнение через `subtle.ConstantTimeCompare`. Без заголовка или с неверным токеном — `401`.
- Частота: token bucket (stdlib, `ingest/ratelimit.go`), общий на сервер, burst 10, `INGEST_RATE_PER_MIN` запросов в минуту (по умолчанию 60). Проверяется после авторизации: неавторизованные запросы лимит не расходуют. Превышение — `429`.
- Тело запроса — не более 1 MiB (`http.MaxBytesReader`; больше — `413`). JSON декодируется с `DisallowUnknownFields`: неизвестное поле — `400`.
- `POST /v1/model_run` — JSON `ModelRun`: клиентский `run_id` (UUID, обязателен), `trigger_type` ∈ {`calendar`,`news`,`manual`}, `price_deck` ∈ {`spot_flat`,`consensus_lt`,`own_scenario`}, `probabilities` (ключи только `bull`/`base`/`bear`, каждый вес 0–100, сумма 100 ±0.1), `gold_scenario` (с `horizon`: `Q<n>-YYYY`, `YE-YYYY`, `YYYY` или `YYYY-MM-DD`; блоки сценариев с `point` (число, если задан) или `low`/`high`), `nav_per_share`, `nav_bull/base/bear`, `market_price`, `upside_pct`, `discount_rate`, `wacc`, `usdrub_path`, `comment`. Ответ `200 {"inserted": 1}`; `400` — ошибка валидации или JSON.
- Запись: сначала `forecast_log` (две строки: `metric = 'nav'`, `predicted = nav_per_share`; `metric = 'xau_q_avg'`, `predicted` = Σ p×point / Σ p; `forecast_date` — дата сервера, `target_date` — конец горизонта, `actual` и `error_pct` = NULL), последней — `model_runs` (`run_date` = время сервера, `nav_beta_gold` = NULL, поля в входе нет). Строка в `model_runs` — маркер фиксации прогона.
- Идемпотентность: повторный POST с тем же `run_id` ничего не пишет (проверка `count() ... FINAL` + мьютекс, один инстанс). `ReplacingMergeTree` по `(run_date, run_id)` дубли сам не схлопывает. Ответ при дубле такой же, как при записи: `200 {"inserted": 1}`.
- `POST /v1/manual_series` — JSON-массив `{"series", "date" (YYYY-MM-DD, диапазон Date32 [1900-01-01, 2299-12-31]), "value", "source"?}`; пишется в `macro_series` с `source` точки, при пустом — `manual` (допустимы `manual`, `webbridge`, `imf`). Ответ `200 {"inserted": N}`; пустой массив — `N = 0`; `400` — ошибка валидации любой точки (запись не выполняется).
- `POST /v1/gold_prices` — JSON-массив `{"venue", "date" (YYYY-MM-DD, диапазон Date32), "usd"}`; пишется в `gold_prices` (venue по whitelist `comex_front`, `usd > 0`). Ответ `200 {"inserted": N}`; пустой массив — `N = 0`; `400` — ошибка валидации любой точки (запись не выполняется).
- `POST /v1/gold_forecasts` — JSON-массив `{"author", "published" (YYYY-MM-DD, диапазон `Date` [1970-01-01, 2149-06-06] — уже Date32, колонка объявлена `Date`), "horizon", "scenario", "low", "high", "point", "probability"}`; пишется в `gold_forecasts` (ключ `(author, published, horizon, scenario)`, повторная запись строки — норма под `ReplacingMergeTree`). Валидация строки (ошибка любой — `400`, запись не выполняется): `author` и `horizon` непусты после `TrimSpace`; `published` — формат `YYYY-MM-DD` и диапазон `Date` (`parsePointDate` отвечает за формат и Date32, поверх — проверка `Date`); `scenario` ∈ {`point`,`range`,`bull`,`base`,`bear`}; `low`/`high`/`point` ≥ 0 и хотя бы одно > 0 (строка из нулей — незаполненный прогноз, а не цена); если заданы оба — `high ≥ low`; `probability` 0–100 (0 — «не задана»). Ответ `200 {"inserted": N}`; пустой массив — `N = 0`.
- Ошибка записи в ClickHouse — `500 insert failed`, детали в логе.
- Реализовано: ограничение частоты (`429`), предел тела 1 MiB (`413`). Не реализовано: TLS в самом процессе — предполагается reverse proxy с TLS (в репозитории не описан).

### 6.6 Отчётность Полюса: разбор PDF колоночной моделью и известные ограничения (пакет `polyus/`)

С 2026-10-10 извлечение текста идёт через **`pdftotext -tsv`** (координаты слов), а значения раскладываются по **колонкам, выведенным из шапки по X**, — вместо `-layout` и позиционного сопоставления. Спека: [docs/superpowers/specs/2026-10-10-polyus-column-model-design.md](docs/superpowers/specs/2026-10-10-polyus-column-model-design.md); план: [docs/superpowers/plans/2026-10-10-polyus-column-model.md](docs/superpowers/plans/2026-10-10-polyus-column-model.md). Предыдущая спецификация (`2026-10-10-polyus-parsers-design.md`) описывает перенос из legacy и остаётся историей.

Модули:

- **`polyus/source.go`** — `extractPage` вызывает `pdftotext -f N -l N -tsv -nopgbrk -enc UTF-8`; `extractPDF` извлекает страницы по отдельности и склеивает их (`joinFiles`), поэтому в одном файле может быть несколько страниц и несколько таблиц.
- **`polyus/words.go`** — `Word` (текст, `Page` из колонки `page_num`, `Left`, `Top`, ширина/высота, `Block`, `Line`), `Line` (слова одной страницы с одинаковым `Top`, по возрастанию `Left`), `parseTSV` (только строки уровня 5; строка заголовка TSV отбрасывается по имени первой колонки — в склеенном файле она повторяется в середине), `groupByLine(words, deltaTop)`. Штатный допуск — **`deltaTop = 0`**: у слов одной визуальной строки `Top` совпадает точно (допуск оставлен страховкой от дрейфа базовой линии).
- **`polyus/columns.go`** — `Column{Period, Type, Left, Right}`, `columnsFromHeader([]Line)` (вход — **полоса** шапки: у FY2024 расшифровка «(if not mentioned otherwise)» набрана мельче и уехала на 0.77pt), `Column.covers`, `widenColumns` (границы расширяются до середины промежутка между соседями: подписи выровнены по левому краю, а числа — по центру). Помощники шапки: `unitsMarker`, `isPeriodHeaderLine`, `isTableHeader`, `firstHeaderLine`, `headerBand`, `changeLabels`.
- **`polyus/kpi.go`** — `parseKPILines` / `recordsFromLine` / `parseKPIPage`: находит полосы шапок, строку обслуживает ближайшая шапка сверху, дедупликация метрик — **на полосу** (две таблицы на странице — два независимых набора), многословные числа («1 069») склеиваются по X.
- **`polyus/ifrs.go`** — `parseIFRSPage`: колоночная модель не применяется (на МСФО-странице шапки нет, ровно два столбца периодов); берётся первое число после метки, период отчётности приходит параметром.
- **`polyus/guard.go`** — резерв: отбрасывает только записи с пустым `Period` (ошибка разбора: ключ `(metric, "")` схлопнул бы весь набор в одну строку) и сообщает число значений, не попавших ни в одну периодную колонку. `polyus/import.go` печатает этот счётчик в итоговой строке и предупреждает, если он не нулевой.

**Границы шапки — по ролям строк, а не по зазору (2026-10-10).** `headerBand` собирает полосу шапки, продолжая её, пока следующая строка играет роль строки шапки (маркер единиц, подписи периодов, подписи изменений), а не пока она подходит по вертикальному зазору. Позиционный критерий (`headerContinuationGap = 2pt`) не работал на шапках, разорванных по двум строкам: в релизе 2019FY строки `Q-o-Q / Y-o-Y / 2019 / 2018 / Y-o-Y` и `otherwise) / 2019 / 2019 / 2018` отстоят друг от друга на 5.04pt и 5.28pt, и полоса шириной 2 оставляла `4Q 2019`, `3Q 2019` и `Q-o-Q` без колонок — 48 значений уходили в счётчик нераспределённых. По ролям полоса доходит до строки данных, и квартальные колонки разбираются.

**Склейка разорванных подписей периодов.** Метка периода, разбитая переносом строки («4Q» на одной строке полосы, «2019» на другой), собирается по X: слова двух строк полосы, совпадающие по горизонтали, склеиваются перед `columnsFromHeader`. Без этого `4Q` и `2019` не дали бы периода, а два квартала 2020 (`4Q 2020`, `3Q 2020`) схлопнулись бы в два одинаковых годовых `2020FY`, и три числа 710 / 771 / 2 766 встали бы под один ключ. Тест `TestKPIValuesHistoryReports` (`polyus/kpi_test.go`) закрепляет каждый квартал как проверку «колонка не слилась с соседней».

**Живая приёмка (2026-10-10, прогон контролёра через `make import STAT=polyus_financial_metrics`, не самостоятельный замер этой задачи; таблица с тех пор заменена на `company_financials` и ключ расширен — актуальная приёмка ниже):** 66 строк и итоговая строка `Imported 66 rows (11 reports skipped as disabled, 0 failed, 0 periodless records dropped, 3 duplicate keys skipped, 26 values outside period columns)`. По периодам: `2014FY` 8, `2014H1` 8, `2014H2` 8, `2025H1` 9, `2025H2` 9, `2026H1` 16 (было 39 строк: два ранее терявшихся слота периода — `2014H1` и `2025H2` — теперь разбираются). Контрольные значения `2026H1` сохранены: `gold_output` 1 287, `tcc_per_ounce` 1 069, `total_revenue` 4 674, `profit_for_period` 829, `stripping_capex` 397. RU `2025H2`: `gold_output` 1 218, `tcc_per_ounce` 814 (раньше в этом слоте стояло процентное изменение `−2`). `2014H2`: `revenue` 1 232 — настоящая цифра второго полугодия 2014; FY2013-е 2 329 в `2014H2` больше не попадает.

**Живая приёмка релизов 2019–2024 (2026-10-10, самостоятельный прогон той задачи).** Тогда таблицей была ещё `polyus_financial_metrics` с ключом `(company, metric, period)`: 265 строк, `0 duplicate keys skipped` нет — итоговая строка `Imported 265 rows of polyus_financial_metrics (5 reports skipped as disabled, 0 failed, 0 periodless records dropped, 82 duplicate keys skipped, 178 values outside period columns)`. **Эти 82 отброшенных повтора ключа и были потерей, которую закрыла смена схемы** (§6.2, §6.3): после перехода на `company_financials` и расширения ключа до документа они стали настоящими строками — актуальный прогон 2026-10-10: `make import STAT=polyus_financial_metrics` → `Imported 347 rows of company_financials (5 reports skipped as disabled, 0 failed, 0 periodless records dropped, 0 duplicate keys skipped, 178 values outside period columns)`, в `v_company_metric_sources` 347 строк при 265 различных `(company, metric, period)` и `source_kind ∈ {kpi, ifrs}`. Все шесть включённых релизов разобрались, `0 failed`. `gold_output` сверен с закреплённой таблицей по каждому периоду: 2019FY 2 841, 2018FY 2 440, 2019Q4 804, 2019Q3 753; 2020FY 2 766, 2020Q4 710, 2020Q3 771, 2019Q4 804; 2021FY 2 717, 2021Q4 684, 2021Q3 770, 2020Q4 710; 2022FY 2 541, 2021FY 2 717; 2023FY 2 902, 2022FY 2 541; 2024FY 3 002. `revenue` 2019FY = 4 005. Несовпадений нет. Невыровненным остался только «квартальный» слот релиза 2023FY: он печатает полугодия (`2023H2` 1 454 / `2023H1` 1 448) вместо кварталов, и это форма самих шести отчётов 2022–2024, а не потеря колонок. Счётчик нераспределённых вырос с 26 до 178 — это ожидаемо: в полосы шести отчётов попадают колонки-изменения без года (`Y-o-Y`, `H-o-H`), их числа и есть нераспределённые значения.


**Закрытые дефекты (ROADMAP §8.1).** Все три закрыты. (1)–(2) колоночной моделью: (а) guard больше не «отбрасывает последнюю колонку» — непериодная колонка («Изм. за год», `change`, `Y-o-Y`) занимает своё место по X, её числа не читаются, и слот `2025H2` русского релиза разбирается; (б) `2014H2` больше не несёт цифры FY2013 — `change` не становится периодной колонкой, значения кладутся по X, `revenue 2014H2 = 1 232`. `untrustworthyPeriod` удалена (её позиционная эвристика больше не нужна: колонка-изменение распознаётся по отсутствию периода в шапке). При этом `scanPeriodColumns` и тип `PeriodColumn` **остались в коде как мёртвый код**: после перехода на `columnsFromHeader` их не вызывает ни один продовый путь, только собственный тест (`polyus/kpi_test.go`); `unused`-линтер их не ловит, потому что тест обращается к функции. Это уборка для отдельной задачи, не дефект разбора.

Дефект (3) — **ключ `(company, metric, period)` без измерения источника** — **закрыт 2026-10-10 сменой схемы** (спека [2026-10-10-company-financials-views-design.md](docs/superpowers/specs/2026-10-10-company-financials-views-design.md) §3.1): ключ стал `(company, metric, period, source_kind, source_url)` в новой таблице `company_financials` (§6.2). Одного `source_kind` не хватало: он различает вид документа (`kpi`/`ifrs`), но два KPI-релиза (FY2023 и FY2024) несут один и тот же `kpi` и на ключе из четырёх полей всё равно схлопывались бы — поэтому в ключ добавлен `source_url`, признак самого документа. Масштаб дефекта был измерен на шести включённых релизах 2019–2024: среди ключей, которые они печатают, **79 встречаются более чем в одном отчёте, и 17 из них несут РАЗНЫЕ значения** (62 — одинаковые). Показательный случай — `gold_output` за `2023FY`: релиз FY2023 печатает **2 902**, релиз FY2024 — **2 799**; так же расходятся `revenue` 2023FY (5 436 против 5 237), `operating_profit` 2023FY (3 172 против 3 123) и ещё 14 ключей. Это не ошибка разбора: обе цифры прочитаны верно, спорят документы. **Проверено живым прогоном 2026-10-10:** импорт даёт 347 строк при **265 уникальных** `(company, metric, period)` и `0 duplicate keys skipped` — проигравший документ перестал исчезать и виден в `v_company_metric_sources` (`gold_output 2023FY` — две строки, 2 902 и 2 799, с разными `source_url`), а правило разрешения спора применяется только в `v_company_financials` (одна строка, 2 902). Прежнее поведение («первый отчёт в порядке `reports`») отменено: порядок отчётов в `polyus/pages.go` больше не решает исход.

Дефект (4) — **агент MCP данных Полюса не видел** — **закрыт 2026-10-10** витринами `v_company_*` с комментариями и грантом `kimi_reader`; подробности — §6.3 и §6.5. Витрина сделана общей для сектора (`company_financials`), а не набором `v_polyus_*`; перевод металлургов — `docs/ROADMAP_DCF_METALS.md`.

**Ограничения, оставленные осознанно** (проверенные, не гипотезы; не исправлялись в этой задаче):

1. **`unitsMarker` привязан к строке, а не к смыслу.** `columns.go` ищет только склеенные `$млн`, `$mln`, `$million`. Отчёт, печатающий `US$ million`, оставит набор колонок пустым, и парсер вернёт **0 записей с `err == nil`** — молчаливо пустую страницу. (Форма `US$ million` — находка контролёра по другим релизам каталога; ни один из девяти включённых отчётов её не несёт: у всех фикстур 2019–2024 напечатано `$ million`, и оно склеивается.) Ограничение остаётся для отключённых 2015–2018 и будущих отчётов: тихий нулевой результат не отличим от «в отчёте нет метрик», и включение отчёта с такой шапкой потребует сначала расширить маркер.
2. **`parsePeriod` не знает формы `FY 2014` (год с пробелом).** Проверено контролёром: `parsePeriod("FY 2014")` и `parsePeriod("FY2014")` возвращают `unknown period format`, работает только голый год — `parsePeriod("2014")` → `2014FY`. Следствие для колонки, подписанной `FY 2014` в шапке: она не распознаётся как период и попадает в набор как `Column{Period: ""}`. Своё место по X она сохраняет — колонки справа не сдвигаются, значения чужим периодам не приписываются; но **её значения не читаются вообще** и попадают в счётчик нераспределённых импортёра. Это тот же класс тихой потери, что и ограничение 1: единственный сигнал — число в итоговой строке импорта (`... values outside period columns`), а строки данных при этом просто исчезают.
3. **Допущение «первое число = отчётный период» на МСФО-страницах не проверяется.** Оно выполняется на обеих текущих страницах (проверено: стр. 6 — `2026` на x=472.54 против `2025` на 522.82; стр. 7 — 465.79 / 515.98), но во время прогона ничто это не контролирует: отчёт, напечатавший сравнительный столбец первым, молча поменяет периоды местами.
4. **Счётчик guard'а не покрыт сквозным тестом.** Направление «парсер → счётчик» закреплено тестом, а последний переход в итоговую строку импортёра требует шва на уровне `Import` и подтверждён только живым прогоном.
5. **`pageOfLine` возвращает первую ненулевую страницу слова.** Это корректно, потому что `groupByLine` гарантирует одну страницу на строку; инвариант зафиксирован комментарием и проверен пробой, но теста, сканирующего фикстуры, у него нет.
6. **Полоса шапки по ролям строк может расти вниз.** `headerBand` продолжает полосу, пока строки играют роль строк шапки (маркер единиц, подписи периодов, подписи изменений). Роль «подпись изменения» опознаётся по словарю меток (`Y-o-Y`, `H-o-H`, `Q-o-Q`, `change`), и строка с такой подписью, стоящая в области данных, попадёт в полосу; её слова уйдут в `columnsFromHeader` не колонками, а метриками такой отчёт не прочитает (тот же класс тихой потери, что и ограничение 1). На девяти включённых отчётах недостижимо: замерено, полосы обрываются на строке данных. Но 2015–2018, которые включает следующий пункт, несут подписи изменений в области данных. Записано, не исправлено.
7. **Подъём полосы вверх ограничен расстоянием `maxFragmentLiftGap = 8pt`.** Якорь полосы — строка с меткой единиц, и она не обязана быть верхней строкой шапки: у релизов 4Q/FY 2020 и 2021 строка кварталов «4Q 3Q 4Q» стоит НАД якорем (зазоры ровно 5.40pt), а голый «4Q» периодом не является (`parsePeriod` читает только «4Q 2020»). Если квартал не поднять, он не склеится со своим годом на строке ниже, и «4Q 2020» с «3Q 2020» молча станут двумя годовыми колонками `2020FY` — три разных значения под одним ключом. Подъём поэтому берётся, но только на строку, состоящую целиком из обрывков периодов **и** прижатую к якорю: разрыв не больше 8pt. Настоящий обрывок дальше 8pt от якоря не будет поднят, и его квартальные колонки потеряются — то же схлопывание «4Q/3Q» в годовые, только уже без всякого сигнала в счётчике нераспределённых (значения останутся на своих местах, сменится лишь ключ периода). Порог измерен по фикстурам: настоящие случаи — 5.40pt, ближайшая строка не-обрывок над якорем — 7.07pt, первый реалистичный разрыв между таблицами — 18.18pt и больше; запас 1.5× снизу и 2.3× сверху. Сетка на эту ошибку — `TestKPIPeriodsAreUniquePerMetric` (`polyus/kpi_test.go`): два квартала, схлопнувшись в один годовой период, дают дубликат ключа внутри полосы, и тест валит его громко — по всем метрикам, а не только по `gold_output`. Записано, не исправлено.
8. **`foundMetrics` внутри полосы отбирает по первому `Top`.** Дедупликация метрики на полосу (метка может встретиться и в сноске той же таблицы) устроена как «строка метрики с меньшим `Top` побеждает»: `foundMetrics[definition.Name]` выставляется первой строкой, давшей записи, а совпавшая позже отбрасывается. Если на странице выше настоящей строки стоит другая строка с той же меткой, побеждает она, и настоящая строка теряется молча. Воспроизведено синтетически; на закоммиченных фикстурах не встречается. Существующий комментарий описывает эту дедупликацию только как подавление повторов, а не как выбор по первому `Top`.
9. **Дефект словаря метрик (существовал до этой работы):** `metrics.go` перечисляет `"Earnings per share – basic (US\nDollar)"` со встроенным переводом строки, который не может совпасть со склеенным текстом строки; следствие — на фикстуре FY2024 `parseKPIPage` не даёт ни одной записи `eps_*`. Записано, не исправлено.
10. **Отключённые отчёты сузились до 2015–2018 (плюс 2025H2)** — после включения шести релизов 4Q/FY за 2019–2024 причина отключения у оставшихся не в выверке страниц, а в типе документа: 2015–2017 — MD&A с консолидированной отчётностью, 2018 — консолидированная МСФО-форма, у которых нет шапки «Comparative financial results», а 2025H2 — англоязычный 2H25-релиз с двухшапочной таблицей. Включение 2015–2018 — следующий пункт (спека [docs/superpowers/specs/2026-10-10-polyus-history-reports-design.md](docs/superpowers/specs/2026-10-10-polyus-history-reports-design.md), §4 «Границы»): у каждого файла свои `Kind`, `Lang` и `Pages`, и, возможно, понадобится несколько `Pages` на отчёт.

Ограничение «агент MCP не видит данные Полюса» (`v_polyus_*` и гранта `kimi_reader` не было) **снято 2026-10-10** — витрины `v_company_*` с комментариями и грантом (§6.3, §6.5).


### 6.7 Дашборды Grafana как код (реализовано 2026-10-12)

Дашборд статьи `gold-thesis` — не экспорт из UI, а артефакт сборки: источник истины — Go-код модуля `grafana/` (grafana-foundation-sdk), артефакт `dashboard/gold-thesis.json` (k8s-ресурс `dashboard.grafana.app/v1beta1`, uid `gold-thesis`) коммитится и генерируется целью `make grafana-build` (`cd grafana && go run . -out ../dashboard/gold-thesis.json`). Генерация детерминирована: повторный прогон не меняет файл — на этом стоит CI-проверка diff. Таблица выше — краткая сводка для людей: даты и пороги в сиде точнее, а WGC в сиде — одна дата 2026-10-30 (GDT), а не «10-е число ежемесячно». При расхождении верна таблица `events_calendar`, а эту сводку нужно обновить.

**Два ряда на одну дату заседания: каноническая строка и ручной аналитический триггер.** С этого PR `events_calendar` наполняется из двух источников, и они не конфликтуют, потому что у строк разный `title`, а ключ `ReplacingMergeTree` — `(event_date, category, title)`. На 23.10.2026 и 18.12.2026 в витрине `v_events_calendar` поэтому лежат **по два ряда `category='cbr'`**: (а) канонический факт заседания, который пишет импортёр из `cbr.ru/dkp/cal_mp/` — `title='СД ЦБ РФ: заседание по ключевой ставке'`, `event_time='13:30'`, `threshold='{}'` (порогов нет: это не триггер, а дата решения), и (б) ручная строка-триггер сида `sql/events_calendar_q4_2026.sql` — «СД ЦБ РФ: ставка (14%) — снижение → флаг перетока ликвидности» (23.10.2026) и «СД ЦБ РФ: база — −25 б.п. до 13,75% + ребалансировка индекса MOEX» (18.12.2026) с заполненным `threshold` и `event_time = NULL` (время триггера не фиксировано). Читателю (и агенту) нужно различать их по `title`/`threshold`: первый отвечает на вопрос «когда заседание», второй — «что модель делает при таком исходе». Канонические строки **аддитивны**: если ЦБ перенесёт заседание, добавится новая строка, а старая останется историей (она не удаляется и не перезаписывается). Порядок строк в витрине, как и раньше, задаётся `Select` витрины; строки сида импортёр не трогает — повторный прогон идемпотентен, и на тех же датах не появляется третьего ряда.

**Даты заседаний СД ЦБ и экспираций KEYRATE — из биржи, а не из этой таблицы.** Дата экспирации серии расчётного фьючерса KEYRATE (`LSTDELDATE`) — это и есть дата заседания, по ставке которого считается индекс: импортёр `keyrate_futures` берёт её у биржи, обновляет ежедневно (`dagu/moex.yaml`, 19:13 МСК, шаг 3) и складывает в `keyrate_contract.last_trade`, поэтому срок жизни серии виден агенту из `v_keyrate_expectations` (§6.3) и из `v_series_catalog` (source `moex`). Календарь заседаний ЦБ публикуется на [cbr.ru/dkp/cal_mp/](https://www.cbr.ru/dkp/cal_mp/) и с этого PR забирается оттуда тем же импортёром `events_calendar` (`dagu/calendar.yaml`, ежедневно 10:07 МСК): канонические строки заседаний пишутся по карточкам с полной датой (в закоммиченной фикстуре `calendar/testdata/cal_mp.html` разбор даёт 68 дат — 2020-02-07 … 2027-12-17, включая четыре внеочередных заседания 2022-02-28, 2022-04-08, 2022-05-26 и 2023-08-15), а карточки-незаседания и карточки без года (2019 и табличные секции 2014–2018) пропускаются. Ручными в этой таблице остаются **только строки-аналитические триггеры** (другой `title`), а срок жизни серий KEYRATE ведёт биржа: при сверке дат ориентируйтесь на `v_events_calendar` и на биржевой `keyrate_contract.last_trade`, а не на сводку выше. ⚠️ Инструмент низколиквиден (открытые позиции — десятки контрактов), вменённое значение индикативно: это не прогноз рынка и не ценовое обязательство.

## 8. Правила для AI-ассистента (Kimi Code)

1. **Новый источник = новый файл** в доменном пакете + регистрация в `chimport.Stats`. main.go не править (пакет уже импортирован) — если пакета нет, добавить blank-import. Регистрация — на пакет: в большинстве пакетов её делает `init()`, а в `cbr/` персональных `init()` по файлам импортёров нет — новая запись идёт в реестр `cbrImporters` (`cbr/importers.go`), иначе импортёр не попадёт в `chimport.Stats` и тест `TestCbrImportersPrefixedAndRegistered` его не увидит (§3).
2. Использовать шаблон Б (`util.ClickHouseImport`) — и для XLSX-источников, и для краулеров (`ImportFunc` / `CrawFunc`); шаблон А — только если нужна кастомная логика поиска ссылки или источник не XLSX (API/CSV/JSON).
3. Вставка только батчами (`PrepareBatch`/`Append`/`Send`). DDL `IF NOT EXISTS`. Значения новых таблиц — Float64.
4. HTTP — только через `util.HttpClient` / `util.GetXlsx` / `util.GetCSV` (там нац. сертификаты и UA); для JSON-источников — `util.GetJSON`, для RSS/XML — `util.GetXML`: в отличие от `GetFile`, оба проверяют HTTP-статус (не-200 — ошибка с фрагментом тела, а не «успешно» прочитанный HTML WAF) и держат собственный дедлайн запроса (60 с; `GetFile` — свой, 2 мин, `fileTimeout`); `GetXML` к тому же разбирает `xml.Decoder` с таблицей `xml.HTMLEntity` и требует пина корня через `XMLName` (§3); POST-JSON (LLM-слой) — `util.PostJSON` (заголовки накладываются поверх, ключ LLM едет `Authorization` и в тексты ошибок не попадает).
5. **Не хардкодить секреты** (в т.ч. в комментариях и curl-примерах) — только `os.Getenv`.
6. **Не делать сетевых вызовов в `init()`** — URL вычислять внутри `Import()` (бывший legacy-баг `minfin/fedbud_mes.go` исправлен; сетевых вызовов в `init()` в репозитории не осталось).
7. Русские даты/месяцы — через `util.MonthsToNum`; форматы времени — константы рядом с импортёром.
8. Накопленные значения «с начала года» конвертировать в потоки разностями (паттерн `fedBudImport`).
9. Ошибки не проглатывать: парсинг чисел — с проверкой `err`; в `Import()` ошибка → `return count, err`.
10. Пакет `financial/` — legacy (database/sql, свой main): новый код туда не добавлять, новые корпоративные импортёры делать на clickhouse-go/v2 в новых пакетах. Парсеры Полюса уже вынесены в `polyus/` (см. §6.6); в `financial/` остаётся `databook_ugk` и мёртвый код металлургов.
11. Сборка-проверка: `make all` (gofmt, golangci-lint, `go vet`, `go test -race`, сборка). Тесты (фикстуры, без сети) есть у большинства источников — `bls/`, `bea/`, `bold/`, `calendar/`, `cbr/`, `craw/`, `dcf/`, `eia/`, `forecast/`, `fred/`, `gold/`, `ingest/`, `minfin/`, `moex/`, `news/`, `polyus/`, `rosstat/`, `util/`, `views/`, `wgc/`; для новых импортёров тесты парсера и HTTP-слоя обязательны (`httptest.Server` + подмена base URL-переменной пакета).
12. После изменения архитектуры — обновить этот файл.
13. **Источник, чей файл обновляется реже прогонов, не скачивает его каждый раз** — точка контроля публикации объявляется **полями шаблона** `util.ClickHouseImport`, а не пишется кодом в импортёре: `PublicationCountPoints` (SQL числа точек ряда; непустое значение включает префлайт — она же даёт `points` строки версии), `PublicationSource` (ключ версии в `source_publications` и префикс лога префлайта; пусто → `TableName`) и `AfterImport` (производные — каталог и витрина — после точек и до строки версии). Полный цикл `Import`: DDL → `BeforeImport` → префлайт → точки → `AfterImport` → строка версии последней. Префлайт — лёгкий HEAD (`util.HeadFingerprint`) плюс общая служебная таблица `source_publications` (`util.EnsurePublications`/`PublicationKnown`/`SavePublication`, §6.2): если версия уже импортирована и число точек своего `source` в целевой таблице совпало, прогон становится **no-op без скачивания и без записи в БД**; строка версии пишется последней — после успешного `Send` точек и публикации производных (утверждает «эти точки записаны и опубликованы»); сбой производных или сбой `CountPoints` при записи версии оставляет версию незаписанной, и следующий прогон повторяет полный путь (идемпотентно), а новый файл даёт новую строку и полный импорт-обновление. Недоступный HEAD и сбой `SELECT` версии — не сбой, а деградация: warn и полный импорт без записи версии (иначе следующая волна считалась бы уже импортированной); сбой самого `count()` — ошибка прогона (без числа точек не сходится ни чек, ни `points` будущей записи, спека §3.4). **Объявлено у 14 импортёров**: десять в `cbr/` (`cbr_mp_survey`, `cbr_mo_br`, `cbr_households_b_mes`, `cbr_m2`, `cbr_credit_m2x`, `cbr_loans_to_corporations`, `cbr_loans_to_individuals`, `cbr_bank_int_rate`, `cbr_indicators_cpd`, `cbr_infl_exp`; запросы и расписание — §6.1) и четыре вне него (`rosstat/ipc_mes`, `rosstat/salaries_mes`, `rosstat/vvp_kvartal`, `bank/sber_finansovie_rezultaty`); **осознанно не объявлено** у дневных `cbr_key_rate`/`cbr_ruania`/`cbr_currency_usd`/`cbr_gold`, у недельного `ipc_weeks`, у падающего `tbank_group_ifrs` и у контурного `cbr_mp_summary` (у него не один артефакт версии, а индекс материалов заседаний и набор документов: известность документа — адрес карточки в индексе **∧** строки блоков по дате заседания **∧** regex-строки каналов, и HEAD-отпечаток страницы резюме на вопрос «какие резюме уже разобраны» не отвечает — §6.1). Пер-источниковых таблиц версий не заводим — версии всех источников лежат в общей `source_publications`. Механизм не защита от подмены, а ответ на вопрос «это тот же файл, что импортировали?».
14. **LLM-разметка — только через `util.PostJSON` и переменные окружения, с деградацией вместо отказа.** Единственный потребитель — слой 2 разметки каналов `cbr_mp_summary`: `LLM_BASE_URL`, `LLM_API_KEY`, `MP_SUMMARY_LLM_MODEL` (§5), OpenAI-совместимый `POST <baseURL>/chat/completions`. Значения — только `os.Getenv` (правило 5); ключ уходит заголовком `Authorization`, поэтому в логи и тексты ошибок не попадает, а URL в ошибку `PostJSON` не подставляется. Любая пустая переменная, отказ провайдера или невалидный JSON после одного ретрая — `log.Warnf` и деградация: документ остаётся со слоем 1 (`method='regex'`), догон повторится следующим прогоном, ежедневная цепочка `dagu/cbr.yaml` при этом не краснеет. Фактическое имя модели пишется в данные (колонка `model` таблицы `cbr_mp_summary_channel`) и входит в ключ вместе с `prompt_version`: разметка другой модели или редакции промпта добавляется рядом со старой, не затирая её, поэтому ансамбль моделей включается конфигом без миграции схемы. Цитаты модели валидируются — обязаны дословно присутствовать в нормализованном тексте резюме, иначе отбрасываются с warn (§6.1).
